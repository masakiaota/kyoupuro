# Important Properties

このファイルは、問題の重要な性質を整理する場所である。記号の定義・代表名・型・制約は `notes/notations.md` を参照し、ここでは性質そのものだけを書く。

## 1. 出発線 prefix 固定

### 主張
出発線 `r` で `dep[r][0..p] = target_seq(r)[0..p]` が成立した後、`p` より後ろだけを操作する限り、この prefix は壊れない。

### なぜ成り立つか
出発線に対する操作は末尾からの取り出しと末尾への追加だけであり、先頭側の車両を直接抜いたり、その前に挿入したりできないからである。

### 実装上どう効くか
出発線側は先頭から順に確定する構築と相性がよい。確定済み prefix をロックし、未確定 suffix だけを探索対象にすれば、状態管理と正当性確認を単純にできる。

## 2. 待避線先頭アクセス

### 主張
待避線から取り出せるのは常に先頭側の block だけである。あとで早く使う車両を待避線の深い位置に埋めると、先頭側の車両を先に処理しない限り取り出せなくなる。

### なぜ成り立つか
待避線に対する操作は、先頭への追加と先頭からの取り出しだけである。待避線の途中や末尾を直接操作する方法はない。

### 実装上どう効くか
待避線へ置く順番は、将来の取り出し順から逆算する必要がある。短期的な置き場所として使う線と、完成形を育てる線を混ぜると、目標 block が塞がりやすい。

## 3. ブロック順序保存

### 主張
1 回の移動では、対象 block の内部順序は変わらない。相対順を変えられるのは、どこで block を切り、どの順に別 block として連結するかだけである。

### なぜ成り立つか
問題文で、連続した `k` 両を対象とし、その順序は保存されると定められているからである。

### 実装上どう効くか
目標列上で連続している車両列は、なるべく同じ block として扱う価値がある。1 両ずつ分解すると操作数が増えやすく、既に揃っている相対順も活かしにくい。

## 4. 正順隣接 block の縮約

### 主張
同一線上で `10r+c` の直後に `10r+c+1` が正順に隣り合っているなら、この 2 両は以後 1 つの block として扱える。この性質は、`target_seq(r)` 上で連続する複数車両の正順 block 全体に拡張できる。

### なぜ成り立つか
目標配置でも `10r+c` の直後は `10r+c+1` であり、移動は block 内部の順序を保存する。したがって、一度正順に隣接した目標連続部分を分割しても得られる利点は小さく、完成を目指す構築では分割しない前提にしてよい。

### 実装上どう効くか
状態を評価するとき、`target_seq(r)` 上で正順に連続する block を 1 単位の車両群として扱うとよい。移動候補は block 境界だけで切るように制限でき、探索空間を減らせる。特に、連続 block を育てる方針では「隣の目標 ID を接続できる move」の価値を高く見積もり、接続済み block を割る move は原則として生成しない。

## 5. 片端アクセスと逆順格納

### 主張
出発線上の車両を取り出すには、その車両より末尾側の車両を先にどかす必要がある。待避線上の車両を取り出すには、その車両より先頭側の車両を先にどかす必要がある。また、出発線から待避線へ複数回移すと、後から入れた block ほど待避線の先頭側に来る。

### なぜ成り立つか
出発線は末尾側、待避線は先頭側にしか操作できない。さらに `type = 0` は出発線の末尾 block を待避線の先頭へ連結するため、待避線内では後から入れた block が先に取り出される位置に置かれる。

### 実装上どう効くか
ある待避線から `a,b,c` の順に取り出したいなら、単純には `c` 側の block から先に入れ、最後に `a` 側の block を入れる必要がある。各線を片端アクセスの列として見て、取り出し順と格納順を逆算するのが重要である。

## 6. 非交差バッチング

### 主張
同じ移動回数でも、移動ペア `(i,j)` を非交差な集合にまとめられるほどターン数は少なくなる。特に、同一ターン内の操作を `i` 昇順に並べたとき `j` も昇順になっていれば、その操作集合は同時実行できる。

### なぜ成り立つか
問題のスコアで使われるのは移動回数ではなくターン数 `T` である。同一ターン内では 1 本の出発線・待避線を重複使用できず、さらに `i_1 < i_2` なら `j_1 < j_2` でなければならないため、交差する操作同士は別ターンに分ける必要がある。

### 実装上どう効くか
バッファ割り当てや完成形の置き場所は、できるだけ `i` と `j` の対応が同じ向きに単調になるように選ぶとよい。例えば最終搬入を `(0,0),(1,1),...,(9,9)` にできれば 1 ターンで済むが、`(0,9),(1,8),...,(9,0)` のような逆順対応は交差が多く、複数ターンに分割されやすい。

## 7. 目標線順バッファ配置

### 主張
目標線 `r` の車両を待避線 `j` に置くと、将来その車両を目標線へ搬入する操作はおおむね `(r,j)` になる。複数の目標線について、`r` の並びと `j` の並びが同じ向きに近いほど、搬入操作を非交差にまとめやすい。

### なぜ成り立つか
操作そのものには距離 `|r-j|` のコストはない。しかし、同時実行できるかどうかは `(i,j)` の順序関係で決まる。したがって、目標線番号と待避線番号の対応が逆向きになるほど、後で交差する搬入操作が増えやすい。

### 実装上どう効くか
一時置きでも、目標線 `r` の車両はできるだけ待避線 `r` 付近、特に可能なら待避線 `r` に寄せるとよい。ただし待避線は先頭アクセスなので、取り出し順を壊してまで近い待避線へ置くべきではない。優先順位は、取り出し順を保つこと、目標線順と待避線順をそろえること、可能なら `j = r` にすること、の順で考える。

## 8. 線種対称な完成列

### 主張
線 `r` の `target_seq(r)` が出発線 `r` または待避線 `r` のどちらかに正しい順で完成していれば、低コストで最終的な出発線 `r` の完成形へ移せる。特に、待避線 `r` の先頭から `target_seq(r)` が並んでいれば、最後に `type = 1, i = r, j = r, k = 10` で出発線 `r` へ一気に戻せる。

### なぜ成り立つか
`type = 1` は待避線の先頭 block を、順序を保存したまま出発線の末尾へ連結する。各 `r` について `(i,j) = (r,r)` の操作は互いに交差せず、全線で同一ターンに並列実行できる。

### 実装上どう効くか
完成形を育てる場所は出発線だけに限定しなくてよい。出発線側では先頭 prefix を揃え、待避線側では最終列の末尾側から前に向かって揃える、という見方ができる。問題は「どちらの線種でどの完成済み部分を保持し、途中の block をどこへ挿入するか」に整理できる。

## 9. 完成優先

### 主張
提出方針としては、部分点の局所改善よりも 4000 ターン以内の完成可能性を優先すべきである。

### なぜ成り立つか
`R = 10` なので完成時スコアは `5000 - T` である。一方、未完成時は出発線上の各車両が最大 10 点で、最大でも 1000 点にしかならない。したがって `T <= 3999` で完成できれば、どの未完成解よりも高い。

### 実装上どう効くか
探索中の評価として部分点を使う価値はあるが、最終方針は完成を保証する構築に寄せるべきである。ターン数削減や並列化は、まず完成する操作列を得てから詰めるのが安全である。
