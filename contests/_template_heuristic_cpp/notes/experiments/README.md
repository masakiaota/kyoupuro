# 実験ノートの運用

このディレクトリは実験の正史である。1 実験につき 1 つの Markdown ファイルを作り、派生元、実験前の仮説、変更、評価結果、考察を同じファイルに記録する。

## ファイル名と実験 ID

- ファイル名は `v0001.md`、`v0002.md` のような `vNNNN.md` とする。
- Front Matter の `id` はファイル名から拡張子を除いた値と一致させる。
- solver は実験と同じ 4 桁の version 番号を使う。たとえば `v0003_reconnect` の実験ノートは `v0003.md` である。
- 採番は [AGENTS.md](../../AGENTS.md) の「採番」に従う。1 つの version 番号を複数の実験に使わず、過去の実験 ID を再利用しない。
- `v0000_template` は共通土台であり、実験には数えない。最初の実験は `v0001.md` とする。

## Front Matter

必須項目は `id` と `parents` である。

```yaml
---
id: v0003
parents:
  - "[[v0001]]"
  - "[[v0002]]"
---
```

- `parents` には直接の派生元だけを書く。すべての祖先を列挙しない。
- 派生元がない実験は `parents: []` とする。
- 各親は既存の実験 ID を指す。自分自身や子孫を親にしない。
- 複数の既存実験を組み合わせる場合は、親を複数指定してよい。
- Wikiリンクは引用符で囲む。これにより通常の YAML 文字列として扱え、Obsidianでは実験ノートへのリンクとして利用できる。
- `tags`、`status`、`score`などは必須にしない。運用上の必要が生じた場合だけ追加する。

## 本文の書式

実験を始める前に「実験前」を記入し、評価後に同じファイルの「実験後」を記入する。必要な説明や作業ログは節を追加して同じファイルに残してよい。

```markdown
---
id: v0003
parents:
  - "[[v0001]]"
---

# v0003: 実験名

## 実験前

- 仮説:
- 変更:
- 機構確認:
- 評価目的:
- 比較基準:
- 判定基準:

## 実験後

- 判定: 基準通過 / 基準未達 / 中断
- 結果:
- 考察:
```

「評価目的」には、登録時点の [目標](../status.md#目標) と [評価方針](../status.md#現在の評価方針) のうち、この実験で検証する内容を書く。「比較基準」には、基準とする solver を書く。「判定基準」には、評価セット、評価指標、基準通過とする条件を書く。代理指標を使う場合は、目的との対応と限界も書く。

判定は、この実験の比較基準に対して判定基準を満たしたかどうかだけを表す。

- 基準通過: 判定基準を満たした。
- 基準未達: 機構確認を通過したうえで、判定基準を満たさなかった。
- 中断: 判定に至らず打ち切った。

基準通過は、提出に採用したことを意味しない。別の実験系統のほうが良ければ、基準通過した変更も提出には使われない。どの solver を提出候補とするかは [status.md](../status.md) だけに書く。

「変更」には `parents` からの差分を書く。親が複数ある場合は、各親から何を引き継いだかも書く。再試行する条件が明確なら、実験後に「再開条件」を追加する。

## 運用規則

- 実装を書き始める前に実験ノートを作り、「実験前」の各項目を記入する。
- 全体の目標や比較基準が更新されても、登録済みの実験の評価目的、比較基準、判定基準は保持する。新しい目的や基準で再検討する場合は、新しい実験として登録する。
- 実装途中の修正や同じ実験の再評価では、実験ノートを増やさず同じファイルを更新する。
- 判定後は、誤記や事実誤認の訂正を除いて内容を書き換えない。新しい仮説は新しい実験として派生させる。
- 長い考察、設計、作業ログも該当する実験ノートに書く。行数制限は設けない。
- ケースごとのスコアは `results/` 以下を正本とし、実験ノートに羅列しない。全体の平均スコアや特徴的なケースのスコアは、比較・判定・考察に必要な範囲で書いてよい。実験ノートの中心は比較対象、差分、判定である。
- 特定の実験を超えて成り立つ知見は、`notes/backlog.md` の観察に短く記録する。
- `parents` の整合性は実験ノートの作成時に確認する。専用の CLI、自動検証、索引生成は導入しない。
