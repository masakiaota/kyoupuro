# v047: 保存解から始める長時間探索と参照手順の蓄積

## 実験前

- 根拠: B-64、O49、O55、O57〜O59、O62。ユーザーから、性質の異なる5〜10ケースを1件30分〜1時間探索する実装、同時に使う探索コアを2以下にすること、ログと実行コマンドの用意を依頼された。実行はユーザーが手動で行う。v001〜v046のFront Matter、backlog、親v039の探索・時計・保存量を照合した。長時間探索の記録基盤は既存実験と重複しない。
- 仮説: v039の再挿入近傍を保存済みの短い解から長時間動かすと、既存の参照解を更新できる。長い1探索と、初期解・乱数を変える複数探索では、改善の続き方と到達する解が異なり得る。
- 変更: v039の再挿入探索・候補生成・受理条件を引き継ぎ、初期構築を保存解の読み込みへ置き換える。実時間の探索予算、乱数種、保存先を明示的な引数とする。改善時の操作列、変更直前の現在解、変更前後の共通区間、近傍の種類、経過時間、CPU時間、乱数状態、定期進捗を保存する。長時間だけ必要になる履歴の掃除は、最大200反復の再試行制限を既に過ぎた項目に限る。不正候補・入出力の失敗を隠さず異常終了する。v000と既存solverは変更しない。
- 機構確認: 今回はLOCALあり・なしのビルド、探索を呼ばない準備処理、保存済み初期解の独立再生、引数・保存・並列上限の検証まで行う。solverは実行しない。ユーザー実行時には、初期解と改善解の合法性・E=0、単調に減る最良T、継続側の1回の探索、再出発側の異なる乱数・初期解、同時子プロセス数2以下、計算時間と進捗の保存を確認する。
- 採否基準: 実装の受け渡しはビルド・準備・保存契約の検証を通過し、ユーザーが1コマンドで起動できること。探索結果は実行前に固定したケースごとの最良保存解と比較する。全成果物の合法性と追跡可能性を必須とし、1件でも厳密な短縮が得られれば参照解の収集として有効、短縮0件なら今回の探索構成では成果なしと記録する。継続と再出発の優劣は、このケース群・時間配分での観測として報告し、準最適性や2秒版への効果は主張しない。実行後の改良は新しい指示を受けてから行う。

## 実行と計時

- ケースを順に処理し、各ケースで単一スレッドC++を2プロセスだけ並行実行する。1つが継続探索、もう1つが既定60秒の再出発探索を繰り返す。ケースの並列実行はしない。OpenMP等のスレッド上限も1へ固定する。
- 既定は1ケース30分。10件で約5時間、60分へ変更すると約10時間となる。準備・ビルド・保存・検証の時間は別途かかる。OSの物理コアへの固定は行わず、同時に計算する探索プロセス数で上限を管理する。
- `JUDGE_TIME_LIMIT_SEC=1.90`、`LOCAL_TIME_RATIO=0.80`、`PROGRAM_TIME_LIMIT_SEC` は共通の値とする。CLIの秒数は実時間であり、`PROGRAM_TIME_LIMIT_SEC` に対する倍率に換算して長時間予算を作る。通常評価のLOCAL補正と既存evalは変更しない。探索期限・温度・近傍の時間配分はその予算に対する割合を使う。
- main開始直後から計時する。1回の長い探索では全時間をかけて温度を下げ、再出発側では各ラウンドで同じ温度曲線をやり直す。2秒版を中断してそのまま継続した比較ではなく、時間尺度と出発点を変えた診断である。
- `results/long_search/v047/<run_id>/` にソース、実行ファイル、入力、初期解、設定とSHA-256、各プロセスの履歴、最良解、集計を置く。通常評価のCSV・JSONL・scratchへ追記しない。同時実行の重複を避けるためevalと同じロックを使う。
- 初期解と改善解は保存前に再生検証し、操作列は一時ファイルからrenameする。Ctrl+Cでは子へ停止要求を送り、保存済みの最良解と途中集計を保持する。異常終了を正常完了扱いにしない。

## 手動実行

プロジェクト直下から、次のコマンドを実行する。起動時にC++をビルドし、入力と保存解を検証してから開始する。Python 3.10以降とGCC 15を使う。Macでは`caffeinate -i`により実行中のアイドルスリープを抑止する。

```sh
caffeinate -i python3 adhoc/scripts/run_v047_long_search.py --minutes-per-case 30 --workers 2
```

既定の10件を順に処理するため、探索は合計約5時間となる。1ケース1時間にする場合は`--minutes-per-case 60`へ変更する。探索は単一スレッドの2プロセスで行い、`--workers 3`以上は受け付けない。Linuxでは`caffeinate -i`を外したコマンドを使う。

対象を5件にする例は次のとおりである。

```sh
caffeinate -i python3 adhoc/scripts/run_v047_long_search.py --minutes-per-case 30 --workers 2 --cases 0035 0033 0064 0066 0019
```

`--restart-seconds 60`が再出発側の1ラウンドの既定時間である。継続側は最短の保存解から1回だけ探索する。再出発側は自身の最良解と、準備時に保存した最大8本の解を交互に使う。同じケースでも各ラウンドの乱数種は異なる。

Ctrl+Cでは探索プロセスへ停止を伝え、終了を待って途中集計を保存する。停止に応じない子プロセスは5秒後に終了させる。ケースをまたいだ途中状態からの自動再開機能はなく、次の起動は新しい実験記録になる。完了済みのケースを省く場合は`--cases`で残りを指定する。

## 保存先と分析の入口

起動時に`results/long_search/v047/<run_id>/`が表示される。各実行は独立したディレクトリを作り、既存の保存先を上書きしない。

| 保存物 | 内容 |
|---|---|
| `manifest.json` | 設定、対象ケースの特徴、初期解の出典、ファイルのSHA-256、コンパイラ情報 |
| `snapshot/` | 実行したC++とPython、親ソース、実験ノート、実行ファイル |
| `status.json` | 実行全体の状態。失敗理由と最大同時探索数も記録する |
| `summary.csv` | ケース別と探索方式別の初期T、最良T、短縮手数、実時間、CPU時間、最大常駐メモリ |
| `learning_curve.csv` | 2秒、10秒、30秒、1分、5分など、経過時点ごとの最良T |
| `improvements.csv` | 改善の時刻、近傍の種類、操作列と変更前の操作列への相対パス |
| `cases/<case>/input.txt`と`seeds/` | 凍結した入力と初期解 |
| `cases/<case>/best.txt` | 両方式を合わせた最良解。ケース終了時と集計時に更新する |
| `cases/<case>/<mode>/best.txt` | その方式の最良解。実行中も更新する |
| `cases/<case>/<mode>/status.json` | その方式の現在の進捗 |
| `cases/<case>/<mode>/round_*/round.json` | ラウンドのコマンド、乱数種、開始時刻、終了コード |
| `cases/<case>/<mode>/round_*/search/events.jsonl` | 初期解、改善、定期進捗、終了の逐次ログ |
| `cases/<case>/<mode>/round_*/search/solutions/` | そのラウンドで最良になったすべての操作列 |
| `cases/<case>/<mode>/round_*/search/before/` | 改善を作った直前の現在解。直前の最良解とは異なる場合がある |
| `cases/<case>/<mode>/round_*/stderr.log` | LOCALの集計とエラー |

`mode`は継続側が`continuous`、再出発側が`multistart`である。ケース終了時にCSVを更新し、終了または中断時にも再集計する。実行中に集計したい場合も、探索を追加せず次のコマンドを使える。

```sh
python3 adhoc/scripts/run_v047_long_search.py --summarize results/long_search/v047/<run_id>
```

改善した操作列と変更直前の操作列は、C++での保存前とPythonでの読み取り時にそれぞれ独立再生する。集計時にも再生し、TとEの一致を確認する。公式採点器はこの入口では呼ばない。

時間の推移は、各プロセス内の経過時間へ親プロセスの起動時点を加えて集計するため、プロセス起動の遅延分の誤差を含む。2秒時点の値も長時間向けの温度曲線で得たものであり、2秒版の性能比較には使わない。`saved`は各探索方式の最良解なら凍結した最短初期解との差、`improvements.csv`ではそのラウンド内の直前の最良解との差を示す。

## 追加分析：連携の短縮を2秒版へ還元する設計

2026-09-29の追加指示により、短縮した動作と既存コードを照合した。保存手順の再生と分析だけを行い、ソルバーは変更も実行もしていない。以下の動作の短縮は確認済みだが、提案する探索器の速度と完成スコアは未測定である。

### 還元する中心部分

最初の実装候補は、再挿入候補へ適用する経路短縮を、束の合流と分離をまたぐ共同短縮へ拡張することである。1〜2個の束について、集める場所、先に通す束、到着時の向き、途中に残す踏み台を、数回の受け渡しを含む区間で一緒に選ぶ。

v039の`smoothRoutes`は、同じ束を続けて運ぶ間を短縮し、その束が変わる境界では全盤面を元と一致させる。この境界の固定により、今回の2か所のジャンプを同時に短くする例を取りこぼす。`causalReorder`も、同じ出発点か着地点に触る操作の順序を保持するため、合流先や合流順そのものを変える例は扱わない。参照箇所は[smoothRoutes](../../src/bin/v039_exact_board_lns.cpp#L1023)と[causalReorder](../../src/bin/v039_exact_board_lns.cpp#L1974)である。

### 最終解で変わった量

0019では単独輸送が68操作減り、1操作の平均積載数は約12.7%増えた。総輸送量は6.3%減り、手数は20.1%減った。単独輸送の減少と搭載数の増加が現れている。

0005と0097では、総輸送量の減少はそれぞれ1.1%と1.5%にとどまった。一方、運ぶ匹数で重み付けした平均飛距離は、0005で1.23から1.43、0097で1.21から1.41へ増えた。平均積載数は0005で約1%増、0097では約1.6%減だった。長い距離を少ない輸送操作で進むことが、手数差に強く現れている。

同じ位置と積み順にある同じ個体群を、踏み台として2回以上使うジャンプの数も、一律には増えていない。0005は20回増、0097は18回増だったが、0019は21回減った。これらは完成解の記述統計であり、各指標の差を独立した原因として手数差へ配分したものではない。

### 同じ盤面を結ぶ短縮例

改善直前と改善直後の操作列から、始点と終点の全盤面が色と積み順まで一致する区間を抽出した。以下の例では、区間外の変更を根拠に短縮量を数えていない。操作番号は0-based、塔は下から上の順で記す。

#### 1. 同色便を分けず、別の踏み台を経由する

0097、継続側の記録`000062`では、横一直線に次の塔があった。

```text
(6,4) cccc   (6,5) bbbb             (6,8) c
```

変更前の3操作は、cを1匹だけ4マス先へ飛ばし、残るcの3匹を隣のbの塔へ運び、そこから3マス飛ばすものだった。変更後はcの4匹をまとめてbの上へ載せ、そこから3マス飛ばす2操作となった。着地時の高さは8以下で、最後の3マスジャンプ後にもbの4匹が同じ順序で残る。

長く飛べる1匹を先に出すと、その踏み台役だった3匹に別の輸送が必要になる。全4匹を帰すまでの操作数を比較すると、初手を1マスにした方が短かった。同色の内部順序を区別しなくてよい性質2が、そのまま探索の削減に使える。

#### 4. 2か所の偶数距離ジャンプを組み合わせる

```text
変更前：1+1マス → 1匹を下に加えて1+1マス → 下の1匹を残して1+1マス
変更後：  2マス → 1匹を下に加えて1+1マス → 下の1匹を残して  2マス
```

最初と最後の移動では、下に1匹残せるため2マス跳べる。1か所だけを短縮すると7匹の向きが逆になるが、2か所を変えると最終的な向きが元に戻る。途中で合流したeの個体も、同じ場所に残る。

既存の経路短縮は、最初の区間を終えた時点で7匹の向きまで元と一致させる。そのため最初の1操作短縮を受け付けず、後の区間で向きを戻す組み合わせへ進めない。性質6に基づき、途中の向きを2通り残して次の合流と分離まで比較すれば扱える構造である。

### 探索途中へ組み込む理由

継続側の最良更新385回のうち、363回は1手、18回は2手、4回は3手の短縮だった。合計411手の短縮は、この更新の累積である。両方式を合わせた413手とは区別する。

更新直前が直前の最良解と同じ操作列だったのは16回だけだった。350回は同手数の別操作列で、うち328回は各マスに触る操作の履歴まで異なり、互いに無関係な操作の並べ替えだけでは説明できなかった。残る19回は、直前の最良解より1〜2手多い現在解からの更新だった。

ただし、間に受理されたすべての操作列は保存されていない。そのため、同手数のどの変形が必要だったか、単調な改善だけでも到達できたかは未確定である。385回の最後の変更だけから、全探索経路の必然性は判断しない。

巣での3操作から2操作への型と、同じ束に向き制約付きの直進短縮が2か所ある型を限定した検出器で数えると、初期10解にはどちらも0件だった。対応する改善直前の手順では各1件を検出し、改善後は消えることを確認した。長い準備や、連続していない直進区間をすべて列挙した調査ではないが、これらの例については、探索中に生まれた形を短縮する必要がある。

したがって、既存の同手数候補の受理を維持しつつ、組み直した候補の合流と分離をすぐに共同短縮する設計を第一候補とする。単一の向きを途中で確定せず、候補内部では同手数の別の向きや到着順を残して、後続区間込みの手数で選ぶ。

### 具体的な探索単位

1. 操作列を再生し、各束の輸送と、その構成が変わる合流、分離、帰巣を記録する。各マスに触る前後の操作も索引にする。
2. 分割した同色便が再び同じ場所へ集まる箇所、外へ出て戻る集荷、容量を空けるための待ち、向きだけが短縮を妨げる複数区間を候補にする。現在の「抜けば消える操作数／匹数」の優先度へ、これらの具体的な短縮機会を加える。
3. 1〜2個の束と2〜3回程度の受け渡しを対象に、元の発着点を使った合流先、到着順、合流を省く順序を少数比較する。単独の原始操作を全盤面で展開する形にはしない。
4. 受け渡しの間は既存の向き付き最短経路を使う。未分割の束には向き2通りを残す。合流後は最大8匹の実際の色列を保持し、帰巣と残す踏み台を操作規則どおり更新する。
5. 区間内で独立な他の操作は保持する。対象外の操作が触る塔を変更したい場合は、その操作まで比較範囲へ含める。開始と終了の全盤面が一致し、設置と回収を含めた操作数が減る候補だけを短縮として採用する。
6. 再挿入で変わった箇所を優先し、候補数と時間配分を制限する。最初は同色便の分割取り消しのような少ない比較で済む型から実装する。処理時間は`PROGRAM_TIME_LIMIT_SEC`に対する割合で管理し、2秒版の実測前に速度を断定しない。

固定した周囲の塔を使う経路探索は、現在の実装なら床数の2倍以下の位置と向きの状態を持つ。共同探索でも、この経路部分を使い回し、組み合わせを増やす対象を受け渡しの順序と向きに絞る。ただし、合流によって周囲の塔や帰巣条件が変わった区間では、その状態に合わせて経路を計算し直す必要がある。

この設計は、配送の各段階で「誰が運ばれ、誰が残って次の便を支え、いつ帰巣するか」を選ぶ部品になる。初期構築にも使う場合は、既存の終了盤面がないため、次の配送へ何を残すかの評価が別途必要である。まずは終了盤面を固定して短縮を確かめられる再挿入後の処理へ還元する。

### 過去の実験との違いと検証条件

v041は帰巣のない最大4マス、合計8匹を扱った。今回の巣上の集荷は帰巣を含み、0005の例は7マスに10匹、0019の通過順変更は4マスに15匹が関わる。塔ごとの高さは8以下でも、区間全体の匹数を8に制限すると除外される。

v043は、将来の接触関係から切り離せる集合の全員を帰巣させる探索だった。今回の設計は途中の盤面へ戻る区間を対象にし、後で他の便と接触する個体も残せる。v044の原始操作探索とは異なり、受け渡し間の経路を最短経路へまとめ、節目の組み合わせへ探索を絞る。これらの違いが2秒の性能改善につながるかは未検証である。

最初の機構確認では、ここに挙げた保存手順を番号や座標の特例なしに候補抽出し、既知の短い手順を表現できることと、自動探索で発見できることを別々に確認する。特に、容量超過、向きを1か所だけ変える操作、早すぎる帰巣を誤って受け付けないことが必要になる。

その後、今回の初期解と改善直前の手順で、候補の出現数、短縮数、計算時間を測る。改善直前の手順は成功例を選んだ資料なので、その成功率を本番の途中解へ外挿しない。通常99件の完成スコアと時間内の試行数を測るまでは、413手の回収率や平均200手への到達は約束できない。
