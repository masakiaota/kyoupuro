# v052: 区間末尾の塔を復元する共同探索

## 実験前

- 仮説: v043の束単位の共同探索を、全帰巣まで独立する集団から有限区間へ移すと、中盤の合流、分割、積み順の変更を扱える。区間の入口と出口の全盤面を一致させれば、後続の操作を保って完成スコアを下げられる。根拠はB-68、O54、O56、O65、O67、O68である。
- 変更: solver全体はv050を保持し、v043の固定背景上の束の経路探索と共同探索の構成を引き継ぐ。全帰巣という終了条件を、指定した区間末尾の位置と色順の完全一致へ変更する。候補区間の開始時に存在する対象塔を全体として動かし、対象外の塔を背景として保持する。出発点と着地点の帰巣もv043と同じく扱う。元の関連操作だけを先に置換し、対象マスに触れない操作は元の順序で後から実行する。完成版への適用位置はv050の共同短縮の後とし、既存の最終期限の残り時間だけを使う。初期構築、LNS、乱数、既存3処理、時間配分は変更しない。LOCALと非LOCALの両方で有効とする。
- 機構確認: 保存済みv050の100解から対象区間を抽出し、独立Python実装の候補集合と照合する。長時間探索で得た同色便の統合、巣への呼び込み、合流回避、2か所の向き変更について、元手順と参照手順を新しい遷移で表現できることを確認する。既知の0005の6操作から4操作、0019の巣への呼び込みの3操作から2操作を自動発見することを必須とする。固定背景の保存、着地前の容量、帰巣、完全一致する終了条件、不可逆な帰巣による枝刈り、期限を独立再生で確認する。保存100解への適用では、元の解を固定して全盤面一致と追加短縮を測る。
- 採否基準: 機構確認を通過し、保存済みv050の100解で追加1手以上の短縮が得られれば、通常100件をLOCAL、時間補正0.80、並列数2で1回評価する。追加短縮0なら通常評価へ進まない。通常評価は全件合法かつE=0、100,000操作以内、外部計測2,000 ms以内、構築とLNSのエラー、不正候補、作り直し0を必須とする。新処理が同一実行内で1手以上短縮し、保存済みv050より合計Tが少なく、case0000が43手以下なら今回の比較で採用する。直接の削減と時間依存の探索を含む版間差を分けて記録する。

## 探索条件

区間の範囲は上記の調査と同じとする。共同探索では、上段の束を選び、固定された背景上で次の節目まで最短経路で運ぶ。到着時の両方の向き、すべての分割位置を扱う。節目は区間内の全マス、現在の対象塔、対象色の巣とその隣接床、開始塔の2つからの距離和が小さい4床とする。

終了時に残すべき色の匹数を下回った状態は、帰巣した個体が戻らないため除く。各塔で現在の色列と目標の色列の下側から一致する部分を調べ、そこより上を動かす必要がある出発点数と、追加の受け取りが必要な着地点数の大きい方を残り操作数の下界とする。1操作は1出発点と1着地点を変更するためである。この下界と実費用で上限を超える枝を除く。

状態の優先順位には実費用と上記の下界に加え、まだ配置が合わない色から必要な着地点までの距離、積み順が合わない匹数を使う。距離はv043と同じ高さ由来の飛距離目安で割り、重み0.5、匹数は重み0.125で加える。この部分は候補の順位付けだけに使い、下界とは扱わない。ビーム幅12、展開上限192をv043から保持し、節目の数は短縮前の関連操作数未満とする。

候補区間は関連操作数と下界の差を降順に並べ、同点なら関連操作数、参加匹数、開始位置の昇順とする。通常の追加処理では、巣を含むか4マスを超える区間に絞る。同じ開始位置は最優先の1候補だけを試し、1ケース最大32試行とする。採用した区間と重なる候補は除く。各試行は `PROGRAM_TIME_LIMIT_SEC` の0.3%以内かつ既存の最終期限以内とする。

固定仕事量の診断では時計だけを外し、同じ候補順、試行数、幅、展開上限で保存100解を1回ずつ処理する。改善解を次の診断ケースへ戻さない。通常評価前にLOCALありとなしをビルドし、完全な前処理差分をv050と照合する。今回のソースと資料は `adhoc/v052_audit/`、通常評価の集計は `results/analysis/v052/` に保存する。同じ実装の再評価によるノイズ測定は行わない。

## 実験後

### 判定

棄却。通常100件の合計Tは保存済みv050比で38手増（0.18306%悪化）、35勝30分35敗だった。新処理が11ケースで13手短縮したが、完成版の採用基準を満たさなかった。提出候補はv050を維持する。

全100件が公式採点と独立した個体追跡で合法かつE=0、最大1,571 ms、case0000は43手だった。構築とLNSのエラー、不正候補、作り直し、盤面領域の未返却は0だった。ソース、入力、親の保存出力のハッシュは評価前と一致した。

### 直接の短縮と版全体の差

通常評価では12区間を置換し、13手減った。終了時に対象の塔を残す区間で12手、巣を含む区間で9手減った。これらの分類には重複がある。旧来の共同短縮は64手減であり、今回の13手はその後の追加分である。

新処理に入る時点では親の完成解より合計51手多く、そこから13手減って最終差が38手増となった。初期構築直後には2ケースで合計4手少なかった。LNS試行数は親比2.32306%減ったが、追加処理はLNS終了後に実行し、LNSの時間配分は保持している。完成版の悪化や試行数減少を、追加処理の実行時間がLNSを直接奪った結果とは判定しない。コード配置を含む実行速度の差と、時計に依存する探索経路の変化の寄与は未分離である。

### 探索時間による制約

新処理は平均23.07749 ms、最大23.881 msだった。100件中98件で全体の期限に達し、各ケースの試行数は5〜32回、合計1,333回だった。試行単位の期限到達も98ケースで計205回あった。展開数上限到達は0だったが、ビーム幅による候補削減は1,637,366件あり、探索の完了や最適性を意味しない。

時計を外した保存解の診断は3,193回を試し、96ケースで24 msを超えた。今回の探索量を完成版の残り時間で処理しきれないことは確認できた。保存解の24手と通常評価の13手は対象の操作列も異なるため、その差11手から時間制限だけの影響は分からない。

### 保存解で得た連携

固定したv050の保存解で短縮した20区間を、別のPython実装で再生した。全区間で入口と出口の全盤面が一致し、置換直後には対象外の塔が入口の状態へ戻ることを確認した。区間内にある計130個の無関係な操作は元の内容と順序を保つ。以下の手数は関連操作だけを数え、塔内の文字列は下から上の順である。

| ケースと元の区間 | 短縮した連携 | 変化 |
|---|---|---:|
| 0084、191〜197 | 別便の`h`を`bbb`と同乗させ、到着後は`h`を踏み台にして`bbb`を巣へ跳ばし、最後に`h`を帰す | 7操作から5操作 |
| 0036、95〜103 | `ccggg`を中継の`aaa`を飛び越えてG巣へ送り、`aaa`を後から載せる。上段の`ccaaa`を搬出すると下段の`ggg`も帰巣する | 4操作から3操作 |
| 0019、595〜612 | `abaa`をA巣へ直接4マス跳ばし、途中にいた`a`は別に帰す。他方の塔の`f`6匹も一便でF巣へ送る | 8操作から5操作 |

0084では、運ばれる`h`を途中から踏み台へ変える連携が成立した。元の手順は`bbb`の配送に3操作、`geffh`の移動と分割に4操作を使っていた。新しい手順は次の5操作で、`geff`の最後の積み順も一致する。

```text
1. (8,8) の上段 h を (8,9) の cbbb へ載せる      → cbbbh
2. 残る geff を (9,8) の gg へ送る                 → ggffeg
3. (8,9) の c を残し、bbbh を南へ2マス送る         → (10,9) に hbbb
4. h を残し、bbb を西へ2マス送る                   → B巣へ帰巣
5. 残る h を南へ1マス送る                          → H巣へ帰巣
```

この例では、同乗で束の向きを変え、その向きで底に来る`h`を踏み台として使う。出発時の下段1匹を残すことで2マス跳べる性質を、途中の合流と分割で2回利用している。0036では巣上の自色をすぐ帰さず、上段の搬出と同時に帰す順序が使えた。これらは有限区間の終点を保ちながら、合流先、束の構成、帰巣の順番を変えた具体例である。

### 次の実験に引き継ぐ前提

終了時に塔を残す条件でも、v043の束単位の共同探索は短い手順を発見できた。長時間探索の4参照例もすべて自動発見できたため、この4例を表現する能力と発見する能力は確認済みとなった。一方、固定した保存100解で追加24手、通常評価で追加13手という規模にとどまり、完成スコアの改善は未達だった。

今回の方式を再検討するときには、約23 msで試せる区間数と、その中に短縮区間を含められるかを実測する必要がある。特定の既知例が短時間で解けることだけでは、完成版でその区間を選べる根拠にならない。探索途中の解への適用も、今回の完成解への適用からは判定できない。

再開条件: 有限区間の短縮例を保ちつつ、完成版の残り時間内での候補選択、処理費用、既存探索への影響を改善する具体的な根拠が得られ、追加検証の指示を受けた場合。結果報告後、ユーザーから「もうちょっと工夫したら良い効果だけ残せない？」と追加の検討指示を受けた。今回の判定を保持し、追加検証は別の実験とする。案3のB-69は未着手である。
