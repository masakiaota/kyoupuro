# v009: 通常輸送に織り込む1匹踏み台と段階的な帰巣

## 実験前

- 仮説: O5と固定踏み台網の性質から、同色の荷物を集約する途中で1匹だけを中継点に残し、後続の輸送が済むまで帰巣を遅らせれば、配置専用の操作を設けずに2マスジャンプの配送網を育てられる。配置場所と帰巣順を共同で選び、踏み台の回収費を含めても操作数が減る。
- 変更: B-12を独立実装する。既存solverからの直接の派生元はない。各色に通常配送と踏み台回収の2イベントを持たせ、通常配送が先という制約で順序を探索する。通常配送中の集約点で1匹を残す位置も探索する。新しい位置への配置は、そこに集まった同色2匹以上のうち1匹を残して残りを発送できる場合に限る。初期位置の1匹を維持する選択も許す。各イベントは、他の色と回収待ちの1匹を下段に残し、同色の荷物だけを運ぶ。初期順序は端側の色を先にし、実際の全操作数で順序と配置を最適化する。
- 機構確認: 最終出力を再生し、`relocated_supports`（輸送の途中で新しい位置に残した1匹）、`relocated_support_jumps`（再配置した1匹からの2マスジャンプ）、`cross_event_support_jumps`（配置イベントより後での利用）、`consecutive_two_jumps`（同じ荷物の連続2マスジャンプ）を確認する。新設時に同じ位置から荷物を発送していること、定常状態の踏み台が高さ1であること、全踏み台の回収と `E = 0` をLOCALの検証で確認する。
- 採否基準: `tools/in` の全100件を既定のLOCALビルド・`-j 2`で1回evalする。全件で合法出力・`E = 0`・操作数制限内であり、通常生成99件の合算で上記4つの機構カウンタがすべて正、かつ全100件の合計Tが保存済みの `v008_lightweight` より小さければ提出候補として採用する。通常生成99件の差分も併記する。機構確認が失敗した場合は効果の否定とせず中断とする。

### 事前照合と独立実装の範囲

- backlog全体と `v001`〜`v008` のファイル名・Front Matterを照合した。B-12の再配置と段階的帰巣を中心にした実験は未実施であり、決着済み実験の再開ではない。
- ユーザー指定に従い、たたき台完成前は既存solverおよび共通templateの実装を参照しない。問題文、記号、重要な性質、backlog、実験メタデータ、ビルド・eval運用だけを参照して作る。類似実験の実装詳細との照合とtemplateの時間・計測基盤の取り込みは、たたき台完成後に行う。
- 比較対象は着手時点で100件の保存済み評価がある最新の `v008_lightweight`（label: `lightweight_all`）とする。既存実装を組み込んだ場合は、実行前に直接の派生元と取り込み範囲を追記する。

### 実装設計

1. イベント間の盤面を「各マスに0匹または1匹」で表す。各イベントでは対象色を上側の同色荷物として集約し、対象外の1匹を踏み台として維持する。
2. 隣接移動と、高さ1の踏み台からの2マス移動で巣への有向グラフを作る。巣からの逆向きBFSで距離を求め、距離が減る辺から同色荷物を合流させやすいものを選ぶ。
3. 配置候補を踏み台として仮定して経路を作り、新設位置に2匹以上集まらない候補を外して経路を再構築する。候補数が毎回減るため有限回で確定する。初期位置にある対象色の1匹はそのまま保留できる。
4. 高さ8の制約を満たす量ずつ発送する。着地点が満杯なら木の巣側へ先に送り出して空きを作る。配置予定の1匹は下段に残す。全操作を数えた値で配置・イベント順序・経路の同点選択を探索する。
5. 最良の計画を再構築して出力する。LOCALでは独立した塔の再生で高さ制約・反転・両端帰巣・全帰巣を確認し、最終解の機構カウンタを記録する。

- 静的確認で、満杯の着地点を先に発送した際、新たに1匹を下段へ残して容量が変わり得ることを確認し、空き容量を先行発送後に再計算するよう修正した。solver実行前の修正である。

## 実験後

### 判定

棄却（提出候補として）。全100件の合法性・全帰巣と、事前登録した4つの機構カウンタの発動を確認した。合計Tが保存済み `v008_lightweight` を上回り、採否基準のスコア条件を満たさなかった。

### 結果

- 全100件で公式scorerが成功し、公式スコア・出力行数・予測Tが一致した。全件で `E = 0`、操作数制限内、`fallback_count = 0` だった。LOCALの個体単位の再生で、各操作の容量・反転・両端帰巣と、各イベント終了時に予定した高さ0または1の配置を確認した。
- v008比で、全100件の合計Tは1,900手増（7.0116%悪化）、6勝0分94敗だった。通常生成99件では1,895手増（7.0061%悪化）、6勝0分93敗だった。
- 通常生成99件の機構確認は下表のとおりで、採否基準の4カウンタはすべて正だった。

| 機構カウンタ | 合計 | 発動したケース数 |
| --- | ---: | ---: |
| 新しい位置に残した1匹 `relocated_supports` | 533基 | 92 / 99 |
| 新設踏み台からの2マスジャンプ `relocated_support_jumps` | 2,087回 | 92 / 99 |
| 後続イベントでの利用 `cross_event_support_jumps` | 1,621回 | 88 / 99 |
| 同一個体の移動履歴で連続する2マスジャンプ `consecutive_two_jumps` | 3,059回 | 99 / 99 |

- 通常生成99件では新設した456基を2回以上利用した。初期位置で留置した踏み台は329基だった。新設時には同じ位置から別の同色個体を発送していることを確認しており、配置だけを目的とする専用操作は設けていない。
- 踏み台回収は通常生成99件中92件で発動し、合計2,254操作、全Tの約7.79%を占めた。49件では、回収を後続色の通常配送より前に挟む順序が選ばれた。全99件で初期の端側優先順からイベント順序が変わった。
- 通常生成99件の最終解は、同一実行内の留置なし初期構築から4,763手（14.1310%）減った。探索では配置・帰巣順・経路選択を同時に変えており、この削減を配置だけの効果とは解釈しない。
- 全100件のローカル実行時間は平均1,440.05 ms、最大1,444 msだった。全件2,000 ms未満であり、探索時間は平均約1,428.51 ms、復元は約0.05 ms、独立再生は約0.02 msだった。

正本ログは `results/score_summary.csv`、`results/score_detail.csv`、`results/eval_records.jsonl` にある。今回の `run_id` は `20260926T020313+0900_v009_relay_weave_c8c93b`、ラベルは `b12_relay_weave` である。比較対象の `run_id` は `20260926T014405+0900_v008_lightweight_fdf782` である。

### 考察

通常の同色輸送で1匹を中継点へ残し、後続配送まで維持してから全員を帰巣させる構成は成立した。新設した踏み台は同じ配送イベントだけでなく、88件で後続イベントにも使われた。したがって、今回の不採用は機構の不発によるものではない。

配置専用操作をなくしても、留置した個体を帰す費用は残った。回収イベントが全Tの約7.79%を占める事実は確認できたが、その全額を留置による純粋な追加費用とはみなせない。留置しない場合にも当該個体の輸送は必要であり、同じ経路・順序を固定した費用差は測っていない。

v009は独立実装であり、v008との比較には踏み台の高さだけでなく、経路構築・探索変数・計算量の違いも含まれる。この結果から「高さ1の再配置一般が不利」とは結論しない。一方、今回の実装全体がv008を上回るという採用条件は満たさなかった。

次の実験の前提として、輸送途中の1匹留置・後続利用・段階的回収の成立性は確認済みとなった。スコア上の優位性と、端側から処理する順序そのものの効果は未確認のままである。
