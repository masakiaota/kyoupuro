# v015: 二色の混載集荷木と分離配送

## 実験前

- 仮説: 二色を集荷途中から混載して経路を共有し、巣以外も含む合流点で下段を踏み台に上段を発射すれば、色別集荷と巣の巡回を中心とする v013 より全帰巣までの操作数を減らせる。この配送方法に合わせた便の結合・分割・再分配を同時に探索する。根拠はユーザー提示の `ahc072_mixed_tree.cpp`、混色集荷に関する Q2・O2・O7・O13 である。
- 変更: `ahc072_unified.cpp` との差分から v013 の直接派生と判断し、`src/bin/v015_mixed_tree.cpp` に登録する。二色の集荷・分離配送と、それを利用する便の再編を中心アイデアとして扱う。持ち込みコードの探索内容を保持し、既存の共通時間管理・LOCAL計測・最終出力の独立検証を接続する。
- 機構確認: `mixed_decoded` と `mixed_routes` で新しい二色配送の構築試行を確認し、LOCAL専用の `mixed_completed` で合法な全帰巣経路の構築成功を数える。`mixed_trials`、`mixed_merges`、`mixed_splits`、`mixed_repartitions` で便の再編候補を確認する。これらは探索中の試行・構築成功であり、最終計画への採用回数ではない。最終出力は独立再生し、合法性・容量制約・両端帰巣・`E = 0`・操作数と行数の一致を確認する。
- 採否基準: `tools/in` 全100件を既定の LOCAL・並列数2で1回評価する。全件で公式採点成功、`E = 0`、100,000操作以内、実行時間2,000 ms未満を満たすことを必要条件とする。通常生成99件で二色配送の構築成功と便の再編候補生成が発動し、全100件の合計Tが保存済み v013 を下回れば提出候補として採用する。通常生成99件と手作りのcase0000も区別して記録する。新機構が未発動なら、効果の否定とせず機構未確認として記録する。

## アイデアと実装の対応

### 1. 集荷途中から混載して経路を共有する

v013 は色ごとの集荷木を作ってから混色の便を組み立てる。今回の `GatherPlan` は、二色の部分集団を同じ集荷木で扱う。便に含まれる同色の個体を集め切る前でも、近くの異なる色を合流させて一緒に運べるため、重複する移動を減らせる可能性がある。

`buildGather(..., true)` は部分集合DPで合流点と集荷経路を選ぶ。色の並びを連続した区間に保つ組み合わせだけを許し、`collectGather` はジャンプによる上下反転の偶奇に合わせて合流順を選ぶ。これにより、二色を上下のまとまりとして分離できる積み方を作る。

### 2. 合流点から上下を別々に配送する

`mixedDelivery` は、床上の合流点と、どちらの色を下段にするかを候補にする。集荷費に、下段を踏み台として上段を発射する費用と、残った下段を巣へ返す費用を合わせて順位づけする。上位候補を最大6通り実際の盤面上で構築し、合法に全員を帰せた中で操作数の小さい経路を使う。既設の踏み台による飛距離と塔の容量も判定に含む。

空の盤面での候補評価にも、集荷木と上段発射の概算費を組み込む。概算値だけで候補を確定せず、実経路の構築と全計画の操作数で比較する。

### 3. 混載配送に合う便へ組み直す

`mixedRegroup` は、近接性と既存経路の共通部分を手掛かりに、合計で二色となる便を選ぶ。二つの便の結合、一つの混載便の分割、二つの便への個体再分配を候補にする。配置に使用する踏み台個体が所属する便は変更対象から除外する。便数が変わっても、同じ個体集合を持つ便は識別して経路を再利用する。

この再編を配送順探索と踏み台探索に接続する。新しい二色配送を作れなかった場合に従来の配送処理へ進む経路は、提示コードの仕様として保持する。

### 対象範囲

便の容量は提示コードの `CAP = 7` を保ち、一便ごとに対象個体を全帰巣させる。v014 は2〜3便・合計12匹以下を対象に集荷と分離を継続する共同配送であり、今回の二色・最大7匹の集荷木とは別の実験である。v014 の実装・時間配分は取り込まない。

## 実験後

### 判定

採用（今回の評価セットでの提出候補）。全100件で合法出力・全帰巣・実行時間2,000 ms未満を満たし、v013比で合計Tを225手、0.9310%削減した。通常生成99件すべてで新しい二色配送の構築成功と便の再編候補生成を確認し、機構確認も満たした。

### 結果

- 評価は1回のみ実行した。全100件で公式採点が成功し、公式スコア、LOCALの最終操作数・検証操作数、保存出力の行数が一致した。保存出力を独立再生し、全操作の合法性・容量制約・両端帰巣・`E = 0`・100,000操作以内を確認した。
- 全100件の実行時間は平均1,483.99 ms、最大1,501 msだった。LOCALの最終出力検証は平均0.0212 msだった。
- 比較対象は保存済みv013とする。勝敗はTが小さい場合をv015の勝ちとする。絶対スコアは `results/` のCSVを正本とし、小数を含む平均は `total_sum / total_cases` で求める。

### 考察

二色の部分集団を混載して集め、合流点から上下を送り分ける配送は、今回の通常生成99件すべてで構築できた。便の結合・分割・再分配も候補として発動し、この構成全体がv013の最終操作数を下回った。次の実験では、二色の混載集荷木と便数変更を含むv015を比較基準の候補にできる。

主探索が作った操作列は後処理前の時点でv013より短かったが、後処理による追加削減は減った。二色配送、便の再編、候補評価の変更、時間制限付き探索の実行変動を含む比較であるため、225手の差をいずれか一つの仕組みだけの効果とは断定できない。

今回の対象は二色・最大7匹の便であり、便の対象個体を全帰巣させてから次の便へ進む。最大8匹の混載や帰巣後の追加集荷を中心とするv014の実験とは対象範囲が異なる。case0000の改善も今回は得られなかった。

持ち込みコードのアイデア、派生元、移植内容、評価結果を記録し、評価1回で終了した。評価後のsolver変更や再評価は行っていない。
