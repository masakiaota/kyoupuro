# v021: 2塔の部分再構築と末尾側からの操作並べ替え

## 実験前

- 仮説: v020の途中時点からの再挿入を2つの塔へ広げ、末尾側からも依存関係を保って操作を並べ替えれば、別々に組み上がった荷物の経路共用を探せる。再挿入遷移と候補管理の計算を軽くする変更も組み合わせることで、同じ時間内に操作数の少ない解を得られる。根拠はユーザー提示の `ahc072_paired_event_lns.cpp`、O29の塔の部分再構築の成立、O14とO15の再計算量と維持費に関する観察である。
- 変更: 提示コードを `src/bin/v021_paired_event_lns.cpp` として登録する。v020から直接引き継いだ構築と再挿入探索に、2塔の上段の共同再構築、末尾側からの並べ替え、連続する直進2操作の短縮を狙う同点評価を加えている。再挿入遷移は高さと挿入位置から直接計算し、候補の重複管理には再利用するハッシュ表を使う。これらを組み合わせた原版全体を対象とする。移植では非LOCALを原版から保持し、LOCALの時間補正、計測、独立検証だけを追加する。
- 機構確認: 既存の試行、再挿入成功、受理、最良解更新に加え、`lns_paired_attempts`、`lns_paired_accepted`、`lns_backward_attempts`、`lns_backward_accepted`、`shortcut_support_states` を記録する。2塔の近傍と末尾側からの並べ替えについて最良解更新と短縮量も分ける。開始直後の経路短縮と並べ替え、探索ループ内の最良解更新の合計が `pre_lns_ops - final_ops` に一致することを確認する。保存出力を独立再生し、全操作の合法性、高さ制約、両端での帰巣、E=0、操作数と出力行数を検証する。例外による作り直し、処理エラー、候補検証での破棄も記録する。
- 採否基準: `tools/in` 全100件を既定のLOCAL、並列数2で1回評価する。全件で公式採点成功、合法出力、E=0、100,000操作以内、実行時間2,000 ms未満を必要条件とする。初期解と最終解の例外による作り直し、構築エラー、LNSエラーが0で、通常生成99件の合計で `lns_attempts`、`lns_insertions`、`lns_accepted`、`lns_improvements` と上記5つの追加機構カウンタがすべて正、かつ全100件の合計Tが保存済みv020を下回れば提出候補として採用する。機構が未発動なら機構未確認として扱う。v019とも参考比較し、通常生成99件と手作りのcase0000を分ける。

## 中心アイデアと実装の範囲

### 同じ途中時点にある2つの塔を対象にする

操作列の途中を選び、次の操作の出発点にある塔と、その近くにある別の塔の上段を取り出す。取り出す個体数の上限は合計6匹を基本とし、4分の1の確率で8匹まで広げる。相手の塔は床上距離10以内から、塔間の距離、含まれる色の巣同士の距離、次の移動先かどうかで順位づけする。

その時点より前の操作列を固定し、取り出した個体を除いた後続操作を修復する。各個体には元の塔と高さの順位を残し、帰巣距離や乱数、塔ごとの優先順位で1匹ずつ再挿入する。両方の塔を含む開始盤面全体が元の盤面と一致した候補だけを残す。以後の操作では分離、同乗、混載を許すため、個体が元の塔ごとに移動し続ける制約はない。

巣の上の塔へ戻すときは、元から上にあった個体を先に戻して途中の帰巣を防ぐ。2塔の試行は原則17反復に1回で、探索開始後の経過時間に対する累積使用時間が11%未満の間に行う。

### 末尾側からも依存関係を満たす順序を作る

v020と同じく、同じ出発点または到着点を使う操作の前後関係を保つ。追加した方式では、後続の依存操作が残っていない操作から末尾側へ選び、最後に全体を反転する。次に続く荷物と着地後の色列が合う運搬を優先する。生成後は最初から再生し、全帰巣と合法性を確認して経路短縮へ渡す。並べ替えの6種類のうち3種類が末尾側からの方式である。

### 再挿入の計算と同点評価を変える

挿入した個体や束が移動後にあるマスと高さ、巣で消える上端部分を、元の操作と盤面の高さから直接求める。v020のように各挿入位置ごとに2つの塔の色列を組み直す処理を減らす変更である。移動直後かつ帰巣前の容量制約は残している。原版のこの式が全状態でv020と同値かどうかの網羅的検証は今回の登録には含めず、評価では最終出力の独立再生と候補検証の診断を確認する。

同じ色の荷物を同じ方向へ続けて運ぶ2操作について、下段が増えれば1操作にまとめられる条件を調べる。再挿入した個体や束を下段に残す遷移が必要な高さを満たす場合、追加手数が同点の候補の評価を上げる。`shortcut_support_states` はこの加点条件を満たした遷移の検討回数であり、実際に最良解で短縮した回数とは区別する。

候補の重複管理は `unordered_map` から世代番号付きの開番地法の表へ変わり、個体集合の出現パターンと作業配列も再利用する。最適化pragma、乱数の基本生成方法、前半の構築、時間定数、悪化候補の確率的受理はv020から引き継ぐ。ただし追加近傍などで乱数の呼び出し回数は変わる。

## 事前照合と移植方針

backlog全体とv001〜v020のファイル名およびFront Matterを照合した。v020の原版と今回の提示コードの差分から直接の派生元を確認し、今回の依頼をB-26へ登録する。未着手のB-20は過去のv015の移植を対象としており、今回の登録では変更しない。

非LOCALは原版のグローバル時計の開始位置、時間定数、呼び出し形、乱数、データ構造、最適化pragmaを保持する。LOCALだけでmain冒頭を計時基準とし、`JUDGE_TIME_LIMIT_SEC = 1.90`、`LOCAL_TIME_RATIO = 0.80`、`PROGRAM_TIME_LIMIT_SEC` を使って秒単位の定数を換算する。終了期限は原版1.930秒、LOCAL1.544秒、探索ループの終了目安は原版1.900秒、LOCAL1.520秒で、いずれもv020と同じである。割合、反復回数、温度、距離の重みは時間補正の対象にしない。

原版の例外による作り直しと候補の破棄を保持し、新しい救済経路は加えない。評価前にLOCALありとなしをビルドし、完全なマクロ展開後のソースと非LOCALの生成命令を原版と照合する。単発試走は追加せず、既存の評価処理によるウォームアップ1件と本評価100件を1回行う。

v020との差には複数の探索変更と計算方法の変更が含まれる。時間定数が同じでも、実行速度と探索経路に依存する1回の比較から個々の変更の単独効果は判定しない。評価後はsolverを変更せず、保存結果の検証と記録で終了する。

## 評価前の確認

arm64のmacOS上でGCC 15.1.0、C++23を使い、LOCALありとなしの両ビルドに警告なく成功した。SDKは `xcrun --show-sdk-path`、deployment targetは15.0を指定した。原版のGCC最適化pragmaを保持した。x86_64専用の命令セット指定はこの環境では有効にならず、x86_64上でのビルドと評価は行っていない。

`-E -P` で完全にマクロ展開した非LOCALソースは、追加計測が消えた場所の空行以外は原版と一致した。生成アセンブリも、ファイル名に由来する静的初期化のシンボル名以外は一致した。LOCAL側の差分は、時間補正と計時開始、計測、独立検証だけである。照合結果と差分は `adhoc/v021_port_audit/` に保存した。

## 実験後

### 判定

採用（今回の評価セットにおける提出候補）。全100件の合法性、全帰巣、操作数制限、実行時間を満たし、事前に指定した9つの機構カウンタは通常生成99件すべてで正だった。処理エラーと例外による作り直しは0で、全100件の合計Tは保存済みv020より169手、0.8001%少なかった。

### 評価結果と比較

LOCAL、並列数2で評価を1回実施し、全100件で公式採点に成功した。保存出力の独立再生でも、全操作の合法性、高さ8以下、両端での帰巣、E=0を確認した。公式スコア、出力行数、LOCALの最終操作数と検証操作数は全件一致し、100,000操作以内だった。実行時間は平均1,532.02 ms、最大1,545 msで、全件2,000 ms未満だった。

### 追加機構の発動

通常生成99件では、2塔の近傍と末尾側からの並べ替えの両方で、全99件に受理候補が生じた。

| 追加機構 | 試行 | 受理 | 最良解更新 | 更新ケース数 | 短縮量 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 2塔の部分再構築 | 43,692回 | 5,022回 | 157回 | 71 / 99 | 193手 |
| 末尾側からの並べ替え | 3,369回 | 3,322回 | 48回 | 34 / 99 | 67手 |

直進2操作の短縮に必要な高さを満たす同点加点 `shortcut_support_states` は、通常99件すべてで発動し、合計8,276,913回だった。これは遷移の検討回数であり、その回数だけ操作を短縮したことや、同点評価単独の性能効果を示す値ではない。

探索全体では、通常99件で749,261候補を試し、再挿入成功の記録は1,921,070回、受理は144,516回、ループ内の最良解更新は3,216回だった。再挿入成功は1匹または束の挿入ごとの加算で、後続の挿入が失敗した未完成候補も含む。

### 最良解の短縮内訳

通常99件では、前半の構築が基準解から6,283手、後半の探索と経路短縮が6,608手を短縮した。後半の短縮は99件すべてで発生した。最良解を更新した処理ごとに重複なく分類すると次のようになる。

| 最良解を短縮した処理 | 短縮量 | 短縮したケース数 |
| --- | ---: | ---: |
| 開始直後の経路短縮 | 21手 | 11 / 99 |
| 開始直後の先頭側からの並べ替えと経路短縮 | 109手 | 9 / 99 |
| 通常の個体除去と再挿入、その後の経路短縮 | 5,594手 | 99 / 99 |
| 1塔の束を保つ再挿入、その後の経路短縮 | 140手 | 42 / 99 |
| 1塔の分解を許す再挿入、その後の経路短縮 | 354手 | 87 / 99 |
| 2塔の部分再構築、その後の経路短縮 | 193手 | 71 / 99 |
| 探索中の先頭側からの並べ替えと経路短縮 | 130手 | 51 / 99 |
| 探索中の末尾側からの並べ替えと経路短縮 | 67手 | 34 / 99 |
| 合計 | 6,608手 | 99 / 99 |

全100件では後半の短縮は6,618手だった。開始直後の2種類の短縮と、探索ループ内の最良解更新による短縮の合計は、各ケースの `pre_lns_ops - final_ops` と一致した。ループ内の近傍別の短縮量を足した値も一致した。`backward_saved` は `reorder_saved` の内数であり、二重に加算していない。

未採用候補も含む原版の `shortcuts` は通常99件で259,657手だったため、上表の短縮量には使わない。また、先行する別種の近傍が作った同点候補や悪化候補を経由する影響は、候補種別ごとの短縮量から分離できない。

全100件で、初期解と最終解の例外による作り直し、構築エラー、LNSエラー、候補検証での例外破棄、`finishSingles` の呼び出しはすべて0だった。`construction_deadlines` は3,607回で、現最良以上の候補の打ち切りを含む。`lns_deadlines` は0だった。

構築時間は全100件平均393.42 ms、後半の探索は平均1,126.72 ms、独立検証は平均0.0195 msだった。候補集合の再構築は平均145.28 ms、1塔の部分再構築の探索は平均73.05 ms、2塔の部分再構築の探索は平均24.03 msだった。候補集合の再構築時間は保存済みv020の平均171.28 msを下回ったが、探索経路と構築回数も異なるため、同じ仕事量での速度比較とは扱わない。

case0000ではv020と同じ操作数だった。通常の個体除去と再挿入を経て9手、束を保つ再挿入を経て1手を短縮し、合計5回の最良解更新で10手を短縮した。2塔の再構築は247候補、末尾側からの並べ替えは170候補を受理したが、それら自身による最良解更新はなかった。

### 考察

同じ途中時点にある2塔を対象として、開始盤面を復元しつつ後続操作を作り直す近傍が成立した。末尾側から操作の依存関係を満たす順序を作る方式でも、合法な候補と最良解更新を確認した。次の実験では、両機構を使うこの構成を比較基準の候補にできる。

v020とは時間定数が同じで、後半開始前の操作数も全件一致した。その条件で完成版の合計Tは169手減った。一方、2塔の再構築が最良解を更新した際の短縮193手と、末尾側からの並べ替えによる67手を足しても、版間の差169手とは一致しない。この2つは同一実行で最良解を更新した候補の分類であり、版間では他の近傍による短縮量も変わっている。計算時間配分、探索経路、遷移計算、候補管理の影響は未分離である。この1回の評価から追加機構それぞれの単独効果や、実行時変動を除いた恒常的な改善量までは特定していない。

提出用処理は提示原版から保持できた。命令の照合と評価はarm64上であり、x86_64の専用命令を使うAtCoder環境でのスコア、実行時間、メモリは未評価である。評価後のsolver変更と追加評価は行っていない。
