# v016: 合流点と分離点を選ぶ継続配送木

## 実験前

### 仮説

一色を帰すまでの集荷と分離を配送木として構築し、残った単色の荷物を次の配送木へ引き継げば、v014で失った合流の自由度を回復し、8匹の混載と複数便にまたがる経路共用の利益を操作数の削減へ結び付けられる。根拠はbacklogのO21〜O24、Q2と重要な性質1〜4である。ユーザーから原因の切り分け、新しい実験一つの作成、評価までの指示を受けた。

### 変更

- v015の通常便、便の再編、踏み台探索、既存の出力修復を土台にする。v014から共同配送便の表現、128 bitの個体集合識別、計画全体での結合候補評価を引き継ぐ。
- 中心アイデアは「一色を帰す集荷・分離木をつなぐ共同配送」である。最大12匹・最大3色を対象とし、1本の木で集める塔は最大8匹とする。
- 集荷木では両側から任意の合流点へ運べるようにする。二色の上下のまとまりを保ち、巣以外も含む分離地点を選ぶ。上段または下段の一色を帰し、残りを次の集荷の初期塔として引き継ぐ。途中の荷物回収ごとの枝刈りをやめ、一色の帰巣後に候補を比較する。
- 集荷中の予定外の帰巣を避けるため、対象色の巣を集荷経路から除き、巣への最終進入を帰巣・分離の遷移として扱う。操作列は実盤面で検証する。
- 共同配送に結合する便の事前配置を解除して構築する候補を追加する。外部の踏み台配置は維持し、前後の便も含めた全計画の実Tで採否を決める。
- 新しい出力後処理は追加しない。評価値にWを使わず、集荷・分離・帰巣に必要な操作数と残りの訪問地点の概算を使う。
- 共同配送の探索枠は `PROGRAM_TIME_LIMIT_SEC` の124/190〜149/190を基本とし、1構築は全体の9%以内に制限する。帰巣後の状態を幅12で保持し、一つの集荷集合につき見積もり上位の分離候補を実構築する。終了時刻は既存と同じ184/190とする。

### 機構確認

共同配送の構築・採用・削減手数に加え、任意の合流点、初期位置以外の分離、出発点帰巣、帰巣後に残る荷物の継続、事前配置解除を数える。case0000と通常生成99件を分けて記録する。LOCALの独立再生、公式採点、保存出力のPython再生で合法性と全帰巣を確認する。

### 採否基準

- `tools/in` 全100件を既定のLOCAL・並列数2で一度評価する。比較対象は保存済みv013、v014、v015とする。
- 全100件で合法かつE=0、最大実行時間2,000 ms未満を必要条件とする。
- 通常生成99件で新機構の採用を確認し、合計Tが現時点の最良v015を下回れば提出候補として採用する。
- 大きな改善の目標はcase0000を49手から44手以下へ減らすこととする。通常生成99件でv015比1%以上の削減を得た場合も、汎用性の面で大きな改善として別に評価する。どちらも未達なら、その旨を明記する。
- 構築機構が未発動なら、効果を否定せず未確認とする。評価後は結果に基づくコード修正・追加評価を行わず、記録して終了する。

## 原因の切り分け

既知の43手と保存ログを、選択対象・状態表現・遷移・順位づけ・制限・採用判定の順に照合する。既知手順の到達を妨げる制約と、実行ログから寄与を確定できない要因を区別する。各要因を外した際のスコア差を複数のsolver実行で測る方式は採らず、保存手順の条件検査と新実験1回の機構計測を行う。

### 保存手順とv014の照合

`adhoc/scripts/audit_v014_case0000.py` は、既に復元済みのtsukammo氏の43手を再生して制約を調べる。解の探索・生成は行わない。結果は `adhoc/v014_case0000_constraint_audit.json` に保存した。

| 要因 | 確認できたこと | v016での対応・残る限界 |
| --- | --- | --- |
| 目的関数 | 全帰巣なら評価対象はTであり、Wの短縮は目的ではない。v014の採否も全計画のTを使っている | 同じ目的を維持する。床上距離は候補の順位づけに限る |
| 共同配送の大きさ | 43手のうち、赤の準備4手と回収4手を除く35手は、他の3色12匹だけで閉じた配送になっている | 最大12匹・3色、物理的な移動塔は8匹とし、この規模を表現する |
| 個体集合・容量・両端帰巣 | v014の128 bit集合、8匹の移動、出発点帰巣は実装済みで、通常生成ケースでも発動している | 表現を引き継ぐ。この三点の未実装がcase0000の原因ではない |
| 事前配置と対象選択 | v014は結合前の配置を維持する。結合候補の具体的な個体集合・配置・費用は旧ログにない | 対象便の配置を解除する候補も評価する。外部の踏み台は残るため、その配置自体の最適性は保証しない |

| 積み順と枝刈り | 旧概算では(6,4)の `ccccdddd` と `cdcdcdcd` がともに13となり、分離しやすさを区別しない。旧ビームの通過順位は未保存 | 二色を上下のまとまりとして構築し、帰巣後に残る単色の塔を状態とする。幅制限の損失は依然あり得る |
| 時間制限 | v014のcase0000は構築10回・成功10回・採用0回・時間切れ0回。共同配送は14.406 ms | 旧版のこの段階は時間切れで止まったのではない。新版では層別の候補数、復元数、時間切れを計測する |
| 全計画での採否 | 旧版は構築できても改善を採用しなかった。候補ごとの手数が未保存なので、何手負けたかは不明 | 候補を全計画の実手数で評価し、合法な不採用と構築失敗を別々に数える。小規模入力では対象個体と費用も出す |
| 時間配分と出力修復 | 通常99件ではv014の主探索の削減が完成版の改善に残らなかった | v015を比較基準にし、主探索前後と既存修復後を分ける。版間差から各要素の単独効果は断定しない |

確定した障害は集荷方向と分離地点である。順位づけ・旧配置・候補選択については、既知手順との構造上の不一致や情報不足を確認した段階であり、それぞれを解消した場合の削減手数まで因果的に分離した結果ではない。

### 実装の範囲

- `executeCooperative` が継続配送を構築する。一回の集荷で帰す色の全員と、引き継ぐ一色の部分集合を選ぶ。集荷木は部分集合DPで合流点を求め、操作ごとの反転に合わせて子の実行順を選ぶ。
- 一色の帰巣後だけで候補を比較し、幅12を残す。各層は概算上位24組の集荷集合をDPで計算し、各集合の上位6候補まで実盤面で復元する。途中で持ち越す塔は一つ・単色という制約がある。
- `cooperativeSearch` は近接する2〜3便を主探索の計画上で結合する。対象便の配置を解除する候補を先に、時刻を保てる既存配置の候補を続けて評価する。外部配置の時刻をまたぐ結合は行わない。
- 12匹の集合識別、実行キャッシュ、共通接頭辞の再利用を拡張する。通常便の空盤面評価は7匹のまま維持し、共同配送便をそこへ誤って渡さない。
- 新しい探索にcase番号・特定座標・入力ハッシュによる分岐はない。小規模入力の詳細ログだけを `M <= 24` で有効にする。

ソースの静的確認とLOCALあり・なしのビルドを先に行い、solverの試走は追加しない。評価処理の標準ウォームアップと本評価100件を一度実行した後は、solverを変更しない。

- GCC 15 / C++23でLOCALあり・なしのビルドが成功し、警告はなかった。SDKは `xcrun --show-sdk-path`、deployment targetは15.0を指定した。
- 評価前のsolver SHA-256は `269e5b55794896229070a9a92a910260a4d74d8ab6ec1c64fa39914e5d357a98` である。v013〜v015のソースハッシュも従来の記録と一致し、変更していない。

## 実験後

### 判定

棄却（汎用的な提出候補として）。機構確認と合法性・時間の必要条件は満たしたが、通常生成99件の合計Tがv015比で92手、0.3850%増えた。case0000は4手、8.1633%改善したものの、事前登録した44手以下の目標には1手届かなかった。通常99件の1%以上の改善も未達である。v015を汎用比較の基準として維持する。

### 検証と全体結果

- 評価は標準ウォームアップ1件と本評価100件の一度だけ実行した。全100件で公式採点成功、LOCALの独立再生成功、保存出力のPython再生成功、E=0を確認した。公式スコア・最終T・検証操作数・出力行数は一致した。
- 平均実行時間1,488.26 ms、最大1,552 msだった。全件で2,000 ms未満を満たした。
- 評価後にsolverは変更していない。SHA-256は評価前の記録と一致する。v013〜v015も変更していない。

### case0000の改善と残った2手

共同配送フェーズは7.032 msで、赤・緑・黄の12匹をまとめる一候補を評価・採用した。対象便の配置を一つ解除し、その時点の全計画を5手短縮した。後続の探索を経た出力修復前の手数は従来の完成出力より3手少なく、既存の修復でさらに1手減った。最終的に49手から45手となった。

新機構の採用経路で、8匹の混載、出発点で緑を帰しながら黄を発射する動き、帰巣後の集荷を確認した。完成出力の19〜20手目には、(9,1)の緑の塔を待たせ、黄を(11,1)から運び込む動きも現れた。v014で表現できなかった集荷方向を実際に使えている。

43手の保存手順と完成出力を比較すると、残る2手差は黄と青の分離区間に対応する。赤を除く盤面は区間の前後で一致し、その後の青の帰巣7手は操作列まで一致した。これは保存済み二手順の比較であり、評価後に置換した解を生成・実行したものではない。

| 区間 | v016完成出力 | 43手の保存手順 |
| --- | --- | --- |
| 開始状態 | (9,8)に下から青2・黄4 | 同じ |
| 分離と再配置 | 33〜38手目の6手 | 29〜32手目の4手 |
| 終了状態 | 黄が全帰巣し、青2が(9,11) | 同じ（赤の帰巣時期を除く） |
| 以後の青の操作 | 7手 | 同じ7手 |

v016の6手は「一部分を分けて運ぶ→残した青を移す→再合流→黄を帰す→青を2手で移す」という構成だった。43手の4手は「塔全体を1手移して積み順を反転→青を発射→黄を2手で帰す」という構成だった。

ログとコードの照合から、共同配送の対象選択にも制約が残ったと分かった。最初の赤・緑・黄12匹の改善を即時採用した後は、残る青4匹との結合が12匹上限を超える。通常の再編処理も共同配送便を変更しないため、動画の緑・黄・青12匹という別の対象集合は全計画評価に進まなかった。したがって、case0000の共同配送フェーズが7 msで終わった理由は候補集合が尽きたことであり、このフェーズの時間切れではない。

これは「別の対象集合なら必ず43手を発見した」という証明ではない。集荷集合の上位24候補、分離の上位6候補、帰巣後の幅12という制限による損失も残り得る。それらの各手数への寄与は未測定である。

### 通常ケースで最終結果が悪化した位置

通常生成99件では、v015比で出力修復前の合計Tが59手少なかった。一方、既存修復の削減量が合計151手小さく、最終差が92手増となった。内訳は枝分割の削減が10手増、連続区間の削減が7手減、依存関係に沿う組み直しの削減が154手減である。

同一実行内の共同配送採用による275手の削減と、別実行のv015に対する59手の差は異なる比較である。時間配分、前後の探索が訪れる配置、既存修復との重なりを含むため、275手をそのまま最終的な改善量とは扱わない。

共同配送を採用した64件に限るとv015比で合計112手増、採用しなかった35件は20手減だった。この事実から、採用時の手数減少だけで完成版の優位を判断できないことが確認できる。ただし、この分割は採用の有無による観察であり、新機構を有効・無効にした同条件の因果比較ではない。

### 考察と次の前提

v014で欠けていた集荷方向と分離地点の自由度は実装・発動を確認でき、case0000の手数も減った。今後は「継続配送の表現自体が作れない」ことを前提とする必要はない。一方、共同配送の対象集合を一度採用した後の変更制限と、主探索の削減が既存修復後にどれだけ残るかは未解決である。

今回、既知手順を排除する構造上の制限、発動しなかった要因、候補の採否、完成版で差が出た段階を切り分けた。全要素を個別に無効化した評価は行っておらず、各要素の単独効果まで定量的に分離できたとは主張しない。

再開条件: ユーザーから新たな明示指示があり、残る対象選択・枝刈り・修復との関係のどれを検証するかを事前登録できる場合。今回の評価結果に基づくsolverの変更、追加の解生成、再評価は行っていない。
