# v007：独立枝の差分評価と再計算の削減

## 実験前

- 仮説：ユーザーの高速化指示、backlog の B-07、O14に基づく。v006の局所変更に伴う全盤面・全色の再計算を減らせば、同じ時間と探索方針で評価できる候補数が増え、操作数Tを減らせる。
- 変更：`v006` の輸送モデル、候補の種類、部分集合DP、時間配分を引き継ぎ、評価と候補生成の計算量を改善する。中心は、巣に直結する枝ごとの独立性を用いた厳密な差分シミュレーションである。変化のない色の再利用、順位データのキャッシュ、整数集合、DP作業領域の再利用、設置木の線形後順走査、設置用個体の距離順リストも、同じ再計算削減の一環として導入する。solverは `src/bin/v007_incremental.cpp`。
- 機構確認：差分評価と旧方式の全体評価をLOCALで抜き取り照合し、T・流量・出発回数の一致をassertする。`partial_simulations`、`partial_nodes`、`partial_full_equivalent_nodes`、`flow_delta_nodes`、`unchanged_inventory_hits`、`priority_order_reuses`、`schedule_without_simulation`、`reference_checks` で発動と削減量を確認する。全操作の合法性、各色の全帰巣、対象外配置の保存も確認する。
- 採否基準：既定の `tools/in` 全100件をLOCAL・既定 `-j 2` で1回evalする。全件で公式scorer成功、E=0、実行時間2,000 ms未満、参照照合成功を必要条件とする。通常生成99件の集計で差分評価・無変更再利用・順位再利用が正に発動し、`partial_nodes < partial_full_equivalent_nodes` を満たし、合計Tが保存済み `v006_branch_reconnect` より小さければ提出候補として採用する。処理量削減とスコアの採否は分けて報告する。

## 実装設計

### 巣に直結する枝の独立性

単色の輸送木では、巣の直下の部分木どうしは頂点を共有しない。巣へ入った対象色は即座に帰巣し、他色の下段だけが残るため、異なる部分木の容量処理は干渉しない。途中のジャンプが別の枝を飛び越えても、通過マスの塔は操作に影響しない。

各頂点に、所属する直下部分木、親子の双方向リンク、流量、活動頂点の順位ビット集合を持つ。一辺変更では旧親・新親から根までの流量を差分更新し、所属が変わる部分木だけを付け替える。操作数は、影響した高々二つの直下部分木だけを再シミュレーションする。棄却時は同じ辺変更の逆操作と、出発回数・費用の変更ログで戻す。

隣接順位の交換が別の直下部分木にまたがる場合や、活動頂点の相対順を変えない場合は、費用再計算を省略できる。同じ部分木の実行順が変わる場合は、その部分木だけを評価する。packingの切替など全体へ影響する変更は、全活動頂点を評価する。

### 再計算を減らす構造

- 踏み台変更で変化したマスを抽出し、各色の下段・需要が変わるかだけを確認する。無変更の場合は、現在解とキャッシュした同一seedの初期構築費用の比較で、元のrefitと同じ選択を行う。
- seedで決まる頂点優先順位を保存し、盤面変更後の順位はhop数の安定な計数整列で組み立てる。
- 複数枝再接続の位相順は、順位をキーとする二段階のビット集合で構築する。比較ヒープの対数コストを除く。
- DP配列は対象領域だけを初期化する。距離伝播のバケットは各伝播の終了時に空になる性質を利用し、毎回の全クリアを除く。
- 設置用個体を各地点からの距離順に前計算し、候補選択時の全個体走査とソートを減らす。
- 設置木の集約順は葉からのキュー処理で作り、各頂点から根までの反復走査と深さソートを除く。

### 検証と時間

時間定数と72%・96%の切替はv006を維持する。LOCAL・提出相当の両ビルド、静的な整合性確認を行った後、`0019.txt` で機構確認し、同じコードで全件evalする。実行後の結果に基づくsolver改変は行わない。

既存 `v001`〜`v006` のFront Matterとbacklog全体、派生元v006の本文を照合した。独立枝の差分評価を中心にした既存実験はない。共有ログへの評価は `--wait-lock` で直列化する。

### 実装した計算量の変更

| 対象 | v006 | v007 |
| --- | --- | --- |
| 一辺変更 | Phaseを複製し、対象色の全頂点で流量・輸送を再計算 | 親鎖の流量と所属変更部分木を更新し、影響する直下部分木だけを再計算 |
| 隣接順位交換 | 対象色を全体評価 | 同じ枝の活動頂点同士ならその枝だけを評価。それ以外は評価不要 |
| 踏み台変更 | Solutionを複製し、全色を再構築・再評価 | 変更マスを一度抽出し、下段・需要の変わらない色は保存結果を再利用 |
| 同一seedの経路順位 | 全頂点を比較ソート | seedの優先順を共有し、hop数による線形の計数整列 |
| DP後の位相順 | 比較ヒープで旧順位が最小の頂点を取り出す | 400頂点以下の整数順位を二段階ビット集合で管理 |
| DP初期化 | 各部分集合で全配列・全バケットをクリア | 対象頂点のDP値だけを初期化し、排出済みバケットを再利用 |
| 設置用個体の選択 | 全個体を走査し、上位4匹を部分ソート | 不変の距離順を前計算し、未使用の4匹が見つかるまで走査 |
| 設置木の集約順 | 各頂点から根まで深さを求めてソート | 子数を減らす葉からのキュー走査で線形に構築 |

一辺変更でも、対象色の荷物がほぼ一つの枝に集まる場合は全体評価に近い量を走査する。部分集合DPの指数部分と、必要な輸送操作そのもののシミュレーションは残る。高速化の主張は、不要な再計算・複製・整列の削減である。

親子リンクの兄弟順は意味を持たない。棄却時は元の親辺を再適用して流量と所属を戻し、保存した出発回数・枝費用を復元する。LOCALの参照照合では、T・流量・出発回数に加えて、活動頂点集合、枝所属、親子リンクも確認する。無変更色の再利用も抜き取りで再構築し、配置と保存済み初期費用の一致を確認する。

## 実験後

LOCAL・提出相当の両ビルドはGCC 15 / C++23で成功し、警告はなかった。最初のsolver実行前にコードを確定した。機構確認と全件evalに使うソースのSHA-256は `54a5628e3d01387d461e4eac8d4270f1dc01006d1746e55ae9d98431102d03f6` である。

`0019.txt` の機構確認は成功した。公式scorerが受理し、E=0、全体参照照合258回・無変更色の再構築照合18回が一致した。差分評価4,357回で、活動頂点の走査は全体評価相当227,573に対して140,983だった。ログは `adhoc/v007_mechanism/0019.txt.err` に保存した。その後、コードを変更せず、既定100件のevalを完了した。

### 判定

**提出候補として棄却する。比較対象v006を維持する。** 正確性と各機構の発動は確認できたが、合計Tの改善条件を満たさなかった。保存evalでは評価候補数も減少した。ただし、後述の追加診断により、これを実装自体の速度低下と解釈する判断は訂正する。

### 結果

- `tools/in` 全100件、LOCAL、既定 `-j 2`、ラベル `incremental_exact` で1回evalした。公式scorerの成功100件・失敗0件。独立したPython再生でも全操作の合法性とE=0を確認した。
- v006比で合計Tが95手増、全100件で0.3502%悪化した。内訳は40勝12分48敗。通常生成99件では0.3509%悪化した。
- 全件の平均実行時間は1,494.2 ms、最大1,546 msであり、時間の必要条件を満たした。全体参照照合46,003回、無変更色の再構築照合3,576回に不一致はなかった。
- 通常生成99件すべてで差分評価、無変更色再利用、順位再利用、評価不要な順位交換が発動した。差分評価807,397回の活動頂点走査は、同じ候補を全体評価する場合に対して**21.46%減**だった。
- 通常生成99件の無変更色再利用は887,358回で、踏み台候補に対する色別refitの22.47%を省略した。順位再利用は3,760,217回だった。設置用個体の走査は、同じ選択回数で全個体を走査する場合に対して**89.91%減**だった。
- 通常生成99件の評価候補数は保存済みv006の**56.49%**、再接続DP回数は**39.14%**に減った。時間当たりでは評価候補が約27,580回/秒から15,577回/秒、再接続DPが約39,995回/秒から15,654回/秒になった。
- 小規模21件（`M <= 35`）では合計13手減ったが、大規模21件（`M >= 100`）では26手増えた。集計全体の採否は変更しない。

評価run_idは `20260926T010349+0900_v007_incremental_5192fb`、比較対象は `20260926T001205+0900_v006_branch_reconnect_d22a2b` である。スコアの絶対値とケース別結果は `results/score_summary.csv`、`results/score_detail.csv`、`results/eval_records.jsonl` に保存した。分析は `adhoc/scripts/analyze_v007_results.py` で再現でき、集計・参照比較・出力再生結果は `adhoc/v007_analysis.json` にある。

### 考察

巣に直結する枝の独立性を用いた差分評価は成立し、計算の省略箇所も実測できた。ただし活動頂点の走査削減は約2割にとどまり、同時に枝所属・親子リンク・活動集合・取り消し情報を維持する処理が増えた。全体再構築時にも追加メタデータを作っているため、局所的な走査量の削減だけから探索全体の高速化を予測できない。

保存evalで候補数が減った原因は、そのログだけでは特定できない。メタデータ維持やコピー、LOCAL参照照合の費用、DP対象の変化、実行環境差を個別に測っていないためである。候補の仕事量も探索状態によって変わるので、候補数比を個別関数の速度比とは解釈しない。この比較だけを実装自体の高速化仮説の否定に使った点は、下記の追加診断を受けて訂正する。

次の実験の前提は、「差分評価が正確なら候補数が増える」から「差分の維持費を含めた実測で利益を示す必要がある」へ変わった。輸送モデルの正しさと、データ構造を増やすことの性能上の利益は別に判定する。

再開条件: ユーザーから新たな明示指示があり、評価速度低下の時間内訳を確認してから、維持費を含めた変更範囲を事前登録できる場合。今回の実行結果に基づくsolver改変や再evalは行っていない。

### 速度の解釈に関する訂正

ユーザーの定数倍に関する指摘を受け、同一ソースのv006/v007を同じビルド設定で直列にサンプリングした。評価候補数は `0001` でv007が1.97倍、`0019` で1.65倍となり、保存evalの比較と逆転した。前半探索では両実装とも輸送木の再構築が支配的だった。詳細は `adhoc/v007_cost_profile/README.md`、生データは同ディレクトリにある。

これにより、「管理構造を増やしたため実装が遅くなった」という因果関係は確認できていないと訂正する。全件evalのスコアと判定は変えない。定数倍も含めた実時間改善を目的とするというユーザー要件に合わせ、性能比較の条件を揃える必要がある。追加診断後にsolverは変更していない。
