# v020: 変化箇所からの再挿入探索と、塔の部分再構築の組み合わせ

## 実験前

- 仮説: v019で成立した個体の再挿入を、盤面変化に応じた更新で高速化し、組み上がった塔の部分再構築と操作順の変更を組み合わせれば、限られた時間でより多様な共有経路を試し、全帰巣までの操作数を減らせる。根拠はユーザー提示の `ahc072_o3_event_lns.cpp` と、O28の個体除去と再挿入の成立である。
- 変更: 提示コードを `src/bin/v020_o3_event_lns.cpp` に登録する。v019の盤面表現、混載構築、個体除去と再挿入を直接引き継ぐため、親をv019とする。変化箇所からの探索更新、塔の一部を束のまま戻す探索と1匹ずつ戻す探索、依存関係を守る操作の並べ替え、短い悪化の確率的受理を組み合わせた原版全体を対象とする。原版の最適化pragma、整数乱数の変換、構築打ち切りと時間配分の変更も含む。移植では探索内容を保持し、LOCALの時間補正、計測、独立検証だけを追加する。
- 機構確認: `lns_attempts`、`lns_insertions`、`lns_accepted`、`lns_improvements`、`lns_block_attempts`、`lns_flexible_attempts`、`lns_reorder_attempts` と `event_layers`、`event_reopens` を記録する。束と個体への分解を使う探索は受理回数と最良解更新も集計する。開始直後の経路短縮、開始直後の並べ替えによる短縮、探索ループ内の最良解更新による短縮を分け、合計が `pre_lns_ops - final_ops` と一致することを確認する。最終出力を独立再生し、全操作の合法性、高さ制約、両端での帰巣、E=0、操作数と行数の一致を検証する。原版の例外救済、処理エラー、候補検証での破棄も記録する。
- 採否基準: `tools/in` 全100件を既定のLOCAL、並列数2で1回評価する。全件で公式採点成功、合法出力、E=0、100,000操作以内、実行時間2,000 ms未満を必要条件とする。初期解と最終解の例外による作り直し、構築エラー、LNSエラーが0で、通常生成99件の合計で上記9つの機構カウンタがすべて正、かつ全100件の合計Tが保存済みv019を下回れば提出候補として採用する。機構が未発動なら機構未確認として扱う。v017とも参考比較し、通常生成99件と手作りのcase0000を分ける。

## 中心アイデアと実装の範囲

### 盤面の変化箇所から再挿入の探索を更新する

既存操作列へ追加個体を戻す際は、追加手数ごとのバケットを使って移動先を探索する。既存操作が進むと、移動の両端と、それらへ到達できる位置を更新の起点にする。高さの変化に加えて、同じ高さのままでも巣への帰巣などによって従来の最上段の状態が悪化した場合は、流入する経路を再検討する。

時点ごとの待ち行列は世代番号で初期化し、盤面全体の管理配列を毎回消去する処理を抑える。既存操作で運ばれる個体と16操作ごとの盤面も保存し、除去対象を変える試行で使う。

### 組み上がった塔の一部から、以後の操作列を作り直す

操作列の途中から、塔全体、移動する上段、最上段の2匹などを取り出し、後続操作を修復する。束を保つ近傍では、上下反転と巣での上端の帰巣から到達できる色列を扱い、束ごと再挿入する。

分解を許す近傍では、取り出した2〜8匹を異なる順序で1匹ずつ再挿入する。元の塔内の順位から挿入位置を求めることで、探索開始時点の塔は元と一致させる。その後は個体ごとに分離、同乗、再合流できる。取り出す対象集合も、初期位置の近さや実際に同じ移動先で接した個体へ広げている。

### 操作間の依存関係を保って運搬を連続させる

同じ出発点または到着点を使う操作の前後関係を保ち、それ以外の操作を並べ替える。同じ荷物の運搬が連続する候補を優先し、並べ替え後に既存の経路短縮を適用する。経路が途中を通過するだけのマスは、この依存関係の対象に含めない。

探索中は、現在解より最大2手の悪化、かつ最良解より4手以内の候補を温度に応じて確率的に受理する。出力用の最良解は短縮した場合だけ更新し、停滞時には最良解へ戻す。束の近傍、分解を許す近傍、並べ替えの回数と寄与は分けて記録するが、今回の採否は組み合わせ全体で判定する。

## 事前照合と移植方針

backlog全体とv001〜v019のファイル名およびFront Matterを照合し、直接の派生元であるv019と持ち込みコードの登録方法を確認した。今回の依頼をB-25に登録する。

非LOCALは原版のグローバル時計の開始位置、時間定数、呼び出し形、乱数、データ構造を保持する。LOCALだけでmain冒頭を計時基準とし、`JUDGE_TIME_LIMIT_SEC = 1.90`、`LOCAL_TIME_RATIO = 0.80`、`PROGRAM_TIME_LIMIT_SEC` を使って時間定数を換算する。原版の終了期限1.930秒はLOCALで1.544秒となり、v019より32 ms長い。探索ループの終了目安は原版1.900秒、LOCAL1.520秒である。前半の構築時間と停滞による打ち切り条件も変わるため、版間のスコア差には時間配分の違いが含まれる。

原版はGCCの `O3,unroll-loops,omit-frame-pointer` を指定し、x86_64の場合だけ `avx2,bmi,bmi2,lzcnt,popcnt` を指定している。ローカルでは適用される設定をそのまま保持する。整数乱数の生成はv019の剰余から乗算の上位ビットへの変換に変わっており、探索経路の同一性はv019との間では要求しない。比較対象は提示された原版と移植後の非LOCALである。

初期解や最終解の例外時の作り直しは原版のまま保持し、LOCALで発動を記録する。候補の検証失敗を捕捉して破棄する処理も保持する。`Deadline` による打ち切り、候補の破棄、探索全体の処理エラーを区別する。未採用候補の短縮も含む原版の `shortcuts` は、最終出力の短縮量には使わない。

評価前にLOCALありとなしをビルドし、完全なマクロ展開後のソースを照合する。非LOCALの生成命令も原版と比較する。単発試走は追加せず、既存の評価処理によるウォームアップ1件と本評価100件を1回行う。時刻に依存する探索のため、1回の版間比較から各変更の単独効果や実時間での同一性は保証しない。評価後はsolverを変更せず、保存結果の検証と記録で終了する。

## 評価前の確認

arm64のmacOS上でGCC 15.1.0、C++23を使い、LOCALありとなしの両ビルドに警告なく成功した。SDKは `xcrun --show-sdk-path`、deployment targetは15.0を指定した。原版のGCC最適化pragmaを保持した。x86_64専用の命令セット指定はこの環境では有効にならず、x86_64上でのビルドと評価は行っていない。

`-E -P` で完全にマクロ展開した非LOCALソースは、追加計測が消えた場所の空行以外は原版と一致した。生成アセンブリも、ファイル名に由来する静的初期化のシンボル名以外は一致した。LOCAL側の差分は、時間補正と計時開始、計測、独立検証だけである。照合結果と差分は `adhoc/v020_port_audit/` に保存した。

原版のSHA-256は `31aa757ce69483489bfe4ca2cb9bdb5d7235319c8fc396202ce94b56453669ba`、評価前のsolverは `f72457719eab84b838a4189741fee92e194fb2cc6aaf707959656e7c696b432a` である。ここまでsolverは実行していない。

## 実験後

### 判定

採用（今回の評価セットにおける提出候補）。全100件の合法性、全帰巣、操作数制限、実行時間を満たし、事前に指定した9つの機構カウンタは通常生成99件すべてで正だった。処理エラーと例外による作り直しは0で、全100件の合計Tは保存済みv019より2,407手、10.2299%少なかった。

### 探索の発動と短縮量

通常生成99件では、前半の構築が基準解から合計6,283手を短縮した。後半の再挿入探索と経路短縮は99件すべてで最良解を更新し、合計6,439手を短縮した。

| 機構 | 合計回数 | 発動ケース数 |
| --- | ---: | ---: |
| 候補の試行 `lns_attempts` | 691,044 | 99 / 99 |
| 再挿入成功の記録 `lns_insertions` | 1,748,946 | 99 / 99 |
| 候補の受理 `lns_accepted` | 138,293 | 99 / 99 |
| 探索ループ内の最良解更新 `lns_improvements` | 3,068 | 99 / 99 |
| 塔の一部を取り出す試行 `lns_block_attempts` | 97,851 | 99 / 99 |
| うち分解を許す試行 `lns_flexible_attempts` | 64,874 | 99 / 99 |
| 並べ替えの試行 `lns_reorder_attempts` | 6,165 | 99 / 99 |
| 既存操作を進めた更新層 `event_layers` | 287,235,596 | 99 / 99 |
| 流入経路の再検討を要求した両端の数 `event_reopens` | 557,172,799 | 99 / 99 |

`lns_insertions` は、通常の近傍と分解を許す近傍では1匹の再挿入成功ごとに加算し、束を保つ近傍では束全体の再挿入成功ごとに加算する。完成前に後続の挿入が失敗した試行も含む。v019の「1匹の再挿入成功」と完全に同じ単位ではない。`event_reopens` は各更新層で最大2つの端点を数え、実際の経路更新数や重複しない位置数を表すものではない。

塔の一部を取り出す近傍は6,392候補を受理し、90件で330回の最良解更新があった。そのうち分解を許す近傍は5,395候補を受理し、89件で287回の最良解更新があった。短縮量を重複なく分類すると次のようになる。

| 最良解を短縮した処理 | 短縮量 | 短縮したケース数 |
| --- | ---: | ---: |
| 開始直後の経路短縮 | 21手 | 11 / 99 |
| 開始直後の並べ替えと経路短縮 | 109手 | 9 / 99 |
| 通常の個体除去と再挿入、その後の経路短縮 | 5,655手 | 99 / 99 |
| 束を保つ再挿入、その後の経路短縮 | 80手 | 33 / 99 |
| 分解を許す再挿入、その後の経路短縮 | 411手 | 89 / 99 |
| 探索中の並べ替えと経路短縮 | 163手 | 56 / 99 |
| 合計 | 6,439手 | 99 / 99 |

この分類は、その時点で最良解を更新した候補の種類による。先行する別種の近傍が作った同点候補や悪化候補を経由する影響は分離していない。未採用候補も含む原版の `shortcuts` は通常99件で246,917手だったため、この表の短縮量には使わない。

全100件では後半の短縮は6,449手だった。開始直後の2種類の短縮と、探索ループ内の最良解更新による短縮の合計は、各ケースの `pre_lns_ops - final_ops` に一致した。ループ内の短縮量を近傍別に足した値も一致した。

通常99件では、悪化した候補の受理は2,337回で全99件に発生した。最良解へ戻る処理は913回で67件に発生した。これらを含む探索の結果、出力用の最良解は各ケースで保持されていた。

全100件で、初期解と最終解の例外による作り直し、構築エラー、LNSエラー、候補検証での例外破棄、`finishSingles` の呼び出しはすべて0だった。`construction_deadlines` は3,594回で、現最良以上の候補の打ち切りを含む。`lns_deadlines` は0だった。

構築時間は全100件平均393.68 ms、後半の探索は平均1,126.52 ms、独立検証は平均0.0189 msだった。後半の内訳として候補集合の再構築は平均171.28 ms、塔の部分再構築の探索は平均71.14 msだった。通常99件すべての最終出力で高さ8の塔を使い、98件で8匹の同時輸送を確認した。

case0000では、前半の構築による基準解からの短縮はなく、通常の個体除去と再挿入を経た3回の最良解更新で10手を短縮した。塔の部分再構築は380候補を受理したが、その候補自身による最良解更新はなかった。並べ替えによる直接の最良解更新もなかった。したがって、v019との差1手をこれら追加近傍の直接効果とは特定していない。

### 考察

塔が組み上がった途中時点から一部を取り除き、元の塔を正しく復元しつつ以後の移動を作り直す構成が、通常99件すべてで受理可能な候補を生成した。束の分解を許す近傍と依存関係を保つ並べ替えの双方で最良解の更新を確認した。次の実験では、この組み合わせを比較基準の候補にできる。

v019からの改善幅は全100件で10.2299%だった。ただし原版では、探索更新方法、近傍、確率的受理、乱数の変換、低水準処理、最適化pragma、構築打ち切り、時間配分がまとめて変わっている。LOCAL期限も32 ms長い。この1回の比較から、どの変更が版間の改善を何手ずつ生んだかは判定していない。各近傍の同一実行内での短縮量と、機構を外した場合の性能差も区別する。

提出用処理は提示された原版から保持できたが、命令の照合と評価はarm64上のものである。x86_64の専用命令を使うAtCoder環境でのスコア、実行時間、メモリは未評価である。今回の依頼に対する評価は1回で完了し、結果を受けたsolver変更や再評価は行っていない。
