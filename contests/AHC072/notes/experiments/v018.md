# v018: 帰巣を遅らせた踏み台の利用と共同回収

## 実験前

- 仮説: 帰巣予定のスライムを後続便の踏み台として残し、役目を終えた個体を通常便や他の踏み台とまとめて回収すれば、全帰巣までの操作数を減らせる。根拠はユーザーの「なるべく帰宅を遅延させてジャンプ台として活用する」という意図、O10、O16、O19、Q3、B-15である。
- 変更: ユーザー提示の `ahc072_relay_pickup.cpp` を `src/bin/v018_relay_pickup.cpp` として登録する。元の `ahc072_mixed_tree.cpp` との差分は、帰巣延期と共同回収の処理、その探索フェーズ、診断出力である。直接の派生元をv015とする。提示コードの探索内容を保持し、LOCALだけに時間補正、計測、検証を追加する。
- 機構確認: `relay_trials`、`relay_accepted` で候補の評価と受理を確認する。実際に採用された留置計画について、`relay_sites`、`relay_output_saved`、後続便の長距離ジャンプで留置個体が下段にいた回数 `relay_later_jumps` を確認する。後者は出力修復前の採用計画を探索終了後に再生して数える。最終出力は別に独立再生し、全操作の合法性、高さ制約、両端での帰巣、E=0、操作数と行数の一致を確認する。
- 採否基準: `tools/in` 全100件を既定のLOCAL、並列数2で1回評価する。全件で公式採点成功、合法出力、E=0、100,000操作以内、実行時間2,000 ms未満を必要条件とする。通常生成99件の合計で `relay_trials`、`relay_accepted`、`relay_sites`、`relay_output_saved`、`relay_later_jumps` がすべて正で、全100件の合計Tが保存済みv015を下回れば提出候補として採用する。機構が未発動なら機構未確認とし、効果の否定にはしない。保存済みv017とも参考比較し、通常生成99件と手作りのcase0000を分ける。

## ユーザーの意図と実装の対応

帰巣を遅らせて後続便のジャンプ台として使う仕組みは実装されている。残す場所、匹数、回収する便の時点を選び、配置から回収までの操作数で比較する。既存の配送計画を作った後、終盤の短い探索で追加する方式である。

### 残す個体と回収時期の選択

留置計画は最大5組で、1組につき1〜3匹を残す。既設の塔をその便の配送対象から外して残す方法と、集荷済みの荷物から同色の下段を残す方法がある。二色を運んで下段を残す候補では、ジャンプによる上下反転も扱う。

候補の順位には、後続便が短縮できそうな移動、設置費、回収費、留置期間を使う。既設の塔を残す候補は後続の全便を回収時点の候補とする。新たに残す候補では主に9便先までを見て、条件を満たす場合は最後まで残す候補も加える。その後の探索では回収時点を前後に動かす。

「なるべく遅く帰す」という意図の適用範囲には限りがある。主探索の配送順や全個体の帰巣を一律に遅らせる目的関数は導入していない。候補の順位づけには留置期間への小さな罰則があり、最終的には全帰巣までの操作数が厳密に減る計画だけを出力へ採用する。長く残すほど有利と扱う設計ではない。

### 後続便の再計算と共同回収

留置後は変更された盤面上で後続便を再計算する。残したスライムは下段として盤面に存在し、他の荷物の長距離ジャンプに使える。元の経路の修復と便の作り直しを比較し、留置を終えた後の回収費も含めて全体を評価する。

回収では、期限が来た踏み台と同時点の通常便を仕事の単位に分け、部分集合DPでまとめ方と順序を選ぶ。容量7匹と原則二色の制約内で一緒に帰せる組を探す。二色の通常便を色ごとに分けて回収に組み込む経路もある。回収時点が来た個体は全帰巣させる。

### 計測値の意味

`relay_accepted` は焼きなまし探索中の受理回数であり、改善しない候補の受理も含む。`relay_plan_saved` は探索元の配送計画からの短縮、`relay_output_saved` は実際の暫定最良出力からの短縮を表す。`relay_later_jumps` は留置後、回収期限より前の便で下段に利用された回数とし、留置した便自身と回収便を除く。最終の出力修復で操作が変わり得るため、採用時の計画の実測と最終出力の合法性を区別して記録する。

## 事前照合と移植方針

backlog全体とv001〜v017のファイル名およびFront Matterを照合し、v009、v015、v017の本文を確認した。B-15の通常配送からの留置と回収を、v015の二色配送へ組み込む構成としてB-23に登録する。v009の独立実装を再評価する実験ではない。v016の継続配送木も取り込まない。

非LOCALでは原版の計時開始位置、時間定数、呼び出し形、乱数、データ構造を保持する。LOCALは `JUDGE_TIME_LIMIT_SEC = 1.90`、`LOCAL_TIME_RATIO = 0.80` を使い、時間定数を `PROGRAM_TIME_LIMIT_SEC` に対する割合へ換算する。計時はmain冒頭から開始し、探索期限は従来と同じ1.472秒とする。計測用の処理と宣言は非LOCALの前処理結果から除去する。

評価前に両ビルドを確認し、マクロ展開後の非LOCALソースを原版と照合する。ファイル名とassertの表示行番号などの診断差は分けて記録する。LOCAL側も差分を確認する。評価対象はLOCALであり、この結果からAtCoder上のスコアやメモリ使用量の一致までは保証しない。O25とO26を踏まえ、版間の1回のスコア差と同一実行内の留置フェーズの短縮量を分けて記録する。

単発試走は追加せず、評価処理のウォームアップ1件と本評価100件を1回実行する。評価後はsolverを変更せず、保存結果の検証と記録で終了する。

## 実験後

### 判定

棄却（今回の評価セットにおける提出候補として）。合法性、全帰巣、実行時間、帰巣延期の機構確認は合格したが、全100件の合計Tが保存済みv015より85手、0.3550%増え、事前の採否基準を満たさなかった。

ユーザーの意図はコードと実行結果の両方で確認できた。採用された留置計画では179匹の帰巣を遅らせ、そのうち164匹を後続便の長距離ジャンプの下段として使った。長く残すこと自体を優先する設計ではなく、回収費を含めて操作数を減らす範囲で帰巣を延期する実装である。

### 帰巣延期の発動

通常生成99件の計測値を以下に示す。留置計画の利用実績は出力修復前の採用計画に対する値である。

| 項目 | 合計 | 発動ケース数 |
| --- | ---: | ---: |
| 候補評価 `relay_trials` | 2,673回 | 93 / 99 |
| 探索中の受理 `relay_accepted` | 635回 | 76 / 99 |
| 最良出力への留置計画の採用 `relay_adopted` | 48件 | 48 / 99 |
| 採用した留置 `relay_sites` | 83組 | 48 / 99 |
| 帰巣を延期し、最後に回収した個体 | 179匹 | 48 / 99 |
| 後続便の長距離ジャンプで使った留置個体 | 164匹 | 46 / 99 |
| 後続便の長距離ジャンプでの下段利用 `relay_later_jumps` | 123操作 | 46 / 99 |
| 留置フェーズによる出力短縮 `relay_output_saved` | 116手 | 48 / 99 |

83組の内訳は、単色の配送途中から残す方式が68組、二色を運んで下段を残す方式が8組、既設の塔を配送対象から外して残す方式が7組だった。作成から回収までの便番号の差は平均約5.49、最大17であった。この差には回収する便の時点も含まれる。

123操作のうち122操作では、留置個体を下段から除くと同じ距離のジャンプができなくなることを確認した。これは選んだ操作における下段の必要性を示す値であり、留置による純粋な削減手数とは一致しない。留置による構成全体の短縮量は、設置、後続便の経路変更、共同回収を含む116手として扱う。

採用した留置計画の再生でも全個体の帰巣を確認した。留置組数、方式別の組数、回収時期、延期個体数と回収個体数、フェーズ前後の操作数差がログと一致した。case0000は留置計画の採用がなく、保存済みv015およびv017と同じ操作数だった。

### 考察

帰巣の延期と後続便での踏み台利用は発動し、同一実行内では回収まで含めて116手を削減した。この構成の成立性は、次の実験の前提にできる。今回の不採用は機構の不発によるものではない。

v015との比較では、留置フェーズの前に合計Tが32手多く、留置フェーズで116手減らしたため、出力修復の前は84手少なかった。その後の出力修復による削減量はv015より169手少なく、完成版では85手多くなった。初期解の操作数は全100件でv015と一致した。

留置探索が後半の時間を使うこと、修復対象の操作列が変わること、LOCALの計測と時間依存の探索変動が比較に含まれる。169手の差を時間配分だけに帰属させる切り分けは行っていない。O25とO26のとおり、今回1回の版間比較から恒常的な優劣も断定しない。以後に検証する場合は、留置フェーズの短縮が完成版まで残る条件を、既存の出力修復との関係を含めて扱う必要がある。

再開条件: ユーザーの新たな明示指示のもと、留置探索と既存の出力修復の関係、時間配分、回収方法のいずれかを切り分ける追加実験を事前登録する場合。
