# v003：寿命を計画した踏み台網

## 実験前

- 仮説：backlog の O4、O5 と B-03 に基づく。後で帰巣する色を踏み台として保存し、同じ踏み台を繰り返し使う輸送を計画すれば、長距離ジャンプによる短縮が設置費と踏み台自身の帰巣費を上回る。色の処理順と容量を考慮した輸送経路も同時に最適化する。
- 変更：`v001` から入出力、地形前計算、操作検証、時間管理の構成を引き継ぐ。B案の混色グループ探索を、C案の踏み台配置、色順、同色の輸送木の探索へ置き換える。solver は `src/bin/v003_spring_network.cpp` とする。
- 機構確認：`long_jump_moves`、`support_departures`、`reused_support_cells` で踏み台の利用を確認する。`pad_proposals`、`pad_accepted`、`built_pads`、`built_support_long_moves`、`setup_moves` で新しい踏み台の設置と利用を確認する。各色の終了時に対象色の全帰巣と他色の保存を検証し、最終的な `E = 0` と予測操作数の一致も検証する。
- 採否基準：既定の `tools/in` 全100件を `LOCAL`、既定 `-j 2` で1回評価する。全件で公式 scorer 成功、`E = 0`、ローカル実行時間2,000 ms未満を必要条件とする。通常生成99件で長距離ジャンプ、踏み台の反復利用、設置した踏み台からの長距離ジャンプがそれぞれ発動し、合計 `T` が保存済み `v001_mixed_deque` より小さければ採用する。機構の不発と、発動したうえでのスコア不足を区別する。

## 実装設計

### 踏み台の設置

初期個体をそのまま利用するほか、同色の2〜4匹を指定した床へ集める。構成員の重複を禁止し、設置先は空き床か構成員の初期位置とする。自色の巣は設置用の経路から除く。少数の構成員を合流させる木を作り、各枝を1回ずつ運ぶ設置費を求める。

設置は色ごとの帰巣処理より先に行う。最大4匹の設置用の塊は、先に作った高さ4以下の踏み台にも着地できる。すべての設置操作を総 `T` に含める。

### 色順と容量付き輸送

現在の色より後に処理する色だけを踏み台として残す。踏み台の高さに応じた直線ジャンプを辺とする有向グラフを作り、現在の色の巣を根とする輸送木を計画する。

各マスの輸送用容量は高さ8から踏み台の高さを引いた値とする。空き床では最大8匹をまとめ、容量の小さい着地点では分割する。着地前の容量制約を守って、子から親へ集約し、満杯の親から先へ送る。部分的に先送りしても輸送回数が増えない場合を、残る流量と容量から判定する。

輸送木は根へ向かう順序を持つため循環しない。対象色がすべて巣に入るまでが1つの通常の色処理であり、踏み台の構成員もその担当色の処理時に帰巣する。

### 時間内の探索

輸送木の接続先、容量処理の順序、色順、踏み台の追加と削除、構成員、高さ、設置場所を焼きなましで変更する。目的関数には設置操作と全色の輸送操作を含む実際の操作数を使う。隣接する色順の交換では、その2色の輸送を再評価する。

`main` 冒頭から時間を測り、テンプレートの `JUDGE_TIME_LIMIT_SEC = 1.90`、`LOCAL_TIME_RATIO = 0.80` を使う。探索の終了は `PROGRAM_TIME_LIMIT_SEC` の96%とし、残りを復元と検証に使う。

### 検証と評価

ビルドと静的確認の後、単発の機構確認を行い、同じ実装を全100件で評価する。実行結果を見た後の solver 改変は行わない。SDK と deployment target は `v001` と同じ環境変数で指定する。

## 実験後

### 判定

採用。事前登録した合法性、全帰巣、時間、機構発動、`v001` に対する改善の条件をすべて満たした。既存3案の中で、今回の評価セットの合計操作数が最小となった。

### 結果

- 全100件で公式 scorer が成功し、公式スコア、出力行数、予測した操作数が一致した。全件で `E = 0`、`fallback_count = 0` だった。踏み台の設置後の配置と、各色の処理後に残る他色の配置も、実際の操作を適用して確認した。
- 通常生成99件で、`v001_mixed_deque` より合計操作数を3,340手、10.96%削減した。ケース別では89勝、2引き分け、8敗だった。seed 0を含む100件では10.97%削減し、90勝、2引き分け、8敗だった。
- 補足比較として、保存済み `v002_mono_steiner` より100件合計で15.94%少なく、全100件で操作数を減らした。この比較は事前登録の採否基準を追加するものではない。
- 自身の初期構築に対して、通常生成99件で総操作数を15.51%削減した。seed 0を含む100件では15.53%削減し、全100件で初期構築を改善した。
- 通常生成99件の最終計画には合計640個の踏み台があり、設置した踏み台からの長距離ジャンプは2,154回、初期個体を使う長距離ジャンプは2,299回だった。99件すべてで設置した踏み台の長距離利用と、踏み台の反復利用を確認した。
- 通常生成99件で踏み台の設置に使った操作数は総操作数の約14.39%だった。この費用と踏み台自身の帰巣を含めたうえで、上記の改善が得られた。
- 全100件のローカル実行時間は平均1,474.63 ms、最大1,581 msで、全件2,000 ms未満だった。焼きなましは平均1,455.83 ms、操作列の復元と検証は平均0.03 msだった。
- 通常生成99件の探索反復は平均約78,213回だった。単発確認には最大217匹の `0019.txt` を使い、公式 scorer 成功、全帰巣、15個の踏み台設置、設置した踏み台からの長距離ジャンプ77回を確認した。その後、同じ実装を全件評価した。

正本ログは `results/score_summary.csv`、`results/score_detail.csv`、`results/eval_records.jsonl` にある。今回の `run_id` は `20260925T232056+0900_v003_spring_network_356717`、ラベルは `c_spring_network_sa` である。ケース別の操作列と計測値は `results/out/v003_spring_network/` にある。

実行コマンド：

```bash
SDKROOT="$(xcrun --show-sdk-path)" MACOSX_DEPLOYMENT_TARGET=15.0 \
  python3 scripts/eval.py --wait-lock --label c_spring_network_sa v003_spring_network
```

### 考察

踏み台の設置から自身の帰巣までを含むC案が、全入力で通常の輸送計画として成立した。特に、通常生成99件すべてで、設置した踏み台の長距離利用と踏み台の反復利用が実際の出力に現れた。今回の改善を、踏み台を作っただけで利用しなかった結果と解釈する必要はない。

設置費を含む総操作数は、混色配送の `v001` と同色集約の `v002` の両方を下回った。ただし、今回の差には踏み台、色順、容量に応じた分割、輸送木の探索がすべて含まれる。踏み台の設置だけの単独効果や、個々の踏み台の回収条件までは分離して測っていない。

次の実験の比較基準を、C案の成立性が未確認の状態から、全帰巣と機構発動を確認した `v003_spring_network` へ更新できる。`v001` が勝ったケースも8件あるため、C案がすべての入力で優位という結論にはしない。
