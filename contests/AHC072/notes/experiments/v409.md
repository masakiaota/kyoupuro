# v409: 追加費用0の再挿入で到達不能となった残り時刻を省く

## 実験前

- 仮説: O34・Q6の失敗再挿入費用の問いを根拠に、追加費用上限0で有限の未帰巣ラベルが全滅した後は復活できないため、残りの予定操作の走査を厳密に省ける。ただし以前の失敗候補費用の大半は先行する成功挿入であり、回収可能費用とはみなさない。
- 変更: 直接親はcloud401原本 `adhoc/imports/v401/original.cpp.txt` (SHA256 0c241cc3a862d12faf100050df4ea3bafa3c520261d81e5237a41e3c54f25658)。`insert_at` のcap==0に限り、有限ラベルのある床のビットと床数を維持。p/qのラベル消去時にビットを消し、有限の後続ラベルを書いた床を追加する。イベント完了境界で床数0かつGOAL未到達ならfalse。cap>0、候補・順序・乱数・時間・温度・pool4・方策・LNS配分は保持。LOCAL/非LOCAL双方で有効。
- 正当性: cap0では有料の空間遷移と帰巣阻害時の脱出遷移が無効。予定操作で変化するのはp/qのみ。他の床の待機ラベルは残る。同色隙間の閉包は同じ床内のコピーであり、空の床を新たな到達床にできない。有限前駆が全滅しGOALも未到達なら、その先に有限後継は生まれない。GOAL既到達では打ち切らない。
- 機構確認: cloud401の保存済みtools/in全100出力を固定。各入力でseed=409001+caseとして通常候補を構築し、既存候補順でgrow_dependencyの成功した集合を正確なsorted IDsで重複除去、最初の32集合（不足時は全件）を選ぶ。成否・スコアで再選択しない。各集合seed=409001+1000*case+ordinalを共通初期乱数にして、通常extract→距離乱数順序→2〜4匹ならinsert_two_orders、それ以外は通常逐次insertを親と候補それぞれ一度だけ実施。allowanceは保存plan.size()+4。cap0を人工注入しない。全体成否、各insert成否、成功操作列、最終乱数、pool4回収を照合し、早期falseは親の最後まで走査したfalseと一致を必須とする。
- 固定仕事量の費用: 全選択集合のextract/repair・順序生成・再挿入をprocess CPU時計で一度の対比較。成功/失敗とcap>0を含め、追跡初期化・更新・影響しない分岐費用を含む。(32*case+ordinal)が偶数なら親→候補、奇数なら候補→親。同じセットごとに新しい同型LNSを使い、事前の候補構築は同一のものを双方へ渡す。診断ログ処理を対称にし、各insert後の完全な操作列記録だけを同じCPU時計で測定して全体から差し引く。比較・JSON出力は計測外。履歴コピーと両側共通のログreserveは計測外、通常作業配列の確保・初期化・破棄は計測内。timed scopeを事前固定する。ログ配列の確保/コピーは差し引いてもcache/allocatorへ影響し得るため、instrumented paired CPUである点を明記する。小規模/中規模/大規模はM<=50 / 51<=M<=100 / M>=101。
