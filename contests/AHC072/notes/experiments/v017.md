# v017: 提出時の計時開始位置を持ち込みコードへ揃える

## 実験前

- 仮説: v015で計時開始をmain冒頭へ移したことが探索経路に影響しているなら、持ち込みコードと同じSolver初期化時へ戻すことで、提出相当のスコアとメモリ使用量が改善する可能性がある。根拠はO25と、ユーザーが指定した計時だけの切り分けである。1回の比較から恒常的な優劣やAtCoderでの差の原因までは確定しない。
- 変更: v015を直接の派生元とし、非LOCALの計時開始だけを `ahc072_mixed_tree.cpp` と同じ位置へ戻す。非LOCALではメンバーの初期化で時刻を取得し、mainは元の `new Solver` を使う。LOCALの計時、時間定数、ラムダ、探索処理、乱数、キャッシュ構造はv015を保持する。
- 機構確認: 評価前にLOCALありとなしの両ビルドを確認する。LOCALの条件分岐を処理したソースがv015と一致すること、および非LOCALのSolver初期化とmainが元コードの計時順序と一致することを確認する。非LOCALの生成命令でも、時刻取得が入出力設定とSolver用メモリ確保の後にあることを確認する。solverの試走は追加せず、評価出力を公式採点と独立再生で検証する。
- 採否基準: `tools/in` 全100件を既定のLOCAL、並列数2で1回評価する。ウォームアップ1件は保存と集計から除く。機構確認に合格し、全件で公式採点成功、合法出力、E=0、100,000操作以内、実行時間2,000 ms未満を満たせば、再提出で比較する候補として採用する。それ以外は候補として採用しない。LOCALのソースはv015を保持するため、保存済みv015とのスコア差は参考値とし、提出時の計時変更の効果とは判定しない。提出時のスコアとメモリの改善については、AtCoderでの比較まで未判定とする。

## 比較条件

ユーザーの補足により、ローカル評価では既存の時間補正を維持する。`LOCAL_TIME_RATIO = 0.80`、LOCALの探索期限1.472秒を使う。提出時には、元コードと同じ計時開始位置で約1.84秒を使う。ローカルで既存実験と比較できることと、提出時の挙動を元コードへ揃えることを、それぞれのビルドで満たす。

評価には `scripts/eval.py` をそのまま使い、v017だけを1回実行する。保存済みv015のLOCAL評価と通常生成99件、手作りのcase0000を分けて比較する。v015の再評価や非LOCALでの評価は行わない。今回の評価処理はRSSを記録しないため、提出時のメモリ同等性について新しい実測の結論は出さない。

この条件の修正は、ユーザーの補足を受け、solverの実装とビルドと評価を始める前に行った。v015の保存出力は更新しない。

## 事前照合と実装範囲

backlog全体とv001〜v016のFront Matterを照合した。直接の親はv015であり、計時変更の再試行に該当する判定済み実験はない。B-20のうち計時開始位置だけの比較をB-22として切り出す。v016の継続配送木は取り込まない。

今回のユーザー指示を、非LOCALの計時開始位置に限ったプロジェクト規約の例外として扱う。共通テンプレートとLOCALのmain冒頭計時は変更しない。依頼の範囲はローカルの実験登録と評価までとし、AtCoderへの提出は行わない。

## 実装と評価前の確認

実装は `src/bin/v017_timer_origin.cpp` とした。v015との差分はファイル名と、Solverの開始時刻の初期化およびmainの条件コンパイルだけである。探索中の処理と時間定数は変更していない。

GCC 15.1.0、C++23でLOCALありとなしの両ビルドが警告なしで成功した。LOCALの条件分岐を処理した、マクロ未展開のソースは、コメントと空白を除いてv015と一致した。非LOCALの生成命令では、入出力設定、Solver用メモリ確保、`steady_clock::now()` の順序を確認し、元コードの計時開始位置を再現できている。詳細は `adhoc/v017_timer_audit/static_verification.json` に保存した。

確認範囲の訂正（2026-09-26、追加調査時）：上記のLOCAL照合は `-fdirectives-only` によるもので、assert内のファイル名と行番号まで展開した結果の一致を意味しない。保存済みLOCAL実行ファイルを追加照合すると、94,886命令のうち異なる13命令はすべてassert失敗時の表示行番号であり、それ以外の命令と配置は一致した。データ各節も、assert用のソースファイル名以外は一致した。追加のsolver実行は行っていない。根拠は `adhoc/v017_timer_audit/local_binary_comparison.json` と `adhoc/scripts/audit_v017_local.py` に保存した。

評価前のsolverのSHA-256は `6e6ff1ab864bc4228f20cfec7a28325cd4e092dd30f909c8641aeb6f8d6a25ce`、親v015は `dc9411f97e1d28a2bfba2a0a51d40b1aa989db0fbb77c49df593d8db3cb8fa30` である。評価後に両方の一致を確認する。

評価コマンドは以下のとおりである。LOCALは既定で有効となり、並列数は既定の2を使う。

```bash
SDKROOT="$(xcrun --show-sdk-path)" MACOSX_DEPLOYMENT_TARGET=15.0 \
  python3 scripts/eval.py --wait-lock --label timer_origin_local v017_timer_origin
```

## 実験後

### 判定

採用（再提出で比較する候補）。機構確認に合格し、LOCALの全100件で合法出力、E=0、100,000操作以内、実行時間2,000 ms未満を満たした。提出時のスコアとメモリの改善については未判定である。

### 結果

LOCAL評価を1回実施した。公式採点結果、出力の行数、LOCALの最終操作数と検証操作数が全100件で一致した。保存出力の独立再生でも、全操作の合法性、容量制約、両端での帰巣、全個体の帰巣を確認した。実行時間は平均1,485.15 ms、最大1,568 msだった。

LOCALの条件分岐後・マクロ未展開のソース一致と、非LOCALの計時開始順序を評価前に確認した。評価後もv015とv017のソースハッシュは評価前と一致している。

保存済みv015のLOCAL評価との比較を以下に示す。勝敗はTが小さい方を勝ちとする。この差は提出時の計時変更の効果を表さない。

| --- | --- | ---: | ---: | ---: |
| 全100件 | 保存済みv015 LOCAL | -109手 | -0.4552% | 53、7、40 |
| 通常生成99件 | 保存済みv015 LOCAL | -109手 | -0.4562% | 53、6、40 |
| 手作りのcase0000 | 保存済みv015 LOCAL | 0手 | 0% | 0、1、0 |

実行IDは `20260926T225428+0900_v017_timer_origin_dba982`、比較対象は `20260926T215637+0900_v015_mixed_tree_483f92` である。スコアの正本は `results/` 以下のCSVとJSONLとし、独立再生と比較の集計は `adhoc/v017_evaluation_summary.json` に保存した。

### 考察

ローカル評価の時間補正を維持しながら、提出時の計時開始位置だけを元コードへ戻す版を用意できた。LOCALの処理を保持した状態でも、今回と保存済み評価との間にはスコア差が出た。今回無効な非LOCALの計時変更に、その差を帰属させることはできない。

次の比較の前提は、ローカルでの正常動作と提出側の計時順序が確認済みであることだ。AtCoderでのスコアとメモリが元の提出へ近づくかは、提出結果で確認する必要がある。非LOCALのローカル評価、v015の再評価、RSSの追加測定、AtCoderへの提出は行っていない。評価後のsolver変更も行っていない。
