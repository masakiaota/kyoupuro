## 手動実行

プロジェクト直下で次を実行する。開始時に入力と保存解を凍結し、GCC 15で探索コード、Cargoのrelease設定で公式採点器をビルドする。

```sh
caffeinate -i python3 adhoc/scripts/run_v800.py --workers 2
```

ケースごとの予算は300秒に固定している。探索は単一スレッドの2プロセスで、継続側は5分の1回、再出発側は最大60秒のラウンドを繰り返す。ケースの並列実行は行わない。探索だけで約7時間30分を要する。Macの`caffeinate -i`はアイドルスリープを防ぐ。Linuxではこの接頭部分を外す。Python 3.9以降、GCC 15、Cargoを使う。

開始時に`results/long_search/v800/<run_id>/`が表示される。Ctrl+Cで停止すると、探索プロセスを終了させ、保存済みの最良解と履歴を残す。次のコマンドで再開できる。

```sh
caffeinate -i python3 adhoc/scripts/run_v800.py --resume results/long_search/v800/<run_id>
```

再開時は完了したケースを省く。未完了ケースは保存済みの最良解から5分をやり直すため、中断したケースだけ合計時間が増える。再開時も保存したC++実行ファイルを使い、入力や実行管理コードが準備時から変わっていた場合は停止する。強制終了によって前回の探索プロセスが残っている場合も、2プロセスを超えないよう開始を拒否する。

準備だけ確認する場合は次を使う。評価表へは登録しない。この保存先を`--resume`へ指定すれば、本探索を開始できる。

```sh
python3 adhoc/scripts/run_v800.py --prepare-only
```

### 次の仮説

1. **修復費を見積もってから除去対象を選ぶ（B-78）**。削除できる操作数に加え、消える踏み台を利用する残存ジャンプと、その修復費を候補の評価へ入れる。踏み台を残して利用者側を変更する集合と、踏み台・利用者をまとめて変更する集合を比べる。まず既存保存解で現在の優先順位と実際の修復負担の対応を調べる。成功率を上げるだけでなく、時間あたりの新しい最良更新が増えるかを判定する。一般的な候補数の拡大とは別の変更として扱う。
2. **改善後の解を引き継ぐ再出発を比較する（B-77）**。長時間用には、一方の継続を保ち、他方が使う古い保存初期解の代わりに、更新後の最良解や構造の異なる同等品質の解を使う案がある。初期解の選択だけを変える比較と、温度だけを変える比較を分ける。別初期解が有効だった0014も診断対象に残す。2秒版への還元は、構築後の探索条件で別途確認する。
3. **除去・再挿入を限られた期間で完結させる（B-79）**。踏み台の利用、合流、分割がつながる期間を選び、入口と出口の盤面を保持したまま、その中で同手数の組み替えと短縮を繰り返す。無関係な操作は固定して再走査を減らす。v057に導入済みの変更箇所周辺への短縮処理とは区別し、除去・再挿入そのものの対象期間を限定する案である。短い境界では連携を閉じ込められない場合があるため、保存された成功例について必要な範囲と再利用できる計算を先に調べる。

2秒版への還元では、まずB-78の候補選択を優先する。長時間探索を次に変更する場合はB-77を先に分離比較する。B-79は変更範囲が大きいため、保存手順の分析で短い期間に改善を閉じ込められる根拠を得てから扱う。

以上は凍結したv800の分析である。v800はv047にv050の開始・終了時の短縮を加えた構成で、後発のv057の探索中短縮や、実装済み・評価保留のv058の配分変更は含まない。今回の数値を、それらの版の性能へ直接外挿しない。仮説の記録までで、solverは変更していない。v800全100件の完了判定と登録確認は実行終了後に残る。

### 新しい具体例：1匹を後続便へ回して跳躍数を減らす

改善: (8,13) の下段を2匹にし、上段6匹を3マス跳ばす

前半の2操作が1操作になり、回収便の操作数は増えなかった。元の120手目の分割量を変え、末尾を含む手順全体を1手短縮している。入口と出口の全盤面がそろう最短区間は、元の`[120,256)`の136手から置換後の135手への変更だった。変わる操作文面は2操作から1操作、接触履歴が変わるのは3マスである。途中の塔には長く差が残る。
