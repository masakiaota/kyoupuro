# v053: 追加処理による既存探索の関数展開への影響を抑える

## 実験前

- 仮説: v052の追加処理がコンパイラの関数展開に使う予算を消費し、既存の構築とLNSの生成命令を変えている。1回だけ使う追加処理の優先度を下げ、既存探索の関数展開への影響を抑えることで、同じ解を短縮する利得を完成スコアへ残せる可能性がある。根拠はB-71、O25、O41、O69と、結果報告後のユーザーの追加検討指示である。
- 変更: v052の有限区間探索の大きな関数を`[[gnu::cold, gnu::noinline]]`で低頻度の処理として指定する。対象は候補列挙、束の経路探索、有限区間の探索、追加処理の入口とする。追加処理のアルゴリズム、候補順、幅、上限、既存探索、乱数、時間配分は保持する。LOCALと非LOCALの両方で有効とする。通常の短い共通関数への強制展開指定は混ぜない。
- 機構確認: LOCALありとなしをビルドし、完全な前処理結果の差が属性だけであることを確認する。元のmainを持つ生成命令を比較し、`TemporalLNS::insertAt`の盤面コピーへの独立呼び出しがv050と同じ0箇所へ戻ることを必須とする。`optimize`の時計確認と操作列の移動代入、構築処理の呼び出しの変化も記録する。固定時計の診断用コピーで親v052と全100入力を各1回実行し、出力、共通計数、乱数状態、時計の呼び出し数を照合する。これは実時間での一致や速度の証明には使わない。
- 採否基準: 機構確認を通過すれば通常100件をLOCAL、時間補正0.80、並列数2で1回評価する。全件合法かつE=0、100,000操作以内、外部計測2,000 ms以内、エラー、不正候補、作り直し0、case0000が43手以下を必須とする。追加処理で1手以上減り、合計Tが保存済みv050より少なければ今回の比較で採用する。親v052との比較も記録する。生成命令の変化をスコア改善の原因と断定せず、追加処理前後の差を併記する。

backlogの既読全体と追加項目、v001〜v052とv800のFront Matterを照合し、類似するv034〜v036、v039の記録を確認した。v036では共通の色判定への強制展開だけでは明確な速度改善を得られていない。今回は追加した処理側の展開優先度を変える。B-72の複数機構の組み合わせ、案3のB-69は含めない。

## 実装前の生成命令の比較

solverは実行せず、既定のLOCALビルドに対応するv050とv052の生成命令を比較した。v050の`insertAt`に盤面コピーの独立呼び出しは0箇所、v052には1箇所あった。v052では操作列の移動代入にも独立呼び出しが増えた。`optimize`では時計確認1箇所、移動代入4箇所が追加された。構築の`planPair`にも`reverseWord`と`joinWord`への独立呼び出しが各2箇所増えていた。

GCCの関数展開診断には、盤面コピー、時計確認、操作列の移動代入などで`--param inline-unit-growth limit reached`と記録されていた。これはコンパイラの展開制限が働いた証拠であり、v052のスコア差38手や試行数減少を説明する速度測定ではない。初期の集計スクリプトはmacOSの関数終端を誤読したため、`LFE`ラベルまでの範囲に修正した。保存した`preliminary_assembly.json`は修正後の値である。

診断用の固定時計は1回の照会につき100,003 ns進め、実時間のログ以外を照合する。追加処理も同じ時計で動かし、関数属性以外の差が結果に入らないようにする。固定時計を使うソースは`adhoc/`だけに置く。本体の時計は保持する。

資料は`adhoc/v053_audit/`、通常評価は`results/analysis/v053/`へ保存する。v050とv052を通常評価し直さず、比較には保存評価を使う。

## 実行前の静的確認

最初の4関数への指定では、LOCALの`optimize`で時計確認の独立呼び出しが消え、移動代入も4箇所から1箇所へ減った。一方、必須とした`insertAt`の盤面コピーの呼び出しは残った。追加処理の統計出力もmainへ展開されるため、この1回だけ使う`FiniteStats::summary`にも同じ属性を付け、同じ仮説の機構確認を続ける。この時点でsolverは未実行である。

統計出力への指定だけでも盤面コピーの呼び出しは残った。有限区間探索に閉じた経路復元、状態の変換、状態評価、ハッシュ、下側一致長にも同じ指定を広げる。既存探索と共有する関数の本文や属性は変更せず、追加した処理が展開予算を消費する範囲を減らすという仮説と、機構確認の条件を保持する。

補助関数へ指定を広げても盤面コピーの独立呼び出しは残った。次に、同じ追加関数だけへ`gnu::optimize("Os")`を指定し、追加処理のコード量を抑える。関数属性によって既存探索への展開予算の影響を減らす検証であり、関数本文と採否基準は変更しない。元ソース先頭の最適化指定はO3であり、既存探索の最適化水準もそのまま保持する。

## 実験後

### 判定

機構確認に未達のため中断。追加関数への属性指定だけでは、必須とした再挿入処理の盤面コピーの展開を戻せなかった。固定時計での実行と通常評価には進んでいない。速度やスコアへの効果は未判定であり、「効果がない」という結論には使わない。提出候補はv050を維持する。

### 静的確認の結果

LOCALありとなしの両ビルドが警告なしで通過した。完全な前処理結果は、追加した12箇所の関数属性と診断用のファイル名や行番号以外が親v052と一致した。ソースのSHA-256は`79cad4f077c5e5d92a9bca69fb8311dc44acede1b02cbc69be5624aa633c9c1c`である。照合スクリプトのファイルサイズ取得にあった誤記を修正したが、solverは変更していない。

以下は元のmainを含む生成命令にある呼び出し箇所数であり、実行回数や実行時間ではない。

| 条件と呼び出し | v050 | v052 | v053 |
|---|---:|---:|---:|
| LOCALの`insertAt`から盤面コピー | 0 | 1 | 1 |
| LOCALの`optimize`から時計確認 | 0 | 1 | 0 |
| LOCALの`optimize`から操作列の移動代入 | 0 | 4 | 3 |
| LOCALの`planPair`から`joinWord` | 0 | 2 | 0 |
| 非LOCALの`insertAt`から盤面コピー | 0 | 1 | 1 |
| 非LOCALの`optimize`から時計確認 | 1 | 2 | 1 |
| 非LOCALの`optimize`から操作列の移動代入 | 0 | 3 | 3 |
| 非LOCALの`planPair`から`joinWord` | 0 | 2 | 0 |

一部の関数展開は戻ったが、盤面コピーや移動代入の差は残った。v052との関数本文の一致だけでは、既存探索の生成命令を維持できないことを確認した。今回の静的確認はApple M3とGCC 15.1.0に対するもので、AtCoder上の生成命令は未確認である。

### 引き継ぐ前提

追加処理を低頻度と指定するだけで、既存探索を同じ生成命令へ戻せるという前提は置けない。共通関数側の展開を直接指定する方法や、コードの分離方法は別の検証として扱う必要がある。過去のv036でも、関数呼び出しを消すだけで明確な高速化が得られたわけではないため、生成命令の確認と実時間の効果を分ける。

再開条件: 追加関数の属性指定から検証方法を変える新しい指示を受けた場合。AGENTS.mdの「機構確認がどうしてもパスできないとき」は停止して相談するという手順に従い、採否基準を変えずにここで中断する。B-72の複数機構の組み合わせは将来の未着手候補として保持した。
