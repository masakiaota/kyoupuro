# v022: 踏み台の利用履歴をたどる共同再挿入

## 実験前

- 仮説: 除去対象に含まれる踏み台を利用していた個体も一緒に解き直せば、残存ジャンプの修復負担と経路の固定を減らせる。既存の再挿入器を保ったまま、制限時間内の完成操作数をv021より少なくできる。根拠はB-29、O28〜O30、重要な性質3、および添付資料の保存出力分析である。
- 変更: v021の通常除去候補を選ぶ機会の4回に1回、元の操作列で支持数が不足するジャンプの利用側を除去集合へ追加する。合計8匹を上限とし、異なる時刻の利用関係もたどる。初期構築、再挿入の計算と順序、受理条件、既存の他近傍、時間設定、最適化設定を保持する。候補生成の変更はLOCALと非LOCALの両方で有効である。
- 機構確認: 保存済みv021の100出力を再生し、生成候補を独立な集合演算と照合する。実行時は `lns_dependency_generated`、`lns_dependency_multistep`、`lns_dependency_attempts`、`lns_dependency_extracted`、`lns_dependency_completed`、`lns_dependency_accepted` が通常99件の合計ですべて正であることを確認する。最後の値は同点受理を含む。最良解更新数と短縮量、修復失敗、再挿入失敗、元の消失操作数と除去後の純削減数、所要時間も記録する。複数段階の拡張がない場合は、時刻をまたぐ機構の確認未了とする。
- 採否基準: `tools/in` 全100件をLOCAL、並列数2、既定の時間補正0.80で1回評価する。全件で公式採点成功、独立再生で合法かつE=0、100,000操作以内、実行時間2,000 ms未満、例外による作り直しと構築・LNSエラーが0を必要条件とする。機構確認を満たし、全100件の合計Tが保存済みv021より少なく、case0000が43手以下なら提出候補として採用する。通常99件とcase0000を分けて報告する。機構が働いても基準を満たさなければ今回の構成は棄却する。

## 資料照合と比較対象

ユーザー指定の案1は、参照会話末尾の「踏み台と利用側をまとめて解き直すLNS」（B-29）である。以前のジャンプ距離による集約評価（B-27）は今回の変更に含めない。

添付 `ahc072_paired_event_lns.cpp` とZIP内の同名ソースは、v021の移植元として記録されたSHA-256 `0c4d00f6cdd6bc161a2331852415b29c62220363bda01a7abd62072cbe077b2f` と一致した。v021も評価前のSHA-256 `b0064f908e7dde07765feedf800f9a80b490a9f17ef2ba78f8297f92fcacedee` を保持している。ZIP内の入力は `tools/in` と100件すべてバイト一致した。資料は `adhoc/chatgpt_next_actions_analysis.zip` に保存した。

分析資料の88.36%は、元の履歴で支持数不足が生じる上位候補の割合である。動的な帰巣・経路修復・再挿入を行った失敗率ではない。資料の評価案には反復測定があるが、本実験はAGENTS.mdの運用に従い、既存のv021評価を比較基準として新実装を1回だけ評価する。固定試行数で両ソルバーを走らせる追加診断も行わず、共通の保存出力による候補生成の診断を先に行う。1回の版間差と変更に起因する効果を区別する。

backlog全体、v001〜v021のファイル名とFront Matterを照合した。類似するv018の留置と回収、v019の個体除去、v021の同時点の2塔再構築を確認した。今回の差分は既存操作列の複数時刻にまたがる支持関係による通常候補の拡張である。B-30の開始時刻追加、B-31の再挿入順複数保持は加えない。

比較基準のrun_idは `20260927T093556+0900_v021_paired_event_lns_987039` とする。初期構築終了時の操作数、試行数、候補再構築時間も比較し、時間依存の揺れや計算負担を完成スコアの差と混同しない。

## 候補生成の仕様

1. 現在解の再生中に、距離2以上の各ジャンプについて、下段の個体、飛ぶ個体、時刻、除去しても飛距離を維持できる下段の匹数を記録する。
2. 通常候補の選択と順位はv021を使う。4回に1回の拡張対象では、選択集合によって支持数が不足し、飛ぶ個体がまだ残るジャンプを探す。
3. 飛ぶ個体を全員追加しても8匹以内の候補から、追加匹数が最少のジャンプを選ぶ。同数なら元の飛距離が長い方、さらに同数なら早い時刻を優先する。これを追加可能なジャンプがなくなるまで繰り返す。上限のため未解消の支持関係が残ることは許す。
4. 追加が一度もできなかった選択は試行を行わず次の反復へ進む。拡張後の個体集合には既存と同じハッシュを付け、直近24反復以内に試した集合は省く。候補を生成できた場合だけ既存の除去・修復・再挿入へ渡す。通常候補を保持する残り3回の選択は従来どおりとする。

集合の追加は決定的であり、それ自体で乱数を消費しない。近傍変更後の探索経路と乱数の呼び出し回数は変わり得る。新しい候補に専用の救済経路は追加しない。元の例外処理は保持する。

## 検証手順

- 診断専用C++と独立な集合演算で、保存出力からの候補生成、元集合の包含、上限8匹、重複なし、追加の根拠、複数時刻の連鎖を確認する。この診断は探索や経路修復を呼ばず、新しい解を出力しない。
- 既定のウォームアップ1件と本評価100件を実行し、保存出力を独立に再生する。評価結果を見てsolverを変更せず、判定と記録で終了する。

## 評価前の確認

GCC 15.1.0、C++23、Apple M3（arm64）でLOCALあり・なしをビルドし、両方とも警告なく成功した。SDKは `xcrun --show-sdk-path`、deployment targetは15.0を指定した。完全にマクロ展開したソースを親と比較し、非LOCALでは支持関係の記録・候補拡張・選択頻度・拡張集合の再試行抑制、LOCALではそれらに加えて診断処理だけが変わっていることを確認した。初期構築、再挿入DP、受理条件、時計設定は保持している。

保存済み100出力の39,771候補を独立な集合演算と照合し、候補集合と拡張段階数がすべて一致した。拡張された25,424候補のうち15,916候補が複数段階をたどり、そのような候補が全100ケースに存在した。最大8匹、包含関係、個体の重複なし、ハッシュの一致を確認した。支持数の余裕、消失済み利用側、部分選択、別時刻の連鎖、上限超過、ちょうど8匹を含む7件の境界条件も通過した。この検証ではsolver本体・経路修復・再挿入を呼ばず、新しい解を生成していない。

### 追加機構の発動

以下は通常生成99件の合計である。生成された候補のうち、直近24反復以内に試した8,407候補を再試行の対象から外した。

| 段階 | 回数 | 発生ケース数 |
| --- | ---: | ---: |
| 依存関係による候補拡張 | 81,967 | 99 / 99 |
| 2つ以上の時刻をたどる拡張 | 36,808 | 99 / 99 |
| 除去・修復を試行 | 73,560 | 99 / 99 |
| 除去・修復が成功 | 70,598 | 99 / 99 |
| 全個体の再挿入が成功 | 17,303 | 99 / 99 |
| 同点・悪化許容を含む受理 | 3,893 | 99 / 99 |
| 現在解より短い候補 | 322 | 91 / 99 |

現在解からの短縮は合計637手、最良解を更新した際の短縮は合計531手だった。全100件ではそれぞれ653手と532手となる。これらは同一実行内の候補の記録であり、v021に対する完成版の改善量とは区別する。新しい近傍の最良解短縮は既存カウンタ `lns_regular_saved` の内数であり、二重加算しない。

通常99件では、除去・修復の失敗が2,962回、除去後の再挿入の失敗が53,295回だった。後者は再挿入段階で制約や既存の手数上限を満たす経路を得られなかった候補であり、直ちにバグを示す値ではない。今回は失敗理由を順序・手数上限・その他に分けていない。

除去・修復が成功した候補に限ると、元の履歴で集合に完全に含まれた操作は計1,178,187手、実際の除去後の純削減は計874,837手であり、差は303,350手だった。元履歴の静的な消失数と、帰巣や修復を含む実際の純削減が異なることを確認した。実際に修復経路を生成したジャンプは147,409回、元の1操作からの追加は343,384手だった。この後者には最終的に除去処理が失敗した候補の途中処理も含むため、303,350手との差を別機構の寄与とは解釈しない。親の同じ種候補を同じ開始解で修復する比較はしておらず、修復負担が親より減ったかは未判定である。

### 完成版の差と計算負担

前半の構築が終了した時点の操作数はv021と98件で一致し、残る2件を合計すると11手多かった。後半全体の短縮量はv021より13手多く、差し引き完成版が2手少なくなった。

| 全100件の短縮内訳 | v021からの差 |
| --- | ---: |
| 追加した依存関係の近傍 | +532手 |
| それ以外の探索・短縮処理の合計 | -519手 |
| 後半全体 | +13手 |

これは保存ログの差分の内訳であり、追加近傍を無効にした同じ実行との比較ではない。時間依存の探索経路や乱数の消費も変わるため、519手を追加機構による損失と断定できない。

全100件の探索試行数はv021比で115,366回、約14.7%少なかった。通常99件でも110,236回、約14.7%少なかった。拡張できない選択を省くこと、候補の大きさ、探索経路の違いを含むため、この比率を処理速度の低下率とは扱わない。

依存関係の近傍に使った時間は全100件平均208.85 msで、後半平均1,120.86 msの約18.6%だった。候補拡張ができない選択、除去や再挿入の失敗、受理後の候補再構築を含む計測である。候補再構築全体の平均時間は親より15.36 ms少なかったが、再構築回数も探索経路も異なり、同じ仕事量の速度比較ではない。

### 考察と次の実験の前提

複数時刻の支持関係をたどった最大8匹の候補を、既存の除去・再挿入器へそのまま渡せることを確認した。通常99件すべてで受理され、85件で最良解を更新したため、この候補生成自体は今後の比較に使える。

一方、完成版の差は2手にとどまった。今後は新近傍だけの短縮量で有効性を判断せず、他近傍の試行と短縮量、前半の構築終了時点の差も含めて評価する必要がある。除去後の再挿入で完成しない候補が多いという観測は得たが、その原因と改善手段は今回のログだけでは決まらない。支持関係をたどることによって修復負担が減るという仮説の中間部分も、同じ種候補の直接比較では未確認である。

B-30、B-31は未着手のままとし、今回の結果を見たsolverの変更や追加評価は行っていない。AtCoder環境でのスコア・実行時間・メモリは未評価である。
