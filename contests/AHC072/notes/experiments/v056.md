# v056: 計算結果を保つ高速化の組み合わせ

## 基準版の扱い

2026-09-29のユーザー指示により、v055を暫定採用して本実験の基準にする。v055の事前基準に対する棄却判定と測定結果は過去の記録として保持する。既存の探索判断を保って完成後の短縮処理を追加した版を、今回の高速化へ引き継ぐ。

## 実験前

- 仮説: 到達元の記録、試行盤面の差分復元、盤面コピーの関数展開を組み合わせると、同じ候補の成否、操作列、乱数消費を保ったまま処理費用を減らせる。個別には小さかった効果を、完成解の短縮を追加した現行構成でまとめて検証する。根拠はB-72の第2段階、O31、O34、O41、O47、O70と、v055を基準に高速化するユーザーの指示である。
- 変更: v055を土台とする。v024から1匹再挿入の`IncomingLaunches`を移し、ビットを元の方向と距離の順に走査する。v023から`planPair`の試行盤面に限る高さと向きの保持、変更2マスの保存と復元を移す。v055で独立呼び出しになった`Board`のコピーコンストラクタへ強制展開を指定する。候補選択、評価、同点処理、乱数、時計の呼び出し位置、探索時間、v055の完成後の短縮順序と探索幅は保持する。変更はLOCALと非LOCALの両方に適用する。
- 機構確認: 両ビルドの完全な前処理差分を確認し、登録箇所以外の一致と、再挿入内の盤面コピーの独立呼び出しが消えたことを確認する。固定時計で親と全100入力を各1回実行し、出力、共通計数、最終乱数、時計の呼び出し数を照合する。保存済みv055の解から共通候補を作り、固定仕事量で成否、評価値、全操作列、乱数を直接比較する。到達元の記録は素直な周辺走査と照合し、試行盤面は高さ、向き、帰巣、連続操作、例外時の復元を検証する。本評価では到達元の走査と更新、試行盤面への変換と復元の計数が正であることを確認する。
- 採否基準: 上記の一致と合法性を必須とする。固定候補を処理するCPU時間の通常99件合計について、親に対する比率の5巡中央値が1%以上短ければ、今回の固定仕事量で高速化したと判定する。個別部品ごとの5%短縮は要求しない。正しさを通過すれば速度の基準とは独立に通常100件を1回評価する。全件合法かつE=0、100,000操作以内、外部計測2,000 ms以内、case0000が43手以下、構築とLNSのエラー、不正候補、作り直し、盤面領域の未返却0を必須とする。速度の基準を満たし、合計Tが保存済みv055以下なら採用する。結果を見て基準や組み合わせを変更しない。

## 比較範囲

backlog全体とv001〜v055およびv800のファイル名、Front Matterを照合し、v023、v024、v036、v039、v053、v055の関連する記録と補助コードを確認した。以前の1,600 byte盤面と異なり、比較元は床数ぴったりの領域を再利用するv055である。再開条件はこの統合対象の変更と、B-72に基づく組み合わせへの明示指示である。

v053は追加関数側への属性指定では盤面コピーの展開を戻せなかった。今回はコピー側へ直接指定する。色判定はv055の両ビルドで既に展開されているため、v036の属性を追加する対象ではない。fast-mathと第2順序の省略は計算内容を変えるため、今回の登録範囲に含めない。

## 固定仕事量の測定

入力と保存解は全100件を固定し、case0000は正しさの確認に含め、主速度指標から除く。保存解は`results/out/v055_final_reductions/`を使う。

1. 合流候補: 各解の0、1/4、1/2、3/4時点の盤面からvariant=0で候補を作り、優先度順に最大4候補を処理する。候補と盤面の準備、照合は計時外とし、`planPair`内の変換、経路探索、復元、評価を含める。必要なDPの初回計算をウォームアップしてから測る。
2. 再挿入: 保存解から通常候補と依存関係候補を作り、2〜4匹の重複しない集合を最大64組保持する。親子で同じ集合と乱数を用い、候補生成、チェックポイント構築、除去と2順序再挿入、経路短縮、転送圧縮を測る。既存のv039比較の構成を引き継ぐ。到達元の初期化と維持費も含める。
3. 完成後: 同じ保存解へv055の全短縮処理を適用する。診断だけ期限を無限にし、探索幅、候補順、最大試行数を保つ。親子の全出力を照合する。完成後の費用も主指標の合計へ含める。

親子を交互の順で1巡ウォームアップし、その後5巡を一つの事前登録した測定計画として実施する。通常評価を繰り返してノイズを測るものではない。候補の結果は次の入力へ反映しない。実時計の本文と元のmain相当を保持した測定用ソースを作り、生成命令の呼び出しも本体と比較する。固定時計は別の一致診断だけに使い、速度を測る時計には用いない。

CPU時間を主指標とし、実経過時間と各処理の内訳を補助指標にする。測定中は評価ロックを取得し、速度測定同士や通常評価と重ねない。CPUを使う同時処理は最大2とする。固定候補は途中解の分布全体を再現するものではなく、その速度比をsolver全体へ外挿しない。

ソースと診断は`adhoc/v056_audit/`、通常評価の追加集計は`results/analysis/v056/`へ保存する。README、v000、記号一覧、重要な性質は変更しない。

## 実行前の確認

GCC 15.1.0、macOS対象15.0でLOCALありとなしをビルドした。XcodeのmacOS 27.0 SDKを明示した。登録した10箇所の置換を戻すと親ソースと完全に一致し、実際にマクロを展開した後も診断用のファイル名と行番号を除いて一致した。差分は`source.diff`と両ビルドの`*_preprocessed.diff`へ保存した。

両ビルドの`TemporalLNS::insertAt`で、盤面コピーの独立呼び出しは1箇所から0箇所へ変わった。色判定は0箇所、時計確認は2箇所のままだった。全呼び出し箇所数は42から43へ増えており、盤面コピーの展開だけから速度改善を判断しない。

測定用コードも元のmain相当を保持した。盤面コピー、色判定、時計確認の呼び出し数はそれぞれ本体と一致した。全呼び出し数は測定用では親子とも本体より3箇所多く、生成命令全体の一致を確認したわけではない。

solverのSHA-256を`f400d133d5a4c23eb15c59bf3921a4fb911d8861e84f874c138271ab9bec3e00`で固定した。ソース、入力、親の保存出力、検証器など337ファイルのハッシュを実行前に保存した。検証器のビルドでは未使用の型別名1件を削除したが、solverの変更は伴わない。

## 計算結果の一致

保存済みv055の100解から作った63,349集合の除去と修復、197,433回の1匹再挿入で、親子の成否、成功した全操作列、乱数状態が一致した。途中の塔の再構築25,944試行と2塔の再構築6,400試行も一致した。到達元の記録は、独立した方向と距離の走査による6,579,173確認を通過した。

高さ、分割位置、向き、帰巣を組み合わせた26,112条件で試行用の塔表現を照合した。保存解の20,812操作を逐次適用した盤面も一致し、通常のスコープ終了と例外による復元の計41,624確認を通過した。これらの検証器は未定義動作検出を有効にして実行した。

別に、1回の時計照会につき100,003 ns進める診断で全100入力を親子各1回実行した。全出力、225種類の共通計数、最終乱数、時計の呼び出し数が全件一致した。両版とも独立再生で合法かつ全帰巣、構築とLNSのエラー、不正候補、作り直し0だった。固定時計での一致から、実時計での解や速度の一致は導かない。

資料は`mechanism_summary.json`、`mechanism.csv`、`fixed_clock_summary.json`と`fixed_clock/`に保存した。solverと保存入力のハッシュは実行前から変わっていない。

## 固定仕事量の処理時間

100解から得た6,352組の再挿入候補を共有し、合流候補と完成後の処理も含めてウォームアップ1巡と計測5巡を実施した。すべての巡回で、親子の成否、評価値、全操作列、乱数が一致した。各巡回の結果を次の入力には反映していない。

以下はcase0000を除く99件合計のCPU時間について、各巡回で親に対する増減率を求めた5値の中央値である。時刻の制約を外した固定仕事量の比較であり、2秒版の時間配分の比率ではない。

| 処理 | v055比のCPU時間 |
|---|---:|
| 候補とチェックポイントの生成 | −0.147% |
| 除去、2順序の再挿入、一時領域の解放 | ＋2.869% |
| 経路短縮 | −2.994% |
| 転送圧縮 | −0.932% |
| 合流候補の試行 | ＋0.644% |
| 完成後の全短縮処理 | −0.085% |
| 合計 | **＋0.395%** |

合計の増減は5巡で＋0.432%、＋0.470%、＋0.318%、＋0.395%、＋0.227%だった。除去と再挿入の区間も全5巡で2.257〜2.988%増えた。1%以上短縮する速度基準には届かなかった。合流試行の差は巡回間で符号が変わり、単独の速度効果を確定しない。実経過時間の増減率の中央値は＋0.496%だった。

完成後の処理はこの診断では上限時間を外しているため、主指標の約8割を占めた。実際のsolverでは探索時間を区切るため、この合計の0.395%を全実行の速度差とは解釈しない。合流試行、到達元の維持、コピーの展開それぞれの単独寄与も未分離である。

資料は`fixed_work_samples.csv`と`fixed_work_summary.json`に保存した。結果の一致を通過したため、事前登録どおりコードを変更せず通常100件の評価へ進む。

## 実験後

### 判定

高速化版としては採用を見送る。計算結果の一致と通常評価のスコア条件は満たしたが、固定仕事量のCPU時間を1%以上短縮する条件に届かなかった。ユーザーが暫定採用したv055を基準版として維持する。

### 通常100件の結果

run_idは`20260929T141839+0900_v056_combined_speedups_4d7b7c`。LOCAL、時間補正0.80、既定並列数2で1回評価した。公式採点と独立再生は全件成功し、合法かつE=0、最大1,569 ms、case0000は43手だった。構築とLNSのエラー、不正候補、作り直し、診断エラー、盤面領域の未返却は0だった。

保存済みv055比で合計Tは36手減（0.17298%改善）、40勝29分31敗だった。絶対値とケース別の手数は`results/score_summary.csv`、`results/score_detail.csv`、`results/analysis/v056/`に保存した。

新機構の6計数は全100件で正だった。試行盤面への変換129,817回、復元を伴う試行838,211回、保存した操作3,123,581回を確認した。到達元の再開点走査は600,890,038回、対象2,377,462,576マス、高さ変更の更新599,083,756回だった。盤面コピーの展開も静的確認を通過しており、機構が発動しなかったための採用見送りではない。

探索試行数は親比4.812%減った。構築終了時の手数は3ケースで変わり、合計17手少なかった。v055で追加した完成後処理の入口は、親の同じ入口と比べて35手少なく、その処理の直接短縮が親より1手多かったため、最終差が36手減となった。

引き継いだ完成後処理は8ケースで計12手を直接削減した。内訳は有限区間8手、4マスの共同短縮3手、同色便集約1手。平均時間は21.629 msで、有限区間の全体期限への到達は97ケースだった。

### 考察と次の前提

今回の組み合わせでは、計算内容の保持と処理時間の短縮を分けて判定する必要がある。固定時計と固定候補では親と同じ結果を返したが、到達元の初期化と更新、盤面の変換と復元を含む固定仕事量では速くならなかった。盤面コピーの独立呼び出しを消すだけでも、合計時間の短縮は保証されない。

通常評価の36手減は観測された改善として残すが、高速化によって得られた改善とは説明できない。時間依存の温度と打ち切りによる探索経路の変化を含み、通常評価の探索回数減少も固定仕事量の遅延率そのものではない。

到達元の記録、試行盤面、コピー展開の個別寄与は測っていない。したがって、3部品すべてが遅いという結論にも使わない。再開条件: 個々の部品を同じ固定仕事量で分けて測り、残す部品を選ぶ検証、または初期化と更新の費用を減らす具体的な変更について新しい指示がある場合。

solverは最初の機構確認から変更しておらず、通常評価の再実行も行っていない。README、v000、記号一覧、重要な性質、親のソースと保存出力は実行前のハッシュと一致した。第3段階の途中解への短縮は今回の実験に含めていない。
