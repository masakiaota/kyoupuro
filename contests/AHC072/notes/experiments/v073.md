# v073: 修復負担の減点係数を新規100件で自動調整する

## 実験前

- 仮説: 除去候補の修復負担に掛ける係数を調整すると、再挿入の完了しやすさと短縮余地の配分が変わり、絶対スコアの合計を減らせる。根拠はO77とB-93である。減点ありの候補も短縮に寄与しており、係数1が最適とは確認していない。
- 変更: v071の通常候補の順位式にある修復負担の係数だけをコンパイル時定数にする。候補集合、近傍の配分、他の順位係数、乱数、温度、時間補正、既存の計数は保持する。LOCALと非LOCALの両方に有効で、今回はLOCAL・時間補正0.80で調整する。
- 機構確認: 登録したソース差分だけで親から生成できること、両構成のビルドと完全な前処理結果を確認する。各実行ファイルの係数・ビルド引数・ハッシュを保存し、順位式で使う定数が指定値になったことを前処理結果で確認する。探索制御の検証は仮の評価器で行い、ウォームアップ2回の除外、3回目からの測定、測定の重複なし、ケース単位で最大2並列、同点時の選択、異常終了時の停止を確かめる。実測では全出力を公式採点し、E=0と既存のエラー計数・盤面領域の返却を検査する。
- 採否基準: 全100件が合法・E=0・100,000操作以内・各エラー0、最大外部時間2,000 ms以内の候補から絶対スコア合計が最小の係数を選ぶ。同点なら1に近い係数、それも同じなら小さい係数を選ぶ。3回目に測定する係数1の合計より厳密に少ない場合を「今回の調整用100件で改善」とする。未使用入力への改善や最適性は未検証とし、提出基準の置き換えまでは判定しない。

## 探索条件

ユーザーの今回の指定により、評価入力は公式generatorで新規生成する100件に変更する。通常の`tools/in`、`validation1`は評価しない。既存入力との重複をハッシュで確認し、今回の100件は本実験内だけで繰り返し使う。入力、seed、出力は分析のため保存し、将来の既定評価セットには登録しない。異なる入力集合の旧スコアとは直接比較しない。

対象は修復負担の減点係数1個である。0から2.5まで0.125刻みの21候補を、生成AIを呼び出さない固定の全探索で評価する。実行結果による範囲・刻み・候補数の変更は行わない。

1. 全候補を先にビルドする。ビルドも最大2並列とし、測定の間にコンパイルを挟まない。
2. 係数1で新規100件を2周する。2周ともケース単位で並列数2とし、スコアを順位表・集計ログへ含めない。合法性を確認し、成功したウォームアップの出力は破棄する。
3. 3周目に同じ係数1・同じ100件を測定し、比較の基準とする。
4. 残り20候補を事前に固定した順序で1回ずつ測定する。順序は固定seed 7301による並べ替えで、実行前の計画ファイルに保存する。
5. 最良係数、候補別・ケース別の結果、最良係数を既定値にした単一C++ファイルを保存して終了する。

同時に評価するパラメーターは1候補だけとし、同じ候補のケースを2並列で実行する。1プロセス内の追加並列は使わない。ユーザー指定のウォームアップ2周を除き、同じ係数の再測定は行わない。総数はウォームアップ200ケース、測定2,100ケースである。最初の2周は温度をそろえるための手順だが、実行中の温度を一定にする保証ではない。温度・CPUの定期監視やsolver内の追加計測は行わない。

## ルールと記録

`ahc-llm-rules-en.txt`の「The use of tools like Optuna for automated parameter tuning or score evaluation without using generative AI is also allowed.」を確認した。ユーザーの指示に従い、係数変更、評価、最良候補の選択は実行前に固定したスクリプト内で完結させる。AIへの問い合わせや、実行結果を受けたAIによる実装の書き換えは行わない。

backlogのB-93、関連するO77・O81・O82、v001〜v072・v800のFront Matter、親v071と関連するv059の既読の記録を照合した。候補は従来の修復負担の係数調整であり、新しい候補除外や短縮処理は含めない。

入口は`adhoc/scripts/tune_v073.py`、solverは`src/bin/v073_repair_weight.cpp`とする。起動コマンドは次のとおりである。

```sh
python3 adhoc/scripts/tune_v073.py launch
```

保存先は`results/tuning/v073/`とし、再起動時に存在していたら二重実行を拒否する。状態は`status.json`、全体ログは`run.log`、測定の順位表は`trials.csv`、ケース別は`cases.jsonl`、最終結果は`best.json`と`report.md`に保存する。`best/v073_repair_weight.cpp`は最良係数が既定値になった提出可能な単一ファイルである。既存のsolverは変更しない。

評価本体は既存の`scripts/eval.py`の実行・公式採点処理を再利用する。今回のウォームアップ2周と候補ビルドを専用入口で制御する。測定結果は`results/eval_records.jsonl`と`results/score_summary.csv`にも評価セットと係数のラベルを付けて記録し、`tools/in`専用の`score_detail.csv`は更新しない。評価ロックは準備から完了まで保持する。

エラーや中断時は状態と診断を残して停止し、自動再試行は行わない。起動後のAIによる監視は行わず、ユーザーの次の指示を待つ。終了時の集計と実験ノート・台帳への結果記録も、事前に書いたスクリプトで行う。

## 起動前の検証

制御テスト7件を通過した。ウォームアップの除外、3回目からの測定、候補値の重複防止、最大2並列、エラー時の新規投入停止、残存個体のある出力の棄却、同点時の選択と最良係数の書き出しを確認した。制御テストは仮の評価器を使い、solverを実行していない。

GCC 15でLOCAL・非LOCALをビルドした。親v071との差分はファイル名、係数の定義、候補順位の式だけだった。完全な前処理結果も、登録した追加宣言と式の変更、およびassertの診断用ファイル名・行番号を正規化すると親と一致した。係数1の新しい式は、有効範囲内の整数の修復負担に1を掛けるため、元の順位式と同じ値を表す。実時計での探索結果の一致までは保証しない。

資料はadhoc/v073_audit/のcontrol_tests.log、preflight.json、前処理済みソース、registered_changes.json、source.diffである。起動前のsolver実行数は0で、実際の最初の200ケースは指定されたウォームアップになる。起動時刻とPIDはresults/tuning/v073/launch.jsonに記録する。

## 実験後

- 判定: 今回の調整用100件で改善。提出基準の置き換えは未判定。
- 結果: 21候補の最良係数は0.875。同じ新規100件の係数1に対し合計-61手、最大外部時間1891 ms。
- 機構確認: 候補ごとの係数・ビルド引数・ハッシュと前処理を照合した。全測定の公式採点・全帰巣・既存エラー計数・盤面領域返却が正常だった。ケース並列数は2、ウォームアップ200ケースは集計から除外した。
- 考察: 選択に使った入力での最良値であり、未使用入力への改善と最適性は未検証である。通常のtools/inやvalidation1とのスコア比較は行っていない。
- 保存資料: results/tuning/v073/のbest.json、report.md、trials.csv、cases.jsonl、input_manifest.json、frozen.json。最良係数の単一C++はbest/v073_repair_weight.cpp。
- 再開条件: ユーザーから追加の検証指示がある場合。今回の評価セットは再利用しない。
