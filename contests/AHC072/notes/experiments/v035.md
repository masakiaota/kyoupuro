# v035: v028の地形参照を保ってTower配列を床数別容量にする

## 実験前

- 根拠: B-45、Q8とv034の測定。v033の構成は容量400でも元のv028より10.320%遅かった。一方、同じ構成内でTower配列だけを縮めると保存量が平均47.636%減り、固定候補の合計時間は1%以内の非劣性を満たした。ユーザーから、遅延を生んだ構成変更を持ち込まず、Tower配列の容量削減をv028へ取り入れて新しい実験の検証まで行う指示を受けた。backlog全体とv001〜v034のFront Matterを照合し、v028、v033、v034の関連記録を確認した。
- 仮説: 共有地形への直接参照と容量に依存しない処理を保ち、複製するTower配列だけを床数以上の32刻みに縮めれば、v028の主処理を悪化させず、省メモリ化と一部のコピー処理の高速化が得られる。短縮した時間を探索に使える場合は、完成スコアも改善し得る。
- 変更: v028を直接の親とし、通常Boardを容量別の固定長配列にする。Geometryは元のグローバル実体と配置を保ち、共有ポインタを加えない。読み取り専用の初期配置はGeometry内の400要素を保ち、試行盤面を作るときに必要な容量だけコピーする。WorldとConstructorを容量別の型にし、TemporalLNSはTower配列を扱うメンバー関数だけをテンプレート化する。容量に依存しない探索の補助型は共有し、探索全体を包むSolver型は作らない。個体ID盤面、距離表、他の作業配列、塔の32 bit表現と操作、探索方針、乱数、最適化設定、時計と時間配分はv028を保持する。変更はLOCALありとなしの両方で有効である。v000と既存solverは変更しない。
- 機構確認: LOCALありとなしをビルドし、完全な前処理結果とソース差分を保存する。容量に無関係なクラスと塔の操作が親と一致し、Geometryへの直接参照が残ることを静的に確認する。全13容量と全400床数の選択、保存済み100ケース20,894操作、38境界盤面の内容を照合する。固定時計で全100件の出力、共通計数、乱数状態、時計呼び出し数を親の保存診断と一致確認する。同じ候補処理でも成否と全操作列を照合し、生成命令を確認する。LOCALログに選択容量とBoardの保存量を加える。
- 採否基準: 全件の内容一致を必須とする。固定候補の通常99件合計CPU時間の5巡中央値と全5巡が、元のv028比で1%以内の増加なら速度の非劣性を確認する。中央値が1%以上短く、5巡中4巡以上で短ければ速度改善を確認する。容量400の対照版が同基準を満たさない場合は、導入時の構成変更の影響を避けたとは判定しない。通常評価はtools/in全100件、LOCAL、時間補正0.80、既定並列数2で1回のみ行う。公式採点と独立再生の全件成功、E=0、100,000手以内、最大2,000 ms未満、構築とLNSのエラー、不正候補、初期解と最終解の作り直しの計数0を必須とする。速度の非劣性と必須条件を満たし、保存済みv028より合計Tが増えず、case0000が43手以下なら提出候補として採用する。小差の恒常的なスコア改善までは断定しない。

## 比較条件と実行順

1. ソースを確定し、静的照合と両ビルド、生成命令の確認を行う。
2. 保存操作の再生と固定時計で挙動を照合する。固定時計は1回の読み取りを100,003 nsとし、親のv033診断に保存された出力と比較する。
3. 固定候補で、元のv028、v035の容量400、v035の床数別容量を比較する。v034と同じ100ケース6,357候補を使い、前回の保存チェックサムとも照合する。
4. 1巡のウォームアップを除外し、実行順を巡回ごとに入れ替える5巡を一度の計測計画として実施する。主計時はCPU時間、実経過時間は補助指標とする。通常99件の合計を主指標とし、ケース別と容量別の逆転も残す。
5. ソースを変更せず通常評価を1回実施し、結果と考察を記録する。実行結果を見て実装や採否基準を調整しない。

固定候補の区間は候補とチェックポイントの生成、除去から2通りの再挿入まで、経路短縮とする。入力準備、地形構築、内容照合は計測外とし、補助コードでは時計による打ち切りを無効にする。測定は非LOCALの単一プロセスで行い、評価用ロックを使う。v028の保存評価は`20260927T184531+0900_v028_two_order_lns_c6311b`を比較対象とし、親の通常評価は繰り返さない。

## 実行前の実装確認

最初の実装では、共有地形を元の実体に戻しても、TemporalLNSを容量別のクラスにすると、insertAtの静的な呼び出し箇所が親の40箇所から62箇所に増えた。まだ解法プログラムは実行していない。TemporalLNSはBoardをメンバーに持たないため、クラスと補助型を元の共有型に保ち、配列が必要な関数だけをテンプレート化する。仮説と採否基準は変更しない。修正後の同じ測定用実行ファイルでは、親のinsertAtが2,155命令と50呼び出し箇所、v035の容量400が1,342命令と32箇所、容量192が1,353命令と32箇所だった。命令数は次のシンボルまでの静的な数であり、実行回数や速さを示さない。速度の判定は事前登録した測定で行う。

## 実験後

### 判定

**今回のv035は採用見送り。** 操作の同一性と合法性は確認でき、通常評価の合計Tはv028より42手減った。しかし、同じ候補を処理する合計CPU時間が2.162%増え、事前に定めた1%以内の速度の非劣性を満たさなかった。容量400の対照版にも2.675%の遅延が残った。

Tower配列を縮める部分には効果があった。新実装の容量400と比べると、床数別容量では配列1個の保存量が平均47.636%減り、経路短縮の時間が14.352%、測定区間全体が0.500%減った。この結果と、v028への今回の移植版全体の採否を分けて扱う。

### 実装と機構確認

- `v035_tower_capacity_lns.cpp`を作成した。共有地形はv028と同じグローバル実体への直接参照とした。共有ポインタと探索全体を包むSolver型は導入していない。
- 通常Boardだけを床数以上の32刻み、最大400要素にした。Towerの32 bit表現、塔の操作、乱数、時計、EmptyDP、TemporalLNSの補助型と保存メンバーは親と一致した。
- LOCALありとなしの両方を警告なしでビルドした。両条件の完全な前処理結果と差分を保存した。通常評価の実行ファイルは、事前に固定したLOCAL版とSHA256まで一致した。
- 全13容量の保存量、1〜400床の全選択、38境界盤面を確認した。保存済み100ケース20,894操作の各段階で、塔の色と個体IDの状態が親と一致した。
- 固定時計の全100ケースで、出力、127種類の共通計数、乱数状態、時計の呼び出し数が親の保存診断と一致した。子の診断版は未定義動作検出を有効にして正常終了した。
- 固定候補の100ケース6,357候補について、3条件の成否、盤面、操作列、乱数状態が全巡回で一致した。v034の保存チェックサムとも一致した。
- 実行開始後はsolverと測定コードを変更していない。v000、v028、v033、元の入力とv028の保存解もハッシュで変更がないことを確認した。

### 同じ候補を処理する時間

Apple M3、GCC 15.1、非LOCALの単一プロセスで測定した。入力と地形の準備、内容照合は計測区間に含めない。1巡のウォームアップ後、順番を巡回して5巡測定した。以下は通常99ケースを合計したCPU時間の5巡中央値である。単位はms。各区間と合計はそれぞれの中央値なので、表示した区間値の和が合計と一致しないことがある。

| 条件 | 候補生成 | 除去と再挿入 | 経路短縮 | 合計 |
|---|---:|---:|---:|---:|
| 元のv028 | 59.910 | 1532.907 | 66.923 | 1659.740 |
| v035、容量400 | 59.795 | 1577.366 | 66.981 | 1704.142 |
| v035、床数別容量 | 59.419 | 1578.832 | 57.368 | 1695.619 |

| 比較 | 合計時間の増減 | 短かった巡回 | 1%以内の非劣性 |
|---|---:|---:|---|
| 容量400 / 元のv028 | +2.675% | 0 / 5 | 未達 |
| 床数別容量 / 容量400 | −0.500% | 5 / 5 | 達成 |
| 床数別容量 / 元のv028 | +2.162% | 0 / 5 | 未達 |

- 床数別容量のv028比は全5巡で+1.864〜+2.758%だった。実経過時間でも+2.344%だった。
- 除去と再挿入は、容量400でもv028比+2.900%だった。配列を縮めた場合は容量400比+0.093%で、主処理の遅延を解消しなかった。
- 経路短縮は、配列を縮めると容量400比−14.352%になった。ただし元のv028の測定時間では、この区間は合計の約4%である。
- 個別ケースでは床数別容量のv028比が1%以上短いものが8件、±1%以内が16件、1%超遅いものが75件あった。容量400比では45件、38件、16件だった。配列縮小も各ケース一律の高速化ではない。
- 通常99件のBoardの平均保存量は1,600 byteから837.818 byteになった。IdentityBoardは7,200 byte、共有地形は363,952 byteのままだ。これは配列1個の保存量であり、プロセス全体のメモリ削減率ではない。

### 通常評価

- 実行ID：`20260928T004246+0900_v035_tower_capacity_lns_ab58a3`。
- `tools/in`の全100ケースをLOCAL、時間補正0.80、並列数2で1回評価した。既定のウォームアップ1回は集計から除いた。親は事前登録した保存評価を使用し、再評価していない。
- v028比の合計Tは42手減、0.20101%改善だった。改善39件、同じ26件、悪化35件だった。case0000は43手で条件を満たした。
- 公式採点と独立した操作再生は100件すべて成功した。E=0、操作数上限以内で、最大実行時間は1,544 msだった。構築エラー、LNSエラー、不正候補、初期解と最終解の作り直しはすべて0回だった。
- 通常99件のLNS試行数はv028比7.611%減、見送りを含む反復数は7.749%減だった。構築終了時の操作数は3ケースで異なり、合計7手増だった。
- 合計Tとcase0000の条件は満たしたが、速度の非劣性と容量400の対照版の条件を満たさず、採用基準は未達となった。

### 考察

1. **床数別容量はコピーする量を減らせた。** 同じ新実装の中で容量だけを変えると、Boardの保存量と経路短縮の時間が減った。v028のTowerは元から32 bit表現であり、今回の効果は塔1本の別表現への変更によるものではない。
2. **v028への導入費用が残った。** 配列を縮めていない容量400の対照版でも遅かったため、2%程度の遅延を保存量の削減に帰属させることはできない。共有ポインタと外側のSolver型を導入しなくても、容量別の型と関数に伴う生成コードの差が残る。具体的な遅延箇所と個別要因の寄与は未特定である。
3. **今回のスコア改善を高速化の証拠にはしない。** 固定時計では同じ探索結果になったが、通常時計では処理速度によって打ち切りや探索経路が変わる。42手の改善と試行数の減少は、この1回の評価で得られた結果として記録する。恒常的なスコア改善や悪化なしは確認していない。
4. **次に残る問いは導入費用の内訳である。** 次の実験では、容量400のままで生じた2.675%の遅延を説明できることが前提になる。配列容量をさらに調整する前に、この差を切り分ける必要がある。生成命令の静的な数が少ないだけでは、実行時の高速化を保証できなかった。

テンプレートの床数別容量を否定する結果とは扱わない。今回はv028への移植版の速度の非劣性が成立しなかった。v000と既存の提出候補は変更していない。AtCoderのx86環境での本実験は未実施である。

再開条件：容量400の対照版に残る遅延の切り分け、または提出環境での比較について、ユーザーから追加の指示を受けた場合。今回の実行結果を使ったsolverの改良と再評価は行っていない。
