# v001：混色の集荷と両端荷下ろし

## 実験前

- 仮説：backlog の O2、O3 と B-02 に基づく。近傍の異色を基本7匹以下の塔で集め、両端の色から帰巣させれば、少数色も経路を共用できる。集荷順とグループ分けを制限時間まで探索すると、初期の近傍集荷より総操作数が減る。
- 変更：初めての solver であり、派生元の実験はない。`v000_template.cpp` の時間管理とローカル計測を引き継ぎ、`src/bin/v001_mixed_deque.cpp` に単一ファイルとして実装する。全員をグループへ割り当て、グループごとに全帰巣まで計画する。
- 機構確認：`mixed_carry_moves`、`source_returned`、`home_launch_long_moves` で混色輸送と出発点帰巣を確認する。`sa_iterations`、`sa_accepted`、`initial_T - final_T` で時間内探索の発動と改善を確認する。出力時には全操作の合法性、予測操作数との一致、`E = 0` を検証する。
- 採否基準：既定の `tools/in` 全100件を `scripts/eval.py` の既定 `LOCAL`、`-j 2` で1回評価する。全ケースで公式 scorer 成功、`E = 0`、ローカル実行時間2,000 ms未満を満たすことを必要条件とする。通常生成99件の合計で3つの操作機構のカウンタがそれぞれ正、最終 `T` が個別最短距離合計より小さく、初期構築の `T` 合計よりも小さければ、初回の比較基準として採用する。他方式に対する優位性は今回判定しない。

## 実装設計

### 配送費の厳密計算

集荷後の色列に対し、隣接マスへの塊全体の移動と、自色の巣にある下端の同色部分を残す発射を扱う。後者は `l <= k + 1` の全候補を調べる。

色列が変わるのは帰巣時だけなので、「両端の色、向き、床マス」ごとに、次に帰巣できる状態までの隣接移動距離を前計算する。着地時に上端が帰巣する状態は強制的な終点として扱い、そこを色列を保ったまま通過する経路を許さない。

色列とその反転を共通のキーにし、両端の帰巣イベント後の費用をメモ化する。短くなった色列の費用から再帰的に決まるため、集荷後の配送費はこの操作モデルの中で厳密に求められる。

### 集荷と外側の探索

集荷は決めた順序に従って床上最短路を進み、途中の自動帰巣も再現する。色列が空になった場合は次の未集荷個体から操作を始める。グループ外の個体は元のマスへ保存する。

初期構築は近傍候補を追加する際の配送費込みの節約を調べる。焼きなましでは集荷順変更、グループ間の移籍と交換、列の末尾交換、分割と結合を使う。費用はグループ単位でメモ化し、変更したグループだけ再計算する。最良の全帰巣計画を保持する。

時間は `main` 冒頭から計測する。テンプレートと同じ `JUDGE_TIME_LIMIT_SEC = 1.90`、`LOCAL_TIME_RATIO = 0.80` を使い、`PROGRAM_TIME_LIMIT_SEC` の96.5%までを探索に使う。残りは最良計画の操作列復元と出力に充てる。

### 検証順序

ビルドと静的確認を済ませてから、`0001.txt` で機構確認し、同じ実装を全100件で評価する。solver 実行後は結果に基づく実装修正を行わず、観測結果と判定を記録する。

### ローカルのビルド環境

GCC 15.1 の既定 SDK が存在しない `MacOSX15.sdk` を指していたため、`SDKROOT="$(xcrun --show-sdk-path)"` を指定する。この環境では既定の deployment target も clang が受理しない `18.0` になったため、`MACOSX_DEPLOYMENT_TARGET=15.0` を併せて指定する。solver のコードやビルドスクリプトへ環境固有のパスは埋め込まない。

## 実験後

### 判定

採用。B案の最初の比較基準とする。事前登録した条件をすべて満たした。他方式との比較はまだない。

### 結果

- 全100件で公式 scorer が成功し、出力行数と公式スコアが一致した。全件で `E = 0`、`fallback_count = 0` だった。操作列の復元時に、各グループの全帰巣、全操作の合法性、予測した `T` との一致も確認した。
- ローカル実行時間は平均1,519.17 ms、最大1,569 msで、全件が2,000 ms未満だった。焼きなまし部分は平均1,465.42 ms、復元と合法性確認は平均0.04 msだった。
- 通常生成99件では、個別最短距離合計に対して総 `T` が66.18%少なく、初期構築に対して28.21%少なかった。99件すべてで初期構築から改善した。
- seed 0を含む100件でも、初期構築からの総 `T` の削減は28.18%で、全100件で改善した。
- 通常生成99件の機構確認では、混色輸送14,413回、出発点での帰巣1,774匹、帰巣する下段を使った長距離発射709回だった。混色輸送と出発点帰巣は99件すべて、長距離発射は95件で発動した。
- 通常生成99件で、焼きなましの反復は平均約1,959万回だった。この数には不適合な近傍を棄却した反復も含み、費用を評価した候補は平均約1,224万回だった。
- 単発の `0001.txt` による機構確認でも、公式 scorer 成功と全29匹の帰巣を確認した。その後、同じ実装を全件評価し、実行結果に基づくコード変更は行っていない。

正本ログは `results/score_summary.csv`、`results/score_detail.csv`、`results/eval_records.jsonl` にある。今回の `run_id` は `20260925T220946+0900_v001_mixed_deque_bf1944`、ラベルは `b_mixed_deque_sa` である。ケース別の操作列と計測値は `results/out/v001_mixed_deque/` にある。

実行コマンド：

```bash
SDKROOT="$(xcrun --show-sdk-path)" MACOSX_DEPLOYMENT_TARGET=15.0 \
  python3 scripts/eval.py --label b_mixed_deque_sa v001_mixed_deque
```

### 考察

混色を保った輸送と、巣で下段を帰巣させながら上段を送る操作の両方が、実際の出力で発動した。基本7匹以下に制限して外部の初期個体を保存する構成も、全ケースで全帰巣まで成立した。したがって、B案の操作モデルは実装可能であり、残存分を別の方式で消す処理を必要としなかった。

帰巣イベントまでの距離の前計算と色列のメモ化により、時間予算の大部分を外側の探索に使えた。全ケースで初期構築から改善したため、この実装では時間制限付きのグループ分けと集荷順探索が操作数の削減に寄与した。

次の実験では、B案の成立性と機構の発動を未確認の前提として扱う必要はなくなった。`v001_mixed_deque` を、全帰巣する実測済みの比較基準として扱える。一方、A案やC案に対する優位性、競技全体での到達水準は今回の評価では判断できない。
