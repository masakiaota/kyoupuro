# v208: 合流構築に複数塔の同色集荷を加える

## 実験前

- 仮説: 2塔ずつの利益評価では選びにくい同色のまとまりを、3塔以上の集荷として評価すれば、LNSで短縮しやすい初期解を作れる。根拠はB-122、O96・O97、重要な性質2・3である。保存されたv204の300件では、構築時の最短候補より長い候補が183件で選抜されたため、構築直後だけでなく同じ総時間での完成手数を判定に使う。
- 変更: v204の初期構築に、同色だけからなる3塔以上・合計8個以下の集荷候補を加える。各塔を根として、近い同色塔を順に追加し、集荷費と残りの配送費による利益が最大の組を候補とする。現在盤面で経路を木にまとめ、末端から根へ運ぶ合法な操作列を作り、その実操作数で既存の2塔合流と比較する。外部の塔は下段に保持し、背景高さと集荷総数の合計が8以下の通路だけを使う。色の巣は集荷経路から除外する。初期解の最大5本、15%・15%・70%の選抜、時間設定、NN、LNS、終了処理は親から保持する。変更はLOCAL・非LOCALの双方で有効である。
- 機構確認: LOCAL・非LOCALをGCC 15でビルドし、完全な前処理結果の差分を確認する。診断用の小盤面では分岐集荷、外部塔の保存、容量上限、異色・同一家系の除外、通路の容量不足、期限切れを確認する。初回実行前にソースと入力を固定し、0000・0001を両ビルドで各1回診断する。LOCALの2件合計で集荷候補の生成、実計画の成功、構築への採用、採用を含む構築の完成、選抜候補への保持が正であることを確認する。本評価では全件の合法性、全帰巣、既存エラー0、盤面領域の全返却、5本以内の段階選抜を照合する。集荷を使った初期候補が選抜で勝った件数と追加費用も記録する。
- 採否基準: 通常の `tools/in` 100件と、前回v206の比較に使った `results/analysis/v206/validation200/input` 200件を、それぞれLOCAL・時間補正0.80・既定2並列で1回評価する。先頭入力のウォームアップは集計しない。診断が通れば通常100件の成績にかかわらず別200件も実施する。全件合法・E=0・100,000操作以内・外部時間2,000ms以内・既存エラーと作り直し0・盤面領域の未返却0を必要条件とする。機構確認を通過し、両セットの絶対スコア合計がそれぞれ保存済みv204を厳密に下回れば採用する。実行結果を受けたsolverの変更、追加設定の評価、同条件の再評価は行わない。

## 事前照合と対象範囲

backlog全体、既存実験のファイル名とFront Matter、関連するv002・v015、親v204を照合した。B-122を今回実施する。v207は別の候補保持実験で使用済みのため、番号はv208とする。

v002は色ごとの集約木で配送全体を構成し、v015は二色の集荷と配送を組み合わせる実験だった。今回はv204の構築中に、同色の複数塔をまとめる候補を局所的に追加する。木は最短距離で逐次接続し、厳密なSteiner木の部分集合DPは導入しない。候補の生成は初期塔と更新された塔を根に行い、各意思決定で実計画を試す集荷候補は最大1個とする。

比較対象のrun_idは、通常100件が `20261003T031601+0900_v204_initial_race_tuned_47557d`、別200件が `20261003T100627+0900_v204_initial_race_tuned_bf911d` である。親は再実行せず、保存結果と退避出力を使う。親のソースSHA-256は `5d4ed7aa921a9468d5ff290e61bdce84667f9c5b989a624afaf6caece12e89d4`。評価は共有ロックで直列化し、100件の出力を退避してから200件へ進む。

検査資料は `adhoc/v208_audit/`、集計は `results/analysis/v208/` に保存する。通常100件と別200件の両方を事前に固定するが、これらは既に親の成績を確認したデータであり、未見データでの性能を示す比較ではない。

## 実装と診断

LOCAL・非LOCALともGCC 15で警告なくビルドした。登録した11か所の変更を逆適用すると親のソースへ戻り、両モードの完全な前処理結果も親と一致することを確認した。実際の差分は集荷候補、その構築への接続、LOCAL計測に限定される。初回実行前のソースSHA-256は `de5cf6717e159d3a3fdb0ef783f4799733d77fe652415351f54a801586aa39a1`。両セットの入力と親の保存300出力を独立再生し、既存の保存計数と照合して固定した。

小盤面の8条件は、分岐する集荷、下段に保持した外部塔、合計8個、2塔だけ、容量超過、異色、同一家系、通路不足、期限切れを組み合わせて確認した。成功2条件は独立配列で全操作と完成盤面を照合した。未定義動作を検出すると停止するビルドでも通過した。macOSのGCCにはUBSanの実行時ライブラリがなかったため、診断用ビルドはトラップ方式を使った。

0000・0001をLOCALと非LOCALで各1回実行し、全件の合法性と全帰巣を確認した。LOCALでは集荷の採用が計1,091回、その集荷を含む構築の完成が275回、選抜へ残った初期候補が計6本だった。既存エラーは0、盤面領域は4枚とも返却された。

最初のLOCAL診断後、集計器が親版に存在しない `lns_end_limit` を参照して停止した。この参照だけを除き、完了済み出力を保存して未実行の診断だけを継続した。solverは変更せず、完了済みケースの再実行も行っていない。集計器の修正前後のハッシュと保存出力は `adhoc/v208_audit/analysis_helper_correction.json` に記録した。

## 実験後

### 判定

採用（今回の事前基準）。通常100件と別200件の両方で、保存済みv204より絶対スコア合計が小さくなった。差は小さく、同一実装の再評価は行っていないため、実行時変動を除いた安定した優位性は未確認である。

| 評価セット | v204比の合計差 | 改善率 | 勝・分・敗 | 最大外部時間 |
| --- | ---: | ---: | ---: | ---: |
| 通常100件 | −54手 | 0.26510% | 52・7・41 | 1,572ms |
| 別200件 | −38手 | 0.07932% | 87・23・90 | 1,569ms |

全300件で公式採点と独立再生を通過し、合法・E=0・100,000操作以内・外部時間2,000ms以内、既存エラーと作り直し0、盤面領域4枚の全返却を確認した。LOCAL・時間補正0.80・2並列で各セットを1回評価し、通常100件の出力を退避してから別200件へ進んだ。要約ログに2行、通常入力の詳細表に1行、ケース正本に300行を登録した。

### 集荷の発動と選抜

| 指標 | 通常100件 | 別200件 |
| --- | ---: | ---: |
| 集荷候補の生成 | 194,097回 | 377,537回 |
| 実計画の試行 | 65,547回 | 126,175回 |
| 実計画の成功 | 55,269回 | 105,260回 |
| 構築への採用 | 14,779回 | 26,740回 |
| 集荷を使った構築が1回以上あったケース | 99件 | 194件 |
| 集荷を含む完成した構築 | 1,677本 | 2,527本 |
| 集荷を含む初期候補が選抜へ残ったケース | 86件 | 185件 |
| 選抜へ残った、集荷を含む初期候補 | 405本 | 875本 |
| 集荷を含む初期候補が選抜で勝ったケース | 80件 | 178件 |
| 集荷の生成と実計画の平均費用 | 6.162ms | 6.302ms |

構築は時間内に繰り返すため、採用回数は最終出力に残った集荷の回数ではない。選抜の勝者も初期候補の由来を記録したものであり、その集荷操作がLNS後に残ったことは意味しない。通常100件は初期候補5本が96件、3本が4件。別200件は5本が196件、4本が1件、3本が3件だった。段階選抜と継続再開は全件で整合した。

### 構築とLNSの関係

| 指標 | 通常100件 | 別200件 |
| --- | ---: | ---: |
| 構築直後の最短候補の合計差 | +576手 | +1,176手 |
| LNS終了直後の合計差 | −59手 | −52手 |
| 終了処理後の合計差 | −54手 | −38手 |
| 構築の平均時間（v204 → v208） | 402.245 → 389.210ms | 433.968 → 426.596ms |
| LNSの平均時間（v204 → v208） | 1,118.063 → 1,131.056ms | 1,086.377 → 1,093.747ms |
| LNS試行数（v204 → v208） | 581,275 → 568,888回 | 861,327 → 863,400回 |

両セットとも構築直後の最短手数は悪化したが、LNS終了時には親より短くなった。集荷候補そのものの費用が加わる一方、構築全体は早く終わり、LNSの時間も増えた。初期解の構造、構築の打ち切り時期、LNSの探索経路と残り時間が同時に変わるため、差分を集荷の構造だけによる効果とは断定できない。

次の比較では、v204の選抜とLNSを保持したまま、同色の複数塔をまとめる構築を追加したv208を候補にできる。今回の結果は、構築直後の最短手数だけでは完成スコアを判定できないという既存の比較方針を支持する。別200件では敗数が勝数より多く、平均の改善幅も小さい点を残す。

評価中にユーザーから指摘された「同色個体の区別による再挿入制約」は、独立の未着手案B-129へ記録した。今回のsolverへ追加していない。初回の小盤面診断以降、solverの変更と追加設定の評価は行っていない。
