# v033: 床数に合わせて盤面と探索用配列を一括で縮める

## 実験前

- 根拠: B-44、O38・O39。ユーザーが、通常Boardだけに限定せず、同じ考え方で軽量化できる全箇所の変更と、評価・考察・次の改善案の記録を指示した。v028では床IDが既に連続しており、床数を超える要素は探索に使わない。一方、通常Boardのほか個体ID付き盤面、距離表、Group、経路探索の作業配列、マス別のvectorにも最大400枠が残っている。
- 仮説: 入力ごとに床数以上の32刻み容量を選び、床数を上限とする全固定長配列を縮めれば、コピー・比較・初期化・確保容量と距離表の行幅が減る。同じ候補処理が速くなり、同じ制限時間内の探索量と完成スコアを改善できる。
- 変更: v028を直接の親とし、容量32・64・…・384・400の型から起動時に1回選ぶ。Board、IdentityBoard、Geometryの床別配列と距離表の両次元、Groupの距離配列、Router・PortionRouter・DeliveryDP・Constructor・TemporalLNSの床別作業配列、床別vector、LOCALの独立再生配列を対象とする。座標→床ID表はN×N、入力行はN行だけ持つ。既に実床数から確保している探索ラベル等はその方式を保持する。塔の高さ8、色数上限12など別の制約の配列、候補数に関するreserveは保持する。構築の距離打ち切り・重み添字の上限800は容量から分離して維持する。重み表は参照可能な範囲だけ確保する（後述）。探索手順、近傍、乱数消費、評価関数、コンパイル設定、時計と時間配分はv028から引き継ぐ。変更はLOCAL・非LOCALの両方で有効である。v000は変更しない。
- 機構確認: LOCAL・非LOCALをビルドし、完全なマクロ展開と容量に関係しない処理の正規化比較で差分を確認する。全13容量のsizeofと全400床数の選択を確認する。保存済みv028の100操作列を縮小盤面・個体ID盤面で再生し、盤面内容と全帰巣を照合する。診断専用に時計を1呼び出し100,003 nsずつ進める版を作り、親と子の100入力の出力、主要計数、最終乱数状態を照合する。固定した候補処理でも成否と操作列を照合する。LOCALログには選択容量、Board・IdentityBoard・Geometry・Group等の保存量を追加し、全ケースで発動を確認する。
- 採否基準: 内容照合が全件一致することを前提とする。固定仕事量の主指標は通常99件の候補再構築・経路短縮・候補再生成を合わせたCPU時間合計の5巡中央値とし、親より3%以上短く、5巡中4巡以上で短時間なら速度改善を確認したとする。3%未満は同程度と判定する。本評価はtools/in全100件、LOCAL、既存時間補正0.80、既定並列数2で1回だけ実行する。公式採点と独立再生の全件成功、E=0、100,000手以内、最大2,000 ms未満、構築・LNS・不正候補・初期解と最終解の作り直しの計数0を必要条件とし、保存済みv028より合計Tが少なくcase0000が43手以下なら今回の提出候補として採用する。速度とスコアの判定は分け、小差を恒常的な改善と断定しない。

## 事前照合と範囲

backlog全体とv001〜v032のファイル名・Front Matterを照合した。直接の親v028、関連するv030・v032の本文を確認した。v030・v032はコピーと少数操作の部品比較であり、v028の全配列縮小と探索全体の評価は未実施である。「実際の保持数・参照順・追加状態量が決まり、その使い方に合わせた比較の指示を受けた場合」という再開条件を今回の指示が満たす。

MVをそのまま置換すると、構築時の `d >= 2*MV` と重みの `min(steps, 2*MV)` まで変わるため、その上限800を明示的に保持する。Routerの状態は床×向きの2×床数個で、最短経路の長さは2×床数−1以下である。2本を合わせたstepsは4×床数−2以下なので、重み表の必要要素数は `min(800, 4*capacity-2)+1` で足りる。同じ添字の重みの式を保持する。

容量ごとに探索全体をテンプレート化する。Geometryの実体は選ばれた型のものだけを起動時に作り、各処理が共通の参照先を使う。型ごとに大きなGeometryの実体を全て静的確保する構成は避ける。この構造変更の費用も、親v028との固定仕事量比較に含める。

## 固定する測定条件

- 親の保存評価は `20260927T184531+0900_v028_two_order_lns_c6311b` を用いる。全100入力と保存出力のハッシュを保持する。
- 固定仕事量は保存済みv028出力から各件最大64個の2〜4匹の候補集合を選ぶ。通常候補と依存関係で拡張した候補を列挙し、集合の重複を除く。候補の選定は親側で1回だけ行い、全方式へ同じ集合・hash・乱数初期値を渡す。
- 各ケースで候補管理とチェックポイントを再生成し、各集合を除去・修復して2通りの順序で再挿入する。完成した候補には経路短縮を1回適用する。出力を次の試行の入力へ引き継がない。候補再生成、再構築、経路短縮の区間も補助指標として記録する。
- 時計による打ち切りを無効にするのは診断・固定仕事量用の補助コードのみである。親と子で同じ計測を用いる。計測外で1巡ウォームアップし、順序を交代する5巡を1回の固定計画として実行する。内容検証・入力準備・出力は計測外とする。
- macOSのApple M3 / GCC 15系で非LOCALの固定仕事量を測る。`results/.eval.lock` を使って他の評価と重ねない。AtCoderの速度はこのローカル結果から断定しない。
- ソース確定後に動作照合・固定仕事量・通常評価を順に行う。実行結果を見て方式やパラメータを調整せず、判定・考察・次の改善案を記録する。同じsolverの通常評価を繰り返さない。

## 実験後

### 判定

棄却。容量削減と内容一致は確認できたが、固定仕事量は親より8.755%遅く、通常評価も合計64手増（0.30631%悪化）となった。速度改善の基準と完成スコアの条件を満たさなかった。v033は実験記録として保存し、v028とv000は変更していない。

### 実装と機構確認

- LOCAL・非LOCALを警告なしでビルドし、両方の `-E -P` による完全なマクロ展開結果を保存した。地形参照の表記を正規化したソース差分も確認した。容量、入力・地形の所有方法、重み表の保存範囲、型の選択と計測項目が変更点で、距離打ち切り800・乱数・探索の判定式・時間配分・最適化設定は維持した。
- 全400通りの床数で選択容量を確認し、全13型のsizeofとコピー可能性を検証した。38種類の境界盤面では座標対応、距離表、移動先表を親と照合した。
- 保存済み100ケースの20,894操作を再生し、通常盤面・個体ID盤面と親の内容、帰巣数、最終状態が一致した。
- 固定時計で親と子を全100入力について比較し、出力全バイト、共通の全計数、最終乱数状態、時計呼び出し数が一致した。子は未定義動作検査を有効にし、違反時に停止するビルドでも全件を通過した。この照合は同じ時計進行での挙動一致であり、実時間の探索経路の一致を保証するものではない。
- 固定仕事量の6,357集合（通常99件は6,336集合）について、除去の成否と盤面、再挿入の成否、短縮前後の操作列、乱数状態が両方式で一致した。ウォームアップ1巡と計測5巡で内容が変わらないことも確認した。
- 通常評価の全100ケースで選択容量と各構造体の保存量が期待どおりだった。機構の未発動による棄却ではない。LOCALのTemporalLNSには計測用boolとパディングが追加されるため、非LOCALのsizeof表とは分けて照合した。

### 固定仕事量の結果

Apple M3 / GCC 15.1、非LOCAL、単一プロセスで実施した。各区間について通常99件のCPU時間を合計し、その5巡中央値を示す。ウォームアップは含めない。候補は保存済み最終解から同じ規則で選んだものであり、実際の探索途中の候補分布とは異なる。

| 処理 | v028 | v033 | 時間の増減 | v033が速い巡回 |
|---|---:|---:|---:|---:|
| 候補・チェックポイント生成 | 59.173 ms | 59.125 ms | −0.081% | 3 / 5 |
| 除去・修復・2通りの再挿入 | 1,496.002 ms | 1,650.785 ms | +10.346% | 0 / 5 |
| 経路短縮 | 64.868 ms | 51.487 ms | −20.628% | 5 / 5 |
| 合計 | 1,619.894 ms | 1,761.714 ms | +8.755% | 0 / 5 |

経路短縮は事前の速度基準を満たしたが、全体の約9割を占める除去から再挿入までの処理が遅くなった。実入力に現れた10容量帯のすべてで合計時間が増え、帯ごとの増加は4.14〜14.05%だった。特定の1容量だけで起きた逆転ではない。

### 通常評価

run_idは `20260927T220424+0900_v033_capacity_lns_ae68b1`。LOCAL、時間補正0.80、並列数2、tools/in全100件の評価を1回行った。

- 全100件で公式採点と独立Python再生に成功し、合法・E=0・100,000手以内だった。最大実行時間は1,546 msで、構築エラー・LNSエラー・不正候補・初期解と最終解の作り直しはすべて0だった。
- 保存済みv028比で合計64手増（0.30631%悪化）、30勝14分56敗。case0000は43手を維持した。
- 構築終了時点では0019だけが8手増で、残り99件は親と同じだった。LNSで短縮した手数は親より合計56手少なかった。
- 通常99件のLNS試行数は9.469%減った。依存関係候補の見送りを含めて復元した反復数も9.491%減り、単純な計数対象の違いでは説明できない。1匹の再挿入呼び出しは8.486%減、束の再挿入は8.460%減、処理した操作層は8.230%減だった。

固定仕事量の遅延と本評価の探索量減少は方向が一致した。ただし時間制限下では温度・打ち切り・訪問する候補も変わるため、64手の差をそのまま今回の変更の恒常的な効果とは扱わない。AtCoder上の評価は実施していない。

### 生成命令から分かったこと

実行済みベンチマークと同じバイナリの `insertAt` を逆アセンブルした。関数本体の静的な命令数は親が2,016、容量192の新構造が2,574、容量400の新構造が2,579だった。呼び出し命令の箇所数も40から62へ増えていた。容量400の新構造は追加実行せず、既に生成されていた命令を読み取っただけである。

容量を400にした型でも関数本体が増えているため、配列の縮小と同時に行った構造変更・コンパイラの展開判断が影響した可能性がある。今回の構成では地形へのアクセスが固定の共有実体から、選んだ型の実体を指す共有ポインタ経由へ変わっている。命令配置、インライン展開、参照の読み出し、配列の大きさは切り分けられていない。静的な命令数は実行された命令数ではなく、増分が遅延の原因とまでは確定していない。

### 考察と次の改善案

容量削減そのものは発動し、コピー・比較を繰り返す経路短縮で利点が出た。しかし、v028への一括適用では探索の主処理の生成命令も変わり、その負担を含めた全体の改善にはならなかった。次の実験の前提は、「容量が小さければ全体も速い」から「主処理の命令と参照方法を保ったうえで容量を減らせるか」へ変わった。

次は同じ固定仕事量のベンチマーク内で、①親v028、②新構造を容量400固定で使用、③新構造を床数別容量で使用、の3条件を比較する案を優先する。②が①より遅ければ構造変更側、③が②より遅ければ容量変更に伴う生成命令・配置側を調べる根拠になる。両方の影響がある場合も分けて記録する。②が遅い場合の修正候補は、地形の参照先を探索オブジェクトの安定した参照として渡し、共有ポインタの読み出しや展開判断への影響を減らす構成である。現時点ではこの修正の効果は未確認で、追加の実装・実行はしていない。

再開条件: 上記の比較、または地形参照と容量変更を分離する具体的な構成について、ユーザーから新たな実験指示を受けた場合。
