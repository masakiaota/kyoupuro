# v071: v059の命名と不要な記述を整理する

## 実験前

- 仮説: v059の探索内容を保持したまま、名前と意味の不一致、未使用関数、過去の検証用分岐、古いコメントを整理できる。今後の変更箇所を読み取りやすくすることを主目的とし、高速化は確認できた場合の副次的成果とする。根拠はユーザーのリファクタリング依頼と、構成変更で生成命令が変わるというO70・O83・O85である。
- 変更: v059から単一ファイルの整理版を作る。地形を`Board`、変化する盤面を`State`、領域管理を`StatePool`と呼び、`C`、`cell_count`、`cell_id`、`floor_dist`などをv000と記号一覧へ合わせる。実装用の関数・変数をsnake_caseへ統一する。塔内の色は従来の`c + 1`の符号を保持し、符号を扱う名前で表現する。使われない2関数と過去の監査専用分岐を除き、コメントを現在の意図に合わせて整理する。計測の重複した条件分岐はv000と同じLOCALマクロへまとめる。LOCALと非LOCALの両方で有効だが、候補集合、評価式、乱数、走査順、時計の照会位置、時間配分、データの配置は保持する。
- 機構確認: 両構成をビルドし、完全な前処理結果について改名と登録した削除・整理を照合する。固定時計は`tools/in`全100件×2構成で親子を各1回実行し、操作列、共通計数、計時値、時計照会数、乱数、盤面領域の返却を一致確認する。同じ固定時計の診断プロセスでCPU時間を外側から測り、通常solverに計測処理を増やさない。公式採点に加え、既存の独立再生器で出力を検証する。
- 採否基準: 改名と削除の静的照合、固定時計200組の一致、行数減少、通常100件の全件合法・E=0・100,000操作以内・外部計測2,000 ms以内・各エラー0を満たせば整理版として採用する。完成スコアの差は別に報告し、改善した場合も1回の評価差を高速化の因果効果とは断定しない。提出性能の比較基準として元のv059とその保存結果を保持する。正しさの照合に失敗した場合は結果を報告して停止する。

## 範囲と検証条件

v059、v000、記号一覧、重要な性質、README、判定済み実験ノートは変更しない。v000との対応は概念と命名に合わせる。塔のビット表現、色符号、`ray[p][d][l]`の距離添字、操作の格納形式、時計の更新方法をv000へ移植する作業は含めない。これらは単なる改名では処理を保持できないため、違いをソースに短く明記する。

ソース中のブログ由来の説明と版ごとの追加範囲コメントを削る。既存の出典と経緯は元のv059および`notes/compiler_optimization_20260926.md`に残っている。操作の合法性、探索の制約、処理順の理由を説明するコメントは残す。

盤面領域に関する既存の計測キー5個も`state_*`へ合わせる。固定時計の比較ではキーの対応と、それに伴う辞書順の差を正規化して照合する。通常評価に新しい計数や時計照会は加えない。

backlog全体の項目とv001〜v070・v800のFront Matterを照合した。直接の親v059、過去の整理版v013、およびO70・O83・O85を確認した。過去の性能改善案の再実験は含めない。対応する台帳はB-91である。

通常評価はLOCAL、時間補正0.80、`tools/in`100件、並列数2で1回とする。比較対象はv059の`20260929T235217+0900_v059_repair_priority_6879ca`。同じ実装の再評価でノイズを測らない。詳細な速度測定は独立した固定時計の診断だけで行う。

```sh
CARGO_BUILD_JOBS=2 python3 scripts/eval.py v071_refactored tools/in -j 2 --label v071_refactored
```

実装と検証器は最初の実行前に凍結する。結果を受けての改良は新しい指示を受けてから行う。差分・ビルド・診断は`adhoc/v071_audit/`、評価結果と保存出力は`results/analysis/v071/`へ置く。

## 実験後

### 判定

整理版として採用する。事前に定めた静的照合、固定時計での一致、行数減少、通常評価の正常性と時間上限を満たした。高速化は確認できず、通常評価はv059比で96手増（0.467%悪化）だった。提出性能を比較する基準は、保存済みv059を維持する。

### 整理した内容

| 対象 | 変更 |
| --- | --- |
| 共通の概念 | 地形の`Geometry`を`Board`、盤面の`Board`を`State`、`BoardPool`を`StatePool`へ改名した。構築中の操作列を持つ`World`は`ConstructionState`とした。 |
| 記号との対応 | `grid`→`C`、`V`→`cell_count`、地形の`id`→`cell_id`、`dist`→`floor_dist`とした。構築途中の残存数は`E`とした。 |
| 内部表現 | `Word`を`TowerBits`とし、符号化した色を扱う`nest_code`、`top_color_code`などを明示した。データ配置と値の表現を保持した。 |
| 実装用の名前 | 全体で153識別子を統一した。`make_candidates`、`insert_at`、`causal_reorder`などをsnake_caseにした。 |
| 不要なコード | 呼ばれていない`DeliveryDP::evaluate`と`TemporalLNS::eraseToken`、過去の監査専用分岐、常に未指定だった監査出力引数2個を除いた。 |
| 重複とコメント | 終了処理3か所のLOCAL分岐を共通マクロへまとめた。ブログ由来・旧版の追加範囲・古いビルド方法の説明を削り、残すコメントは現在の制約と意図を日本語で記述した。 |

行数は3,787行から3,624行へ163行減った（4.30%）。内訳はコメント105行、空行5行、その他のコード53行である。主な成果は名称と不要記述の整理であり、探索機構の統合・削除による行数減ではない。識別子を具体的にしたため、ソースのバイト数は187,070から188,907へ増えた。

v000と異なる色符号、`ray`の添字、`Move`の格納、時計の更新方法は、挙動を保つため従来どおりとした。元のv059、v000、記号一覧、重要な性質、READMEを変更していない。

### 検証

- GCC 15でLOCAL・非LOCALのビルドに成功した。完全な前処理結果は、改名を戻し、登録済みの整理、assertのファイル名・行番号・式の診断文字列を正規化して照合した。探索に意図しない変更は検出されなかった。
- 固定時計の100入力×2構成、200組すべてで操作列・共通計数・計時値・時計照会数・最終乱数が一致した。計測キー5個の改名と、その辞書順の違いだけを正規化した。全出力を独立再生し、全帰巣と盤面領域4枚の返却を確認した。
- 固定時計の同じ仕事を行う診断全体の合計CPU時間は、LOCALで0.084%減、非LOCALで0.093%減だった。各構成約4〜5秒の合計に対する小差であり、高速化が成立したとは判定しない。通常solverへの追加計測は0である。
- 生成命令の`insert_at`の呼び出し箇所数は、親子ともLOCAL 36、非LOCAL 42だった。この一致だけで関数全体の命令列や速度が等しいとはしない。
- 実行前にソース・検証器・入力・比較対象・基準を凍結し、診断・通常評価の後にもハッシュを照合した。実行結果を受けたsolver変更は行っていない。

### 通常100件の結果

実行IDは`20260930T120052+0900_v071_refactored_26713d`。`tools/in`、LOCAL、時間補正0.80、並列数2で1回評価した。

- v059比で絶対合計96手増、37勝19分44敗だった。
- 全件で公式採点と独立再生が成功し、E=0、100,000操作以内だった。構築・LNS・不正候補・作り直し・診断エラー・盤面領域の未返却は0だった。
- 最大外部時間は1,568 ms、平均は1,558.08 msだった。

固定時計では同じ探索を行えた一方、実時計での完成スコアは一致しなかった。時間により温度・打ち切り・探索経路が変わる実装であり、この1回の差からリファクタリングの恒常的な性能差は確定しない。今後の編集用には整理版を使えるが、スコア改善の比較は引き続きv059の保存結果に対して行う。
