# v075: 候補サイズの指数を0.8から1.6まで広げて調整する

## 実験前

- 仮説: 通常の除去候補に対する匹数の割引を強めると、再挿入の完了しやすさと短縮余地の配分が変わり、絶対スコアをさらに下げられる。根拠はO77、B-94、B-95である。v074の保存結果では探索上限の0.95が最良だったが、さらに上で改善が続くか、連携の取りこぼしで悪化するかは未確認である。
- 変更: v074が保存した最良設定の単一C++を親とし、通常候補の`removal_size_exponent`の許容範囲だけを0.8〜1.6へ広げる。既定値と比較基準は0.95とする。修復係数0.83、乱数幅0.10、開始温度0.70、終了温度0.08、依存拡張の間隔4、再試行待ち係数0.50を固定する。候補生成、順位式、乱数消費、近傍の配分、時間管理、LOCAL時間補正0.80を引き継ぐ。指数の変更はLOCALと非LOCALの双方に有効で、評価はLOCALで行う。
- 機構確認: 親との差分を登録し、LOCALと非LOCALの完全な前処理結果で、基準設定の差がファイル名と許容範囲の宣言だけであることを照合する。基準と上限1.6の両構成をビルドし、全6条件も評価前にビルドして指数が順位式へ接続していることを確認する。制御テストは代役の評価器で行い、ウォームアップの除外、3周目からの測定、条件の重複なし、ケース単位の最大2並列、失敗時停止、選択と保存を検査する。実測では公式採点、全帰巣、既存のエラー計数と盤面領域返却を検査し、候補評価と依存拡張の発動を既存計数から確認する。solver内の追加計測は行わない。
- 採否基準: 今回専用の新規100件で、全件合法、E=0、100,000操作以内、既存エラー計数0、盤面領域返却を満たし、最大外部時間2,000 ms以内の条件から絶対スコア合計が最小の指数を選ぶ。同点なら基準0.95に近い値、さらに同点なら小さい値を選ぶ。同じ新規入力で3周目に測定する0.95より合計が厳密に減れば「今回の調整用100件で改善」とする。未使用入力への改善、最適性、提出基準の置き換えは未判定とする。

## 固定する探索手順

指数は`0.8, 0.95, 1.0, 1.2, 1.4, 1.6`の6条件とする。実行後に候補や範囲を追加しない。ほかの有望な係数を組み合わせる実験はB-96へ残し、今回は指数だけを変える。

1. 公式generatorで今回専用の100件を生成する。通常入力、validation1、v073とv074を含む過去の調整用入力との重複をハッシュで拒否する。
2. 全6条件を先にビルドする。コンパイルの並列数も最大2とする。
3. 基準の指数0.95で100件を2周する。ケース単位の2並列で動かし、合法性を確認したウォームアップの出力を破棄する。スコアと時間を測定のログや順位表へ含めない。
4. 3周目に同じ指数0.95で100件を測定する。残り5条件は固定乱数種7501で並べ替え、各条件を100件ずつ1回だけ測定する。途中の成績による打ち切りは行わない。
5. 全結果、指数順の曲線用CSV、最良指数を既定値にした単一C++を保存する。選択後のC++はLOCALと非LOCALでビルドし、追加評価は行わない。実験ノートと台帳への判定記録もスクリプト内で完結させる。

合計はウォームアップ200ケース、測定600ケースである。同時に測る設定は1つだけとし、その設定のケースを2並列で実行する。solver内では追加の並列を使わない。入力は保存結果の分析に残すが、完了後の評価へ再利用しない。異なる入力集合の旧スコアとは直接比較しない。

## 照合と実行方法

backlog全体とv001〜v074、v800のFront Matterを照合し、直接の親v074と関連するv073の記録を確認した。v074の再開条件であるユーザーの追加検証指示を今回受けた。保存結果の分析で答えられない0.95より上の性能を、新しい入力で検証する。親ソースは`results/tuning/v074/best/v074_multi_tuning.cpp`である。

生成AIを呼ばない自動パラメータ調整を許す`ahc-llm-rules-en.txt`の記述を確認した。全条件、順序、判定方法を起動前に固定する。エラーや中断は記録して停止し、自動再試行しない。AIは起動確認後に応答を終了し、結果の確認は次のユーザー指示を待つ。

```sh
python3 adhoc/scripts/tune_v075.py launch
```

保存先は`results/tuning/v075/`とする。状態は`status.json`、全体ログは`run.log`、計画は`plan.json`、条件別は`trials.csv`、ケース別は`cases.jsonl`、既存計数は`mechanism.jsonl`、曲線用集計は`single_parameter_curves.csv`、最終報告は`report.md`と`best.json`へ保存する。最良設定は`best/v075_size_exponent.cpp`となる。

実行と公式採点には既存の`scripts/eval.py`を再利用し、測定結果は`results/eval_records.jsonl`と`results/score_summary.csv`にも追記する。`score_detail.csv`は更新しない。評価ロックを準備から完了まで保持し、二重起動を拒否する。macOSでは実行中だけスリープを抑止する。

## 起動前の確認

代役の評価器による制御テスト7件を通過した。指数6条件だけが変わること、同一設定の2周を測定から除くこと、3周目からの測定、重複測定の拒否、最大2並列、失敗時の新規投入停止、時間超過候補の除外、選択後のソースと記録の生成を確認した。

GCC 15で基準0.95と上限1.6をLOCALと非LOCALの両方でビルドした。基準の完全な前処理結果は、許容範囲の宣言と診断用のファイル名を正規化すると親と一致した。実時計での出力一致を保証する確認ではない。起動前のsolver実行は0回である。

資料は`adhoc/v075_audit/`の`control_tests.log`、`preflight.json`、`registered_changes.json`、`source.diff`と完全な前処理結果に保存した。起動時刻とPIDは`results/tuning/v075/launch.json`に記録する。

## 実験後

- 判定: 今回の調整用100件で改善。未使用入力と提出基準への効果は未判定。
- 結果: 6条件を測定し、指数0.95の基準に対して合計-22手。最良設定はremoval_size_exponent=1.6、priority_noise_amplitude=0.1、lns_start_temperature=0.7、lns_end_temperature=0.08、dependency_interval=4、regular_cooldown_fraction=0.5。最大外部時間1914 ms。
- 機構確認: 全設定の値・使用式・ビルド引数・前処理結果を照合した。全測定の公式採点、全帰巣、既存エラー計数、盤面領域返却が正常だった。候補評価と依存拡張の発動を各条件で確認し、既存計数をmechanism.jsonlへ集計した。ウォームアップ200ケースは集計から除外した。
- 考察: 同じ新規100件での条件選択であり、係数ごとの最適性や未使用入力での改善は未確認。指数順の保存結果から頭打ちや悪化の範囲を調べられる。ほかの係数との組み合わせはB-96で未着手のまま保持する。
- 保存資料: results/tuning/v075/のbest.json、report.md、trials.csv、cases.jsonl、single_parameter_curves.csv、mechanism.jsonl、plan.json、input_manifest.json、frozen.json。最良設定の単一C++はbest/v075_size_exponent.cpp。
- 再開条件: ユーザーから追加検証の指示がある場合。今回の評価セットは再利用しない。
