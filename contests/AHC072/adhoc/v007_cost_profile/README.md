# v006 / v007 の追加性能診断

ユーザーの「定数倍を大きくせず、できれば小さくして計算量を改善してほしい」という指摘を受けて実施した。solverのコードは変更していない。全件evalの再試行やスコア選択ではなく、既存2実装のホットスポットを調べるためのサンプリングである。

## 方法

`adhoc/scripts/profile_v007_costs.py` で両ソースを同じGCC 15・LOCALの設定でビルドし、小規模の `0001.txt` と大規模の `0019.txt` を各実装で1回ずつ直列実行した。`/usr/bin/sample` の1 ms間隔でスタックを記録した。evalの共有ロックを取得し、スコアCSV・JSONLには追記していない。

- v006 SHA-256: `339a6058d9e53764c0a9ca8801893e34311aed2fef3b31c5eeabd4b8b1808cd4`
- v007 SHA-256: `54a5628e3d01387d461e4eac8d4270f1dc01006d1746e55ae9d98431102d03f6`

両方とも保存evalと同一ソースである。生データは同ディレクトリの `.sample.txt`、実行ログは `.err`、CPU時間とカウンタは `records.json` にある。

## 観測

| 入力 | v006 評価候補数 | v007 評価候補数 | v007 / v006 |
| --- | ---: | ---: | ---: |
| 0001 | 31,472 | 61,928 | 1.97倍 |
| 0019 | 9,200 | 15,201 | 1.65倍 |

保存済みの全件eval比較ではv007の候補数はv006の56.49%だったが、この直列診断では逆転した。したがって、保存evalの候補数減少を、そのままv007の実装の定数倍増大に帰することはできない。CPU割当て・同時負荷・並列実行・サンプリングの影響と、探索状態により候補の仕事量が変わる影響を分離していない。2件だけで全件の性能優位を確定することもできない。

前半探索中のサンプルに対する `Router::build` のinclusiveサンプルの比率は、v007で `0001` が776/923（84.1%）、`0019` が759/825（92.0%）だった。比較対象v006でも88.0%と93.9%だった。主な呼び出し元は踏み台変更の `refit` である。

v007の `Router::move_edge` に入っていたサンプルは2件・5件、LOCAL全体参照照合は各1件だった。この粗いサンプリングでは、これらが実行時間全体を支配している様子はない。メタデータの全体構築は `Router::simulate` に含まれ、コピーや初期化も別箇所で起きるため、差分管理の総費用がこの数字だけで確定するわけではない。

## 判断

「v007は複雑な構造の定数倍で遅くなった」とは、現時点では断定できない。前の報告で、別時刻の固定時間evalから実装自体の速度低下まで確定したように述べた点を訂正する。保存evalで合計Tが95手悪化した事実と、そのスコア基準での棄却判定は維持する。

ユーザーの要件は、計算量の式や走査数だけではなく、管理・初期化・コピーを含む実時間を改善することである。以後の比較では、この費用まで含めた同条件・同一仕事量の確認が必要になる。この診断の実行結果に基づくsolver改変は行っていない。
