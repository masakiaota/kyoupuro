# v800: 全100ケースの長時間参照値をeval viewerへ登録する

## 実験前

- 根拠: ユーザーの2026-09-29の指定、O62、O64〜O67、B-64。v001〜v050のFront Matter、backlog、v047とv050の本文、通常評価とeval viewerの記録形式を照合した。
- 仮説: 保存済みの合法な最良解からv047の継続探索と60秒単位の再出発を並行させ、v050の共同短縮を開始時と終了時に組み合わせると、全100ケースについて短時間版より強い比較用の参照値を収集できる。v047で最初の1分に短縮の72.9%を得て、5分では再出発側の合計が継続側より短かった一方、最終到達先には両方式の差があったことを引き継ぐ。
- 変更: v047のC++と実行管理を土台とし、v050の最大4マス、最大8関連操作、帰巣なしの共同短縮を変更せず取り込む。LNSの前後に各1回適用し、LNS後の処理に予算の0.5%を残す。通常評価の保存解を版横断で独立再生して初期候補を選ぶ。既存の長時間探索10ケースは保存最良解を再利用し、残る90ケースだけを各300秒、単一スレッドの2プロセスで探索する。全100件の公式採点が成功した後にbin名`v800`で登録する。
- 機構確認: 今回はC++のLOCALありとなしのビルド、100入力と保存解の準備、探索を行わない代役による2プロセス制御、中断と再開、100件揃うまでの公開抑止、二重登録の防止、eval viewerの実際の集計関数との接続を確認する。実際のC++探索はユーザーが手動で実行する。実行後に開始時と終了時の共同短縮、継続と再出発、独立再生と公式採点、ケース数と出典を確認する。
- 採否基準: 0000〜0099の100件すべてに合法な全帰巣解があり、準備時の最良保存解より悪化せず、eval viewerの`tools/in`に`v800`が表示されること。経過時間の超過は許容する。90件の各5分と最大2探索プロセスを守り、既存10件に追加探索を行わない。採否は参照値の整備として行い、最適性や準最適性の保証には使わない。

## 実行管理

実行時間は90ケース×5分で約7時間30分、CPU時間は探索だけで約15時間となる。準備、ビルド、採点、保存の時間は別にかかる。同じケースの2探索を並行し、ケースは順に処理する。v047と同じ評価ロックを保持し、通常evalとの重複実行を防ぐ。

再利用する10ケースは0035、0033、0023、0064、0060、0066、0068、0005、0097、0019である。完了済みv047記録を読み、入力のハッシュと保存解を確認する。通常評価にさらに短い保存解があれば、その解を採る。探索対象には0000も含める。

途中経過は実行ごとのディレクトリに保持する。再開時は完了ケースを省き、未完了ケースを保存最良解から5分やり直す。中断したケースの追加時間は記録する。全100件が成功するまでは通常の評価表に登録しない。

再利用ケースの`elapsed`には元の長時間探索の経過時間を残す。新規探索ケースには今回の実時間を記録する。そのため`max_elapsed`は5分を超え得る。コピー時間を探索時間として記録しない。ケースごとの再利用、初期解、追加探索時間、公式採点、最良解の出典は別の記録にも保持する。

## 実装と検証

実装は`adhoc/bin/v800.cpp`と`adhoc/scripts/run_v800.py`である。v047の実行管理を読み込んで使う。v047、v050、通常eval、eval viewerのソースは変更していない。v050の共同短縮部分は元ソースと完全に一致する。READMEは変更していない。

2026-09-29に、GCC 15.1.0でLOCALありとなしのビルドが通過した。準備処理では100入力、計800本の保存初期解を独立再生し、全帰巣を確認した。不正として除外した候補は0本だった。

探索を行わない14件の検証が通過した。v047の8件に加え、v800で90件と10件の振り分け、0000を含めること、変更された入力の拒否、中断ケースの最良解保持、完了ケースを省く再開、2プロセスの制御、未完了時の登録抑止、途中で止まった公開処理の再試行と二重登録防止を確認した。固定の合法手順を公式採点器で確認し、eval viewerの実際の集計関数が100件のv800を読み込み、時間超過を含む参照値によって既存版の相対評価を更新することも確認した。探索の代役は事前に用意した操作列を転記するだけである。

C++の探索は未実行で、実際の短縮量と追加した共同短縮の発動はユーザーの実行後に確認する。検証資料は`adhoc/v800_check/`に保存する。

## 手動実行

プロジェクト直下で次を実行する。開始時に入力と保存解を凍結し、GCC 15で探索コード、Cargoのrelease設定で公式採点器をビルドする。

```sh
caffeinate -i python3 adhoc/scripts/run_v800.py --workers 2
```

ケースごとの予算は300秒に固定している。探索は単一スレッドの2プロセスで、継続側は5分の1回、再出発側は最大60秒のラウンドを繰り返す。ケースの並列実行は行わない。探索だけで約7時間30分を要する。Macの`caffeinate -i`はアイドルスリープを防ぐ。Linuxではこの接頭部分を外す。Python 3.9以降、GCC 15、Cargoを使う。

開始時に`results/long_search/v800/<run_id>/`が表示される。Ctrl+Cで停止すると、探索プロセスを終了させ、保存済みの最良解と履歴を残す。次のコマンドで再開できる。

```sh
caffeinate -i python3 adhoc/scripts/run_v800.py --resume results/long_search/v800/<run_id>
```

再開時は完了したケースを省く。未完了ケースは保存済みの最良解から5分をやり直すため、中断したケースだけ合計時間が増える。再開時も保存したC++実行ファイルを使い、入力や実行管理コードが準備時から変わっていた場合は停止する。強制終了によって前回の探索プロセスが残っている場合も、2プロセスを超えないよう開始を拒否する。

準備だけ確認する場合は次を使う。評価表へは登録しない。この保存先を`--resume`へ指定すれば、本探索を開始できる。

```sh
python3 adhoc/scripts/run_v800.py --prepare-only
```

## 保存先とeval viewerへの反映

100件すべての独立再生と公式採点が成功すると、次の場所へ通常評価と同じ形式で登録する。

| 保存物 | 内容 |
|---|---|
| `results/out/v800/0000.txt`〜`0099.txt` | visualizerで再生する最良操作列 |
| `results/eval_records.jsonl` | bin名`v800`、入力集合`tools/in`の100件。eval viewerと相対評価の正本 |
| `results/score_summary.csv` | 全100件の要約を1行追加 |
| `results/score_detail.csv` | 全100件のスコアを1行追加 |

eval viewerを開いていれば、既存の自動更新でv800が追加される。実行時間超過による除外はない。初めて開く場合は、通常どおり`./scripts/dev_vis.sh`で表示環境を起動し、表示されたURLの`/eval.html`を開く。

実行フォルダには次の記録を保持する。

| 保存物 | 内容 |
|---|---|
| `manifest.json`、`snapshot/` | 凍結したコード、設定、コンパイラ情報、実行ファイル、入力と初期解の出典およびハッシュ |
| `status.json` | 実行全体の状態 |
| `cases/<case>/input.txt`、`seeds/`、`best.txt` | 凍結した入力、最大8本の初期候補、現在の最良解 |
| `cases/<case>/status.json` | 再利用の区別、最良手数、出典、追加探索時間、各試行への参照 |
| `cases/<case>/attempts/attempt_*/` | v047と同じ形式の継続側と再出発側のログ、改善前後の操作列、時間別CSV |
| `provenance.json` | 最終100解の出典、ハッシュ、公式採点、再利用時間、今回の探索時間 |
| `publication.json` | 評価表への登録状況。同じ実行の再登録で行を重複させない |

通常の`eval.py v800`はこの実験の入口ではない。保存初期解の指定、2探索の管理、既存10件の再利用、全100件の登録をまとめて行うため、上記の`run_v800.py`を使う。
