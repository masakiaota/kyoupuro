# 床数に合わせたStateのコピー容量の比較

## 結論

Apple M3/GCC 15.1での今回の比較では、床数ぴったりの領域を事前確保し、コピー先を再利用する方式を推奨する。実盤面のコピー＋操作の主6条件中4条件で32刻み固定配列より3.24〜12.10%短時間、2条件で同程度だった。平均データ量も7.26%少ない。

全サイズでぴったり配列が速いわけではない。32・64マスなどの小さい固定長や、127・191マスのコピーだけでは固定配列が速い例があった。実入力100件の床数は96〜368マスである。

| 保存先の状態数 | コピー＋1手の短縮率 | コピー＋4手の短縮率 |
|---:|---:|---:|
| 1 | 3.24% | 0.93%（同程度） |
| 64 | 12.04% | 1.28%（同程度） |
| 8192 | 12.10% | 5.81% |

主指標は通常99件を等重みで平均したCPU時間の6区間中央値である。3%以上短く、6区間中5区間以上で速いことを事前に優位の基準とした。手作り0000は主集計から分けている。

## 比較した実装と処理

| 方式 | 1状態の領域 | コピー |
|---|---|---|
| 32刻み固定 | 床数を32単位で切り上げた `array<Tower, capacity>`。上限400 | 通常の代入 |
| ぴったり | 一度確保した連続領域を、実行時の床数ごとに区切る | 床数×4 byteの `memcpy` |
| 400枠固定 | 現在のv000と同じ `array<Tower, 400>` | 通常の代入 |

両方式とも、保存先の確保・解放・ゼロ初期化は計測外である。ぴったり配列の区画の添字計算は計測に含む。

- `tools/in/0000.txt`〜`0099.txt` と保存済みv025の出力を再生し、各8時点の途中盤面と次の4手を使った。コピー後に0手・1手・4手を適用した。
- 人工の41サイズでもコピーだけを測った。床数8・180・185・399・400と、32〜384の32倍数の前後1マスである。人工サイズは実盤面の集計に混ぜていない。
- コピー先は1・64・8192状態の循環領域とし、順番に更新した。コピー元は各ケース8盤面を循環した。
- 各区間はウォームアップ16,384回と計測131,072回。3方式の全6順序を使い、全18,414区間を1プロセスで測った。測定後の実装修正・再測定・区間の除外は行っていない。
- `build_solver.sh` の非LOCAL設定とv000の `O3,unroll-loops,fast-math` を使用した。環境と全フラグは [environment.json](environment.json) に記録した。

## 検証と結果の限界

独立した色配列による保存操作20,977手の照合と、約845万件の盤面照合を通過した。未定義動作検査も通過し、全計測区間で3方式の結果が一致した。

生成命令では、固定容量32・64のコピーは直接展開され、固定容量96以上とぴったり配列は `memcpy` 呼び出しだった。実入力はすべて固定容量96以上に入る。操作適用は1手では全方式とも共通関数を呼び、4手では全方式とも展開されていた。計測する反復内に領域確保・解放・ゼロ初期化はなかった。

この比較は、コピー量・配置・添字計算を含む実装全体の差である。それぞれの寄与や、実際の探索での不規則な参照の費用は分離していない。コピーのたびにvectorを新規確保する使い方、AtCoderのCPU、solver全体の速度・スコアは測っていない。

経過時間にOSの待ち時間が含まれるため、登録どおりCPU時間を主指標にした。経過時間/CPU時間が1.1を超える106区間も除外していない。CPU周波数やキャッシュによる変動は残る。
