# v030: 床数に合わせた State のコピー容量を比較する

## 実験前

- 根拠: O31では塔の表現と処理内容によって優劣が変わり、v023ではコピー量の削減が処理全体の明確な短縮につながらなかった。ユーザーから、32マス刻みの固定配列と床数ぴったりの配列を、複数の床数で現実的に比較する指示を受けた。
- 仮説: 床数を32マス刻みで切り上げた固定配列は定数長コピーと固定幅の添字計算、床数ぴったりの連続配列はコピー量と保存量の削減に有利である。両者の差は床数、同時に保持する状態数、コピー後の操作数によって変わり得る。
- 変更: 共通土台v000のTowerとapplyの処理を用いる補助ベンチマークを `adhoc/bin/v030_state_capacity_bench.cpp` に作る。比較対象は固定配列、実行時の床数に合わせた連続配列、現状の400枠固定配列である。全方式の保存先を計測前に確保し、コピー中の確保・解放・ゼロ初期化を除く。共通土台を参照した独立した補助計測のため `parents: []` とし、solverとv000は変更しない。計測する処理はLOCAL・非LOCALで同一であり、非LOCALビルドを測定する。
- 機構確認: 保存済み操作列の合法性と帰巣数を独立した色配列で照合する。途中盤面、コピー後1手・4手の盤面と帰巣数が全方式で一致すること、コピー元が変わらないことを計測外で確認する。全計測区間の結果を照合する。コピー削除防止の空アセンブリを全方式へ同じ位置に入れ、生成命令でコピーと操作が残ることを確認する。未定義動作の検査は計測前に別ビルドで行う。
- 採否基準: 通常99件のケース等重みの平均CPU時間を各区間で算出し、6区間の中央値を主指標とする。保存先1・64・8192状態と操作数1・4の6条件を主比較とし、3%以上短く、6区間中5区間以上で同じ側が速い場合を明確な優位とする。条件によって勝敗が変わる場合は用途別に推奨する。3%未満の差は今回の計測では同程度と扱い、管理の簡単さと容量を判断材料にする。単独コピーと人工の床数は差の説明用に使い、そこだけで主比較の判定を変更しない。

### 固定する比較条件

- 実盤面: `tools/in/0000.txt`〜`0099.txt` と保存済み `results/out/v025_fast_math/` を再生する。各操作列から8等分に相当する8時点を採り、そこから連続する4手を保持する。末尾まで4手に満たない位置は4手を確保できる最後の位置へ寄せる。通常99件を主集計、手作り0000は別に示す。床数の分布は96〜368、中央値185である。
- 境界の床数: 8、180、185、399、400と、32〜384の各32倍数の前後1マスを使う。人工盤面ではコピーだけを測る。通常の入力分布と混ぜて集計しない。
- 固定配列: `min(400, ceil(cell_count / 32) * 32)` 要素の `array<Tower, capacity>` をコンパイル時に用意し、通常の代入でコピーする。
- ぴったり配列: 一度確保した `vector<Tower>` を床数ごとの連続区画に分け、実行時に決まる床数×4 byteを `memcpy` する。区画の添字計算も計測に含める。個別vectorの毎回の確保・解放を比較に混ぜない。
- 比較基準: `array<Tower, 400>` を通常の代入でコピーする。固定配列と同じ処理を使う。
- 保存先は1、64、8192状態の循環領域。処理はコピーだけ、コピー＋1手、コピー＋4手。入力参照は各ケースの8盤面を循環する。これはコピーと盤面操作の費用を測るもので、探索全体の時間やスコアを測るものではない。
- 1区間131,072回、各区間直前に16,384回をウォームアップする。3方式の全6順序を1回ずつ使う6区間を、同じプロセスで実行する。区間数と処理回数は測定結果で変更しない。全区間を保存し、外れ値を後から捨てない。
- Apple M3、GCC 15.1、C++23、既存build_solver.shとv000の最適化指定を用いる。単一スレッドの補助計測とし、`results/.eval.lock` を取得して他の評価との重複を避ける。solverのevalを実行せず、既存のLOCAL時間補正・既定並列数・評価ログを変更しない。
- LOCAL・非LOCALをビルドし、ソースと入力・保存出力のハッシュ、環境、生成命令、検証件数、生のCPU時間と経過時間を `adhoc/v030_state_capacity/` に保存する。測定結果を見て方式を修正・追加測定せず、結果と推奨を報告する。v000への反映は今回の範囲に含めない。
