# v045: 地域の出口と共用幹線を固定する混載輸送

## 実験前

- 仮説: 周辺の個体を色によらず地域の出口へ集め、巣を結ぶ幹線を共用すると、混載の集荷距離と経路の分散を抑えられる。幹線上の初期個体を周辺輸送の終了まで固定すれば、設置操作なしで踏み台を繰り返し使える。この利益が、出口への集荷、固定経路の遠回り、最後の踏み台回収の費用を上回る。
- 根拠: backlog O2、O8〜O10、O16、O18、O57とImportant Properties 3、4、6〜9。ユーザーから、解全体へ強い制約を置く構成を新しい実験として検証する指示を受けた。
- 変更: v001の最大7匹の混載便、色列の両端から帰巣する配送DP、便の分割・集荷順の焼きなましを継承する。床上の自由な経路を、入力から一度だけ決める木、地域ごとの出口、周辺輸送から幹線回収への固定した順序へ置き換える。v039の再挿入探索へ局所近傍を足す実験ではない。v003の固定踏み台、v009の外側優先、v018の帰巣延期は照合済みであり、今回は地域・経路・維持期間を同時に拘束する独立構成を検証する。
- 機構確認: 下記の固定した小規模照合、0019の出力監査、全100件の独立再生を行う。予測した便の費用と実際のTが一致し、全件で合法かつE=0であることを必須とする。周辺個体が担当出口を通ること、周辺全員の帰巣まで幹線の初期個体が動かないこと、処理済み地域へ再進入しないこと、幹線の配送が指定した木から外れないことを検査する。通常99件の合算で、地域内の混載便、幹線の初期個体を使う2マスジャンプ、同じ初期個体の反復利用がそれぞれ1回以上あることを必須とし、ケース数と回数も報告する。
- 採否基準: `tools/in`全100件をLOCAL、既定の2並列で1回評価する。全件成功、機構確認通過、最大経過時間2,000 ms未満、通常99件の合計Tが保存済みv039の20,739手未満、全100件の合計Tもv039の20,782手未満なら採用する。v001とv003との差も報告するが、この採否基準は動かさない。通常99件で平均200手以下に届いたかを別途報告する。複数の構造制約を一つの構成として変えるため、個々の制約の単独効果は判定しない。

### 固定する構造

1. 全初期個体からの床上距離の合計が最小の巣を根に選ぶ。同点なら自身の色の個体数が多い巣、床IDの小さい巣を優先する。
2. 根への最短路木を作る。親候補が複数なら、根までの経路上にある初期個体が多い候補、床IDの小さい候補を優先する。
3. 全巣から根への木の経路の和を幹線とする。幹線外の各床には、根へ進んで最初に出会う幹線の床を出口として割り当てる。同じ出口の床を一つの地域とする。
4. 周辺の便は同じ地域の個体だけで作り、最大7匹とする。集荷は木上の1マス移動を使い、残った荷物を必ず出口へ運んでから配送する。幹線上の初期個体は元の位置に1匹の踏み台として保持し、配送で1〜2マスのジャンプを使う。自分の巣で下端を帰巣させる発射では、その匹数に応じた距離も扱う。
5. 地域は出口の根からの深さが大きい順に完了させる。配送は幹線内の木の辺を連続して通る直線に限る。他地域への立ち寄りを認めない。
6. 周辺個体が全員帰巣した後、幹線上の初期個体を回収する。この回収でも混載便を使うが、便どうしの費用を独立にするため、他便に属する残存個体による長距離ジャンプは使わない。1マス移動と、自分の巣で下端を帰巣させる発射を使う。

幹線への追加の踏み台設置、最後に残す色の固定、木そのものの探索、構築後の再挿入・局所修復は今回の変更に含めない。群分けと集荷順だけを焼きなましで最適化する。探索終了は共通のPROGRAM_TIME_LIMIT_SECの96.5%とし、残りを復元と検査に使う。新しい構成はLOCAL・非LOCALの両方で有効である。

### 実行前の静的確認と実行順

- 入力だけの集計では、通常99件すべてに2匹以上いる地域と幹線上の初期個体があった。幹線上の初期個体数の平均は16.73匹、最大地域の初期個体数の平均は15.74匹だった。解や操作列を生成した測定ではない。
- LOCAL・非LOCALをビルドし、ソースと入力のハッシュを保存してから解プログラムを実行する。LOCALでは共通の0.80倍の時間補正とTraceStatsを使う。
- 配送DPは0019の固定幹線で、長さ1〜3の固定した色列と複数の始点について、全遷移を直接列挙する探索の最短費用と比較する。通常輸送の踏み台あり・回収の踏み台なしの両方を調べる。
- 続いて0019を1回実行し、個体IDによる不変条件と独立した出力再生を確認する。失敗なら中断して結果を報告する。通過したら同じソースの全100件評価を1回行う。評価パイプラインのウォームアップは既定のままとする。
- 解プログラムの最初の実行後は、実行結果を根拠にコード・パラメータ・仮説を変更しない。失敗した場合も実装を修正して再実行せず、結果を記録し、新しい指示を待つ。
