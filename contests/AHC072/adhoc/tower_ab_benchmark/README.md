# 塔の案A・案Bの比較

## 計測前に固定した条件（2026-09-27）

ユーザーの依頼に基づき、v000の塔の保存形式を比較する。これは保存済み操作の再生とデータ構造の補助計測であり、解を探索・出力するsolverの実験ではない。v000と各solverは変更しない。

- 案A：1マスを `uint32_t` で保存する。色は `c + 1`、高さは `bit_width` から取得する。反転は4 bitの入れ替え、byte swap、位置合わせを使い、段数のループを使わない。
- 案B：色の `uint32_t[400]` と、高さ・向きの `uint8_t[400]` を保存する。色は `c` のまま。反転は向きの切り替え、向きの異なる非空の塔への連結では移動部分の色順をそろえる。
- 高さが既知の箇所では、両案とも既知の値を再利用する。帰巣は色との差のビット列から上端の同色部分をまとめて除去する。計測する操作に入力検証・assert・動的確保を入れない。
- 根拠：ユーザーのコピー・上下端操作・反転への要求、保存ソースv013の部分取り出しを使い回す候補列挙、v021の32 bit盤面、backlogのO14・O15。
- データ：v001_mixed_deque、v013_unified、v021_paired_event_lnsの保存済み出力。通常生成0001〜0099の297操作列を測定する。0000も正しさの検証に使うが、時間の集計には含めない。
- 途中盤面：各操作列の `floor(r * T / 8)`（r=0..7）時点。案Bは最初から再生した向きフラグを保持する。
- 正しさ：固定長の色配列を使った独立実装と全操作後の状態を照合する。途中盤面の合法手についても全色・高さを照合する。高さ0〜8、全切断位置、両方向、上下端操作も別に検証する。

### 計測項目

1. 実操作再生：初期盤面をコピーし、保存済みの全操作を適用する。各版を別々に測り、1区間512周とする。
2. 合法手列挙：途中盤面から全合法手を列挙する。出発点・kごとの取り出しと反転を使い回し、連結と帰巣を評価する。各版を別々に測り、1区間32周とする。
3. コピーして1手進める：途中盤面の全合法手に対して、400マスの状態全体を複製し、1手適用して評価する。複製先を64状態、8192状態の循環領域に保存する条件をそれぞれ測る。1区間8周とする。
4. 単独操作の補助計測：途中盤面にある非空の塔について、反転、および下端への追加と上端からの取り除きを測る。後者は高さ1〜7のみ。1区間1024周とする。

同じ実行ファイル・1プロセス内で各項目を計測する。1周のウォームアップ後、8区間をA→B、B→Aの交互順に実行する。処理回数は時間で変えない。CPU時間と経過時間、各区間の結果を全て保存する。コンパイラが計算やコピーを消さないよう、結果を空のインラインアセンブリへ渡す。照合用の走査は計測外に置く。

環境はローカルのApple M3、GCC 15.1.0、既存build_solver.shの非LOCAL設定（C++23、-O2、-march=native）。solverの評価と異なり、並列処理を行わない。

### 判定

案A・Bの各8区間の中央値と区間ごとの比を比較する。実操作再生・合法手列挙・コピーして適用する処理を主な判断材料にし、単独反転だけで採否を決めない。項目によって勝敗が変わる場合は条件別に結論を出す。AtCoderのCPUでの速度やスコアへの効果は、この計測から断定しない。計測結果を見て実装・条件を変更して再測定しない。

## 結果

**v000の標準表現には案Aを推す。** ユーザーが重視した盤面のコピーと、途中盤面からの候補生成で案Aが速く、保存量も20%少なかった。操作列を順に適用する用途では案Bが速かったため、すべての用途で案Aが勝つという結論ではない。

### 主な計測値

下表は1操作または1候補あたりのCPU時間で、8区間の中央値を示す。操作再生と合法手列挙は、区間ごとに3版のCPU時間と処理回数をそれぞれ足してから割った。

| 処理 | 案A（ns） | 案B（ns） | 所要時間の差 |
|---|---:|---:|---|
| 保存済み操作の再生 | 4.215 | 3.365 | Bが20.2%短い |
| 途中盤面からの合法手列挙 | 4.657 | 6.740 | Aが30.9%短い |
| 盤面のコピー＋1手適用（保存先64状態） | 25.415 | 32.292 | Aが21.3%短い |
| 盤面のコピー＋1手適用（保存先8192状態） | 28.360 | 43.368 | Aが34.6%短い |

盤面の塔を保存する領域は、案Aが1,600 byte、案Bが2,000 byteだった。状態を8192個保持する場合は、それぞれ12.5 MiBと15.625 MiBになる。地形などの共通データはコピーしていない。

版ごとの中央値も、再生ではB、列挙ではAが速かった。再生でのBの短縮率は11.4〜25.5%、列挙でのAの短縮率は16.6〜39.3%だった。3版を合算した比較とコピーの2条件では、8区間すべてで表と同じ側が速かった。

### 差を理解するための材料

案Bは、保存済みの75,495操作のうち18,996操作（25.2%）で連結時に色順を調整した。残りでは、その並べ替えを避けられる。高さを直接取得できることも案Aとの違いであり、向きフラグ単独の効果は分離していない。

候補列挙では、案Aは出発点とkごとに反転した部分を作り、全移動先で使い回す。案Bは連結先の向きを扱い、最上色の読み出しも向きを解釈する。今回の計測では、これらを含む候補生成全体で案Aが速かった。

コピーして適用する処理には、保存量と生成コードの両方の差がある。生成命令には、案Aで1,600 byte、案Bで2,000 byteの `memcpy` が残っていた。さらに、この処理内では案Aの `apply` はインライン化され、案Bの `apply` は関数呼び出しとして残っていた。コピー量だけが時間差の原因とは断定できない。両案を強制インライン化した場合は測定していない。

単独操作の補助測定は、反転でAが0.501 ns、Bが0.556 ns、下端への追加と上端からの除去でAが0.628 ns、Bが1.094 nsだった。ただし、これは値の読み出しと書き戻しを含む実装の測定である。案Bの反転でも色列を書き戻す命令が残っており、`meta[p] ^= 16` だけの命令コストを測った値ではない。この補助値を、向きフラグ自体が遅いという根拠にはしない。

### 正しさと測定の範囲

- 高さ0〜8、両方向、上下端操作、帰巣、全切断位置を独立した色配列実装と照合した。連結の単体検証は208,896通りだった。
- 手作りの0000を含む300操作列、75,645操作の状態変化が一致した。計測に使った297操作列から2,376盤面を採り、504,162通りの合法手も照合した。
- 合法手列挙とコピー後の評価値は、独立実装から計算した値と一致した。全160計測区間でA/Bの計算結果が一致した。
- 未定義動作の検査は `-fsanitize=undefined -fsanitize-undefined-trap-on-error` で通過した。
- 一部の区間には待ち時間が入り、経過時間がCPU時間を大きく上回った。CPU時間にも変動があったため、8区間の中央値を用い、外れた区間も削除せず保存した。各区間の値と比は集計ファイルに残した。
- 結論はApple M3と既存の非LOCALビルド条件で、ここに保存した実装を使った比較である。AtCoderのCPU、別の最適化設定、探索全体のスコアへの効果は未測定である。

計測後に比較対象のコードを変更したり、再測定したりしていない。v000への反映は行っていない。
