## 新しい構築の考え方

v105はNNが完成列を1本作り、その後でLNSをかける構成だった。v312は、NNの途中盤面からもアルゴリズムで完成列を作る。

最初にv210の同色集荷木（決定的なvariant=0）で全帰巣の完成列を確保する。この処理は常に実行し、NNが失敗したときだけ別の解法へ飛ぶ隠れたfallbackにはしない。以降、完成した操作列の実手数でincumbentを更新する。

NNはv311高速化単独と同じ特徴、26,866パラメータ、合法手、同点処理、盤面重複回避を使う。残存数が初期の3/4、1/2、1/4、1/8を初めて下回る時点で、その盤面をコピーし、配送DPで残りを全帰巣させる候補を作る。1回で複数の境界を越えたら、同じ盤面の再評価はしない。

DPにはv210のDeliveryDPを使う。各段階で最も高い塔を優先し、同高さなら巣から遠い塔を選ぶ。選んだ1塔を分割も含めて帰し、変わった盤面で次の塔を扱う。積み順、支持、帰巣前の高さ8、出発点と着地点の帰巣を保持する。同色を永久結合する制限は追加していない。

初期構築の通常期限はPROGRAM_TIME_LIMIT_SECの22%。DP1候補の上限は同1%。NNの中断時には最後の盤面から追加1枠だけ完成を試す。期限に達した未完の候補は数えて破棄し、既存の完成列を保持する。NNが完走した場合は、その完成列も比較する。

LNSへ渡すのは最短の完成列1本である。前回の複数初期解育成をそのまま復活させたのではなく、生成段階でNNと配送DPを接続した比較だ。NNの途中盤面を評価しても、そのNN経路自体へ書き戻さない。重み更新は行わない。

## 帰巣保証の範囲

保証に使うのはNNの価値予測ではなく、「現在保持している操作列を再生すると全帰巣する」という不変条件である。最初の木構築が完成し、その後は全帰巣を確認した列だけに置き換える。途中DPが任意の盤面を必ず解けるとは仮定しない。固定背景で進めない候補も明示的に計数している。

木構築は一色ずつ処理する。各セルの未処理色は最初の1匹までで、処理中の色だけをその上へ積む。容量が不足すると親側の同色を先に送り出す。各操作で処理色の個体が巣を根とする木の親側へ進み、根では帰巣するので、その色の木上の深さの総和が厳密に減る。木は閉路を持たず、容量を空ける再帰も根側へ進むため終了する。

操作数についても、色iのb_i匹が互いに異なる初期セルにいることから、木の深さ総和はb_i(2*cell_count-b_i-1)/2以下である。入力制約のcell_count<=400、4<=K<=12、密度0.65未満でこの上界を最大化しても98,246手以下になる（緩い上界であり、実測の典型手数ではない）。移動は必ず深さを少なくとも1減らすため、初期完成列は100,000操作以内となる。対応する整数範囲確認をresults/tree_bound.jsonへ保存した。

この議論は公式の初期状態を仮定したアルゴリズム上の性質である。ハードウェア障害、実装バグ、AtCoderでの2秒以内の出力までを数学的に保証するものではない。実際の時間と合法性は別に評価した。

## 初期解の短縮と完成スコアを分ける

inではNN自身が100件とも完走した。したがって、本測定で未完NNを救済したことが改善の理由ではない。

初期解の短縮合計444手のうち、NN完成列と木構築を比べた分が356手、さらに途中DPで短くできた分が88手だった。途中DPの厳密な利益があったのは40件である。これは完成した初期解同士の分解であり、最終LNSの利益へ足し算できない。

最終出力で残った主対照との差は44手だった。初期解の大きな差をそのまま「今回の完成スコアを大幅改善した」とは扱わない。とくに、0005では木構築864手がNNの1,155手より短く、その後のLNSでv312が538手、主対照が607手となった。このケース単独の69手短縮が全体44手短縮を上回るので、他ケースの悪化を隠さない。

inの新構築ではDPを397回試し、323回完成、71回を手数下界で枝刈り、3回は固定背景の到達不能、0回は期限到達だった。最終的な初期列の由来は、木構築4件、途中DP70件、純NN26件だった。同手数の場合は先の候補を保持するため、DP由来の件数とDPの厳密な短縮件数は一致しない。

構築費用は主対照より平均4.927ms増えた。初期解の質、初期列の探索しやすさ、LNSの残り時間が変わるため、最終差をどれか一つの因果効果と断定しない。

## 検証と再現条件

全600本をsolverコードを共有しないPythonとC++のリテラルな塔配列で再生し、合法性、全帰巣、T/E/Sの一致を確認した。公式Rust採点バイナリは実行していない。

6入力でNNを0手、16手、通常上限の3条件に制限した計18検査も全帰巣した。0手と16手の計12条件では、NNの完走がなくても完成列を保持したことを確認した。盤面領域が全返却されることも診断した。

v105、v311高速化単独、v312の埋め込み重みは30,800byteのpackedデータで全バイト一致。パラメータ数は26,866。添付のモデルJSONとcheckpointのSHA256も引き継ぎ記録と一致した。高速推論の関数とLNS本体のソースはv311から不変で、LNSの完全な前処理結果もLOCALと非LOCALの両方で一致した。今回は高速カーネルの新規変更や追加のPyTorch学習を行っていない。

コンパイラはGCC14.2.0、C++23、LOCALなし、2並列。3条件を同じCPU上で連続して実行し、先行順を6通りで循環させた。先頭入力で各版1回のウォームアップを集計から除外し、各入力各版の本測定は1回。LOCALありもビルドし、ウォームアップを別に保存した。

時間式は親と同じ。非LOCALのPROGRAM_TIME_LIMIT_SEC=1.90、通常LNS終了は約1.850777秒、終了処理の期限は1.880秒である。NN、木構築、コピー、DP、初期解比較も同じ時計に含まれる。最初の部分問題実行前に条件とソースをSHA256で固定し、実行後のsolver変更や調整はない。

## 再現

必要なものはLinux、GCC、Python 3、NumPyと、in/validation1を含む添付プロジェクトである。

```bash
# この一式のルート。記録済み結果は別名で保持する。
mv results results_recorded
mkdir -p results bin
cp results_recorded/historical_score_detail.csv results/
CXX=g++ python3 scripts/build.py
python3 scripts/evaluate.py --root /path/to/v105_astra_pro_unpacked
python3 scripts/analyze.py
```

単一提出形式のビルドは次のとおり。実行ファイルは配布せず、その環境でコンパイルする。

```bash
g++ -std=gnu++23 -O2 -Wall -Wextra -march=native -pthread \
  -ftrivial-auto-var-init=zero -fopenmp -DATCODER -DONLINE_JUDGE -DNOMINMAX \
  src/v312_certified_neural_constructor.cpp -o v312
./v312 < /path/to/tools/in/0000.txt > out.txt
python3 scripts/validate.py /path/to/tools/in/0000.txt out.txt
```

make_candidate.pyは今回の生成作業の記録で、再評価には不要である。write_report.pyも今回の初期解分解を使う報告生成用であり、上の再評価手順には含めない。CPU、GCC、実時間での打切りが変われば、同じ手数を再現する保証はない。
