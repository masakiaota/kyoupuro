# v022の高速化余地を判断する追加分析

ユーザーから、完成版の2手差は誤差として扱い、新近傍を高速化して試行数を保つ方針が有望か、という質問を受けた。solverを変更せず、保存ログと保存出力から判断材料を集めた。

## 保存ログで確認したこと

通常99件の試行数は749,261回から639,025回へ減った。ただしv022は、候補を拡張できなかった59,271回と直近に試した集合8,407回を試行前に省く。探索中の例外終了と候補が空になる終了がないことを踏まえて省略分を加えると、反復数は706,703回であり、減少は約5.68%である。1匹の再挿入関数の呼び出し数も約8.56%減った。候補の規模と処理内容が異なるため、どちらの数もそのまま計算速度の比率とはならない。

新近傍は後半の時間の約18.70%を使い、後半の最良解短縮量の約8.02%を占めた。短縮を見つける時期と他の近傍への影響があるため、この比率だけで効率の優劣は判定できない。除去成功後の75.49%で全個体の再挿入が完成しなかった。失敗した何匹目に時間を使ったか、手数上限など何が原因だったかは未計測である。

## 候補拡張の補助計測

`adhoc/bin/profile_v022_candidates.cpp` はv022の保存済み最終出力を再生し、既存の候補集合を作る。各候補のコピーと `growDependency` の呼び出しを100回ずつ測った。最適化探索、経路修復、再挿入は呼ばず、新しい操作列も出力していない。この反復は小さな処理の計時であり、solverの再評価ではない。

通常99件の平均は1候補あたり約0.249マイクロ秒だった。ケース別の平均時間に実際の拡張選択回数を掛けると、1ケース平均約0.243 msに相当する。比較用に、新近傍全体の既存計測は平均209.34 msである。実際の探索途中の操作列と種の選択頻度は再現していないため、0.243 msは本番の内訳を計測した値ではない。候補を拡張するループだけを速くして得られる利益は、この補助計測では小さい。

## 判断

新近傍が改善解を見つける機構は成立しており、計算負担を減らす方針には検証の価値がある。ただし、高速化すればv021を安定して上回るとはまだ判断できない。次に調べる対象は、修復と再挿入の費用、特に再挿入を完了できなかった候補に費やした時間である。共通の再挿入器を速くする変更はv021にも効く可能性があるため、v022専用の利得として扱わない。

## 保存資料

- `saved_log_analysis.json`：保存ログから計算した回数と比率。
- `candidate_profile.csv`：100ケースの候補生成計時。case0000は通常99件の集計から除外した。
- `candidate_profile_summary.json`：補助計測の集計と換算方法。
- `profile_build.log`：GCC 15、C++23、LOCALでの補助プログラムのビルド記録。

```bash
SDKROOT="$(xcrun --show-sdk-path)" MACOSX_DEPLOYMENT_TARGET=15.0 \
  ./scripts/build_solver.sh profile_v022_candidates
./target/release/profile_v022_candidates "$PWD" > adhoc/v022_cost_analysis/candidate_profile.csv
```
