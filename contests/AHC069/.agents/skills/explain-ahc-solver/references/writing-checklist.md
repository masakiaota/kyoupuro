# 解説本文の点検

このファイルは、Phase 2 で subagent に渡す前の解説本文を確定するために使う。
役割は、文章をきれいにすることだけではない。
解説本文が AHC solver の再実装に使える状態かを確認し、検証対象として固定することである。

本文は `japanese-tech-writing` に従う。
この点検で意味を変える編集をした場合、その本文を新しい検証対象にする。
subagent 検証後に意味を変える編集をした場合は、別の新規 subagent で再検証する。

## 説明の順序

- 問題設定が solver に課す制約を最初に説明しているか。
- その制約に対して、solver がどの構造で対処するかを先に示しているか。
- 実装細部より前に、候補生成、評価、選択の流れを説明しているか。
- 近似評価と本評価の役割を分けて説明しているか。
- 時間管理を、単なる定数ではなく、探索量と安全余白の設計として説明しているか。
- 出力形式や実装上の注意を、再実装に必要な範囲に絞っているか。

## 文体

- 一文一行になっているか。
- 見出しが「概要」「実装」のような広すぎる語だけで終わっていないか。
- 「重要なのは」「核心的」「深掘りする」のような空句を使っていないか。
- 実装名や関数名を、読者が追う必要のあるものだけに絞っているか。
- 確認していない効果を、確認済みであるかのように断定していないか。
- 比喩や口語で、処理の条件や因果をぼかしていないか。

## 内容

- 「何をするか」だけでなく、「なぜそれが必要か」を書いているか。
- 削ると壊れる処理について、壊れる理由まで説明しているか。
- Phase 1 で削除できた処理を、本文に残していないか。
- Phase 1 で削除できなかった処理を、必要なら理由とともに説明しているか。
- 偶然良かった seed や特定ケースへの過適応を書いていないか。
- 候補数や比率を書く場合、環境依存の調整値ではなく、再実装に必要な範囲として説明しているか。
- subagent が誤読した箇所を直す場合、本文のどの説明に反映したかを確認しているか。

## 検証対象としての固定

- この本文が、subagent に渡す検証対象そのものか。
- 未点検の本文を subagent に渡していないか。
- 検証後に手順、条件、因果、候補選別、本評価へ回す条件、パラメータの意味を変えていないか。
- 検証後に意味を変えた場合、別の新規 subagent で再検証する前提になっているか。
- 最終報告で、subagent が読んだ本文と最終本文の関係を説明できるか。

## 検証結果の書き方

検証結果は、本文の再現性を支える範囲で書く。
過剰なログ列挙は避ける。

必要な場合は、評価コマンド、成功ケース数、`total_avg`、試行錯誤回数を書く。
失敗から得た曖昧点は、検証報告として残すだけでなく、本文のどの説明へ反映したかまで確認する。
反映した本文は新しい検証対象である。
