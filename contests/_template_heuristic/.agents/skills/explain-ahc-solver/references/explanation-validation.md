# 解説を作り、再現性を検証する

このフェーズの目的は、Phase 1 で抽出した本質を、人間が読める解説に変えることである。
ただし、読みやすいだけでは足りない。
事情を知らない subagent が、その解説だけから solver を再実装し、目標スコアを超えられることまで確認する。

Phase 1 の完成 solver は、このフェーズを通じて固定された正本かつベンチマークである。
subagent solver は、解説の品質を測るための使い捨てプローブである。
subagent solver を改善したり、次の検証のベースにしたりしない。

## 入力

- Phase 1 で作った簡素化 solver
- Phase 1 で記録した採用削除と不採用削除
- 問題文
- `notes/notations.md`
- `src/bin/v000_template.rs`
- `japanese-tech-writing`
- 目標スコア
- 出力する解説ファイル名
- subagent が作成してよい再現 solver 名

## 出力

- 解説 Markdown
- subagent 検証の結果
- subagent が作成した再現 solver
- subagent が曖昧だと感じた点
- 解説へ反映した改善点
- 最終解説が検証対象本文と同一であることの確認

## 成功条件

このフェーズは、次の条件をすべて満たすまで続ける。

- 解説本文が `japanese-tech-writing` に従っている
- 解説本文が、人間にとって読みやすい
- 解説本文が、何をするかだけでなく、なぜ必要かを説明している
- 実装細部を書きすぎず、本質のアイデアを中心にしている
- subagent が v000 以外の既存 solver を読まずに再実装できる
- subagent の再実装が目標スコアを超える
- subagent の結果を、事前に固定した Phase 1 の完成 solver の評価結果と比較している
- subagent の成功が過度な試行錯誤や評価後チューニングに依存していない
- subagent solver を修正、再評価、次の検証のベースとして利用していない
- 検証に使った本文と最終本文が同一である、または意味を変えない編集だけである

## 解説を書く

まず Phase 1 の成果を読む。
残った構造、削れた処理、削れなかった処理、時間管理、不採用の仮説を確認する。

解説では、実装順ではなく、読者が方針を再構成できる順に並べる。
最初に問題のどの圧力へ対処するかを書く。
次に、その圧力に対してどの構造を置くかを書く。
その後、候補生成、近似評価、本評価、時間管理を書く。

解説は、実装を写経させる文章にしない。
ただし、再現に必要な判断は落とさない。
たとえば、推定値だけで候補を捨てると壊れるなら、最後に本評価で選ぶ理由を書く。

説明では「何をするか」だけで終えない。
その操作がなぜ必要か、削ると何が壊れるか、推定と本評価の役割がどう違うかを書く。

seed、特定ケース名、たまたま効いた候補数、環境依存の時間比率は、再現に必要な場合だけ書く。
検証セットへの過適応に見える情報は本文に入れない。

## 文章を点検する

subagent に渡す前に、`japanese-tech-writing` と `writing-checklist.md` で本文を点検する。

未点検の本文を subagent に渡してはいけない。
検証済みになるのは、subagent が実際に読んだ本文だけである。

点検では、次を確認する。

- 一文一行になっているか
- 見出しが内容を特定しているか
- 実装名や関数名を出しすぎていないか
- 空虚な強調を使っていないか
- 確認していない効果を断定していないか
- 候補生成、近似評価、本評価、時間管理の因果がつながっているか

点検で手順、条件、因果、候補選別、本評価への回し方、パラメータの意味が変わった場合、その本文を新しい検証対象にする。

## subagent による検証

検証では、新規 subagent を使う。
以前に対象 solver や失敗実装を読んだ agent を再利用しない。

subagent には、読んでよいファイルを明示する。
通常は次に絞る。

- `problem_description.txt`
- `notes/notations.md`
- `src/bin/v000_template.rs`
- 解説 Markdown
- `scripts/eval.py`
- `scripts/run.sh`
- `Cargo.toml`

subagent には、読んではいけないファイルも明示する。
対象 solver、Phase 1 の簡素化 solver、過去の再現 solver、その他の既存 solver を読ませない。
`rg src/bin` や `sed src/bin/*.rs` のように、禁止 solver が出力されうる探索も禁止する。

subagent には、再現 solver を1本だけ実装させる。
評価コマンドを指定し、ジョブ数を変えさせない。
full 評価を開始した後は、成功・失敗にかかわらずコードを変更、再評価させない。

subagent の final では、次を報告させる。

- 読んだファイル
- 変更したファイル
- 実行した評価コマンド
- `total_avg`
- 成功可否
- 解説で曖昧だった点
- 試行錯誤の回数と内容
- 評価後にスコアチューニングしたか

## 失敗時の扱い

subagent の再実装が目標スコアや時間条件を満たさなくても、直ちに解説不足とは判定しない。

親 agent が、Phase 1 の完成 solver、検証対象の解説、subagent solver の三者を比較する。
差分を、Phase 1 solver にある必要な情報が解説で欠落または曖昧だった場合と、解説に反した subagent 単独の実装ミスに分ける。

前者の場合だけ解説を修正する。
後者の場合は、subagent の失敗を理由に解説へ注意事項や実装細部を追加しない。

失敗した subagent solver は修正、改善、再評価しない。
次の検証のベースラインにも使わない。
本文を直した場合は、別の新規 subagent が新しい solver を最初から実装する。

再検証でも比較対象とベンチマークは Phase 1 の完成 solver に固定し、過去の subagent solver へ移さない。

## 成功時の扱い

subagent の再実装が目標スコアを超えても、すぐに完了にしない。
その成功が解説の力によるものか、subagent の試行錯誤によるものかを確認する。
結果は Phase 1 の完成 solver と比較し、過去の subagent solver とは比較しない。

次を確認する。

- full 評価を何回実行したか
- 評価後にパラメータを変えたか
- seed や特定ケースに寄せたか
- 解説に書かれていない判断をどれだけ補ったか
- 構文修正とスコア改善を区別できているか

何度も full 評価を回して最後に閾値を超えた場合、解説はまだ弱い。
その場合は、具体パラメータではなく運用原則を本文へ戻す。
たとえば「近似評価だけで捨てすぎない」「改善前候補も本評価に残す」「最後は本評価で選ぶ」のように書く。

初回に近い実装で閾値を超え、評価後チューニングも少ない場合、解説は再現性を持つ可能性が高い。

## 再検証

本文を修正したら、再び文章点検を行う。
その後、別の新規 subagent に渡して再検証する。

同じ subagent を使わない。
失敗分析で対象 solver を読んだ subagent も使わない。
過去の subagent solver をコピー、修正、ベース利用しない。

再検証は、成功するまで繰り返す。
ただし、本文が具体パラメータや特定ケースへの過適応に寄ってきた場合は、解説の目的から外れている。
その場合は、本文を本質構造へ戻す。

## 最終確認

最終成果物は、最後に subagent が読んだ検証対象本文と同一内容にする。

検証後に差分が残る場合は、表記ゆれ、誤字、句読点、リンク、意味を変えない言い換えのどれかに分類する。
分類できない差分がある場合は、再検証する。

最終報告では、次を示す。

- 解説ファイル
- subagent が読んだ解説ファイル
- 検証対象本文と最終本文の同一性
- 再現 solver
- 評価コマンド
- `total_avg`
- 試行錯誤の回数
- 解説へ反映した曖昧点
- 反映しなかった細部と、その理由
