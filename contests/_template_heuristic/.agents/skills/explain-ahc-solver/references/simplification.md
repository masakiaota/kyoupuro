# 実装から本質を抽出する

このフェーズの目的は、入力 solver をそのまま解説することではない。
得点と時間設計を保ったまま solver を簡素化し、解説で扱うべき構造と落としてよい実装を切り分ける。

簡素化 solver は、解説のための観察対象である。
元 solver のどの処理が得点に効いていたか、どの処理が過去の試行や補助実装だったかを、削除と評価によって確かめる。

## 入力

- 対象 solver
- 問題文
- `notes/notations.md`
- `src/bin/v000_template.rs`
- 評価スクリプト
- 目標スコア
- 時間制限または `max_elapsed` の許容条件
- 出力する簡素化 solver 名

## 出力

- 簡素化 solver
- 採用した削除と簡素化の一覧
- 不採用にした削除と、その理由
- 評価結果
- 解説本文に残すべき本質構造
- 解説本文から落としてよい非本質部分

## 成功条件

このフェーズは、次の条件をすべて満たすまで続ける。

- 簡素化 solver が目標スコアを超える
- `max_elapsed` がプロジェクトの時間条件を満たすように設計されている
- コードが十分に短く、解説対象として扱える。なるべく短い方が良いが、目安としては2000行以下。
- 残った処理の役割を説明できる
- 削った処理が得点に寄与していない、または解説の本筋に不要だと説明できる
- ハックや特定ケースへの過適応を入れていない

`max_elapsed` は、時間設計を確認するための指標である。
ただし、並列評価では OS のスケジューリングや同時実行の影響を受ける。
そのため、設計上は余裕を持っていても、`max_elapsed` がわずかに超えることがある。
わずかな超過が出た場合は、単発実行や再評価で、構造的な時間超過か計測揺れかを切り分ける。
切り分け後も `max_elapsed` 以内に収まらないなら、その実装は時間条件を満たしていない。

## 反復手順

1. 対象 solver をコピーして、簡素化用 solver を作る。
   元 solver を直接編集しない。

2. 現在の solver の基準評価を確認する。
   `total_avg`, `max_elapsed`, 成功ケース数、行数を見る。

3. 実行フローを読む。
   `main` から到達する処理と到達しない処理を分ける。

4. 削除または簡素化の仮説を1つ立てる。
   呼ばれていない旧探索、使われていない統計、ログ、経路復元、重複した補助関数を候補にする。

5. 仮説の目的を一文で書く。
   「この処理は出力に到達しない」「この統計は local ログだけに使われる」「この経路復元は最終選抜で距離だけを使うため不要」のように、削る理由を具体化する。

6. その仮説だけを反映する。
   複数の削除をまとめて入れすぎない。
   失敗時に戻せる粒度を保つ。

7. compile check を行う。
   AHC project では原則として `--features local` 付きで確認する。
   必要なら提出相当の feature なし compile も確認する。

8. 評価する。
   評価はプロジェクト標準の `scripts/eval.py` を使う。
   ユーザーが指定しない限り、ジョブ数や評価条件を変えない。

9. 結果を判定する。
   目標スコアを割った場合、その仮説は不採用として戻す。
   時間条件を満たすように設計されていない場合も、不採用または追加修正の対象にする。
   条件を満たした場合だけ採用し、次の仮説へ進む。

10. 採用と不採用を記録する。
    採用結果は、解説本文から落としてよい処理の根拠になる。
    不採用結果は、本質または危険な細部として扱う根拠になる。

## 停止条件

次のいずれかを満たしたら、このフェーズを止める。

- 目標スコアと時間設計を保ったまま、コードが十分に短くなった
- これ以上削ると目標を割る可能性が高い箇所だけが残った
- 残った処理を、解説本文の本質構造として説明できる
- 追加の削除がスコア改善や解説改善ではなく、単なるチューニングになり始めた

成功条件を満たした後は、目的のない追加探索を続けない。
追加で触る場合は、時間超過、説明不能な処理、明らかな重複など、解決すべき理由を先に示す。

## 失敗した仮説の扱い

削って目標を割った処理は、単に戻すだけで終えない。
その処理がなぜ効いていた可能性があるかを記録する。

ただし、理由が分からない場合は無理に説明しない。
「削ると `total_avg` が下がったため、本質または安全余白に関わる処理として残した」と書く。

## 時間超過への対応

`max_elapsed` が時間条件を大きく超える場合は、定数を短くするだけで済ませない。
重い処理がどこで始まり、どこで止まれないかを確認する。

自然な修正は、重い処理の外側だけでなく内側にも締切を渡すこと、探索フェーズと後処理フェーズを分けること、最後の実測評価に安全余白を残すことである。

時間対策も評価対象である。
スコアだけを満たしても、時間条件を満たすように設計されていなければ、このフェーズは完了しない。

## 解説への接続

このフェーズの成果は、解説本文の材料になる。

- 残った構造：解説の中心に置く
- 削れた処理：本文から落とす
- 削れなかった処理：必要性を説明する
- 時間管理：探索を成立させる条件として説明する
- 不採用の仮説：読者が誤って削らないように必要なら触れる

このフェーズが終わるまで、解説本文を確定しない。
