# Reflection

## Notation は実装と会話を往復しやすい形にする

今回の議論では、数学的に自然な記法に寄せたことで、TeX のレンダリング失敗やコードとの対応の見えづらさが発生した。

今後は、数学的に綺麗な記法より、会話・実装・検証を往復しやすい notation を優先する。

特に AI との共同作業では、次のような方針が有効である。

- 添字は原則 0-based index に統一する。
- `X[p,g]` のような配列アクセス風 notation を使う。
- コード上の変数名・配列構造と対応しやすい名前にする。
- TeX は必要なときだけ補助的に使う。
- `notes/notations.md` に、議論用 notation とコード上の代表名を併記する。

例:

```text
seg g
z[g]
X[p,g]        p in {0,1}
l[t,g,z]
r[t,g,z]
Y[t]
path[t]
theta[g] = (z[g], X[0,g], X[1,g])
```

ヒューリスティックでは、厳密な数学記法よりも、実装上の状態量が見える notation の方が有効なことがある。

例えば今回の MCMC サンプル列の活用では、次のような名前の方が、数式よりも意図と実装の対応を取りやすい。

```text
edge_cost_sample[g][i][m]
edge_mean[g][i]
edge_var[g][i]
```

このように書けば、MCMC の各サンプルが辺ごとの経験平均・経験分散に変換され、それが Dijkstra の LCB 重みに使われる、という流れを見失いにくい。

反省として、今後は最初に notation を決める段階で、数式としての自然さだけでなく、Markdown で壊れにくいか、コードと対応しやすいか、AI に誤解されにくいかを評価する。

## 数式構造は TeX、変数表現は配列アクセス風 notation にする

一方で、条件付き確率、総和、総積、比例関係などは、ASCII だけで書くとかえって読みにくい。

そのため、今後は次のように役割分担する。

- 数式構造は TeX で書く。
- 変数名・添字・状態量は実装寄りの配列アクセス風 notation で書く。
- 複雑な式はインラインではなく display math にする。
- コードフェンスに TeX を入れない。レンダリングされず、数式として読みにくくなるためである。

例えば、条件付き確率は次のように書く。

$$
p(\theta[g] \mid D[t], \theta[-g])
$$

総積や総和も TeX に任せる。

$$
\prod_{u=1}^{t}
p(y[u,g] \mid X[0,g], X[1,g], z[g])
$$

$$
\sum_{q \ne g}
\left(
l[u,q] X[0,q] + r[u,q] X[1,q]
\right)
$$

更新式も、数式構造は TeX、変数表現は配列アクセス風にする。

$$
p(X[:,g] \mid z[g], D[t], \theta[-g])
\propto
p(X[:,g])
\prod_{u=1}^{t}
p(y[u,g] \mid X[:,g], z[g])
$$

この形なら、`p(...)`、`\sum`、`\prod`、`\propto`、`\mid` のような数式構造は読みやすく、`z[g]`、`X[p,g]`、`theta[g]` のような変数はコードと対応しやすい。

つまり、数学的な構造は TeX に任せ、添字や状態量は 0-based の実装寄り notation に寄せるのがよい。
