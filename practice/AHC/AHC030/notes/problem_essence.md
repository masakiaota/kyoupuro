# AHC030 の問題の本質

この問題の本質は、真の油田配置

\[
\theta^\star
\]

を完全に探索することではなく、観測履歴

\[
\mathcal{D}_t
\]

に基づく事後分布

\[
p_t(\theta)=P(\theta^\star=\theta\mid\mathcal{D}_t)
\]

を、限られた時間内で「十分使える形」に保ち続けることにあった。

最終的に求められるのは \(\theta^\star\) そのものではなく、

\[
A_{\theta^\star}=\{c\mid v_{\theta^\star}(c)>0\}
\]

である。したがって、配置候補 \(\theta\) をどれだけ正確に特定できるかよりも、最終回答となる positive mask をどれだけ早く、どれだけ安全に当てられるかが重要だった。

## 全探索から posterior 近似へ

最初の考え方は、全配置候補

\[
\Theta=\Theta_1\times\cdots\times\Theta_M
\]

を明示的に持ち、各観測に対して尤度を更新するものだった。これは \(M=2\) や一部の \(M=3\) では有効だったが、\(|\Theta|\) は急激に増えるため、一般のケースでは破綻する。

ここで重要だったのは、「全候補を見る」ことではなく、「現在の観測に対して尤度が高い候補を維持する」ことだった。つまり、完全な posterior ではなく、限られた \(\theta\) pool による posterior 近似を使う問題として捉え直す必要があった。

特に、相互情報量

\[
I(\theta^\star;Y\mid\mathcal{D}_t,S)
\]

を丁寧に見ると、寄与が大きいのは主に

\[
p_t(\theta)
\]

が大きい候補であることが分かる。これにより、全候補ではなく高尤度候補だけを使って MI/cost を近似しても、実用上かなり戦えることが分かった。

## 占い集合 \(S\) の選び方

占いは、単に不確実性を大きく下げる集合 \(S\) を選べばよいわけではない。問題では占いコストが集合サイズに依存するため、見るべき量は

\[
\frac{
I(\theta^\star;Y\mid\mathcal{D}_t,S)
}{
\mathrm{cost}(S)
}
\]

である。

ただし、この値を厳密に最大化しようとすると重すぎる。実装を進める中で、厳密な山登りよりも、単体セルの MI で順序を作り、その順序に沿って add/remove sweep を数回行う軽量近似が強いことが分かった。

これは厳密な最適化ではないが、制限時間内で十分多くのターンを回せるという利点が大きかった。重い最適化を少数回行うよりも、軽い近似を安定して回す方が、この問題では有効だった。

## \(\theta\) pool の質

\(\theta\) pool の質はスコアに直結した。ランダムサンプリングだけでは真の配置に近い候補を取り逃しやすい。一方で、pool を大きくしすぎると毎ターンの posterior 更新や MI 計算が重くなり、時間内に処理できなくなる。

そこで重要になったのは、少数の高尤度候補を使って推論しつつ、次ターン用の pool を SA で再生成する方針である。

```text
turn 開始時点では上位候補だけに絞る
↓
その候補だけで posterior / MI / answer 判定を行う
↓
refresh で SA により次ターン用の候補を生成する
```

この方針により、全候補を扱わずに、尤度の高い候補を追跡し続けることができた。

## posterior の過信と補集合占い

posterior が

\[
P(A_{\theta^\star}=\hat A\mid\mathcal{D}_t)>0.95
\]

になっても、それは必ずしも安全な回答を意味しない。なぜなら、その確率は現在の \(\theta\) pool に依存しており、pool が真の配置近傍を取り逃している場合、過信が起きるからである。

この対策として効いたのが、回答候補

\[
\hat A
\]

の補集合

\[
\overline{\hat A}
\]

を占うことだった。

もし \(\hat A\) が正しければ、

\[
v_{\theta^\star}(\overline{\hat A})=0
\]

である。したがって、補集合占いは false negative、つまり \(\hat A\) の外側に油が残っているケースを検出するのに向いている。

v032 で補集合占いが効いたのは、posterior が 0.95 を超えても、実際には pool の偏りによって誤った positive mask を過信しているケースがあったためだと考えられる。

## 数値安定性

もう一つ重要だったのが、尤度計算の数値安定性である。観測 \(y\) の確率は

\[
P(Y=y\mid\theta,S)
\]

として計算するが、正規分布の裾では `f64` の差分計算により確率が 0 に丸められることがある。

その結果、

\[
\log P(Y=y\mid\theta,S)=-\infty
\]

となり、候補 pool 全体の \(\log w_\theta\) が \(-\infty\) になるケースが発生した。これは数学的に確率が本当に 0 という意味ではなく、数値計算上の underflow である。

このため、

\[
\log P(Y=y\mid\theta,S)\ge \mathrm{MIN\_LOG\_PROB}
\]

という下限を入れることが必要になった。これにより、補集合占い後に全候補が数値的に死んで interactive program が途中終了する問題を防げる。

## まとめ

この問題は、単なる探索問題ではなく、制限時間内で posterior をどこまで賢く近似できるかの問題だった。

重要な要素は以下である。

- 巨大な潜在配置 \(\theta\) の posterior 推定問題である。
- ただし最終的に欲しいのは \(\theta^\star\) そのものではなく \(A_{\theta^\star}\) である。
- 全探索は不可能なので、高尤度候補だけで posterior を近似する必要がある。
- 占い集合 \(S\) は MI/cost で選びたいが、厳密最適化は重すぎる。
- 単体セル MI による順序付けと軽量 sweep は、厳密ではないが非常に有効だった。
- \(\theta\) pool の質がスコアを支配する。
- posterior は pool に依存するため過信しやすく、補集合占いによる検証が効く。
- 尤度計算では \(\log 0\) を避ける数値安定化が必要である。

最終的には、「確率推論」「情報獲得」「候補生成」「時間制御」「数値安定性」がすべて絡む問題だったと言える。
