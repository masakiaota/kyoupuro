## 問題の本質

未知の重さを数値として正確に当てる問題ではなく、比較しかできない中で、分散が下がる操作をどれだけ効率よく見つけて採用できるかの問題である。

重さは指数分布で、特に重いアイテムの値がぶれやすい。そのため、単一の推定値で最終分割を作ると外れやすい。一方、2袋だけを変える局所操作なら、天秤比較の組み合わせで「改善したか」を判定できる。上位解法は、候補生成には推定や順序を使いつつ、採用は比較で確認する構造を持つ。

## 共通している考え方

- 最終的な採用は、推定値ではなく天秤比較で改善が分かるときだけ行う
- 袋を軽い順・重い順に管理すると、最重・最軽を狙えて候補の当たり率が上がる
- 同一クエリ、左右反転、空集合、推移律は必ず再利用してクエリを節約する
- `Q` が少ない場合は、アイテム全体のソートより山登り回数を確保する方が重要になりやすい
- `Q` が多い場合は、アイテムソート、貪欲初期解、LDM、推定サンプルなどに投資できる
- 重さ推定は「最終解を直接作る」より「よさそうな候補を選ぶ」ために使う方が強い

- 比較検証型山登り: 公式、siman、tishii2479、ymatsux
- 順序利用型: siman、ymatsux、montplusa、eijirou
- クエリ節約・制約伝播型: tishii2479、ymatsux、eijirou
- 推定補正型: montplusa、eijirou
- サンプリング・期待値型: eijirou、公式で言及されたwata方針
- 構築型初期解: siman、ymatsux、公式
- 後処理改善・再実行型: siman、eijirou

## 実装するならどのルートか

理解のための最小実装は、公式・siman・tishii2479を混ぜたルートがよい。

1. `i mod D` 初期解
2. 袋の比較ソート
3. クエリキャッシュと左右反転キャッシュ
4. 最重・最軽の1個移動
5. 最重・最軽の1個交換
6. 更新した袋の再挿入
7. 残りクエリ消化と最終出力

上位化するなら、次の順で足す。

1. 集合比較グラフでクエリ節約する
2. 単一アイテム順序と失敗枝刈りを持つ
3. `Q` が大きいケースだけアイテムソートと貪欲初期解を入れる
4. LDMまたは2袋再分割を入れる
5. 推定サンプルを複数持ち、改善期待値で候補を選ぶ

## 重要な実装要素

- 状態表現: `N <= 100` なので、集合はbitsetや`u128`で持つと比較キー・差分・包含判定が扱いやすい
- 評価関数: 真の分散は測れない。2袋操作の採否だけを比較で判定する
- 近傍: 1個移動、1個交換、複数交換、2袋LDM、2袋MITM再分割
- 差分更新: 変更された袋だけを軽い順配列へ戻す。全袋再ソートはクエリが重い
- 候補管理: 最重・最軽を優先し、詰まったら2番目以降や任意ペアへ広げる
- クエリ管理: 共通アイテム除去、空集合推論、左右反転、推移律、クエリ残数を一箇所で処理する
- 出力判定: クエリは必ず `Q` 回必要。余ったら安全な単体比較で消化してから割当を出す
- パラメータ: ソート閾値、LDM実行条件、候補数、温度、推定器数は `Q/N` と `D` に強く依存する

## 落とし穴

- 空集合や左右集合の重複をそのまま出力するとWAになる
- `Q` 回ちょうどクエリを投げずに最終出力すると不正になる
- 重さ推定値を信じて最終分割を出すと、指数分布の重いアイテムで大きく外しやすい
- 袋順の更新を忘れると、最重・最軽のつもりで別の袋を操作してスコアが崩れる
- キャッシュキーの正規化を誤ると、同じ比較を何度も投げるか、逆向き結果を誤用する
- 失敗枝刈りの単調性の向きを間違えると、有効な候補を捨てて局所解から動けなくなる
- アイテムソートにクエリを使いすぎると、構築後の改善クエリが残らない
- 集合グラフや推移閉包を重くしすぎると、クエリは節約できても実行時間で負ける
- 推定器の補正を強くしすぎると振動し、弱くしすぎると履歴制約に追従しない

- 公式解説動画は自動字幕から読んだため、動画画面上の順位表や図の細部は完全ではない

- `Q/N` が小さいケースで、推定補正と比較グラフのどちらが費用対効果に優れるかは要実験である
