## 解法の全体像

公式解説の中心は、天秤だけでも「操作後に分散が改善したか」を判定できるため、山登りができるという点である。単純な `i mod D` 初期解から始め、1個移動や1個交換を試し、比較で改善が証明できたら採用する。さらに、クエリ結果のキャッシュ・推移律・袋ソート・アイテムソート・貪欲構築・LDM・重さサンプルによる候補選択へと拡張する流れが説明されていた。

動画では、重さの指数分布は重いアイテムの推定が難しいように選ばれており、単純に各アイテム重量を当てて最終解を出す方針は弱くなりやすい、と説明されている。したがって、推定は初期解や候補選択に使い、最後は山登りで実測検証するのが基本になる。

## 主要アイデア

- 分散そのものは測れないが、2袋だけを変える操作の改善は比較で判定できる
- 1個移動: 片方からアイテムを取り出し、残り袋と移動先袋を比較すれば採否が分かる
- 1個交換: 取り出した2アイテムの大小と、残った2袋の大小が対応すれば採用できる
- 同一クエリ、左右反転、推移律で分かる比較は省く
- `D <= N/4` かつ `Q >= 2N` なので、全アイテムをソートできなくても袋 `D` 個のソートは比較的可能である
- 袋をソートしておくと、最重・最軽を狙えて山登り候補の当たり率が上がる
- `Q` が大きいなら、アイテムをソートして重い順に最軽袋へ入れる貪欲初期解やLDM初期解が使える
- 最上位では、比較制約を満たす重さサンプルから改善期待値を見積もって候補を選ぶ方向が強かった

## 最終コードの構造

コードなし。動画で説明された公式解説用の構造を、実装するなら次のように分けられる。

### 状態表現

- `bags[d]`: 現在の割当
- `bag_order`: 袋を軽い順に並べた順位
- `query_cache`: 過去の集合比較と左右反転
- `relation_graph`: 集合間または単一アイテム間の大小関係
- `item_order`: クエリ数が十分多いときに得るアイテムの重さ順
- `samples`: 上位方針では、比較制約を満たす重さサンプル群

### 観測・制約・入力の扱い

- クエリは空集合を投げられないので、空集合が出る比較は内部で推論する
- 同じ比較・反転比較は再利用する
- `A < B` かつ `B < C` なら `A < C` のように、推移律で省けるクエリがある
- より高度には、不等式制約を線形計画的に扱い、逆向きの制約を仮定したとき矛盾するかでクエリ不要判定できる
- 動画では、writer自身は手軽な範囲のキャッシュ・推移利用をしたと述べていた

### 評価関数

移動や交換の採否は、2袋の関係だけで見る。

1個移動では、アイテムを取り出した後の袋を `B'`、移動先を `A`、取り出したアイテムを `x` とすると、`A < B'` なら `x` を `A` に載せることで両袋が近づく。

1個交換では、2アイテムを取り出した後の残り袋の大小と、取り出したアイテム同士の大小が同じ向きなら、小さい残り袋に大きいアイテム、大きい残り袋に小さいアイテムを戻すことで改善する。

サンプル利用方針では、操作前後の二乗和改善量の期待値をサンプルから推定し、その期待値が大きい候補を優先する。

### 探索・構築・更新

- ベースライン: `i mod D` で均等個数に分ける
- 山登り1: ランダムな1個移動
- 山登り2: 1個移動と1個交換を混ぜる
- キャッシュ・推移律で無駄クエリを減らす
- 袋を比較ソートし、最重・最軽を優先して試す
- `Q` が大きいときは、アイテムソート後に重い順で最軽袋へ入れる貪欲構築を使う
- さらに強い初期解としてLargest Differencing Methodも候補になる
- 推定サンプルを使う場合は、各候補の改善期待値を計算し、最もよさそうな候補だけ実測する

### 操作・クエリ・出力選択

動画で強調されていたのは、天秤は差の大きさを返さないが、改善したかどうかは比較の組み合わせで分かるという点である。そのため、操作候補を作って、必要な比較が成立したら即採用する形になる。

袋ソートを持つ場合、変更後の袋は全体を再ソートせず、既にソート済みの列へ二分探索で戻す。これにより、クエリを候補生成や採否判定に回せる。

### 時間配分・パラメータ

- `Q/N` の大小で有効な方針が変わる
- `Q` が少ない場合は、アイテムソートよりも山登り回数を確保することが重要
- `Q` が多い場合は、アイテムソート・貪欲・LDMなどの構築に使う価値がある
- サンプル方針では、制約を満たす重さを直接棄却サンプリングするだけでは受理率が落ちるため、Gibbs samplingのような更新が話題に出ていた

## 実装上重要な断片

```text
try_move(item, from, to):
    remove item from from
    if weight(to) < weight(from_without_item):
        move item to to
        return adopted
    else:
        restore item
        return rejected
```

```text
try_swap(a from light_bag, b from heavy_bag):
    remove a, b
    compare remaining bags
    compare items a, b
    if smaller remaining bag receives heavier item:
        adopt swap
    else:
        rollback
```

```text
construct_greedy_when_sorted():
    sort items descending by balance
    maintain bags sorted by current weight
    for item in sorted_items:
        put item into lightest bag
        reinsert that bag by binary search
```

## この解法の本質

この問題は「重さを当てる問題」ではなく、「比較しかできない状況で、改善が保証される操作を選び続ける問題」と見るのが重要である。指数分布の重い側は推定誤差が大きく、推定値だけで最終分割を作ると外れやすい。比較で改善を確認する山登りを軸にすれば、推定誤差を候補選択のリスクに閉じ込められる。

また、`N` 全体を把握できなくても `D` 個の袋なら把握しやすい、という制約の使い方も本質である。袋ソートは安価で、候補選択の精度を大きく上げる。

## 真似するならまず実装する部分

まずは公式解説の最小山登りを実装するのがよい。

1. `i mod D` 初期解
2. クエリキャッシュ
3. 袋ソート
4. 最重・最軽への1個移動
5. 1個交換
6. 更新後の袋再挿入

その後、`Q` が大きいケース用にアイテムソートと貪欲初期解を足す。最後に、サンプルで候補選択を改善する。
