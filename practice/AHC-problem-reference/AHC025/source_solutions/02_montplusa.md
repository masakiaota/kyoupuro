## 解法の全体像

基本は「現在一番重い袋と一番軽い袋を均す」山登りである。初期解を `i mod D` で作り、袋の重さ順を比較で管理する。改善操作は、重い袋から軽い袋へ1個移す遷移と、重い袋・軽い袋を推定値にもとづいて2分割し直す遷移が中心である。

この解法は推定値を使うが、推定値だけで出力するのではなく、実際の比較で改善判定を行う。さらに、クエリ結果・過去の袋順・アイテム順を使って推定値を補正し、遷移候補の質を上げる。

## 主要アイデア

- 最重袋と最軽袋の差を縮める操作を繰り返す
- 2袋を「足して2で割る」ような再分割遷移を用意する
- その遷移は推定値依存で不安定なため、1個移動の堅い遷移も使う
- 比較履歴に反する推定値を、クエリごとに少し過剰に縮める・伸ばす
- 過去の袋構成と袋順も制約として扱い、現在の推定値を袋の重さ順に合うよう補正する
- `Q` が十分大きいときは最初にアイテムの重い順を調べ、順位から初期推定値を作る
- 明らかに結果が分かるクエリは投げずに消費を節約する
- クエリ数が少ないケースで順位を大きく落とさない安定性を重視する

## 最終コードの構造

BrowserでAtCoder順位表から最終提出 #46860048 を辿り、Goコードを読めた。以下は提出コードと記事本文を合わせた構造である。

### 状態表現

- `GameState`: `BagIndex`, `NumItemsInBag`, `Order`, `QueryCount`, `CompareHistory`, `ResultHistory` を持つ
- `GameConst`: `NumItems`, `NumBags`, `NumQueries`, 推定値、乱数、比較補助を持つ
- `Action`: 袋の再分割や移動候補を表す
- `estimated_weight[i]`: `updateEstimation` / `updateEstimationByRank` で比較履歴と袋順位から補正される
- `CompareHistory` / `ResultHistory`: 集合比較の左右集合と結果を保存する
- `Order`: 袋の軽い順を持ち、`setRank` / `searchRank` / `compareTwoBags` で更新する

### 観測・制約・入力の扱い

- 初期解は基本的に `item i -> bag i % D`
- 袋順は初回に `D log D` 程度、更新後は `2 log D` 程度の比較で挿入更新する
- クエリ結果は履歴に保存し、新しいクエリのたびに全履歴を見て推定値を補正する
- 空集合、同一クエリ、ソート済みアイテム順から明らかな優越関係は、クエリを投げずに処理する
- 提出コードでは `compareTwoGroups` と `check` がクエリ実行・再利用・履歴更新の中心になる

### 評価関数

明示的なスコア評価式は記事内ではコードとして示されていない。方針としては、最重袋と最軽袋の差を縮めることを主目的にしている。

推定値の補正では、比較結果に対して現在の左右和が逆なら、左右の総和が比較結果に合うよう線形に伸縮する。補正は序盤ほど強く、クエリが進むほど穏やかにする設計である。

### 探索・構築・更新

- 遷移2: 最重袋と最軽袋の中身を推定値で2分割し直す
- 遷移1: 最重袋から最軽袋へ1個移す。成功・失敗のどちらでも情報が得られるため安定する
- 補正1: クエリ履歴に反する推定値を過剰補正する
- 補正2: 過去の袋構成と袋順に、現在の推定袋和が合うよう補正する
- 補正3: アイテム順を得られるケースでは、順位にもとづく期待値を初期推定として使う
- 初期推定: 5から20回程度、全アイテムを推定値で半分に割る比較を行い、補正をかける
- `Q` が大きく、アイテム順が分かる場合は推定値でD分割したものを初期解にする
- `Q` が小さい場合は、推定に賭けすぎず `i mod D` 初期解で安定を取る
- 提出コードでは `splitBag`, `getReasonableDivision`, `getHalf`, `getOptimalPlan` が推定値ベースの候補生成を担う

### 操作・クエリ・出力選択

2袋を再分割する遷移では、移動後に改善しているかを不等式で確認する。袋1を重い袋、袋2を軽い袋とし、残る側・移る側の2つの比較が正しい向きなら採用する。

1個移動では、2つ目の不等式が自明になるため、比較回数が少なく安定している。遷移後は袋順を再挿入して、次も最重・最軽を取りやすくする。

### 時間配分・パラメータ

- アイテム順を調べる条件は、おおむね `N log N + D log D + 30` 以上の余裕クエリがあるかで判断していた
- 初期の半分割クエリは5から20回程度
- 補正の過剰度はクエリ進行とともに小さくする
- 局所解脱出用に、3袋再編成のような遷移も存在したが、頻度は低かったと書かれている

## この解法の本質

不確かな推定値を「強い遷移候補を作る道具」として使いつつ、順位スコアで大損しにくい安定な遷移を混ぜている点が本質である。特に、1個移動は大きな改善が保証されやすいだけでなく、失敗しても「このアイテムは重い」「袋はかなり均されている」といった情報を残す。クエリを探索と観測の両方に使っている。

また、袋順そのものを制約として推定に戻す点が特徴的である。比較で直接得たクエリだけでなく、過去の探索過程から得た順序情報を再利用している。

## 真似するならまず実装する部分

まずは推定補正なしで、次を作るのがよい。

1. `i mod D` 初期解
2. 袋順の比較ソートと、更新後の挿入
3. 最重袋から最軽袋への1個移動
4. クエリ履歴キャッシュ
5. 余裕があれば推定値補正と2袋再分割

補正2や補正3は効くが、状態管理が複雑なので最初から入れると壊れやすい。
