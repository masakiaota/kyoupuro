## 解法の全体像

アイテムの重さを推定するのではなく、比較結果そのものを集合間大小グラフとして保存し、推移律や包含関係から新しい比較結果を推論する。初期解は `i mod D` のように分け、袋を比較でソートする。その後、軽い袋と重い袋を選び、1個移動・1個交換・複数アイテム交換を山登りで試す。

クエリを投げる前に、集合グラフ上で到達可能性を調べ、結果が推論できるならクエリを節約する。操作する袋は基本的に最軽・最重だが、時間経過に応じて2番目以降の軽い袋・重い袋も混ぜ、局所解から抜けやすくしている。

## 主要アイデア

- アイテム集合を `u128` bitsetとしてハッシュ化する
- 比較結果を「軽い集合 -> 重い集合」の有向辺として持つ
- `A subset B` なら `A < B` として辺を追加する
- 2集合の差分が1アイテムずつで、その単体大小が分かるなら集合間大小も推論する
- グラフ上のBFSで到達できれば、実クエリなしで大小を返す
- 山登り操作は移動・交換・複数交換
- 袋ランクは線形探索または二分探索で更新する
- 操作する袋ペアは、時間とともに極端以外も確率的に選ぶ

## 最終コードの構造

### 状態表現

- `groups: Vec<Vec<usize>>`: 現在の袋
- `rank: Vec<usize>`: 軽い順の袋インデックス。`rank[0]` が最軽、`rank[D-1]` が最重
- `Balancer`:
  - `left_edges`: `first < second` の有向辺
  - `right_edges`: 逆向き探索用の辺
  - `cached_results`: 比較結果キャッシュ
- `Interactor`: 入出力とクエリ回数管理
- `Input`: `n, d, q`

`Balancer` がこの解法の中心で、集合比較の推論とクエリ実行の窓口になっている。

### 観測・制約・入力の扱い

- `Balancer::get_result` は、まず空集合比較、キャッシュ、追加辺、グラフ探索を試す
- 推論できなければ実際にクエリを出し、結果に応じてグラフに辺を追加する
- `add_additional_edges` で、包含関係と1アイテム差分の関係を追加する
- グラフ探索は深さ5までのBFSで、過剰な探索時間を避ける
- 使い切れなかったクエリは `0` と `1` の単体比較で消化する

### 評価関数

数値評価関数は持たない。比較で「移動後・交換後が改善している」と分かった操作だけ採用する。

操作する袋ペアの選択は、現在の `rank` による軽い側・重い側の位置を使う。初期は最軽・最重が中心で、時間経過で対象範囲を広げる。

### 探索・構築・更新

- 初期解はアイテムを `i mod D` に割り当てる
- `sort_groups` はランダムピボットのクイックソート風に袋を比較ソートする
- メインループでは時間とクエリが残る限り、操作を確率的に選ぶ
- 操作確率は序盤と終盤で変わる。序盤は移動・通常交換が多く、終盤は複数交換が増える
- `action_move`: 重い袋から軽そうなアイテムを選び、軽い袋へ移す
- `action_swap`: 軽い袋と重い袋から1アイテムずつ選び、交換が改善するなら採用する
- `action_swap2`: 片側に追加アイテムを最大3回足して、複数アイテム交換を作る
- 更新後は `update_rank` で変更袋を軽い順の正しい位置に戻す

### 操作・クエリ・出力選択

`select_g_idx_pair` は、最初は `rank[0]` と `rank[D-1]` を選びやすくする。時間が進むほど `min(5, D/3)` 程度まで軽い側・重い側の候補範囲を広げ、それぞれ確率 `0.3` で選ぶ。

アイテム選択では `find_lighter_in_group` を使い、グラフ上でより軽いと分かる同一袋内アイテムへ辿る。完全な順位を作らず、既存の比較グラフから局所的に軽い候補を探している。

### 時間配分・パラメータ

- 時間制限は `TIME_LIMIT - 0.1` まで探索
- グラフBFSの最大深さは `5`
- ランク更新は `D < 8` なら線形探索、そうでなければ二分探索
- 複数交換の追加試行回数は `3`
- 操作確率は序盤 `[move 0.5, swap 0.4, swap2 0.1]`、終盤 `[move 0.1, swap 0.1, swap2 0.8]` 相当

## 実装上重要な断片

```text
get_result(L, R):
    if empty comparison is decidable: return
    hL, hR = bitset hashes
    if cache has (hL, hR): return
    add edges from subset and one-item-difference rules
    if hL reaches hR in left_edges: return "<"
    if hL reaches hR in right_edges: return ">"
    result = ask query
    add edge according to result
    return result
```

```text
select_group_pair(time):
    range = 1 + round(elapsed * min(D/3, 5) / time_limit)
    light_rank = first selected among low ranks with probability 0.3
    heavy_rank = first selected among high ranks with probability 0.3
    return (light_rank, heavy_rank)
```

```text
action_swap():
    a = light-ish item from light group
    b = light-ish item from heavy group
    if not (a <= b): reject
    remove a,b
    if remaining light group is heavier than remaining heavy group: reject
    swap a,b
    update rank
```

## この解法の本質

比較結果を単なるキャッシュではなく、集合間の半順序グラフとして扱う点が本質である。局所探索では似た集合が何度も現れるため、集合そのものを頂点にすると、過去の比較から新しい比較を推論しやすい。重さ推定を使わず、クエリ節約によって試行回数を増やす方向の解法である。

また、最軽・最重だけを見続けると詰まりやすいことを、時間スケジュールで自然に緩めている。局所解脱出を焼きなましではなく「比較対象の広げ方」で行っている。

## 真似するならまず実装する部分

まずは次の最小構成がよい。

1. `u128` で集合を表す
2. 比較キャッシュと左右反転キャッシュ
3. 包含関係だけの追加辺
4. グラフ到達でクエリを省く
5. `i mod D` 初期解と袋ソート
6. 1個移動と1個交換

1アイテム差分の追加辺や複数交換は、その後に足すとよい。

## 注意点・未理解点

- グラフ辺を増やしすぎるとBFSが重くなるため、探索深さや頂点追加条件が重要である
- 等号を厳密に扱わず `<` 側へ寄せる箇所があり、頻度が低い前提に依存している
- `action_swap2` は効果がありそうだが、試行回数や選ぶアイテムの分布はパラメータ依存である
- コードは読めたが、ローカル実行で各パラメータの寄与までは検証していない
