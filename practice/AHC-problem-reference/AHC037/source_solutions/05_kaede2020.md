## 解法の全体像

本番後に、まず momoharahara 型の中継点追加を試し、その後、AHCラジオや上位実装を参考に強い貪欲とビームサーチへ進む復習記事である。最終目標は、強い貪欲をベースにしたビームサーチで、強い貪欲のスコアを超えることだった。

記事の中心は、完成したアルゴリズムの一枚説明ではなく、ビームサーチを実際に動かすまでの試行錯誤である。幅1で強い貪欲と一致すること、小さい `N` でビームが何を改善するのか確認すること、候補ペアの枝刈り、状態コピー削減、座標型の軽量化、出力復元の軽量化などが具体的に語られている。

## 主要アイデア

- まず中継点追加型の前向き貪欲で問題の感触を掴む。
- 強い貪欲は、全ペアから遠い方、つまり `min(x)+min(y)` が大きいペアを選んでマージする。
- ビームサーチは強い貪欲を幅1とする拡張である。
- 幅を広げる前に、幅1が強い貪欲と同じスコアになることを確認する。
- 小さい `N` で、貪欲より良いマージ順が存在することを目で確認する。
- ペア候補は `x+y` のラインや現在bestを利用して絞る。
- 状態コピー、出力列保持、ソート、重複除去がボトルネックになる。
- `long long` を `int` に変えるだけでも大きく速くなる。
- 余計な枝刈りはseed0では良く見えても全体ではスコアを落とす。

## 最終コードの構造

Browserで読めた提出 #58262357 を主実装として書く。記事本文のビームサーチ試行錯誤と対応するが、細部は提出コードベースである。

### 状態表現

- `Drink`: 座標 `(x, y)`。比較演算、等価判定、`std::hash<Drink>` を持つ。
- `Operation`: マージで生成する前向き操作。`(x, y) -> (x_new, y_new)` を記録する。
- `State`: 現在の有効点列 `drinks`、操作列、評価値、`hash_sum` を持つビーム状態。
- 重複除去は、状態内の有効点のハッシュ和 `hash_sum` を `visited` に入れて行う。
- 出力は `Operation` を逆順にたどる。履歴復元専用ではなく、提出 #58262357 では状態に操作列を保持している。

### 観測・制約・入力の扱い

- `N=1000` で深さは `N-1`。
- 入力に `(0,0)` があるケースで出力漏れが起きたことに触れており、原点やゼロコスト辺の扱いがWA原因になり得る。
- コードテストとローカルで実行時間差があり、ローカル大量テストでTLE/WAを確認している。

### 評価関数

強い貪欲・ビームの基本評価は次である。

```text
merge(p, q) = (min(p.x, q.x), min(p.y, q.y))
gain = merge.x + merge.y
score += gain
```

記事では、強い貪欲を超えるビーム解が何をしているのか、小さい `N=4` で比較して理解している。貪欲の局所的に最大の `gain` が、将来のマージ順まで含めた最適とは限らない。

### 探索・構築・更新

- 中継点追加の復習:
  - 右下中継点を入れる。
  - 右下と左上を入れ、葉なら削除する。
  - X軸・Y軸側へつなげる。
- 強い貪欲:
  - 全ペアから `min(x)+min(y)` が大きいペアを選び、2点を削除して中間点を追加する。
- ビームサーチ:
  - 各深さで、前世代の上位状態から候補ペアを生成する。
  - 候補を評価順に残し、ビーム幅分だけ次状態にする。
  - 枝刈りで、bestより悪い候補を早く捨てる。
  - 状態を丸ごとコピーしないため、ターンごとの行動だけを管理する軽いクラスを作る。
  - 状態に出力を持たせず、履歴から最後に復元する。

### 操作・クエリ・出力選択

- マージで記録した `r -> p`, `r -> q` を逆順に出力する。
- 原点 `(0,0)` を入力点として含む場合や、マージ点が子と同じ座標になる場合は出力漏れ・不要操作に注意する。
- 履歴復元型にするなら、最終状態から親をたどって操作列を復元する。

### 時間配分・パラメータ

- 最初に試した深さ5・幅20はスコア悪化かつ大幅TLE。
- 幅1000の試作では seed0 は良くなったが 1094秒かかった。
- 幅5、各状態から最大150遷移で13秒。
- 高速化後、余計な枝刈りを消すと3秒弱。
- 最終的にはビーム幅3でも強い貪欲を超え、2秒以内に収まったと記載されている。
- 高速化として、`long long` から `int`、出力配列の `reserve`、ソートの代わりに二分探索挿入、ハッシュによる重複除去が挙げられている。

## 実装上重要な断片

ビーム幅1の確認が重要である。

```text
beam_width = 1
run beam search
assert score == strong_greedy_score
```

候補生成と枝刈りの考え方は次である。

```text
for state in beam:
    best = current_best_candidate_value
    for p in sorted_active_points:
        if p.x + p.y is already too small:
            break
        for q in remaining_points:
            r = merge(p, q)
            if r cannot beat useful threshold:
                continue or break only if the ordering justifies it
            push candidate
```

履歴復元型の状態管理は次の方向である。

```text
candidate:
    score
    parent_state_id
    merged_pair
    new_point
    hash

after final depth:
    follow parent_state_id backward
    reverse actions
    output generated edges
```

## この解法の本質

この参照元の本質は、ビームサーチを「幅を増やせば強くなる魔法」ではなく、幅1の貪欲から一つずつ検証する実装課題として扱っている点である。AHC037のビームサーチは状態数より候補ペア数が重く、さらに状態コピーと重複がすぐ支配的になる。アルゴリズムの説明だけでは足りず、候補をどう削るか、同じ状態をどう捨てるか、履歴をどう軽く持つかが成否を分ける。

小さい `N` でビームの目的を確認している点も重要である。貪欲より良い解がどう違うのかを視覚化しないまま高速化すると、誤った枝刈りでもseed0だけ良く見えてしまう。

## 真似するならまず実装する部分

まず強い貪欲を実装し、その後ビーム幅1で同じ結果を出す。次に `N=4` や小さいランダムケースで、幅を広げると貪欲と異なる有利なマージ順を選べることを確認する。

高速化は最後ではなく途中から必要になるが、最初に入れるべきではない。状態コピーを軽くする、出力を履歴復元にする、ハッシュ重複除去を入れる、候補枝刈りを検証しながら入れる、という順序がよい。
