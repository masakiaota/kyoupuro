## 解法の全体像

延長戦で、AHC037 の代表的な3方針を実装して比較している。まず、全点を葉として、`r=(min(p.x,q.x),min(p.y,q.y))` の `r.x+r.y` が大きいペアを優先してマージする強い貪欲を再現する。次に、近い葉を優先するマージがなぜ弱いかを確認する。最後に、強い貪欲の「次に選ぶペア」をビームサーチで複数候補残しに拡張し、本番2位相当の方針に近づけている。

ビームサーチでは、状態の丸ごとコピーが重いこと、同じ有効点集合がマージ順違いで大量に重複すること、ペア候補が多すぎることが主な課題になる。提出コードでは `MiniState` で候補段階の差分だけを持ち、採用時だけ `State` をコピーする。状態重複は、生きている頂点集合のハッシュ和で除去する。

## 主要アイデア

- 後ろ向きに2点をマージし、マージ点から2点への辺を記録する。
- 強い貪欲は `min(p.x,q.x)+min(p.y,q.y)` 最大のペアを選ぶ。
- 近い葉マージはクラスタを作り、終盤のクラスタ間接続が長くなって弱い。
- ビームサーチでは、各深さで複数の有効点集合を持つ。
- 状態の評価は、これまで作った中間点の `x+y` の合計を最大化する形で持つ。
- 有効点集合を `abs(x)+abs(y)` 降順に並べ、候補列挙を途中で打ち切る。
- 候補段階では `MiniState(p,q,score,hash,from)` だけを作る。
- 同じ生存頂点集合は、頂点ごとのハッシュ値の和で重複除去する。
- `inplace_merge` や `shrink_to_fit` など、ビーム幅を上げるための実装高速化・省メモリ化が重要である。

## 最終コードの構造

ここではビームサーチ提出 #57911179 を中心に書く。強い貪欲 #57828180 と近い葉マージ #57828739 も確認した。

### 状態表現

- `Vec2 { x, y }`: 座標。
- `State`:
  - `V`: 現在生きている葉・中間点の集合。`abs(x)+abs(y)` 降順で管理する。
  - `score`: 選んだマージ点の `x+y` の累積。
  - `hash`: 生存頂点集合のハッシュ値合計。
  - `starts, ends`: 後で出力する辺。各マージで `r -> p`, `r -> q` を追加する。
- `MiniState`:
  - `p, q`: 親状態の `V` 内でマージする2点のindex。
  - `score`: 遷移後スコア。
  - `hash`: 遷移後の集合ハッシュ。
  - `from`: 1世代前のどのビーム状態から来たか。

### 観測・制約・入力の扱い

- 入力点をすべて `Vec2` として読み、初期 `V` に入れる。
- 初期 `V` は `abs(x)+abs(y)` 降順にソートする。
- マージ回数は `N-1` であり、各回で有効点数が1つ減る。
- 出力は `starts/ends` を逆順にたどる。後ろ向きマージで最後に作った根側の操作から前向きに実行するためである。

### 評価関数

強い貪欲・ビームで使う基本評価は次である。

```text
r = merge(p, q) = (min(p.x, q.x), min(p.y, q.y))
gain = r.x + r.y
beam_score += gain
```

全点を原点から直接作る場合に比べて、`r.x+r.y` だけ共通化による削減が得られる、と見なせる。そのため、この累積を最大化する。

近い葉マージの提出では、`2e9 - L1(p,q)` を非常に大きく重み付けし、距離が近いペアを優先するようにしている。しかし記事・コメントともに、これはクラスタ化で悪化したと説明している。

### 探索・構築・更新

- 強い貪欲:
  - 全ペアを優先度付きキューに入れる。
  - 使用済み点を含む候補は捨てる。
  - `min x + min y` が最大のペアを取り、2点を使用済みにして新点を追加する。
  - 新点と未使用点のペアをキューに追加する。
- ビームサーチ:
  - 深さ `i=1..N-1` で、前世代の全ビーム状態から候補マージを列挙する。
  - `best` を使い、`abs_sum` が十分小さい候補を打ち切る枝刈りを入れる。
  - 候補をスコア降順にソートする。
  - ハッシュ重複を除きながら上位 `BEAM_WIDTH` 個を採用する。
  - 採用時だけ親状態をコピーし、`V` から `p,q` を消して `r` を足す。
  - `V` はほぼソート済みなので `inplace_merge` で新点を正しい位置へ入れる。
  - 使い終わった前世代の大きい配列は `clear` と `shrink_to_fit` で解放する。

### 操作・クエリ・出力選択

- 各マージで `r -> p` と `r -> q` を記録する。
- 最終状態で根が1点になったら、記録を逆順に出力する。
- 同じ座標への辺が出る場合は、実装によっては出力され得るが、強い貪欲コードでは必要に応じて同座標を避けている。

### 時間配分・パラメータ

- ビーム提出の `BEAM_WIDTH` は70。
- wata_admin の実装では幅2200と記事に記載されている。
- peroon の提出は実行時間 1742 ms、メモリ約25 MB。
- 枝刈りなしでビームを完成させ、幅1が貪欲と一致することを確認してから枝刈りを入れるべきだった、と記事で反省している。
- コメントアウトされた `mx+my<best` の枝刈りは誤りだったとコードに書かれている。

## 実装上重要な断片

強い貪欲は次の形である。

```text
active = all input points
pq = all pairs keyed by min(x0,x1)+min(y0,y1)
repeat N-1 times:
    pop best pair not using removed points
    r = min_pair(pair)
    record r -> p, r -> q
    remove p, q
    add r
    push pairs (r, other active)
output recorded edges in reverse
```

ビームサーチの候補生成は次の形である。

```text
for depth in 1..N-1:
    candidates = []
    for each beam state bm:
        for p in bm.V:
            if abs_sum(p) < best:
                break
            for q after p:
                if abs_sum(q) < best:
                    break
                r = merge(p, q)
                candidates.push(MiniState(
                    p, q,
                    bm.score + r.x + r.y,
                    bm.hash - h(p) - h(q) + h(r),
                    from = beam_index
                ))
    sort candidates by score desc
    select first non-duplicate hashes up to width
```

状態更新は採用後だけ重いコピーを行う。

```text
state = previous_beam[mini.from]
erase q then p from state.V
append r
inplace_merge to keep descending order
state.starts.push(r)
state.ends.push(p)
state.starts.push(r)
state.ends.push(q)
```

## この解法の本質

この参照元の本質は、「強い貪欲がなぜ強いか」と「それをビームへ拡張するとどこが重いか」を実装レベルで切り分けている点である。AHC037では、1手のマージの価値が `min` 座標の原点からの距離で見える。したがって幅1のビームは強い貪欲そのものであり、幅を広げると「少し先を見たマージ順の選択」になる。

ただし、単純なビームは状態コピーと重複で破綻する。`MiniState`、集合ハッシュ、前世代解放、ほぼソート済み配列の差分挿入といった工夫が、方針そのものと同じくらい重要である。

近い葉マージの失敗も有用である。局所距離だけを見ると、その場では自然なクラスタができるが、最終的にはクラスタ同士を原点側でまとめるコストが大きくなる。この問題では「近い」より「右上で共通化できる」が優先される。

## 真似するならまず実装する部分

まずは #57828180 型の強い貪欲を実装する。優先度付きキューと使用済みフラグだけで書け、後ろ向きマージと逆順出力を理解しやすい。

次にビーム幅1を作り、強い貪欲と同じ結果になることを確認する。その後、`MiniState` とハッシュ重複除去を入れて幅を増やす。枝刈りは最後に入れるべきで、枝刈りなし版との差分を必ず確認するのがよい。

## 注意点・未理解点

- 記事で触れられた wata_admin の実装は、ハッシュや上位候補管理の参考として一部読んだが、このメモでは peroon 提出の構造を中心に整理した。
- 生存頂点集合ハッシュは衝突可能性がゼロではない。AHC用途では実用上許容した実装である。
- `V.erase` は `O(N)` であり、幅を大きくすると支配的になり得る。
- `shrink_to_fit` は実装依存の挙動もあるが、この提出ではMLE対策と速度改善として使われている。
- 枝刈り条件を誤ると、seed0では良くても全体スコアや正当性を壊す。記事でもここを強く反省している。
