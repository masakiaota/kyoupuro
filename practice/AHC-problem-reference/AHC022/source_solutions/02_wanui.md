## 解法の全体像

主方針は「お子様ランチ型」の1点高温配置である。盤面上に1つだけ極端に温度の高い旗を置き、ほかの場所は緩やかな山にする。ある出口候補から旗へ向かう相対移動をワームホールに対して試し、その観測値から出口候補とワームホールの尤度を更新する。優先度付きキューで確信度の高い候補ペアから検証し、1位と2位の尤度比が十分開いたら対応を確定する。

最終コードには、この1点高温方式の `ChildLunchSolver` に加えて、高S・高N付近で使う `BitPatternSolver` も含まれている。記事本文は主に `ChildLunchSolver` を説明しているが、提出コードはパラメータ表でソルバと温度を切り替える。

## 主要アイデア

- 観測確率 `P(true_temp, observed)` を 1001 x 1001 の対数確率テーブルとして事前計算する。
- `Likelihood(ec, wh)` は、ワームホール `wh` が出口 `ec` に対応すると仮定したとき、これまでの観測が出る尤度である。
- 1点高温配置では、旗の位置を出口セル群に近い場所に置き、平均移動距離を抑える。
- 優先度付きキューで「次に検証すべき (出口候補, ワームホール)」を管理する。
- 1位と2位の対数尤度差が `log(1500)` を超えたら、そのワームホールと出口を確定する。
- 確定済みワームホール・出口は候補から外し、1対1対応を保つ。
- コード上は高S高Nの一部で、出口周囲9点の高低ビットパターンを焼きなまして識別する別ソルバを使う。

## 最終コードの構造

### 状態表現

- `EXIT_CELLS`: 出口セル番号と座標。
- `placement_t`: 温度盤面 `table` と配置コスト `cost`。
- `Tester`: ジャッジ入出力、ローカルシミュレーション、履歴、評価をまとめる。
- `ec_wh_prob[ec][wh]`: `(ec, wh)` の累積対数尤度。
- `wh_req_cnt[wh]`: ワームホールごとの計測回数。
- `detected_wh`, `detected_ec`: 確定済み管理。
- `priority_queue`: 次に試す候補を確信度で管理する。
- `SolverParam`: S/Nごとの温度範囲とソルバ選択を持つ手書き表。

`BitPatternSolver` では追加で次を持つ。

- `around`: 出口周囲9点の相対座標。
- `checkpoint_high`: 盤面上のチェックポイントが高温か低温か。
- `wh_ar_lh_prob[wh][around_id][low/high]`: ワームホールと周囲位置について、その観測が低温/高温のどちららしいかの対数尤度。

### 観測・制約・入力の扱い

- 観測値の確率は、真温度ごとに丸め・クリップ込みの分布を作り、対数で保持する。
- `measure_request(wh, d)` は、ワームホール番号と相対移動を出力し、観測値を読む。
- トーラス上の最短移動は `getroute(src, dest)` で計算する。
- 計測上限は `REQUEST_LIMIT = 10000` として `Tester` が管理する。

### 評価関数

- 観測更新の基本式は、`ec` から移動 `dir` したセルの温度 `expected` に対し、`log_resp_probability(expected, res)` を `ec_wh_prob[ec][wh]` に加える形である。
- 確定判定は、最尤候補と2番手候補の対数尤度差で見る。差が `log(1500)` を超えれば十分確からしいとみなす。
- 優先度付きキューでは、候補の対数尤度と2番手との差を使う。特定ワームホールに計測が偏りすぎたら `-log(4)` のバイアスで優先度を下げる。
- `BitPatternSolver` の配置評価では、同じビット列になる出口の重複を強く罰し、近接チェックポイントで高低が変わることも配置コスト観点で罰する。

### 探索・構築・更新

`ChildLunchSolver` の構築:

- 旗 `high_point` は、全出口からのトーラス最短マンハッタン距離の合計が小さいセルを選ぶ。
- 盤面は低温を基準に、旗から遠いほど少しずつ低くなる山として作り、旗だけ高温にする。
- S/N別の手書き表から低温・高温・傾斜上限を選ぶ。

`ChildLunchSolver` の計測:

- 初期状態では、旗までの距離が近い出口候補ほど少しだけ優先される。
- PQから `(ec, wh)` を取り出し、出口 `ec` から旗へ向かう移動を `wh` に対して計測する。
- 同じ観測を全未確定出口 `ec'` に対して評価し、`ec_wh_prob[ec'][wh]` を更新する。
- 1位と2位の差が閾値を超えたら確定する。
- 残った候補はPQ順で貪欲に割り当てる。

`BitPatternSolver` の構築:

- 各出口の周囲9点を観測位置候補とし、盤面上で重なったチェックポイントをまとめる。
- 各チェックポイントを高温/低温のどちらにするかを焼きなましで決め、出口ごとの9bitパターン重複を減らす。
- チェックポイント以外のセルは中間温度から始め、配置コストが下がるように温度を微調整する。

`BitPatternSolver` の計測:

- 各ワームホールについて、9点のうち高低判定が最も曖昧な位置を選んで計測する。
- 高低尤度と `(ec, wh)` 尤度を同時に更新する。
- 最後は貪欲割当後、割当交換や単一変更の焼きなましで対数尤度合計を改善する。

### 操作・クエリ・出力選択

- 1点高温方式では、クエリの移動は「候補出口から旗までの相対移動」である。
- 優先度付きキューにより、同じワームホールを固定して順に候補を潰すのではなく、確信度が伸びそうなペアを動的に選ぶ。
- 確定した出口は以降の候補から外す。
- 出力は `wh2ec[wh]` を `-1 -1 -1` の後に並べる。

### 時間配分・パラメータ

- 計測上限: 10000。
- 確定閾値: `log(1500)`。
- `BitPatternSolver` の周囲点: 9点。
- `BitPatternSolver` の配置焼きなまし: 周囲パターン約500ms、温度微調整約250ms。
- `BitPatternSolver` の最終割当焼きなまし: 約500ms。
- ソルバ選択と温度値は、S/Nごとの手書きテーブルで決める。

## 実装上重要な断片

```text
measure_child_lunch():
    pop best (ec, wh) from pq
    dir = route(exit[ec], high_point)
    res = measure(wh, dir)
    for each remaining ec2:
        expected = P[exit[ec2] + dir]
        loglike[ec2][wh] += log_prob(expected, res)
    if best_loglike - second_loglike > log(1500):
        fix wh -> best_ec
    else:
        push updated candidates back to pq
```

```text
make_one_peak_placement():
    high_point = argmin_cell sum_ec dist(exit[ec], cell)
    for cell:
        P[cell] = low - min(dx_limit, low/L) * dist(cell, high_point)
    P[high_point] = high
```

## この解法の本質

この解法の強さは、1点の強いアンカーを使って、出口候補の検証を「その出口なら高温が見えるはず」という判定に変換した点にある。盤面全体に大量の情報を埋め込むと配置コストが大きくなるが、1点だけなら配置コストを抑えやすい。その代わり、どの出口候補の相対移動を試すかを尤度で賢く選び、計測コストを抑えている。

もう一つの本質は、観測値を単なる閾値判定にせず、全候補に対する対数尤度として蓄積することである。旗を直接踏めなかった観測も、周辺温度によって候補の絞り込みに使える。

## 真似するならまず実装する部分

まずは `ChildLunchSolver` だけを実装するのがよい。旗の位置を全出口からの距離和最小のセルに置き、低温と高温の2値に近い山を作る。次に、正規分布の対数確率テーブルを作り、`(ec, wh)` の対数尤度を更新する。最初の計測戦略はPQなしで、未確定ワームホールごとに近い出口候補から試すだけでも形になる。

上位化するなら、PQによる候補選択、S/N別の温度表、`BitPatternSolver` のような高S高N向けの符号化を追加する。

## 注意点・未理解点

- 記事本文は1点高温方式中心だが、最終コードにはビットパターン方式も含まれる。提出全体のスコアは両者の切替込みである。
- 温度パラメータは手書き表への依存が大きく、一般式だけでは再現しにくい。
- `ChildLunchSolver` の初期優先度や計測偏りペナルティは経験的な調整である。
- `BitPatternSolver` は記事本文では詳しく説明されていないため、意図はコードからの推測を含む。
- 尤度正規化をしないため、対数で持つ実装が必須である。
