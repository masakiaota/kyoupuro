## 解法の全体像

歩くだけ、端の壁を使う滑走、固定盤面でのBFS、事前に少数の壁を置く貪欲、ビームサーチ、高速化、将来コスト評価、途中経路での壁配置へ段階的に改善している。

最終提出は、目的地を1つ進めるたびに複数の状態を残すビームサーチである。状態は現在位置、固定されたブロック集合、ここまでの行動列、累積コストを持つ。各状態から「壁を置かない」「現在位置の隣に壁を1枚置く」「次目的地への途中で壁を1枚置く」を試し、現在区間の最短経路と残り全区間の概算コストを足した評価値でビーム幅に絞る。

## 主要アイデア

- 壁配置が決まれば、各目的地間の移動手数は BFS で決まる。
- ビーム状態ごとに盤面を持ち、各区間で壁追加候補を試す。
- 未来の目的地になるマスには、まだ訪問前なら壁を置かない。
- 評価値は `ここまでのコスト + 現在の壁盤面で残り目的地を順にBFSした距離和` とする。
- 現在位置だけでなく、次目的地への最短経路の最初数手を進めた地点でも壁を置く候補を作る。
- PHPではビーム幅15程度だったが、C++化により幅400の単純ビーム、最終的には重い途中壁探索込みで幅9に調整している。

## 最終コードの構造

### 状態表現

- `BitGrid = array<uint64_t, MAX_N>`: 各行をbitで持つ壁盤面。
- `Cmd { t, d }`: `M/S/A` と方向。
- `State`:
  - `y,x`: 現在位置。
  - `wallCnt`: 置いた壁の数。
  - `cost`: ここまでの実出力手数。
  - `score`: ビーム選別用評価値。
  - `map`: 壁盤面。
  - `acts`: ここまでの行動列。
- `BFSWork`: BFS用の `prev/type/dir/seen/que` を固定配列で使い回す。

### 観測・制約・入力の扱い

- `P` に目的地列を保持する。
- `forbid[y][x]` に、そのマスが目的地として現れるインデックスを入れる。
- あるステップ `step` で壁を置く候補 `(wy,wx)` について、`forbid[wy][wx] >= step` なら将来訪問前なので禁止する。
- 壁削除は最終提出では扱わない。置いた壁は最後まで残る。

### 評価関数

- 区間候補の実コスト:
  - 壁なし: `st.cost + path.size()`
  - 現在位置で壁1枚: `st.cost + 1 + path.size()`
  - 途中壁: `st.cost + prefix.size() + 1 + tail.size()`
- 評価値:

```text
score = cost + remainCost(map, current_target_position, next_step)
```

- `remainCost` は、現在の壁盤面を固定したまま、残り目的地を順に `bfsLen` で結んだ距離和である。将来さらに壁を置ける効果は見込まない。

### 探索・構築・更新

- `bfsPath` は、1マス移動4方向と滑走4方向を同じコスト1の辺として BFS し、経路を復元する。
- `bfsLen` は経路復元なしの距離計算で、残りコスト推定に使う。
- 各目的地 `step` について、現在のビーム `cur` から次状態 `nxt` を作る。
- 遷移候補は3種:
  - 壁なしで次目的地まで最短移動。
  - 現在位置の隣接4マスのうち置ける場所に壁を1枚置き、次目的地まで最短移動。
  - 現在の最短経路を先頭 `PREFIX_LEN=6` 手まで進め、その途中位置の隣接4マスへ壁を1枚置いて残りを再探索。
- 候補を `score` 昇順、同点なら `cost` 昇順でソートし、ビーム幅分だけ残す。

### 操作・クエリ・出力選択

- ビーム終了後、`cur.front().acts` をそのまま出力する。
- 壁を置く操作は候補生成時に `A d` として行動列へ挿入する。
- 目的地への到達は常に `bfsPath` の復元経路で保証する。

### 時間配分・パラメータ

- 最終提出の主な定数:
  - `MAX_WALL = 20`
  - `BEAM_SIZE = 9`
  - `PREFIX_LEN = 6`
- 中間提出では C++ 化後に `BEAM_SIZE = 400` の単純ビームを使っていた。
- 最終提出は途中経路での壁候補が重く、実行時間が 1996ms と制限近い。

## 実装上重要な断片

```text
for step in 1..M-1:
    nxt = []
    for st in beam:
        add candidate without wall
        for each direction:
            if adjacent cell can receive a wall:
                add candidate with A at current position
        mid = best wall inserted within first PREFIX_LEN moves
        if mid exists:
            add mid

    sort by (cost + remaining_bfs_distance, cost)
    beam = first BEAM_SIZE states
```

```text
remainCost(map, y, x, step):
    sum = 0
    for i = step..M-1:
        d = bfsLen(map, y, x, P[i])
        if unreachable: return INF
        sum += d
        (y, x) = P[i]
    return sum
```

## この解法の本質

この解法は、ブロック配置を直接のスコア差で評価するのではなく、「固定した壁盤面で残りを全部歩いたらどれだけ短いか」を使って局所的な壁追加を選んでいる。現在区間だけで得な壁ではなく、残り全体でも得そうな壁を残すため、単純貪欲より安定しやすい。

また、現在位置だけでなく移動途中の地点でも壁を置ける候補を作った点が重要である。ブロックは置いた場所そのものより「どの位置から置けるか」が制約になるため、経路途中の自由度を候補化すると使える停止壁が増える。

## 真似するならまず実装する部分

まず `bfsPath` と `remainCost` を作り、壁なし候補と現在位置で隣接壁を1枚置く候補だけのビームを実装するのがよい。盤面は 20x20 の `bool` 配列でも十分始められる。

その後、ビーム幅を増やす、壁盤面をbit化する、途中壁候補を入れる、BFS作業配列を使い回す、という順に強化すると理解しやすい。

## 注意点・未理解点

- 壁削除をしないため、未来目的地を塞がない制約が非常に重要である。
- `remainCost` は将来壁を置ける効果を見ないため、評価が保守的になる。
- 途中壁候補は強いが重い。`PREFIX_LEN` とビーム幅の調整を間違えるとTLEしやすい。
- 壁を置く操作の1手を `cost` に入れ忘れると、壁を過大評価する。
- 記事中の中間提出はAIによる実装も含まれており、手作業の設計意図とコードの細部が完全に対応しているとは限らない。
