## 解法の全体像

0番から順に次の目的地へ向かう貪欲解だが、単に現在の盤面で最短路を取るのではなく、「過去にそのブロック操作をしていたことにする」余地を探索に入れる。移動列とブロック変更列を分けて保持し、あるターンで隣接マスを変更できたという情報を後から使って、滑走の停止用ブロックを過去の出力位置へ挿入する。

これにより、未来で「ここに壁があれば滑走で止まれる」と分かった時点で、過去にそのマスの隣にいたターンを探し、そこへ `A` 操作を挿入する。移動・滑走の本体列は変えず、各移動ターンの前に挿入するブロック操作列だけ増やすため、過去挿入で後続の移動復元が崩れにくい。

## 主要アイデア

- 各マスについて、そのマスをブロック変更できる過去ターン `canChange` を記録する。
- 移動本体 `res` と、そのターン直前に行うブロック操作 `res2[turn]` を分ける。
- 次目的地への経路探索では、既存ブロックだけでなく、過去に作れそうなブロックも滑走停止候補として扱う。
- すでにあるブロックへ1マス移動したい場合は、過去または直前に除去してから移動するため追加コストを払う。
- 経路上で通過したマスや変更したマスの変更可能情報を消し、あとからそのマスをブロック化して経路を壊すことを避ける。
- 経路探索中に必要ブロックの整合性を持つか、操作を復元してから壊れていないか確認する必要がある。
- 延長戦では、ブロック削除も同じ考えで過去改変し、さらに探索中に過去改変を使うか乱択して複数回試す方針が示されている。

## 最終コードの構造

### 状態表現

- `Solver` が全状態を持つ。
- `canChange[y][x]`: マス `(y,x)` をブロック変更できる過去ターンの列。
- `create[y][x]`: そのマスにブロックを作った履歴ターン。番兵を持つ。
- `remove[y][x]`: そのマスのブロックを除去した履歴ターン。番兵を持つ。
- `visited[y][x]`: そのマスにいたターンの列。
- `res`: 移動・滑走の行動列。
- `res2[t]`: `res[t]` の前に挿入する `A` 操作列。
- `cy,cx`: 現在位置。`ny,nx`: 次目的地。
- 経路探索内では 20x20 の盤面を `BitSet[400]` で持ち、ヒープ要素に現在の壁状態も含める。

### 観測・制約・入力の扱い

- 入力は `N,M` と目的地列 `YX` をそのまま保持する。
- 目的地を順に処理し、各区間ごとに現在位置から次目的地への経路を復元する。
- 盤外は滑走停止条件として扱われるが、`A` 操作の対象にはしない。
- 経路上で実際に乗るマスについては `canChange` を消す。あとからそのマスをブロックに変えると出力が不正になるためである。
- 滑走で利用した停止ブロックをあとから除去する、または経路中の通過マスをブロック化するような矛盾を避ける必要がある。

### 評価関数

- 基本は次目的地までの行動数最小化である。
- 記事では、ブロック変更を挟む遷移があるため単純BFSではなく Dijkstra または 0-1-2 BFS が必要と説明されている。
- 提出コードでは、隣接ブロックを除去して1マス進む遷移はコスト2として扱う。
- 滑走停止用ブロックの過去作成については、提出コード上のコスト扱いが記事説明ほど明確には読み切れなかった。出力長は `res2` 挿入分だけ増えるため、探索距離と最終行動数が完全一致していない可能性がある。

### 探索・構築・更新

- `bfs` という名前だが、ヒープを使う Dijkstra 型探索で次目的地への経路を復元する。
- 通常移動:
  - 隣接マスが空ならコスト1で移動。
  - 隣接マスが壁なら、除去を含めてコスト2で移動できる候補とする。
- 滑走:
  - 現在方向へ進み、盤外・壁・過去に作れるブロック候補の直前で停止できるとみなす。
  - 停止に必要なブロック候補が現在はない場合、ヒープ内の壁bitを一時的に立てて探索を続ける。
- 復元後:
  - 各移動開始マスの隣接4マスについて、そのターンに変更可能と記録する。
  - 1マス移動先が壁なら `res2[turn]` に除去操作を追加する。
  - 滑走停止位置の次マスに壁を作る必要があれば、そのマスを変更できる過去ターンを探して `res2[past_turn]` に作成操作を追加する。

### 操作・クエリ・出力選択

- 経路の隣接2点がマンハッタン距離1なら `M`、それ以外なら `S` として出力する。
- 各 `res[i]` を出力する前に、`res2[i]` に溜めた `A` 操作をすべて出力する。
- 目的地は順番通りに処理し、区間ごとの復元経路をそのまま採用する。

### 時間配分・パラメータ

- 記事の本番提出は実行時間 7ms とされ、時間には大きな余裕がある。
- 延長戦では、探索中に過去改変を使う確率を90%にして、時間いっぱい複数回実行する乱択山登りが紹介されている。
- リンク先提出コード自体には、時間いっぱい回す外側ループは見当たらなかった。

## 実装上重要な断片

```text
for each target k:
    path = dijkstra(current_position, target[k], wall_history, canChange)
    for each segment in restored path:
        turn += 1
        record adjacent cells as changeable at turn
        clear changeability on cells used by the segment
        if segment is one-step:
            output M
            if destination currently blocked:
                insert remove action before this turn
        else:
            output S
            if stopper block can be created in the past:
                insert create action at that past turn

for each turn:
    output inserted A actions
    output movement action
```

## この解法の本質

この解法の核は、ブロック操作を「実行時刻のある別レイヤー」として持ち、後から必要になったブロックを過去に挿入できる形にした点である。スケート問題では、あるブロックが未来の滑走停止に効くかどうかは、そのブロックを置く時点では分かりにくい。そこで、過去に置けた場所を予約情報として蓄積し、必要性が判明してから過去の出力へ追加する。

これは短期AHCで強い考え方で、状態構築を前から完全に決め切るのではなく、「将来の最短路探索で必要になったものを、過去の自由度に割り当てる」形にしている。

## 真似するならまず実装する部分

まずは、現在の固定盤面で `M` と `S` を使う最短路BFSを書き、目的地を順に訪問する貪欲を作る。次に、各ターンで隣接4マスを `canChange` に記録し、滑走停止位置の1マス先に「過去に作れる壁」があるなら `A` を過去ターンへ挿入する部分だけを実装する。

削除の過去改変、経路破壊チェック、乱択山登りは後から足すべきである。最初から全部入れると、出力列の整合性確認が難しくなる。

## 注意点・未理解点

- 過去に挿入した `A` により、その後の移動・滑走経路が変わらないことを必ず確認する必要がある。
- 移動で乗るマス、滑走で通過するマス、停止に使ったブロックは、変更候補から消すか依存関係として保持する必要がある。
