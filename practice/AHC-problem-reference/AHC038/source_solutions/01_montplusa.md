## 解法の全体像

箒型の木を固定し、1ターンを1深さとするビームサーチで操作列を作る。各状態からは根の移動5通りと非葉頂点の回転を全探索し、葉の回転と掴む・置く操作はその場で貪欲に決める。状態評価は「これまで何回掴む・置くが進んだか」を主軸にし、改善版では中心から遠いマスを先に処理するボーナスを微小に加える。

記事は最終3位コードそのものではなく、3位解法の核に近いビームサーチの作り方を、段階的なサンプル提出で説明している。

## 主要アイデア

- 深さをターン数、盤面評価を進捗量にする。スコア最小化問題を「同じターン数なら進捗が大きい状態を残す」問題に変換する。
- 木は `0-1-2` を柄にして、頂点2から複数の葉を伸ばす箒型にする。
- 根移動と柄の回転だけを全探索し、各葉は独立に `.`/右/左の3通りから、拾える・置けるなら最良の回転を選ぶ。
- 盤面コピーが重いので、候補手を適用する前に見込み評価を計算し、ビーム上位に入らない候補を捨てる。
- `N <= 30` なので、たこ焼き盤面は行ごとのbit列にしてコピーコストを下げる。
- 終盤で狙った場所へ入れやすくするため、中心から遠い初期たこ焼き・目的地を優先して処理する。

## 最終コードの構造

記事中の最終サンプル #58878428 を主に読む。

### 状態表現

- `GameConst`: `N, M, V`、初期盤面、目的盤面、初期から完了済みの個数。
- `TakoyakiPlate`: 各行を整数bit集合で持つ盤面。たこ焼きの有無と個数を管理する。
- `Tree`: 親配列、辺長、非葉頂点数。箒型を前提にする。
- `GameState`: 根座標、各頂点の親に対する相対角、各頂点が持っているか、現在盤面、進捗、ターン、中心距離ボーナス、ビーム復元用の親indexと直前Action。
- `Action`: 根移動、各頂点の回転、各頂点の `P` 操作。
- `BeamSearchQueue`: 候補状態を評価値順に上位幅だけ残す簡易priority queue。

### 観測・制約・入力の扱い

- 入力の初期盤面と目的盤面をbit盤面に変換する。
- 初期から目的地にあるたこ焼きは完了済みとして数える。
- 根座標は盤面中心から開始する。
- 根移動が盤面外になる候補は列挙しない。アーム自体は盤面外に出てもよいので、葉が盤面外のときだけ掴む・置く候補から外す。

### 評価関数

- 基本評価は `Progress + 今ターンのP操作数 + 乱数微小項`。
- 改善版は、状態適用後の `BonusValue` を微小係数で加える。
- `BonusValue` は、拾った・置いたマスの盤面中心からのマンハッタン距離の累積である。
- 進捗が同じなら中心から遠い場所を処理した状態を優先する意図がある。

### 探索・構築・更新

- ビーム幅は初期版100、高速化後300。
- 1ターンの候補:
  - 根移動: `.` と上下左右の最大5通り
  - 柄の非葉回転: 実装では3頂点想定で `3 * 3`
  - 葉の回転: 各葉ごとに独立に貪欲決定
- `decideGreedily` が各候補の葉操作を決める。
- `TryPossibleActions` は、まず候補Actionの `P` 数から見込み評価を計算し、キューの下限に届かない候補は状態コピー前に捨てる。
- 状態適用時に根、相対角、頂点座標、盤面、持っているフラグ、進捗を更新する。

### 操作・クエリ・出力選択

- 探索で完了状態を見つけたら、各深さの状態に保存した `PrevIndex` と `PrevAction` をたどって操作列を復元する。
- 出力は木、初期根座標、復元した各Actionを問題の2V文字形式に変換したもの。

### 時間配分・パラメータ

- サンプルコードは深さ上限10000、ビーム幅100または300。
- 候補手の早期棄却、bit盤面、評価の簡素化でTLEを削減する。
- ランダム微小項により同点状態の偏りを少し崩す。

## 実装上重要な断片

```text
for state in current_beam:
    for root_move in 5 directions:
        for handle_rotation in 3^num_handle:
            action = greedy_decide_leaf_rotations(state, root_move, handle_rotation)
            optimistic = state.progress + count_pick_or_put(action)
            if not promising(optimistic):
                continue
            next = copy_and_apply(state, action)
            next.value = optimistic + small_bonus(next)
            push_to_next_beam(next)
```

```text
        tie-break by distance from board center
```

## この解法の本質

1ターンに多くの操作を同時にできる問題を、完全な1手全探索ではなく「骨格の動きは探索、指先の細部は貪欲」に分解している点が本質である。ビームサーチは進捗が同じでも別の未来を残せるため、貪欲が終盤で詰まるリスクを下げられる。さらに、評価を厳密な距離最小化にせず「処理回数」という安い指標に寄せることで、状態数を稼いでいる。

## 真似するならまず実装する部分

まず箒型の木、bit盤面、`decideGreedily`、ビーム幅50程度の単純ビームを作るのがよい。最初は中心距離ボーナスや早期棄却を入れず、`Progress` だけで完了解が出ることを確認する。次に状態コピーを軽くし、候補適用前の `P` 数評価で棄却する。

## 注意点・未理解点

- 記事の最終3位提出そのものは公開されていない。読めたのは記事用サンプル提出である。
- `3頂点の柄` を前提にした候補列挙は木の形と強く結びついている。木を変えるなら候補列挙も直す必要がある。
- 葉を独立に決める前提は、葉長が異なり同じ対象を取りにくい構成に依存する。葉位置が衝突する木では予約集合が必要になる。
- ビーム幅、微小乱数、ボーナス係数はパラメータ依存で、再現性と安定性の調整が必要である。
