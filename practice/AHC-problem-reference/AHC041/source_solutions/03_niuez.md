## 解法の全体像

各頂点の高さ `h[i]` を直接状態として焼きなます。高さ列が実行可能である条件は、`h[i]=0` で根になるか、隣接頂点 `j` に `h[i]=h[j]+1` が存在することである。したがって木構造を直接持たず、高さだけを更新し、最後に高さ差1の辺から親を復元する。

遷移は主に、頂点 `i` の高さを隣接頂点 `j` の高さ `h[j]+1` に変える、頂点 `i` を根 `0` にする、隣接2頂点の高さを swap する、の3種類である。高速化のため、各頂点について「高さ `x` の隣接頂点が何個あるか」を持ち、遷移後に親候補を失う頂点がないかを局所的に判定する。

提出コードでは全頂点高さ0から開始し、約2秒で高さ列を焼きなまし、最後に親配列へ復元する。

## 主要アイデア

- 状態は `h[i]` のみで、木の親子関係は最後に復元する。
- 実行可能性は隣接高さカウントで高速に判定する。
- 一点更新では、自分の高さ変更で「自分を親候補としていた隣接頂点」が親を失わないかだけを見る。
- swap では、隣接2頂点とその周辺だけを確認する。
- スコア差分は高さが変わった頂点だけで計算できる。
- `h=0` へ戻す遷移は、孤立的に扱いたい低価値頂点を根にしたり、根の位置を動かす効果がある。
- 可視化から、単純な高さ更新や swap でも根・葉・高さ10周辺がかなり柔軟に動くことを確認している。

## 最終コードの構造

### 状態表現

- `V: [i32; N]`: 各頂点の高さ。提出コードでは全て0で初期化。
- `now_score`: `sum A[i] * (V[i]+1)` から定数項を除いた高さ寄与を管理している形。
- `neibor_levels[i * 12 + h]`: 頂点 `i` の隣接頂点のうち高さ `h` の個数。
- `Input.E`: 辺リスト。
- `Input.G`, `Input.S`: CSR 風の隣接リスト。
- `Input.B`: 隣接判定用 bitset。swap の局所判定で使う。
- `P`: 出力用親配列。

### 観測・制約・入力の扱い

- 入力の座標は読んでいるが、最終コードでは解法本体に使っていない。
- 高さは `0..10` に保つ。隣接頂点が高さ10なら `h_j+1` は不可なので遷移を捨てる。
- 各 `h[i]>0` について、隣に高さ `h[i]-1` が存在することを保つ。
- 遷移前に `h[i]` を変更すると、隣接頂点で `h=old+1` だった頂点が親候補を失う可能性があるため、それを `neibor_levels` で確認する。

### 評価関数

- 差分は一点更新なら `A[i] * (new_h - old_h)`。
- swap なら `A[i] * (h[j]-h[i]) + A[j] * (h[i]-h[j])`。
- 焼きなましでは差分が正なら採択、負なら `exp(delta / T)` で採択する。

### 探索・構築・更新

- 温度は `T0=150.20`, `T1=1.6` の線形減衰。
- 時間制限は約1.998秒。
- 遷移1:
  - 頂点 `i` を選ぶ。
  - 隣接頂点のどれか、または根化を表す番兵を選ぶ。
  - 隣接を選んだら `V[i]=V[j]+1`、番兵なら `V[i]=0`。
  - スコア差分で焼きなまし採択判定を先に行う。
  - 隣接頂点が親候補を失わないか確認してから、`neibor_levels` を更新する。
- 遷移2:
  - 辺 `(i,j)` を選び、`V[i]` と `V[j]` を swap する。
  - swap 後に `i,j` 自身が親候補を持つか、周辺頂点が親候補を失わないかを確認する。
  - `neibor_levels` を両端周辺で差分更新する。

### 操作・クエリ・出力選択

- 最後に全辺を見て、高さが1大きい側の親を小さい側に設定する。
- 親が見つからない頂点は `-1` として根になる。実行可能性を保っているので、これは高さ0の頂点になるはずである。

### 時間配分・パラメータ

- 提出コードの制限時刻は `TL=1.998`。
- 遷移種別は一点更新系が50%、swap系が50%。
- 記事では seed 0000 で約30,807,873回の遷移候補を試せたと述べている。
- ベスト保存はコード上では最後の状態を採用している。Jirotech さんの関連コードはベスト解を保持する実装だった。

## 実装上重要な断片

```text
can_change(i, old_h, new_h):
    for j in adj[i]:
        if h[j] == old_h + 1:
            if count_neighbor_height[j][old_h] <= 1:
                return false
    return true
```

```text
apply_change(i, new_h):
    old_h = h[i]
    score += A[i] * (new_h - old_h)
    for j in adj[i]:
        count_neighbor_height[j][old_h]--
        count_neighbor_height[j][new_h]++
    h[i] = new_h
```

```text
restore_parent():
    parent = [-1] * N
    for (u, v) in edges:
        if h[u] + 1 == h[v]: parent[v] = u
        if h[v] + 1 == h[u]: parent[u] = v
```

## この解法の本質

高さ列は、スコア差分が小さく、実行可能性判定も局所化しやすい表現である。木を直接操作すると部分木全体の高さや閉路を管理する必要があるが、高さ列なら「自分が親を持つか」「自分を親としていた隣が別の親を持つか」に分解できる。

また、`h=0` 化と swap は単純に見えるが、可視化すると根の移動や葉の役割交換に近い働きをしている。少数の近傍で広い構造変化を起こせる点が強い。

## 真似するならまず実装する部分

まず全頂点 `h=0` から始める高さ焼きなましを作る。近傍は「隣接頂点+1にする」と「0にする」だけでもよい。次に `count_neighbor_height[v][h]` を導入し、局所チェックを高速化する。

swap 近傍はバグりやすいが効くため、単体テストやデバッグ検証を入れてから追加するとよい。

## 注意点・未理解点

- 記事にもある通り、親方向の復元を逆にすると混乱しやすい。高さが1小さい隣接頂点が親である。
- `neibor_levels` の更新順序を間違えると、実行可能性判定が壊れる。
- swap の周辺チェックは一点更新より複雑で、`i,j` が互いに代替親になる場合を正しく扱う必要がある。
- 可視化用コードは画像掲載であり、テキストとしての詳細は読めなかった。
- Jirotech さんの関連提出は、`invalidCount` に大罰則をかける評価と複数近傍を持つ類似の高さ焼きなましで、niuez さん本文の「近傍の種類が多い」という記述と一致していた。
