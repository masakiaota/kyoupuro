## 解法の全体像

上位勢の主流である焼きなましではなく、ビームサーチを主方針にした解法である。密な配置を作るための「良い長方形」を `ok_rect` として事前に決め、縦横格子・斜め格子のパリティから16パターンを列挙する。それぞれのパターンを初期条件としてビームサーチし、非 `ok_rect` の遷移で状態を進めた後、新たに合法になった `ok_rect` は必ずすべて適用する。

最後に、最良パターンに対して chokudaiサーチを行い、余った時間を使う。

## 主要アイデア

- ビームサーチで生スコアだけを見ると、途中状態評価が難しく伸びにくい。
- そこで、密に伸びる最終形に近い `ok_rect` を定義する。
- 縦横格子と斜め格子のパリティの組み合わせを16パターン列挙する。
- 「確実に前進」を意識し、1操作をそのまま遷移にせず、明らかに良い `ok_rect` の自動適用まで含めて1遷移にする。
- 最初の20ターンは多様性確保のため、生スコア以外の評価と乱数を使う。
- Zobrist Hash で同一盤面を重複除去する。
- 20ターンまでは各パターンが最低10個残るようにし、パターン多様性を保つ。

## 最終コードの構造

Browserで AtCoder 提出 `35267569` を読んだ。以下は記事本文と提出コードから確認できた構造である。

### 状態表現

- `State`: 現在盤面、使用辺、候補、描画済み長方形列を持つ。
- `StateInfo`: スコア、`ok_nums`、パターン、ハッシュ、直前状態などを持つビーム要素情報。
- `Rect`: `is_ok` を持ち、`_is_ok(pattern)` で16パターンに対する良い長方形か判定する。
- `Hash`: 点と辺の Zobrist Hash。`grid_hash` と `used_hash` を組み合わせる。
- `applyAllOkRect`: 合法になった `ok_rect` を deque に積んで全適用する。
- `transferBeam`: 優先度キューから次ビームを作り、重複ハッシュを捨てる。

### 観測・制約・入力の扱い

- 16種類のパリティパターンを先に作る。
- 各状態で合法な非 `ok_rect` を主遷移として列挙する。
- 非 `ok_rect` を適用した後、合法になった `ok_rect` をすべて適用する。
- 斜め格子のほうがパリティの噛み合わせで重要と見て、縦横格子を先に使い斜め格子を温存するよう候補管理を調整する。

### 評価関数

- 最初の20ターンだけ多様性用の評価を使う。
  - `ok_rect数^0.25 * 生スコア * [0.9, 1.1] の乱数`
  - `ok_rect数 * [0.9, 1.1] の乱数`
- それ以降は生スコアを使用する。
- `ok_rect` を必ず適用するため、評価関数だけでなく遷移設計にも「良い状態へ進む」圧力を入れている。

### 探索・構築・更新

- 16パターンを初期状態にしてビームサーチを行う。
- 遷移は主に非 `ok_rect` を1つ適用すること。
- その後、新たに合法になった `ok_rect` を全適用する。
- Zobrist Hash で既出状態を捨てる。
- 最初の20ターンではパターンごとの最低保持数を確保する。
- 時間が余ったら、最良パターンで chokudaiサーチを行う。この段階では `ok_rect` 全適用の制約を少し緩める。

### 操作・クエリ・出力選択

- ビームまたは chokudaiサーチで得た最良状態の長方形列を出力する。
- 自動適用した `ok_rect` も操作列に含める必要がある。

### 時間配分・パラメータ

- 最初の20ターンは多様性確保フェーズ。
- 20ターンまでは各パターン最低10状態を保持する。
- chokudaiサーチは、通常のビームで時間が余ることへの対処として使われ、得点寄与は5%未満と述べられている。
- メモリ対策として `quick_exit` の利用に触れている。

## 実装上重要な断片

```text
beam_transition(state, non_ok_rect):
    if non_ok_rect is legal:
        apply(non_ok_rect)
        while exists newly legal ok_rect:
            apply(all such ok_rects)
        if zobrist_hash is unseen:
            push next state
```

```text
first_20_turn_eval(state):
    return max(
        ok_count^0.25 * raw_score * random(0.9, 1.1),
        ok_count * random(0.9, 1.1)
    )
```

## この解法の本質

この解法は、ビームサーチの弱点である途中評価の難しさを、評価関数だけでなく遷移設計で補っている。`ok_rect` を「確実に前進する操作」としてまとめて適用し、ビーム幅を悪い途中状態に使わないようにしている。一方で、事前に決めたパリティパターンに強く依存するため、焼きなましほど柔軟にパターンの噛み合わせを調整できない。

## 真似するならまず実装する部分

まず `ok_rect` を1種類のパターンだけで定義し、非 `ok_rect` 適用後に合法 `ok_rect` を全適用するミニビームを作るのがよい。次に16パターン、Zobrist Hash、最初20ターンの多様性維持を追加する。chokudaiサーチは最後でよい。

## 注意点・未理解点

- 提出コードでビーム幅、`ok_rect` 自動適用、Zobrist Hash の実装は確認できた。ただしA-FinalはTLEで、システムテスト上の実行時間リスクは残る。
- `ok_rect` を事前固定するため、パリティの噛み合わせを柔軟に作り替えにくい。
- 記事本人も、焼きなましへ方針転換できなかった点を反省として挙げている。
- 疎なケースでは、この密パターン前提のビームが弱くなりやすい。
