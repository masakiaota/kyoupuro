## 解法の全体像

公式解説は、素手主体の自明解から始め、武器ダメージの分布が強く偏っていることを利用して「大きい攻撃を無駄にしない」方向へ段階的に改善する流れである。前半は開ける宝箱を逐次決める貪欲、途中で宝箱順序を焼きなましの解表現にする案、後半で「攻撃割当を先に決め、DAG制約を満たすものだけ採用する」見方へ移る。

最終的に強い方向として示されているのは、各武器の各耐久回数をどの宝箱へ使うかを直接解として持ち、攻撃先変更を焼きなます方法である。武器 `i` で宝箱 `j` を攻撃する割当は、開封順において `i` が `j` より先でなければならないため、有向辺 `i -> j` とみなす。割当グラフが DAG なら、トポロジカル順で実行可能な攻撃手順に変換できる。

## 主要アイデア

- 入力生成上、`A[i][j]` は 1 桁が多く、高ダメージの組は希少である。
- 単に手持ち武器で最大ダメージを選ぶだけでは、後で代替が効かない攻撃を逃す。
- 攻撃の価値を `min(A[i][j], H[j]) / 残っている武器群が宝箱jへ与えられる総ダメージ` のように正規化し、希少な攻撃を優先する。
- 宝箱を開ける一撃にはボーナスを与え、早く武器を増やす。
- `box_bonus[j]` を山登りし、早く開けたい宝箱への攻撃価値を補正する。
- 攻撃割当を有向辺として扱い、サイクルができる割当を禁止する。
- 上位方針では、各武器の攻撃先候補を `A[i][j]` 上位 20 個程度に絞り、1回の攻撃先を変更または未使用化する近傍を焼く。

## 最終コードの構造

コードなし。以下はスライドから読み取れる実装構造である。

### 状態表現

- `H[j]`: 現在またはシミュレーション上の宝箱残り硬さ。
- `C[i]`: 武器 `i` の残り使用可能回数。
- `assignment[i][k]`: 武器 `i` の `k` 回目の使用先。未使用も持てる。
- `damage_sum[j]`: 残り武器が宝箱 `j` へ与えられる総ダメージ、または二乗重み付き総量。
- `box_bonus[j]`: 宝箱 `j` への攻撃評価に掛ける補正係数。
- `graph`: 採用済み攻撃を辺 `i -> j` とする有向グラフ。

### 観測・制約・入力の扱い

- `N=200`、`H=100..500`、`C=1..6` なので、全攻撃スロット数は最大 1200。
- `A[i][j]` は高い値が少ないため、候補を上位値に絞ることが効く。
- 実行可能性は、武器 `i` を使う前に宝箱 `i` が開いていて、対象 `j` がまだ開いていることに対応する。
- 攻撃割当では、辺 `i -> j` のグラフが DAG ならトポロジカル順で出力可能である。

### 評価関数

- 基本スコアは `sum(H) - T + 1` なので、攻撃回数 `T` の最小化と同値である。
- 武器攻撃の単純価値は `min(A[i][j], H[j])`。
- 希少性を入れる評価として、宝箱 `j` へ残り武器が与えられる総量で割る。
- 公式スライドでは、分子・分母を二乗した `min(A[i][j], H[j])^2 / Σ A[x][j]^2 * C[x]` 型も少し良いとされている。
- 開封攻撃ボーナス、`H[j] <= 5` の宝箱を素手で先に開ける処理、`box_bonus[j]` による補正が追加改善として示されている。

### 探索・構築・更新

- 初期段階の貪欲:
  - 手持ち武器があれば、未開封宝箱との組で最大評価の攻撃を行う。
  - 手持ち武器がなければ、硬さ最小の宝箱を素手で開ける。
- 順序焼き:
  - 宝箱順序を解として持ち、swap や一点移動で順序を変更する。
  - その順序に対して貪欲シミュレーションで評価する。
- DAG貪欲:
  - `(武器, 宝箱)` を評価値順にキューへ入れる。
  - 出次数上限と DAG 制約を満たすなら採用する。
  - 宝箱残り硬さが変わったら評価値を更新して再投入する。
- 直接焼き:
  - 攻撃スロットの対象を別宝箱または未使用へ変える。
  - スコア差分と受理判定は O(1) に寄せる。
  - DAG判定は受理候補に対してだけ O(N) 程度で行う。

### 操作・クエリ・出力選択

- 最終割当が DAG ならトポロジカル順に宝箱を開ける。
- 各宝箱 `v` を開ける前に、すでに開いた武器から `v` への採用済み攻撃を出力する。
- 残り硬さは素手攻撃 `-1 v` で埋める。
- 開いた宝箱を攻撃する出力は WA なので、割当から出力へ変換する際に対象の開封前に攻撃を置く。

### 時間配分・パラメータ

- 閾値貪欲では、弱い攻撃を使わない閾値として 10 から 30 程度を試す。
- `box_bonus` 山登りは 2000 回程度しか回らず、遷移で一度に10箇所ほど変えるのが良かったとされる。
- 直接焼きでは、各武器の攻撃先候補を `A[i][j]` 上位20件程度に絞る。
- サイクル判定は高コストなので、受理候補にのみ行う。

## 実装上重要な断片

```text
evaluate_attack(i, j):
    gain = min(A[i][j], remaining_h[j])
    rarity = sum_over_weapons(A[x][j]^2 * remaining_c[x])
    return box_bonus[j] * gain^2 / max(1, rarity)

try_change(slot, new_target):
    old_delta = local_score_delta(slot)
    change assignment tentatively
    new_delta = local_score_delta(slot)
    if annealing_accept(new_delta - old_delta):
        if graph_is_dag():
            commit
        else:
            rollback
    else:
        rollback
```

## この解法の本質

この問題は「次にどの宝箱を開けるか」だけを考えると見通しが悪い。強い攻撃は数が少なく、どの宝箱に使うかを先に決めた方が、素手回数削減という目的に直接近づく。攻撃割当を DAG 制約付きの辺集合として見ると、手順生成の複雑さが「サイクルを作らない」という明確な制約へ落ちる。この見方が、貪欲・山登り・焼きなましの共通土台になっている。

## 真似するならまず実装する部分

まずは DAG 貪欲を実装するのがよい。全 `(i,j)` を `min(A[i][j], 残りH[j])-1` または希少性補正付き評価で優先度順に処理し、武器出次数上限とサイクル禁止を満たす辺だけ追加する。これで、解表現・実行可能性・出力生成を理解できる。その後、攻撃先候補を上位値に絞った局所探索または焼きなましへ拡張する。

## 注意点・未理解点

- 公式スライドはコードを公開していないため、最終焼きなましの細かい差分更新は推測を含む。
- 親agentの提出一覧調査でも tomerun の該当ACは拾えなかったため、実装ベースの確認はできていない。
- `box_bonus` の更新幅、温度、候補選択確率はスライドだけでは再現できない。
- 「受理された場合だけ DAG 確認」は高速化として重要だが、受理後にサイクルで棄却する場合のスコア差分ロールバックを壊しやすい。
- DAG 割当から出力へ変換するとき、開いた宝箱への攻撃を出さない順序化が必須である。
