## 解法の全体像

単語の順序をビームサーチで決め、各遷移のコストは事前計算したDPで高速に評価する解法である。開始30分の考察として、作る文字列や単語順が決まっていればDPで最適経路が作れること、しかし良い順序を探す必要があることを見抜き、2-opt よりビームサーチを選んでいる。

ビーム探索の評価では、単語ごとの「作りやすさ」を base cost として定義し、累積コストからそれを引くことで、単語自体が難しいだけの状態が不当に悪く見えないようにしている。

## 主要アイデア

- 固定文字列または固定単語順に対する最短キー列はDPで求められる
- 単語順序の探索にはビームサーチを使う
- 2-opt は有向の相性を壊しやすく、`T_i -> T_j` が良くても `T_j -> T_i` が良いとは限らない
- `T_i` の後に `T_j` を付けるときの遷移コストを、終端マス込みで事前計算する
- ビーム状態は「決定済みの単語順序」と「最後のマス」を持つ
- 各単語の base cost を用意し、ビーム中の評価から差し引く
- base cost は最初は全開始マスからの最小コスト平均を使い、調整で平均の0.8倍を試した。後から公式解説と同様に全開始マスに対する最小値へ変更したところ改善した

## 最終コードの構造

BrowserでAtCoder順位表から提出 #49253677 を辿り、C++コードを読めた。以下は提出コードと記事本文を合わせた構造である。

### 状態表現

- 単語 `T_i` をノードとして扱う
- マス `(x,y)` または1次元化した位置を終端状態として持つ
- 遷移前単語 `T_i`、次単語 `T_j`、前単語の終端マス、次単語の終端マスを添字にした遷移コスト表を持つ
- ビーム状態は、使用済み単語集合、これまでの単語順、最後の単語、最後のマス、評価値を持つ構造だと考えられる
- 提出コードは大きなクラス分割ではなく、前計算配列、候補列 `cand` / `ncand`、DP配列を `main` 中心に持つ実装である

### 観測・制約・入力の扱い

- キーボード上の各文字の出現位置を列挙しておく
- ある単語をどのマスで終えるかが後続コストに効くため、単語単位の最小コストだけでなく終端マスを区別する
- 全単語を含める前提で探索する
- 記事本文では単語間重なりの扱いの詳細は明記されていないが、`T_i` の次に `T_j` を付ける遷移コストを計算するため、前後の重なりも遷移DP側で考慮していると読むのが自然である

### 評価関数

- 生の遷移コストだけでは、もともと作りやすい単語を優先しがちになる
- 単語 `t` の base cost を「ある開始マスから `t` を作る最小コスト」の集約値として定義する
- コンテスト中は、全 `N^2` 開始マスからの最小コスト平均を使い、0.8倍程度にしたものが良かったとされる
- 後実験では、全開始マスに対する最小値を base cost にする方が良かった
- ビームの評価は概念的に `累積遷移コスト - 使用済み単語のbase cost和`

### 探索・構築・更新

- すべての単語対と終端位置の組について、接続コストを前計算する
- ビームサーチでは各状態から未使用単語を追加し、追加後の最後のマスごとに候補を作る
- 各深さで評価値の良い状態だけを残す
- 記事中で、初提出時はビーム幅を誤って2にしていたが、70に直して大きく改善したとある
- 残り時間では高速化と base cost の計算方法の調整を行っている
- 提出コードでは単語追加候補を `sort` で絞り、`cand` と `ncand` を入れ替えながらビームを進める

### 操作・クエリ・出力選択

- ビームで最良の単語順と終端マス列を得る
- 各遷移DPの復元情報を使って座標列を出力する構造だと考えられる
- 出力は全単語を含む座標列であり、操作回数は上限5000に収まる

### 時間配分・パラメータ

- 記事中で明記されているビーム幅は70
- base cost の係数として、平均値の0.8倍程度が良かったとされる
- 実装言語はビームサーチの速度を重視してC++

## 実装上重要な断片

単語間遷移コスト前計算のイメージ:

```text
for prev_word in words:
    for next_word in words:
        k = overlap(prev_word, next_word)
        suffix_to_type = next_word[k:]
        for prev_end in positions[last(prev_word)]:
            run DP for suffix_to_type from prev_end
            store cost for each next_end
```

ビーム更新のイメージ:

```text
next_states = []
for state in beam:
    for unused word:
        for end_pos of last_char(word):
            cost = transition[state.last_word][word][state.pos][end_pos]
            eval = state.raw_cost + cost - base[word]
            push candidate
beam = best W candidates
```

## この解法の本質

この解法の強みは、ビームサーチの評価を「単語を消化した量」と「移動のまずさ」に分離した点である。base cost を引くことで、難しい単語を早めに選んだ状態が単にコスト大という理由で落ちにくくなる。

また、終端マスを状態に含めて単語間遷移コストを前計算しているため、ビーム展開時に毎回重いDPを走らせずに済む。探索の質と速度の両方を支えるのはこの前計算である。

## 真似するならまず実装する部分

最初に、単語 `i` の後に単語 `j` を付ける遷移コストを、前単語終端マス・次単語終端マスごとに計算するDPを作るべきである。次に、単純なビーム幅50から100程度のビームサーチを組み、評価値に `-base(word)` を入れる。

完全再現を狙う前に、base cost を「全開始マスの最小値」と「平均値」の両方で比較できるようにしておくと調整しやすい。

## 注意点・未理解点

- コードが公開されていないため、メモリ削減、ビーム状態の重複排除、復元情報の持ち方は不明である
- 遷移コスト前計算は添字が多くなりやすく、素朴に持つとメモリを使う
- base cost の平均・最小・係数調整はスコアに効くが、種ごとのばらつきがある
- ビーム幅を上げるほど強くなる一方、単語数200のままでは展開数が重い
- 2-opt が不向きという判断は、この問題の遷移コストが非対称であることに由来する
