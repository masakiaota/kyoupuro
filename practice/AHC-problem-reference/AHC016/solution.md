## 問題の本質

AHC016は、頂点ラベルが消え、辺が独立に反転する通信路で、`M` 種類のメッセージをできるだけ小さい `N` のグラフとして送る問題である。解法視点では、次の2つを同時に満たす符号設計問題である。

- 頂点番号に依存しない特徴で識別できること。
- 辺反転ノイズ後も候補間の距離や尤度が十分離れていること。

スコアは `0.9^E / N` なので、`N` を小さくするだけでは足りない。誤答数が指数的に効くため、難ケースでは `N` を増やしてでも正解率を上げる価値がある。

| TERRY | 小グラフ同型類 + クリーク冗長化 + 焼きなまし | 中高 | 問題構造に合い、実装可能性と性能のバランスが良い | 焼きなましとパラメータ調整に依存 | クリーク冗長化、popcount差分、混同行列 |

## 共通している考え方

多くの解法は、辺そのものを1bitずつ読むのではなく、ノイズ後も残りやすい集約特徴を読む。

- クリーク冗長化: 多数決により辺反転を平均化する。
- 同型類: 頂点番号が失われても変わらない情報を使う。
- 次数列: 頂点ラベル不変な特徴量として使う。
- 事前シミュレーション: ノイズ後にどの候補へ誤るかを測る。
- 候補集合選択: 全候補を使うより、混同しにくい候補だけを選ぶ方が強い。

## 解法の分類

- 確率推定型: DeNAの小ケース通信路行列。`p(H|G)` を計算して最尤復元する。
- 学習型: DeNAのAttention分類。順列不変/順列等変な特徴を学習する。
- 構築型: TERRYの同型類+クリーク冗長化、Tanakaの3クリークサイズ方式、tsutajのバーコード方式。
- 焼きなまし型: TERRYのグループ復元、Tanakaのグループ割当復元、yunixの候補集合選択、tsutajのグループ分け・配置復元。
- シミュレーション型: yunixの次数列期待値、TERRYの混同行列、Tanakaのサイズ揺らぎ見積もり。
- 後処理改善型: 混同行列投票、補グラフTTA、候補足切り。

## 推奨して理解すべき順序

1. まずTanakaメモで、クリークサイズを情報にする素朴な冗長化を理解する。
2. 次にTERRYメモで、小グラフ同型類をクリークで冗長化する標準的に強い形を理解する。
3. yunixメモで、次数列のようなラベル不変特徴とシミュレーション期待値の使い方を見る。
4. DeNAメモで、通信路行列による理論的な小ケース最適化と、NN分類の上位化を見る。
5. tsutajメモは、別方向のバーコード設計として読むと、なぜ座標復元が難しいかが分かる。

## 実装するならどのルートか

理解のための最小実装は、TERRY解の簡略版がよい。

- `n=4` の同型類代表を手で用意する。
- 各頂点を `K` 個のクリークに展開する。
- 観測頂点を `n` グループへランダム分割し、swap山登りでブロックの一様性を最大化する。
- 復元小グラフを順列全探索で同型判定する。

上位化するなら、次の順で足す。

1. `n=5,6` の同型類代表を列挙する。
2. 焼きなましに温度と複数回試行を入れる。
3. `u128` bitsetとpopcountで差分更新する。
4. `(M, epsilon)` ごとに `n,K,score_coef` をチューニングする。
5. 混同行列で候補選択と投票を補正する。

DeNAのNN解は最終到達点としては強いが、学習環境・データ生成・モデル埋め込みが重く、最初に実装するルートには向かない。

## 重要な実装要素

- 状態表現: 観測頂点のグループ割当、グループ所属bitset、候補小グラフ、候補ごとの特徴量。
- 評価関数: ブロック内の辺密度、ブロック間の多数派度、次数列距離、通信路尤度。
- 近傍: グループ間の頂点swap、1頂点移動、候補グラフの入れ替え。
- 差分更新: swap前後で影響するグループ対だけを更新する。bitset+popcountが効く。
- 候補管理: 同型類代表、混同しにくい候補の選択、`M` の増減に強い順序付け。
- 出力判定: 復元小グラフの同型判定、次数列最近傍、混同行列投票、最尤復元。
- パラメータ: `N`、小グラフ頂点数 `n`、冗長化サイズ `K`、スコア係数、試行回数、温度、候補数。

## 落とし穴

- `N` を小さくしすぎると、1誤答の指数ペナルティでスコアが崩れる。
- 同型類を考えずに頂点位置を復元しようとすると、シャッフルへの耐性が弱い。
- 焼きなまし1回だけでは初期解依存が大きい。
- グループ間ブロックを01に潰すと、境界ケースの情報を捨てる可能性がある。
- 次数列だけの方式は実装しやすいが、同じ次数列を持つ候補が増えると頭打ちになる。
- 候補集合のローカル評価と本番スコアはずれる。混同行列や成功率ベースの評価が必要。
- 巨大な事前計算表や圧縮文字列は提出サイズ制限・バグの温床になる。

## 未解決・要検証事項

- TERRY型のスコア係数 `alpha` を理論的に決める方法。
- ブロック間の実数的な辺密度を、01多数決よりうまく同型判定・尤度判定へ使う方法。
- 次数列以外の軽量なラベル不変特徴の組み合わせ。
- NNを使わずにDeNA後処理版の544候補分類へ近づく職人実装。
- 各記事の非公開ローカル探索・学習・Optuna設定の詳細。
