## 解法の全体像

バーコードのように、グラフの特定領域へビット情報を埋め込む。各コード部の頂点は白・黒の2状態を持ち、`ceil(log2 M)` ビット分を用意して整数を表す。頂点シャッフルに耐えるため、グラフ全体の次数をできるだけユニークにし、復元時にまず頂点をグループ分けし、次にグループ配置を焼きなましで推定する。

見かけ上の頂点をさらにバケットサイズ `B` 個の実頂点で表し、ノイズへの冗長性を持たせる。コード部は1行または2行で、場合によっては対角線上も1ビットとして使う。

## 主要アイデア

- グラフをバーコード状のビット列として設計し、整数を直接エンコードする。
- パターン設計では、頂点次数をできるだけユニークにして、シャッフル後の位置復元を助ける。
- バケットサイズ `B` を導入し、`B` 頂点で見かけ上の1頂点を表す。
- 必要ビット数が多いときはコード部を2行にし、上下を区別する追加ビットを付ける。
- バケットが十分大きいときは対角線もコード部として使い、奇数ビットの調整に使う。
- クエリ処理は、グループ分けの焼きなましと、グループ配置の焼きなましの2段階。

## 最終コードの構造

Browserで AtCoder 提出 `36689263` を読んだ。以下は記事本文、図解、提出コードから確認できた構造である。

### 状態表現

- 見かけ上のグラフ:
  - コード部、位置識別部、補助ビットからなる格子状または行列状の構造。
  - 各見かけ頂点は `B` 個の実頂点で表される。
- `bucket_size`: 見かけ頂点1個を表す実頂点数。`get_optimal_bucket_size` と `get_optimal_decode_rows` で epsilon と `M` から決める。
- `decode_cells`: ビットを読むセル位置。`register_decode_cells` でパターンへ登録し、`decode(B)` で整数へ戻す。
- 送信状態:
  - `bits`: 送る整数を表すビット列。
  - `bucket[v]`: 観測頂点が属すると推定する見かけ頂点。
  - `placement`: 見かけ頂点を設計上のどの位置に置くかの対応。
- 復元状態:
  - グループ分け焼きなましの割当。
  - 配置焼きなましの順序・反転・行位置など。

### 観測・制約・入力の扱い

- `M` から必要ビット数 `ceil(log2 M)` を決める。
- `epsilon` と必要ビット数に応じて、バケットサイズ `B`、コード部1行/2行、対角線使用有無を決めていたと考えられる。
- 観測グラフはまず、バケット単位の見かけ頂点へまとめる必要がある。
- 頂点次数がユニークになるように生成しているため、次数や接続パターンが配置復元の手がかりになる。

### 評価関数

詳細な式は記事にない。推測では、グループ分けでは同じバケット内の辺密度や、期待される次数パターンとの一致度を評価する。

配置焼きなましでは、復元した見かけ頂点を設計上の位置へ割り当てたとき、観測されたブロック間の辺密度が生成パターンとどれだけ一致するかを評価するはずである。

```text
score_grouping = consistency of bucket-internal and bucket-external edge densities
score_placement = agreement between observed block matrix and designed barcode matrix
```

### 探索・構築・更新

- グラフ生成:
  - ビットを表すコード部を作る。
  - 各見かけ頂点の次数がなるべく一意になるように周辺構造を作る。
  - 1行では足りない場合は2行にし、行識別ビットを追加する。
  - 対角線を使えるパラメータでは、1bit分の節約に使う。
- クエリ処理:
- 第1段階: 実頂点を見かけ頂点のバケットに分ける焼きなまし。提出コードでは `fix_groups_beta` がグループ内外の辺密度を見て改善する。
- 第2段階: 見かけ頂点を設計上の場所へ並べる焼きなまし。提出コードでは `get_arrangement_annealing` が配置対応を探索する。
  - 復元したコード部からビット列を読み、整数に戻す。

### 操作・クエリ・出力選択

- 最終的には復元ビット列を整数に変換し、`0 <= value < M` ならその値を出す。
- 範囲外や復元不確実な場合の処理は記事からは不明。
- 2行構成では、上下識別用ビットを先に読んで、各コード部の行を決める必要がある。

### 時間配分・パラメータ

- バケットサイズ `B` が主要パラメータで、ノイズ耐性と `N` の増加を支配する。
- コード部の行数、対角線使用有無、追加識別ビット数もパラメータ。
- 記事の反省点として、1回の焼きなましを長く回すのではなく、複数回回して最良を取るべきだったとある。
- `M` が小さいケースの成績が悪く、パラメータ別分析が不足していたと述べている。

## 実装上重要な断片

```text
make_graph(value):
    bits = binary(value, width=ceil_log2(M))
    choose layout: one row, two rows, optional diagonal bit
    for each apparent vertex:
        expand to B real vertices
    add edges so apparent vertex degrees are mostly unique
    write bit states into code region
```

```text
decode(H):
    buckets = anneal_grouping(H)
    placement = anneal_placement(H, buckets)
    bits = read_barcode_bits(H, buckets, placement)
    return integer(bits)
```

## この解法の本質

この解法は、グラフ同型類を符号語として使うのではなく、グラフの中に座標系を作り、その座標系上のバーコードを読む発想である。頂点番号が失われる問題を、次数を一意に近づけることで「位置復元問題」に変換している。

ただし、位置復元とビット復元の両方を最適化する必要があり、ノイズが大きいと誤差が2段階で増幅する。この点が、同型判定+クリーク冗長化型より不利になったと記事中でも反省されている。

## 真似するならまず実装する部分

まずはノイズなしで、次数がユニークな見かけ頂点列を作り、シャッフル後に次数順で並べ直してビット列を読む実装から始めるのがよい。次に各見かけ頂点を `B` 個に冗長化し、最後にグループ分け焼きなましを入れる。

## 注意点・未理解点

- 提出コードで焼きなまし段階と温度更新は確認できたが、評価式の係数や `bucket_size` の補正は実験依存で、記事だけからは導けない。
- バーコード方式はグループ分けと配置の2段階推定が必要で、失敗箇所が増える。
- 自己ループなし単純グラフでは全頂点次数を完全にユニークにはできない制約がある。
- 同型性判定を直接使う発想に気づけていれば、見かけ頂点数を削減できたと記事で述べられている。
- 複数回焼きなまし、パラメータ別分析、`M` 小ケース対策が未実施または不足していた。
