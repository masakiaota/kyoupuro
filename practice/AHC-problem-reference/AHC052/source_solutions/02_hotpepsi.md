## 解法の全体像

解法は、乱択で「初期移動の直線操作列」と「塗りつぶし用の反復操作列」を作り、各ロボットのボタン割当を部分的に更新しながら良いものを残す構築である。

操作列の形を先に作る。前半は最大 7 個のボタンをそれぞれ何回か連打する初期移動で、ロボットを遠く・ばらばらな位置へ散らす。後半は 3 個のボタンを使って、長い移動、1 歩曲がる、逆向きの長い移動、1 歩曲がる、を繰り返す。これはジグザグに近い塗りつぶしになる。

その操作列に対して、ロボットを 1 台選び、そのロボットの各ボタンへの方向割当をランダム生成する。シミュレーションして全ロボットの塗り集合の和が改善すれば採用する。これを短時間で何度も作り直し、最良の履歴を出力する。

## 主要アイデア

- 操作列の骨格を「初期移動 + 3 ボタンのジグザグ風塗り」に固定する。
- 初期移動には最大 7 ボタンを使い、各ボタンの連打回数と方向割当を乱択する。
- 塗りつぶしには 3 ボタンを使い、2 つの長い直線移動と 1 つの曲がり操作を繰り返す。
- 各ロボットごとに 30x30 の bitset を持ち、和集合の popcount で塗れたマス数を高速に評価する。
- 1 台のロボットのボタン割当だけを作り直し、改善したときだけ採用する。
- 最初の 100ms ごとに乱数範囲を段階的に広げ、塗り切れる範囲を探す。

## 最終コードの構造

### 状態表現

- `Bitset`: 900 マスを 15 個の `uint64_t` で持つ自前 bitset。
- `Command { op, count }`: ボタン `op` を `count` 回押す圧縮操作。
- `History`:
  - `score`: 現在評価値。
  - `turns`: 展開後の操作回数。
  - `ops[robot][button]`: 各ロボットに対するボタンの方向割当。方向は `RDLU` の 0..3。
  - `commands`: 圧縮された押下列。
  - `clean[robot]`: 各ロボットが塗ったマス集合。
- `Params`: 初期移動ボタン数、初期移動歩数、塗り反復数、塗り歩数の乱数範囲。
- `wall[y][x][dir]`: その方向に壁があるか。

### 観測・制約・入力の扱い

- 入力の縦壁・横壁を `wall[y][x][4]` に展開する。
- 外周は壁として初期化され、入力で隣接マス間の壁が設定される。
- ロボットの移動時は、対応方向に壁がなければ座標を更新し、移動先を bitset に追加する。
- 操作数制限 `1800` に対する明示的な複雑な調整はなく、乱数パラメータが小さいため生成される操作列が収まる形になっている。

### 評価関数

- 全ロボットの `clean` の OR を取り、塗れたマス数を数える。
- 全 900 マスを塗れていれば `2700 - turns` に置き換える。
- 部分更新時は、対象ロボットの新しい bitset と他ロボットの既存 bitset を OR して評価する。
- 採択条件は単純で、スコアが現在より大きいときだけ採用する。

### 探索・構築・更新

- `gen` で 1 つの候補 `History` を作る。
- 初期移動:
  - `init_ops` 個の新しいボタンを作る。
  - 各ボタンを乱数で決めた回数だけ連打する。
- 塗りつぶし:
  - 残り 3 ボタンを `op1`, `op2`, `op3` とする。
  - `op2` を `steps` 回、`op1` を 1 回、`op3` を `steps` 回、`op1` を 1 回、を `move_ops` 回繰り返す。
- ロボット割当更新:
  - ロボットをランダムに 1 台選ぶ。
  - そのロボットの各ボタン方向をランダムに作る。
  - 末尾 3 ボタンについては、塗りつぶしが 90 度関係・逆方向関係になるよう補正する。
  - シミュレーションして改善すれば採用する。
- 1 つの `History` に対し 200 回の単一ロボット更新を行う。
- 時間内に `History` 生成を繰り返し、最良を保持する。

### 操作・クエリ・出力選択

- 出力時は、まず `K` 行のボタン割当を出す。
- あるロボットで未使用のボタンは `S` として出力する。
- その後、圧縮された `commands` を展開して、ボタン番号を 1 行ずつ出力する。

### 時間配分・パラメータ

- `TIME_LIMIT = 1900ms` 程度。
- 初期パラメータはおおむね以下である。
  - 初期移動ボタン数: 3..7。
  - 初期移動歩数: 4..7。
  - 塗り反復数: 4..9。
  - 塗り歩数: 4..9。
- 100ms ごとの段階で、まだ塗り切れていなければ初期移動歩数範囲、塗り反復範囲、塗り歩数範囲を広げる。
- 一度全マスを塗れる候補が出たら、そのパラメータで残り時間を使って試行を続ける。

## 実装上重要な断片

```text
evaluate(history, target_robot, target_clean):
    bits = target_clean
    for robot != target_robot:
        bits |= history.clean[robot]
    covered = popcount(bits)
    if covered == 900:
        return 2700 - history.turns
    return covered
```

```text
update_one_robot(history):
    ri = random robot
    ops = random directions for all used buttons
    force last three buttons to form zigzag-like directions
    clean = simulate(ri, ops, history.commands)
    score = evaluate(history, ri, clean)
    if score > history.score:
        commit ops and clean
```

```text
gen(params):
    commands = random initial straight moves using up to 7 buttons
    append repeated sweep pattern using 3 buttons
    turns = sum counts
    repeat 200 times:
        update one random robot
```

## この解法の本質

完全な経路最適化を避け、操作列の形を強く制限したうえで、ロボットごとのボタン割当だけを高速に乱択更新している。ボタン数 10 のうち、初期移動用 7 個と塗り本体用 3 個という分割が単純で、シミュレーションも bitset 和集合で軽い。そのため、方針は粗いが大量試行でき、全マス被覆の判定に直接最適化できる。

## 真似するならまず実装する部分

最初に実装すべきなのは、圧縮操作列、ロボット別ボタン割当、bitset シミュレーション、1 台差し替え評価である。初期移動と塗りつぶしのパラメータは記事・コードの値をそのまま使えばよい。焼きなましや複雑な局所探索を入れる前に、全マスを塗れたかどうかを高速に判定して大量試行する骨格を作るのがこの解法らしい。
