## 解法の全体像

このメモは単一解法というより、AHC024で有効だった近傍と判定高速化を整理している。中心は、1マス隣接色変更だけでは局所解に詰まりやすいため、2マス以上の同時変更、行・列削除、外周削りを組み合わせることだ。記事内の提出コードリンクでは、wata_adminのRust実装として、2マス以上へ連鎖する隣接色変更を焼きなましで回す解法が確認できる。

## 主要アイデア

- 色隣接グラフは平面グラフであり、盤面の回転・反転では隣接関係は変わらない。
- 隣接関係判定は愚直には `O(N^2)` だが、近傍変更では変更セル周辺だけを見れば差分更新できる。
- 行・列削除だけでも20万点台、部分削除を含めると30万点台が狙える。
- 1マスを隣接色で塗る近傍は基本だが、「田」のように4色が絡む場所で動けなくなりやすい。
- 1マス変更で生じる隣接違反を、隣のセルも同時に変えることで解消する2マス以上同時変更が重要である。
- 行・列削除は局所解の改善に効くが、盤面が十分小さくなった後は2マス変更の方が強い模様である。
- invalidを許すなら、余計な隣接の発生は直しやすいが、必要な隣接が切れる状態は直しにくい。
- 連結性判定は3x3や5x5の局所関節点判定で高速化できる。
- 重い妥当性判定の前にスコア差と焼きなまし採択を見て、採択候補だけ判定する順番にすると速い。

## 最終コードの構造

記事内リンクのRust提出 `wata_admin` #45918156 を読んだ内容を書く。

### 状態表現

- `Grid<usize, SIZE>`: 外周番兵つきの盤面。番兵は0として扱う。
- `score`: `1 + 色0セル数`。
- `adj_count[c][d]`: 現在盤面で色 `c` と `d` が隣接している辺数。
- `best`: 探索中の最高スコア盤面。
- `dir4`, `dir8`: 番兵グリッド上の4近傍・8近傍方向。

### 観測・制約・入力の扱い

- 初期盤面を外周0番兵付きグリッドに読み込む。
- `adj_count` を初期化し、現在の隣接関係を辺数で管理する。
- 新しい隣接を作るとき、対応する `adj_count` が0なら、初期にはなかった隣接を作るため違反とみなす。
- 既存隣接を消すとき、減算後に0になるなら、必要な隣接を完全に消すため違反とみなす。
- 連結性は各変更セルについて8近傍の局所消去可能性を見て、`can_delete == 1` であることを要求する。

### 評価関数

- 生スコア `1 + #zero_cells` を最大化する。
- 候補変更で0セルが増えれば `diff > 0`、減れば `diff < 0` になる。
- 焼きなましでは、`diff < 0` でも `exp(diff / T)` で採択する。

### 探索・構築・更新

- 温度は `T0 = 1.0` から `T1 = 0.5` へ、制限時間 `TL = 1.9` 秒で線形に下げる。
- ランダムにセル `p` と方向 `dq` を選び、`p` を隣接セル `q = p + dq` の色へ変えることを起点にする。
- `dq` に垂直な方向 `dv` の両側へ見て、単独変更で隣接不能になるなら、同じ方向に連鎖的に変更範囲を伸ばす。
- 変更範囲の各セルについて、旧色を消しても連結性が壊れないかを8近傍局所判定する。
- `adj_count` を差分更新し、存在しない隣接の追加や必要隣接の消失があればロールバックする。
- 妥当なら範囲内セルを隣接方向の色で塗り替え、スコアと最良盤面を更新する。

### 操作・クエリ・出力選択

- 探索終了後、最高スコアの盤面を出力する。
- 提出コードは途中経過も標準出力に出す箇所があるが、最終的には `best` を `out` に戻して出力している。

### 時間配分・パラメータ

- `TL = 1.9` 秒。
- `T0 = 1.0`, `T1 = 0.5`。
- 4096イテレーションごとに時間と温度を更新する。
- 提出スコアは336,632点、実行時間は約1.9秒である。

## 実装上重要な断片

```text
make_chain_move(p, dq):
    dv = perpendicular(dq)
    range_left, range_right = 0
    while repainting current cell would create forbidden adjacency:
        extend range along dv
    return all cells in range
```

```text
commit_or_rollback(move):
    if score_diff < 0 and not anneal_accept(score_diff):
        reject before heavy checks
    if not local_delete_check(move.old_cells):
        reject
    update adj_count
    if new edge appears or required edge disappears:
        rollback adj_count
        reject
    apply repaint
```

## この解法の本質

このメモが示す本質は、盤面の縮約を1マスずつ行うだけでは足りず、「変えてはいけない隣接関係」を保つために複数セルを同時に動かす必要があるという点である。特に提出コードの連鎖変更は、単独変更が隣接違反を起こす場合に、その違反セルも一緒に動かす。これにより、細長い地形を平行移動するように削れる。

## 真似するならまず実装する部分

理解用には、まず `adj_count` による隣接関係差分判定を実装するのがよい。次に1マス隣接色変更を焼きなましで回す。そこから、垂直方向へ変更範囲を伸ばす2マス以上同時変更を入れる。局所連結判定は最初はBFSで代用し、後から8近傍判定に置き換えるとよい。

## 注意点・未理解点

- jetbeadメモはリンク集を兼ねており、X上の短文知見は全件本文取得していない。記事内で整理された要点を中心に読んだ。
- 8近傍の `can_delete == 1` は高速だが完全判定ではない可能性がある。どのケースで誤判定するかは別途検証が必要である。
- 提出コードの途中経過出力はヒューリスティックジャッジでは問題にならないと見られるが、通常の厳密出力問題では危険である。
- 連鎖変更の範囲決定は添字と番兵に強く依存し、実装ミスで範囲外アクセスや隣接カウント破壊を起こしやすい。
