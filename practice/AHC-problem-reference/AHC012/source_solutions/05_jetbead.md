## 解法の全体像

この参照元は単一解法ではなく、AHC012の有効方針を俯瞰するメモである。中心にあるのは、縦横グリッドへ制限した焼きなまし、DP型の決定的解法、評価関数設計、差分計算である。

メモ内の重要な流れは、任意直線を扱うとピース内イチゴ数の計算が重くなるため、縦横線に制限して高速に状態評価できるようにする、というものだ。上位勢は、線を少し傾けてイチゴ中心を切らない、線数や縦横比を工夫する、公式スコアとは別の滑らかな評価関数を使う、という共通要素を持つ。

記事から辿れるAquariusの99.9M提出コードは、縦横にほぼ平行な斜め線、座標圧縮、2次元累積和、ヒストグラム差分、焼きなましを組み合わせた実装である。

## 主要アイデア

- 任意直線よりも、縦横グリッドへ制限した方が評価と差分更新が圧倒的に楽になる。
- イチゴ中心を切らないように、見た目は縦横だがわずかに傾いた線として出力する。
- 線数は常に縦横同数が最善とは限らず、縦横比を偏らせる方針もある。
- 公式スコアは満たした人数だけを見るため、探索中の評価関数には不足・過剰・分布ずれを入れる方がよい。
- 線移動のたびに全点を再計算せず、変化した帯だけを差分更新する。
- 座標圧縮と2次元累積和を使うと、ある矩形内のイチゴ数を高速に得られる。
- DP方針は、片方向を固定してもう片方向を分割DPする別系統の強解法として整理される。

## 最終コードの構造

ここでは、記事から辿れたAquarius提出コードを中心にまとめる。Jetbead記事自体はコード本体を持たない。

### 状態表現

- 入力:
  - `a[d]`: 要求人数。
  - `x[i], y[i]`: イチゴ座標。
- 座標圧縮:
  - `xcmp`, `ycmp` に `-rad`, `rad`, 全イチゴ座標を登録する。
  - 圧縮後の隣接座標区間をセル候補として扱う。
- 出力線:
  - `hLine(x)` はほぼ縦線、`vLine(y)` はほぼ横線を返す。端点を1ずらすことで、整数座標の点を線上に乗せにくくしている。
- `Helper`:
  - 圧縮座標上の点分布を2次元累積和で持つ。
  - 現在の分割境界 `xs`, `ys` を持つ。
  - `histo` で現在のピース分布を保持する。
  - `amod[i]` で、`i` 個入り要求をイチゴ総量ベースに変換して持つ。
- `Histogram`:
  - indexごとの値を持つ。
  - `save()` と `restore()` により、試行遷移のロールバックを軽くする。

### 観測・制約・入力の扱い

- イチゴ座標を圧縮し、圧縮グリッド上で2次元累積和を構築する。
- 矩形内のイチゴ数は累積和から `O(1)` で得る。
- 初期線は、必要人数に対してやや多めのピース数を作るよう、縦横本数を決める。
- 出力線は座標値を1ずらした斜め線にして、イチゴ中心を直撃しないようにする。

### 評価関数

Aquariusコードの評価は、公式スコアそのものではなく分布の悪さを最小化する形である。

- `histo` は、各ピースサイズに属するイチゴ総量を持つ。
- `amod[i] = a[i] * i` により、要求を「人数」ではなく「そのサイズのピースに必要なイチゴ総量」として扱う。
- `calcScore` では、要求総量と現在総量のズレを二乗で罰する。
- さらに、要求サイズ `i` と現在サイズ `j` を小さい順に貪欲マッチングし、`(j - i)^2` に比例するズレを足す。
- `calcLoss` は、実際に不足している人数に近い値を返し、終盤の最良解選択に使われる。

この評価は、単に配れた人数を数えるより滑らかで、サイズ分布のずれを探索に伝えやすい。

### 探索・構築・更新

- 初期化:
  - 圧縮座標空間上で、縦横境界をおおむね等間隔に配置する。
  - 線数は100本を使い切る方向で調整している。
- 焼きなまし:
  - 2.99秒程度回す。
  - 温度は高めから低めへ下げる。
  - 近傍は、境界線を圧縮座標上で数ステップ動かすものが中心である。
  - 一部、線の再配置に近い操作も持つ。
- 差分更新:
  - 遷移前に `histo.save()` する。
  - 影響する行または列のピース分布を引く。
  - 境界を動かす。
  - 新しい行または列のピース分布を足す。
  - 不採択なら `histo.restore()` と境界復元を行う。
- 最良解:
  - 通常の評価値とは別に、終盤では `calcLoss` が最小の状態を保存する。

### 操作・クエリ・出力選択

- `get()` で現在または最良の `xs`, `ys` から線リストを作る。
- ほぼ縦線、ほぼ横線を合わせて出力する。
- 圧縮座標の境界を実座標に戻すときは、対応する座標値を使う。

### 時間配分・パラメータ

- Aquarius提出コードは約2.99秒を使う。
- 焼きなまし温度はおおむね `500` から `1` へ下がる。
- 線の移動幅は圧縮座標上で最大9程度の近傍が見える。
- AtCoder提出 #33001443 のスコアは99,924,510点である。

## 実装上重要な断片

```text
eval_piece_distribution(xs, ys):
    histo.clear()
    for each cell between consecutive xs and ys:
        c = rectangle_sum_by_2d_prefix(cell)
        histo.add(c, c)
```

```text
try_shift_boundary:
    histo.save()
    remove affected strips from histo
    move boundary in compressed coordinate
    add affected strips to histo
    delta = new_eval - old_eval
    if accept_minimization(delta, temperature):
        keep
    else:
        restore boundary
        histo.restore()
```

2次元累積和でセル内点数を取る設計は、グリッド境界が圧縮座標上にある場合に特に強い。各セルを直接点集合として持たなくても、矩形和でピースサイズを再計算できる。

## この解法の本質

Jetbeadメモから見える本質は、AHC012では「線の自由度」より「評価を高速に回せる表現」の方が価値を持ったという点である。縦横に制限すると理論上の表現力は落ちるが、ランダム点の分割では十分多様なピースサイズを作れる。さらに差分更新や累積和が使えるため、限られた3秒で多数の状態を試せる。

Aquariusコードは、その考えを圧縮座標と累積和に寄せて実装している。点を個別に移動管理するのではなく、矩形クエリでピースサイズを得るため、差分更新対象を線周辺に限定しながら堅く評価できる。

## 真似するならまず実装する部分

最初は、Jetbeadの比較を読み、TERRY型の縦横焼きなましを実装するのがよい。次に、イチゴを切らない斜め出力、公式スコア以外の分布評価を追加する。

上位化を目指すなら、Aquarius型の座標圧縮と2次元累積和に進む価値がある。ただし、圧縮座標上の線移動、ヒストグラムのsave/restore、要求総量ベース評価を同時に実装すると難しいため、段階的に入れるべきである。

## 注意点・未理解点

- Jetbead記事はリンク集・比較メモであり、単一の完成解法ではない。
- Twitter/Xリンクの一部は本文を取得できず、短文解説の詳細は確認できていない。
- Aquariusコードの細かな近傍条件には、圧縮座標上で重複境界を扱う意図が含まれているように見えるが、全ての分岐意図までは断定できない。
- `histo` がピース数ではなくイチゴ総量を持つ点は、一般的な `b[d]` と違うため真似るときに混同しやすい。
- 座標圧縮を使う場合、出力座標が圧縮境界と対応し、かつイチゴを切らないことを必ず確認する必要がある。
