## 解法の全体像

焼きなましを使わず、縦横グリッドの切り方を決定的に構築する。まずイチゴをx座標順に並べ、適当な列数 `M` に分ける。これで縦方向の分割を固定する。その後、y座標順に見た切り口をDPで選び、各横帯と各x列の交差でできるグリッドに何個イチゴが入るかを数える。

DPの状態は、あるy切り口までを処理したときの最良評価値、そこまでに得られたピース数配列 `B`、直前の切り口位置を持つ。固定されたx分割に対し、横切り位置を最適化することで、ランダム探索なしに高得点を得ている。

## 主要アイデア

- 縦方向の分割数 `M` を決め、x座標順のイチゴを `M` グループに分ける。
- 横方向の切り位置だけをDPで選ぶ。
- 遷移 `j -> i` では、y順で `j` から `i` の間にあるイチゴが、各x列に何個入るかを累積和で求める。
- 各列で得られるピースのイチゴ数を `B` に反映し、評価関数で比較する。
- 遷移元 `j` を全探索すると `O(N^2 M)` だが、横帯に `10M` 個以上のイチゴがある候補は効率が悪いとして絞り、`O(NM^2)` へ近づける。
- `M=5..16` など複数の列数とx分割パターンを試し、最も良い出力を選ぶ。
- 公式スコアではなく、少ない種類を優先して埋める独自評価を使う。

## 最終コードの構造

in-app Browser で読んだ提出 #32962653 とコンテスト後修正版 #32971510 の構造である。記事本文の x 分割固定 + y 切り口 DP と一致している。

### 状態表現

- `A[d]`: 要求される `d` 個入りピースの人数。
- `B[d]`: 現在までの分割で得られた `d` 個入りピース数。
- `B[0]`: 記事中の評価関数では切断数または制約管理用の値として使われ、`K` 超過を弾く。
- x分割: イチゴをx座標順に分けた `M` 個の列。
- y切り口候補: y座標順に並べたイチゴの間。
- 実装では `p[i]` が y切り口 `i` までのピース数配列、`val[i]` が評価値、`front[i]` が復元元を持つ。
- 復元用に、各 `dp[i]` から前の切り口を辿る。

### 観測・制約・入力の扱い

- 入力点をx座標順、y座標順にソートする。
- x列ごと、y順prefixごとの累積情報を作り、横帯 `j..i` の各列のイチゴ数を `O(M)` で求める。
- 線数上限 `K=100` は、評価関数やDP状態で管理する。
- 実際に出力する線は、x分割境界とy分割境界に対応する直線である。

### 評価関数

評価関数は不足しているピース種類へのペナルティを合計する形である。記事中の断片から読み取れる主旨は次の通りである。

- `B[d] >= A[d]` ならその種類には追加ペナルティを与えない。
- 不足量 `A[d] - B[d]` に対し、二乗に近い凸なペナルティを与える。
- 重みはおおむね `(4d - 1) / A[d]` で、`d` が大きい種類や要求人数に対する不足率を意識する。
- `B[d]` が1増えたときの改善量が、不足量に比例するようにしている。

公式スコアは「何人配れたか」だけを見るため、簡単に作れる小さいピースへ偏りやすい。この評価関数は、特定の `d` だけが極端に不足する状態を避けるためのものだと読める。

### 探索・構築・更新

- `main` で `div=5..16` と `type=0..4` の x 分割パターンを試す。
- 固定したx分割に対して、y方向の切り口列をDPで構築する。
- 遷移元 `j` と遷移先 `i` の間の横帯を1段追加する。
- その横帯を `div` 列に分けた各ピースのイチゴ数を数え、10個以下なら `B` に加える。
- 遷移元は `max(0, i - div * 10)..i-1` に制限する。
- コンテスト提出は終盤 19/20 以降で公式スコア評価に切り替え、修正版は最後まで独自評価を使う。

### 操作・クエリ・出力選択

- 出力は縦横グリッドの線だけである。
- 各 `M` とx分割パターンについてDPで横線を決め、復元した線群のうち最も評価が高いものを出す。
- 記事では、最終盤にDPの評価を真のスコアへ切り替える割合を調整したことが述べられている。コンテスト後は最後まで独自評価を使う方がよかったとされる。

### 時間配分・パラメータ

- 最初の実装では `M=15`。
- その後 `M=10` も試し、最終的には `M=5..16` を全探索している。
- x分割は等分だけでなく、中央に多めにイチゴが乗るようなパターンなども試している。
- DP高速化後、複数パターンを試して99M台に到達している。

## 実装上重要な断片

```text
solve_for_x_partition(columns):
    build prefix count by y_cut and column
    dp[0] = empty B
    for i in y_cut_candidates:
        for j in recent_candidates_before(i):
            add = piece_counts_between(j, i, columns)
            B2 = dp[j].B + add
            val = custom_penalty(B2)
            relax dp[i] with val
    restore best y cuts
```

重要なのは、DPの値として単一の点数だけでなく `B` も持つ点である。今後どの種類が不足しているかが次の遷移の価値を変えるため、評価と `B` を一体で管理する必要がある。

## この解法の本質

この解法は、AHC012を「2次元の切断位置最適化」から「片方向を固定した1次元分割DP」へ落としている。縦方向の自由度は列数と列境界パターンの列挙に押し込み、横方向だけをDPで最適化する。探索のランダム性を消す代わりに、評価関数を強く設計して、DPが満遍なく要求を満たす方向へ進むようにしている。

焼きなまし勢が近傍と差分更新で反復回数を稼ぐのに対し、この方針は候補構造をかなり限定し、決めた構造の中では強く最適化する。構造化できるヒューリスティック問題では、乱択探索なしでも上位に届くことを示している。

## 真似するならまず実装する部分

まずはx方向を固定列数で等分し、y方向だけDPする最小版を作るのがよい。`M` は1つに固定し、評価関数も不足数の二乗ペナルティから始める。

その後、`M` の複数候補、x分割パターン、遷移範囲制限、評価関数の重みを順に足すとよい。最初から多状態ビームや多数パターンを入れると、DPの復元と線数制約が壊れやすい。

## 注意点・未理解点

- 記事内に直接提出リンクはないため、提出一覧から #32962653 と #32971510 を辿った。DP状態、x分割パターン、線出力の境界処理は提出コードで確認できた。
- DPが各状態で `B` を1つだけ持つ場合、同じ評価値でも将来性の違う状態を落とす可能性がある。記事末尾でもビームサーチ的に複数状態を持つ改善可能性に触れている。
- 横帯が厚すぎる遷移を捨てる枝刈りは合理的だが、最適性を保証するものではない。
- 評価関数の重み `(4d - 1)` が強く効いており、ここを外すとスコアが大きく下がる。
- 線出力は提出コードで確認できた。境界上で同じ座標が並ぶ場合に斜め線を使い、イチゴ中心を切る事故を避けている。
