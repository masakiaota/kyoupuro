## 解法の全体像

隠れ状態を「各油田の左上座標列」とみなし、過去の占い・掘削結果に対する対数尤度が高い配置を焼きなましで集める。毎ターンの流れは次の形である。

```text
初期の粗い占いを数回行う
states = ランダムな8状態

while 操作回数が残る:
    焼きなましで高尤度な配置候補を最大32個集める
    候補の尤度から候補上の事後分布を近似する
    最尤の回答集合の確率が十分高ければ回答する
    そうでなければ、候補を分離しそうなマス集合を占う
    得た観測を履歴に追加し、候補を次ターンの初期状態にする
```

記事では「高尤度配置集合 `X'` に真の配置が含まれている」と仮定し、その集合上で `P(x | Q)` を近似する、と説明している。提出コードもこの方針で、`kNumStates = 8` 個の状態を並列に焼きなまし、`kNumCandidates = 32` 個の候補を `Selector` で保持する。

## 主要アイデア

### ベイズ推定と対数尤度

配置 `x` が決まれば、任意の占い集合 `S` に対する真の総和 `v_x(S)` が決まる。観測値 `r` は正規分布を丸めた値なので、`P(r | x, S)` は正規分布の CDF の差で計算できる。

```text
mu = (k - s) * eps + s * (1 - eps)
sigma = sqrt(k * eps * (1 - eps))

r = 0: P(X < 0.5)
r > 0: P(r - 0.5 <= X < r + 0.5)
```

事前確率は一様とみなし、評価関数は `sum log2 P(r_q | x, S_q)` である。提出コードでは `log2` 尤度に `2^32` を掛け、`long long` の整数値として持つ。極端に小さい確率は `log2(pr) < -200` で打ち切る。

### 高尤度配置を焼きなましで集める

状態は `config[i] = 油田 i の左上マス` と、各クエリに対する総和 `query_counts[q]` を持つ。盤面全体の埋蔵量グリッドは状態には持たない。

近傍は実装上は主に2種類にまとまっている。

- 1油田移動: 3/4 の確率で上下左右に1マス、1/4 の確率でランダム合法位置へ移す
- 2油田入れ替え: 2油田を選び、形状の重なりが最大になる相対位置を使って互いの近くへ動かす

記事では選択率を「1マス移動 9/16、ランダム移動 3/16、2油田入れ替え 4/16」と説明しており、コード上でも `move_oil` が 3/4、`swap_oils` が 1/4、さらに `move_oil` 内で 3/4 と 1/4 に分岐するので一致する。

採択判定は対数尤度差を利益として、初期温度 `6.0 * 2^32`、最終温度 `0.6 * 2^32` の指数冷却を使う。採択率が `0.04` を下回ると温度を `1.05` 倍して、観測が増えた後も動きが止まりにくくしている。

### 差分更新のための履歴構造

新しいクエリを追加するたびに、各油田・各合法位置がそのクエリ集合と何マス重なるかを前計算する。

```text
for oil i:
  for position p:
    cnt = popcount(bit_oil[i][p] & query_set)
    if cnt > 0:
      related_queries[i,p].push((query_id, cnt))
```

油田を `p -> q` に動かすときは、関係するクエリだけ `count_delta` を更新し、そのクエリの古い `log_pr[count]` と新しい `log_pr[count + delta]` の差だけを足す。これにより近傍評価をほぼ `O(変化したクエリ数)` で行う。

## 最終コードの構造

### 状態表現

- `Polyomino`: 各油田の相対マス列、縦横サイズ。
- `BitVector`: 最大400マス程度の集合を `uint64_t` ブロックで表す。
- `IO`: 入出力、コスト、`mu/sigma/sqrt` の表、油田配置ビット集合、油田入れ替え用の最良重なりを持つ。
- `History`: 観測履歴の尤度表、配置ごとの関連クエリ、失敗済み回答集合、油田ごとの採択されやすさを持つ。
- `State`: `config`、各クエリ総和 `query_counts`、整数対数尤度 `log2_pr`、差分更新用バッファを持つ。
- `Candidate` / `Selector`: 重複しない上位32候補を優先度付きキューで保持する。
- `Solver`: 初期占い、候補生成、クエリ選択、回答判定、時間配分を統括する。

### 観測・制約

1マス掘りも複数マス占いも、コード上は同じ `History::push_query` に入る。`k == 1` のときは観測値と真値が一致する状態だけ確率1、不一致は極小確率として扱う。複数マス占いでは、観測値ごとに「真の総和が `ws` ならその観測が出る確率」を `query_log2_pr[query_id][ws]` に保存する。

回答に失敗した正マス集合は `failed_estimations` に入れ、以降の候補集合から除外する。

### 評価関数

焼きなましの評価値は、全履歴に対する対数尤度である。

```text
log_like(state) = sum_q query_log2_pr[q][query_counts[q]]
```

候補の事後確率は、最尤候補との差から

```text
p_i proportional to 2^((log_like_i - log_like_best) / 2^32)
```

で計算する。重みが小さすぎる候補は `1e-4` 未満で切り捨てる。

### 探索

各ターンで、前ターンの候補上位から作った最大8状態を焼きなます。探索中に状態数を少しずつ減らし、低い平均尤度の状態を落とす。これは記事中の「8状態を並行して焼きなまし、少しずつ状態を減らす」に対応する。

初期状態は1ターン目だけランダムで、2ターン目以降は前ターンの高尤度候補を使う。焼きなましを遷移としたビームサーチに近い。

### クエリ選択

最尤配置の正マス集合 `best_bitvector` が候補上で十分な確率を持てば回答する。そうでなければ、次に占う集合を作る。

初期集合は、最尤候補では埋蔵量があり、候補事後分布上の期待埋蔵量より大きいマスである。

```text
if v_best[p] - E[v[p]] > 0:
    S.add(p)
```

その後、候補マスを小さい順に削除して改善すれば採用、再度追加して改善すれば採用、という貪欲な山登りを行う。評価は候補分布の「回答確率の二乗和」に似た量で、観測後に候補がどれだけ集中するかを測っている。記事ではこの評価関数はあまり良くなく、感想戦でエントロピー最小化・相互情報量最大化が自然だと知った、と書かれている。

### 回答判定

候補ごとの配置を正マス集合へ変換し、最尤候補と同じ正マス集合になる候補の確率和を `best_bitvector_pr` として計算する。これが `guess_threshold` 以上なら回答する。

`guess_threshold` は難易度

```text
difficulty = 2 * (N + M) + int(100 * eps)
```

から決める。難しいケースほど慎重な閾値になる。回答に失敗した場合はその集合を履歴に記録し、候補から除外して続行する。

### 時間配分

全体制限はオンラインでは `2.95` 秒。1ターンごとの局所探索時間は残り時間と推定残りターン数から決める。

- 難しいケース: `min(2*N*N, 8*difficulty) - turn` で割る
- 通常ケース: `min(2*N*N, (30 + int(100*eps)) * M) - turn` で割り、序盤寄りに厚くする
- クエリ選択に実際にかかった時間を次回以降の探索時間から差し引く

初期占いはルールベースで、通常ケースでは盤面の半分程度の大きな領域を2回、`M >= 5` なら左上四分の一区域も占う。難しいケースでは盤面を格子状の小領域に分割して占う。

## 実装上重要な断片

尤度表の作り方はこの解法の核である。

```text
push_query(S, observed):
    for each oil i and legal position p:
        cnt = popcount(bit_oil[i][p] & S)
        if cnt > 0:
            related_queries[i,p].append((query_id, cnt))

    for possible true_sum ws:
        if |S| == 1:
            log_pr[ws] = 0 if ws == observed else very_small
        else:
            mu = get_mu(|S|, ws)
            pr = P(round(Normal(mu, sigma)) == observed)
            log_pr[ws] = clipped_log2(pr) * 2^32
```

近傍評価は、動かす油田の寄与があるクエリだけを見る。

```text
try move oil i: p -> q
    delta[related(i,p)] -= cnt
    delta[related(i,q)] += cnt
    gain = sum(log_pr_q[count_q + delta_q] - log_pr_q[count_q])
    if SA_accept(gain):
        commit config, counts, log_like
```

クエリ選択は「最尤と期待値の差」を入口にしている。

```text
for p in board:
    score_p = v_best[p] - E_candidate[v[p]]
    if score_p > 0:
        S.add(p)
greedy_remove_then_add(S, objective = expected concentration after observation)
```

## この解法の本質

大域的な全探索はできないため、「観測履歴に対して尤度が高い配置だけを高速に集め、その小さな候補集合上でベイズ推定する」ことが本質である。焼きなましは単に最尤1点を探すためではなく、事後分布の代表点を複数集めるために使われている。

また、状態に盤面グリッドを持たず、各クエリの総和と配置ごとの寄与表だけで尤度差分を出している点が強い。AHC030 はクエリが増えるほど評価が重くなるので、ここを軽くしないと候補集合を十分に探索できない。

## 真似するならまず実装する部分

1. 油田形状の合法配置を列挙し、各配置のマス集合を `BitVector` で持つ。
2. 観測値に対する `log P(observed | true_sum)` を CDF から作る。
3. 状態を「油田ごとの配置」と「各クエリ総和」で持ち、1油田移動の差分尤度を出す。
4. 焼きなましで上位候補を32個程度集め、候補上の事後確率を正規化する。
5. 最尤候補の正マス集合の確率が高ければ回答し、低ければ `v_best[p] > E[v[p]]` のマス集合を占う。

まずは `swap_oils`、温度自動調整、油田選択バイアス、貪欲なクエリ集合改善を後回しにしても、解法の骨格は再現できる。速度が足りなくなった段階で、`related_queries` による差分更新と観測確率の前計算を入れるのがよい。

## 注意点・未理解点

- 記事本人も述べている通り、クエリ選択の評価関数は相互情報量最大化そのものではない。なぜこの近似評価がどのケースで効くかは完全には説明されていない。
- 提出コードの `calc_new_ans_pr_ex` は、候補分布の集中度を返値ごとに積分しているように読めるが、エントロピーではなく二乗和型の評価である。理論的な最適性は未確認である。
- `guess_threshold` と `difficulty`、初期占いの分割数、時間配分はかなり経験的なパラメータである。
- `swap_oils` は形状同士の最大重なりを使う巧妙な近傍だが、異なる形状の入れ替えでどの程度効いているかは記事でも詳細な寄与が示されていない。
- AtCoder 提出コードは読めたが、ローカルでコンパイル・実行して挙動確認はしていない。今回の目的は参照元解法の読解メモ作成であるため、実行検証は対象外とした。
