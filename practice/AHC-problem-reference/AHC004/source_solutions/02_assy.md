## 解法の全体像

まず、別の文字列に含まれる入力文字列を削除し、残った文字列ごとに「何個の元文字列を代表しているか」を重み `w` として持つ。次に、任意の2文字列についてsuffix-prefixの重複数を計算し、各文字列から見て重複数が最大となる相手だけを接続候補 `opp` として記録する。

1行を作るときは、任意の文字列から始め、長さ20になるまで最大重複候補だけで連結するビームサーチを行う。ビームの評価値は、連結した文字列が代表する重要度の和である。生成された長さ20の候補列のうち、まだ盤面に出現していない元文字列を最も多く含むものを1行として採用する。採用後は出現済み文字列を削除し、同じ処理を繰り返して20行を作る。

## 主要アイデア

- 完全に他文字列へ含まれるヒントは、親文字列が出現すれば同時に満たせるので削除する。
- 各代表文字列に、削除された包含文字列数を含めた重要度を持たせる。
- 全ペアの重なりを前計算し、各文字列からは最大重なりの相手だけへ遷移する。
- 1行を長さ20の超文字列として作る。これはshortest common superstringに近い局所問題である。
- 行候補のビーム評価は重要度和で、最終採用時は未出現文字列の数を基準にする。
- 横方向だけを明示的に構築し、縦方向の出現は副産物として扱う。
- 文字列を3bit/文字のビット表現にして、高速な比較・重複計算を行う。

## 最終コードの構造

Browserで、記事記載の 6,406,046,257 点に対応する提出 `23750876` を読んだ。以下はその実装構造である。

### 状態表現

- `words`: 包含削除後の代表文字列。
- `importance[word]`: その代表文字列が何個の元文字列を含むか。
- `contained_originals[word]`: 代表文字列がカバーする元文字列集合、またはその個数。
- `overlap[i][j]`: `words[i]` の末尾と `words[j]` の先頭が一致する最大長。
- `best_next[i]`: `overlap[i][j]` が最大の `j` の集合。複数あれば全て持つ。
- `used/or appeared`: すでに採用済みの行で出現した元文字列の集合。
- `answer_rows`: 採用した長さ20の行文字列。

実コードでは、文字列を1文字3bitで `unsigned long long bit[i]` に詰める。`bset[i]` と `mask_bset[len]` も持ち、行文字列を2回連結したビット列上で包含判定する。`w[i]` が代表文字列の重み、`remain` がまだ得点対象として残っている代表集合、`alen[i][j]` が重複長、`opp[i]` が最大重複相手集合である。

### 観測・制約・入力の扱い

- 入力文字列同士の包含関係を調べ、他文字列に含まれるものは代表から外す。
- 代表から外れた文字列は消すだけでなく、親代表文字列の重要度へ反映する。
- 行長は20に固定する。ビームで連結して長さ20の候補を作る。
- 横方向のみを主対象にする。縦方向の判定や縦配置は解法本体には入れていない。
- 行内の出現判定は、行を2回連結したビット列で行う。これは横方向の巡回を考慮するためである。

### 評価関数

- 前処理中の重要度: 代表文字列が含む別文字列数。代表が出現すればその分だけ得点できるとみなす。
- ビーム内評価: 連結経路上に追加した代表文字列の重み和。コードでは `cw` を負値で持ち、`sort` で小さい順にして大きい重みを優先する。
- 行採用評価: `calc_sum_w(row)` で、その行に巡回部分文字列として含まれる `remain` 内の代表文字列の重み和を数える。候補行のうちこの値が最大のものを採用する。
- 行を採用したら `remove(row)` で、その行に含まれる代表文字列を `remain` から消し、残った集合に対して `opp` を再計算する。

### 探索・構築・更新

- 包含削除:
  - 全ペアで `s_i` が `s_j` に含まれるか調べる。
  - 含まれる側 `i` の `w[i]` を0にする。
  - 含む側 `j` の `w[j]` に `w[i]` を加える。
- 重複前計算:
  - 任意の2文字列について、末尾と先頭の一致長を求める。
  - 各文字列ごとに最大一致長を持つ相手集合だけを保存する。
- 1行構築ビーム:
  - `remain` の各文字列を開始文字列として試す。
  - 状態は `(負の重み和, 現在行bit, 末尾文字列id, 現在長)`。
  - 現在の末尾から `opp[last]`、つまり最大重複候補だけへ伸ばす。
  - ビーム幅は `BW = 18`。
  - 長さがちょうど `n` になった状態だけを行候補に入れる。長さが超えた候補は使わない。
- 全体構築:
  - 候補行を複数作る。
  - 未出現文字列の出現数が最大の行を答えに追加する。
  - その行で出現した文字列を削除または出現済みにする。
  - `n` 行ぶん繰り返す。AHC004では `n = 20`。

### 操作・クエリ・出力選択

- 出力は横方向に構築した20本の長さ20文字列である。
- `.` は使わず、全マスを `A` から `H` で埋める方針と読める。
- 縦方向のスコア獲得は明示的には狙わず、偶然一致したものだけ加点になる。

### 時間配分・パラメータ

- ビーム幅は実コードで `BW = 18`。
- ビーム幅をケースごとに調整できなかったことを反省点としている。
- ビット表現は高速化の中核で、1文字3bit、20文字60bitとして64bit整数に収める。
- 重複候補は最大重複相手だけに絞るため、ビームの分岐を抑えている。

## 実装上重要な断片

```text
compress_by_containment:
    for each pair (i, j):
        if s_i is substring of s_j:
            remove i from representative words
            importance[j] += importance[i]
```

```text
precompute_best_next:
    for each i:
        best = max overlap_suffix_prefix(words[i], words[j])
        best_next[i] = all j with overlap == best
```

```text
build_one_row:
    beam = states starting from each remaining word
    while length < 20:
        extend only by best_next[last_word]
        merge with overlap
        keep top 18 states by sum of importance
    keep only states whose length is exactly 20
    choose row maximizing calc_sum_w(row)
```

## この解法の本質

この解法の本質は、20x20盤面問題を「価値付きの長さ20文字列を20本選ぶ問題」へ分解している点である。縦方向を捨てる代わりに、横1行の品質を上げる。入力生成では同じ真の行・列から重なった断片が多数出るため、包含削除と重複連結だけでも、多数のヒントをまとめて満たせる。

また、全ての重複候補を探索するのではなく、最大重複相手だけに絞っている。これは厳密性を捨てるが、短期コンテストでビームを回すには有効で、重要度によって「1本の代表文字列が何個分の得点を持つか」を評価に入れている点が強い。

## 真似するならまず実装する部分

まず、包含削除と重要度計算を実装するのがよい。次に、全ペアのsuffix-prefix重複を求め、重複最大の相手へ貪欲に連結して1行を作る。最初はビームではなく、開始文字列を複数試して最良を選ぶだけでもよい。

その後、1行構築をビーム化し、採用済み行でカバー済みになった元文字列を評価から外す。ビット表現は最後でよいが、Mが大きく時間制限が厳しいため、スコアが見えたら導入を検討する。

## 注意点・未理解点

- 記事本文には提出リンクがないため、BrowserでAtCoder提出一覧から `assy` の提出を辿る必要があった。
- 実コードでは「出現していない文字列の数が最大」の対象は、`remain` 内の代表文字列重み `w` の合計である。包含削除された元文字列数も `w` に含まれる。
- 横方向のみのため、縦由来の入力文字列を体系的に拾えない。長い文字列では縦方向の偶然一致はほぼ期待できない。
- 最大重複相手だけに絞ると、局所的には良いが行全体では弱い接続を選ぶ可能性がある。
- ビーム幅固定はケース依存でTLEまたは探索不足になりやすい。
