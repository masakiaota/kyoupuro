## 解法の全体像

最初は完全解を出せる可能性を考え、各入力文字列を盤面内に配置し、その位置を変更する焼きなましを試した。各セルに割り当てられる文字の分布が1文字に集中しているほど良い、という評価を考えたが、使われる文字列が1つだけのセルが過大評価されるなど評価設計が難しく、うまくいかなかった。

その後、完全復元を諦め、横1行ずつ構築する方針へ移る。1文字列を置くたびに状態を進めると、盤面の埋まり具合が候補ごとに揃わず評価が難しいため、「1行分を作る」ことをビームサーチの1ステップにした。さらに縦方向を完全に捨てるのは損なので、先に縦1列、最終的には縦2列を作り、その固定列を使いながら横20行を作る構成にした。

## 主要アイデア

- 完全解狙いの盤面配置焼きなましは評価関数が難しく、短期では切り捨てる。
- 横1行ずつ作れば、最低でも横方向のヒントを多く拾えるという見積もりを置く。
- ビームの1ステップを「文字列1本」ではなく「行1本」にする。状態の粒度を大きくして評価を安定させる。
- 1行分の作成にはランダム性を入れ、ビーム内の多様性を出す。
- 縦2列を先に構築し、その後に横行を作る。横行の先頭が固定されてもスコア低下は小さく、縦で得た得点が上乗せになる。
- 文字列を先頭2文字で分類して保持し、候補検索を高速化する。

## 最終コードの構造

提出 #23751555 の実装に基づく構造である。記事で述べる「1行単位ビーム」と、失敗案として触れられている文字列位置焼きなましの `solve2` が同じ提出内に残っている。

### 状態表現

- 入力ヒント列 `@ss`。文字は `A` から `H` を0..7に変換する。
- 行構築用の `State`。使用済みヒント、現在スコア、行候補、親状態IDのような情報を持つ。
- `Result`: スコアと20行の盤面。
- `connect_str(row, x, si)`: 行候補にヒント `si` を位置 `x` から矛盾なく接続できるか判定し、置けるなら行を更新する。
- 失敗案用の `Pos` と `solve2`。各ヒントの位置・方向を持ち、セルごとの文字分布からスコア差分を計算する焼きなましである。

### 観測・制約・入力の扱い

- 横方向の構築を主に考える。
- 縦方向は、全列を同時に最適化するのではなく、先に少数列だけ構築する。
- 横行を作るとき、先頭1から2文字が縦固定列によって制約される。記事では、この固定による横スコアの損は大きくないと判断している。
- 文字列を先頭2文字で分類し、現在の行候補に接続しやすい文字列を効率よく探す。

### 評価関数

- 失敗した焼きなまし案では、各セルに割り当てられる文字分布の集中度を評価しようとしていた。
- 最終方針のビーム評価式は記事には明記されていない。
- 解法説明からは、行または列を追加したときに新たに満たせる文字列数、今後の行構築しやすさ、候補多様性を評価していたと推測される。
- 少なくとも、1文字列単位の配置状態より、1行単位で完成した状態を評価する方が安定すると判断している。

### 探索・構築・更新

- 失敗方針:
  - 各入力文字列に盤面上の位置・向きを割り当てる。
  - 焼きなましで位置を変更する。
  - 各セルの文字分布が集中するほど良いと評価する。
  - 評価が不安定で断念する。
- 最終方針:
  - `solve` で行単位ビームを行う。
  - `beam = Array.new(total_chars + 1) { [] of State }` とし、得点または使用文字数別に状態を持つ。
  - `beam_width = 1500`, `beam_trial = 200`, `max_spawn = 30` から始め、残り400msで幅100、残り100msで幅10に落とす。
  - 各行で親状態から複数の行候補を生成し、`connect_str` でヒントを接続する。
  - 時間切れが近づくと枝数を落としながら最後まで盤面を作る。

### 操作・クエリ・出力選択

- 出力は、先に決めた縦2列と整合するように作った20行である。
- `.` のボーナスは狙っていないと考えられる。全マスを文字で埋め、出現文字列数を最大化する方針である。
- 最終盤面は、ビーム内で最も評価が高い状態から復元する。

### 時間配分・パラメータ

- 6時間中1.5時間ほどで完全解方針を諦め、横1行ずつの方針へ移行したとある。
- 提出 #23751555 では `beam_width = 1500`, `beam_trial = 200`, `max_spawn = 30` が確認できる。残り時間に応じてビーム幅を下げる。
- 先に作る縦列数は1列より2列が良かったため、最終的に2列。
- 先頭2文字分類が高速化に効いたと述べられている。

## この解法の本質

この解法の本質は、状態粒度の設計である。文字列を1本ずつ盤面へ撒く状態は、部分的にしか埋まっていない盤面を評価しなければならず、評価が不安定になる。1行を完成単位にすれば、横方向の得点貢献が測りやすく、ビームサーチの比較対象もそろう。

さらに、横だけに割り切ると縦由来ヒントを失うが、縦2列だけを先に作ることで縦方向の得点を一部確保する。横行の先頭が固定されても20文字中2文字程度の制約なので、横の構築力を大きく失わずに縦スコアを足せる。この「主軸は単純化し、副軸は小さく固定して取り込む」設計が強い。

## 真似するならまず実装する部分

最初は、縦固定なしで横20行を1行ずつ作るビームを実装するのがよい。1行候補は、重なり貪欲やランダムな文字列連結で作り、評価は新たに満たした文字列数にする。

次に、先頭2文字の分類で行候補生成を高速化する。最後に、縦1列、さらに縦2列を先に固定し、その制約下で横行を作る。完全解狙いの盤面焼きなましは、評価関数設計が難しいため後回しでよい。

## 注意点・未理解点

- 最終提出 #23751555 はBrowserで読めたため、行単位ビームの幅、候補生成上限、`connect_str` による行への接続、失敗案 `solve2` の存在は確認済みである。縦2列の作り方や記事本文との完全な対応は、コード全体の細部まで追っていないため一部未整理である。
- 「1行分を作る中にランダム性を持たせる」の具体的な分布や候補数は分からない。
- 先頭2文字分類がどの方向の接続に使われたかは推測を含む。
- 縦列を固定しすぎると横行候補が狭まり、逆にスコアが落ちる可能性がある。記事では2列が良いとあるが、一般に何列が最適かは要検証である。
- 完全解狙いの評価関数失敗は示唆的だが、最終方針のコードがないため、再現には独自設計が必要である。
