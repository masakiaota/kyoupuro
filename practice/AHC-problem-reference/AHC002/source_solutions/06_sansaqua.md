## 解法の全体像

盤面を 10x10 マスの大ブロック、つまり 5x5 個のメタ盤面に分ける。メタ盤面上でハミルトンパスを作り、その順にブロックを巡る。各ブロックの内部では、次のメタブロックへ到達するまでビームサーチで経路を伸ばす。

gobi の方針と同じく、大域的な移動順を固定して局所探索に落とす構築型である。こちらは Common Lisp 実装で、メタパスを探索し、タイルと位置状態を効率よく持つ実装上の工夫が多い。

## 主要アイデア

- 50x50 を 10x10 ブロック 25 個に分ける。
- スタートが属するメタブロックから、メタ盤面上のハミルトンパスを作る。
- 各メタブロック内でビームサーチを行い、次のメタブロックに入るまで進める。
- 位置、得点、訪問済みタイル、経路復元用の親情報をビーム状態として持つ。
- ブロック内部で完結するタイルやブロック境界をまたぐタイルを扱うため、タイル情報を前処理する。
- ビーム幅は段階によって 1000、6000 などが使われている。記事本文では 6000 から 8000 でスコア改善を試したと説明されているが、読めた提出コード内では最終的に 6000 で切っている箇所が確認できる。

## 最終コードの構造

### 状態表現

- `input` 構造に `si/sj`、タイル行列、得点行列、タイル数、タイルごとの座標一覧を持つ。
- 座標は `(y,x)` として扱い、経路復元用には packed coord も使う。
- メタ盤面は `+part+ = 5`、ブロック幅は `+width+ = 10`。
- ビーム状態は概ね `score, pos-tree, marked, bset` の組である。
- `marked` は訪問済みタイルの bit vector。
- `pos-tree` は経路復元用の親リストに相当する。
- `bset` はブロック内の状態管理、または境界・タイル状態を圧縮した補助情報として使われている。

### 観測・制約・入力の扱い

- 入力時にタイル ID ごとの座標一覧 `tilemap` を作る。
- 同じタイルの 2 マスがどのメタブロックに属するかを見て、ブロック処理中に必要なタイル情報を `tile-indexer` へ落とす。
- 移動候補は盤面内、未訪問タイル、現在許可されるメタブロック領域に入ることを満たす必要がある。
- メタパスから `metamat` を作り、現在メタブロックに対する次メタブロックを即座に参照できるようにする。

### 評価関数

- ビーム内の主評価は得点合計であり、高い順にソートして上位を残す。
- 大域的な到達性はメタパス制約で管理するため、評価関数そのものに広さや閉じ込めペナルティは入れない。
- 記事本文では、ハミルトンパスに沿わせることで TLE 回避と行き詰まり回避を両立する意図が説明されている。

### 探索・構築・更新

- `find-metapath` がメタ盤面上のブロック順を決める。
- `make-metamat` が各メタブロックから次メタブロックへの対応を持つ。
- `solve-beam` が実際の 50x50 盤面上でビームを進める。
- 各メタブロック処理で状態を展開し、候補状態を得点順に並べ、上位だけを残す。
- 次メタブロックへ到達した状態があれば、そこで区切って次のメタブロック処理へ移る。
- 最良状態 `opt` を保持し、最後に `restore-path` で操作列を復元する。

### 操作・クエリ・出力選択

- 経路復元後、方向番号を `U/L/D/R` に対応する文字へ変換して出力する。
- ビームが尽きる、またはメタパスを進み切った時点で、保持している最良状態から回答を作る。

### 時間配分・パラメータ

- ブロック幅は 10、メタ盤面は 5x5。
- 提出コード中では、メタパス探索の途中候補を 1000 に切る箇所、メインのビームを 6000 に切る箇所が確認できる。
- 記事本文ではビーム幅を 6000 から 8000 に増やして 5.2e6 から 5.3e6 程度へ上がったと説明されている。公開提出コード上で確認できた値とは一部対応がはっきりしない。

## 実装上重要な断片

```text
metapath = find_hamiltonian_path(start_block)
metamat = successor_table(metapath)

for block in metapath:
    next_block = metamat[block]
    beam = current frontier
    while beam not empty:
        next = expand all legal moves within allowed area
        update opt by score
        if reached next_block:
            beam = reached states
            break
        beam = top 6000 states by score

answer = restore_path(opt)
```

Common Lisp 実装では、状態コピーの重さを抑えるために bit vector や packed coord を使っている点が重要である。

## この解法の本質

盤面全体を自由に探索する代わりに、メタブロックのハミルトンパスで大まかな通行順を固定する。これにより、ビームサーチの評価値を単純なスコア合計にしても、全体を回るという性質を外側の構造で担保できる。大域制約を先に設計し、局所最適化を単純にする発想が本質である。

## 真似するならまず実装する部分

10x10 ブロック分割と、スタートブロックから全ブロックを一筆書きで回るメタパスを作る。次に、現在ブロックから次ブロックへ入るまでのビームサーチを実装する。境界タイルの圧縮管理やメタパス探索の一般化は後回しで、まず固定メタパス + 単純ビームで動かすのがよい。

## 注意点・未理解点

- Common Lisp コードは最適化マクロや圧縮表現が多く、`bset` など一部の補助状態の意図は完全には追い切れていない。
- 記事中のビーム幅 8000 の記述と、読めた提出コード中の 6000 切りの対応は不明である。
- ブロック境界をまたぐ 2 マスタイルの扱いは壊れやすい。
- メタパスで大域順序を固定するため、焼きなまし型に比べると局所的な高得点回収の自由度は低い。
