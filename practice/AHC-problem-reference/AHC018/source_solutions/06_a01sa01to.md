## 解法の全体像

完全ルールベースのグリッドサンプリング解法である。最初は単純に家から水源へ直線で掘る実装から始め、統計によりパワーを下げ、さらに一定間隔で試し掘りして硬い方向を避ける DFS + ダイクストラに発展している。

最終コードでは、各セルを `None / NotBroken / Broken / Flowing` と掘削回数で管理する。家を近い水源または既に水が来た家へ順に接続する。DFS で `DFS_WIDTH=12` 間隔の粗い点をパワー128で試し、壊れた点だけを伸ばす。既に壊れている点や水が流れている点を見つけたら、粗い壊れ点グラフ上でダイクストラし、最後は `connect_greedy` で隣接セルをまっすぐ掘って接続する。

## 主要アイデア

- 岩盤分布の統計を取り、中央値234、平均776.58などから固定フルパワーの弱さを確認する。
- パワー128で一定間隔の点を試し掘りし、壊れた点を「通れそうな点」として扱う。
- DFS は目標方向を優先し、遠くへ行きすぎる候補を捨てる。
- 現在位置から最寄りの水源または既に流れている家へ動的に目標を変える。
- 近くに水路や破壊済みセルがあれば、そこへ接続して無駄な掘削を減らす。
- 粗い点同士はダイクストラでつなぎ、最後の実セル列は貪欲に掘る。
- 始点・終点が1回で壊れた場合は、間のセルも弱いと仮定してパワーを小さくする。
- C が大きいと掘削回数が重いので、C に応じて接続パワーを上げる。

## 最終コードの構造

### 状態表現

- `RockState`: `None`, `NotBroken`, `Broken`, `Flowing`。
- `bedrock[x][y] = (RockState, i32)`: 状態と、そのセルを掘った回数。
- `Point`: 座標とマンハッタン距離・ユークリッド距離計算。
- 定数:
  - `POWER = 128`
  - `DFS_WIDTH = 12`
  - `BREAK_AC_INIT = 3`
  - `NEAR_AC = 15`
  - `FLOWING_AC = 12`
  - `BROKEN_AC = 8`

### 観測・制約・入力の扱い

- `query` は既に `Broken` または `Flowing` なら出力せず状態を返す。
- 実際に掘る場合は `x y p` を出力し、結果を読む。
- `res == -1` または `res == 2` なら即終了する。
- `res == 1` なら `Broken` にし、`res == 0` なら `NotBroken` にする。
- コードは累積パワーではなく掘削回数を主なコスト情報として使う。

### 評価関数

- 粗い壊れ点グラフ上のダイクストラでは、次点の掘削回数 `bedrock[nx][ny].1` をコストにする。
- 斜め移動は信頼度が低いとして倍率3をかける。
- DFS の打ち切りでは、現在位置が目標から遠すぎるかどうかを `upper_dist` で判定する。
- `connect_greedy` の接続パワーは、両端の掘削回数と C から決める。

### 探索・構築・更新

- `main` は家を最寄り水源への距離で優先度付きキューに入れる。
- 家が水に接続されたら、その家を新たな接続先候補として他の家との距離をキューへ追加する。
- `dfs` は目標へ近づく方向を優先して、`DFS_WIDTH` 先をパワー128で最大 `break_ac` 回だけ試す。
- 試した点が壊れれば、近くの壊れ点や水路を探し、接続できるなら接続する。
- `connect_bfs` は壊れた粗い点だけを通る8方向ダイクストラで、粗い接続経路を復元する。
- `connect_greedy` は粗い点間を実セルでまっすぐ掘って接続する。

### 操作・クエリ・出力選択

- DFS の試し掘りは基本 `POWER=128`。
- `query_until_broken` は壊れるまで再帰的に掘る。高火力後は `round(p/1.5)` 方向へ弱めつつ、最低 `POWER` を保つ。
- `connect_greedy` では、両端がともに1回で壊れた場合、間のセルを `POWER/4` で掘る。
- そうでなければ、`POWER * min(src_count,target_count) * (C/32 + 1) / 4` を丸めた値を使う。

### 時間配分・パラメータ

- DFS間隔は最終的に12。
- 斜め移動倍率は3。4も試したが悪化したため戻している。
- 遠すぎ判定は最終的に、スタートから目標までの距離の2倍を上限にする方向へ落ち着いている。
- パワー調整は、128で1回破壊できたときに64や32でいける条件付き確率を見て導入されている。
- 最終提出は1ケースで Stack Overflow によりTLEしたと記事にある。

## 実装上重要な断片

```text
dfs(now, target):
    if now is flowing:
        connect_bfs(src, now)
        return true
    if now is near target:
        connect_greedy(now, target)
        connect_bfs(src, now)
        return true
    if near flowing cell:
        connect_greedy(now, flowing_cell)
        connect_bfs(src, now)
        return true
    for directions toward target:
        probe next grid point up to BREAK_AC times
        if broken:
            recurse
```

```text
connect_greedy(src, target):
    break endpoints
    while current != target:
        power = small if both endpoints broke in one hit
                else C_and_count_dependent_power
        dig current cell until broken
        step toward target
```

## この解法の本質

この解法は、硬さの連続推定をほとんど行わず、「128で何回叩いたら壊れたか」という粗い観測だけで進む。理論的な推定器はないが、DFS間隔、方向優先、既存水路への合流、C別パワー調整により、無駄掘りをかなり抑えている。

上位解法に比べると推定は粗いが、実装量に対する効果が高い。グリッドサンプリング型解法の最小構成として参考になる。

## 真似するならまず実装する部分

まず、`RockState` と掘削回数を持ち、家から水源へ `POWER=128` で粗いDFSを行う部分を実装する。壊れた粗い点だけを通る `connect_bfs` と、実セルをまっすぐ掘る `connect_greedy` を分けて作るとよい。

その後、目標を既に水が流れている家へ動的に切り替える処理、近くの水路への合流、C に応じたパワー調整を足す。

## 注意点・未理解点

- 累積ダメージではなく掘削回数中心なので、硬さ推定としては粗い。
- 再帰DFSが深くなるケースで Stack Overflow し、システムテスト1ケースTLEしたと報告されている。
- 統計分析用の `Stats.xlsx` と `res.txt` は巨大で、本文の要約値だけを使った。
- 記事では改善履歴が詳しい一方、最終コードの全パラメータがなぜその値かは実験依存である。
