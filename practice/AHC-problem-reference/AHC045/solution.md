## 問題の本質

この問題は、不確かな都市座標のもとで、指定サイズの連結成分を作るための短い森を構築する問題である。解法視点では、次の3つを同時に解く必要がある。

- 距離情報の獲得: クエリで返るMSTから、どの都市対が近いかをどれだけ引き出すか。
- 不確実性の表現: 都市座標を中心点、候補領域、サンプル、離散候補、距離順位のどれとして持つか。
- 容量付き構築: 指定サイズ `G` を守りながら、近い都市をグループ化し、各グループ内で短い木を作るか。

クエリは真の辺長を返さないが、MSTのcut/cycle性質から大量の距離大小関係を返していると見なせる。この大小関係を、座標推定・距離順位・辺置換・クエリ評価のどこへ使うかが解法の差になる。

## 共通している考え方

- クエリ応答のMSTは、木辺そのもの以上に、距離大小関係として価値がある。
- 近い都市だけを聞くと最終構築に効きやすいが、同じ場所を聞き続けると情報が飽和する。
- 座標中心だけで構築すると、範囲の広い都市を誤って長辺でつなぎやすい。
- 最終構築は、指定サイズを守るために全体MSTを切る、2グループを再分割する、容量付き森を局所探索する、のいずれかへ落とすと扱いやすい。
- 絶対距離を正確に推定できなくても、短い辺の順序が改善されればMST構築は良くなる。
- `L` が小さいケースでは1回のクエリから得られる情報が少なく、クエリ戦略を変える必要がある。

## 解法の分類

- サンプル推定型: eijirou。
- 制約違反最小化型: eijirou、wanui。
- 離散候補・粗視化型: tanaka-a、official_mya3。
- 距離順位型: uta_ccc、official_mya3。
- 全体MST分割型: tanaka-a、uta_cccの初期方針。
- 容量付き森局所探索型: eijirou、wanui。
- 2グループ破壊再構築型: wanui、uta_ccc、official_mya3。
- クエリ多様化型: eijirou、wanui、uta_ccc。

## 推奨して理解すべき順序

1. tanaka-aメモで、中心距離、全体MST、部分木占い、木DP分割という素直な発展順を理解する。
2. uta_cccメモで、絶対座標ではなく辺順序を直す見方と、2グループ切り直し近傍を見る。
3. 公式mya3メモで、候補範囲を凸多角形として削る方法と、不等式DAGによる距離順構築を理解する。
4. wanuiメモで、距離大小ルールを大量に持ち、違反量を差分更新して座標を合わせる方法を読む。
5. eijirouメモで、サンプル、情報量クエリ、森焼きなまし、高速化を統合した上位解法を見る。

## 実装するならどのルートか

理解のための最小実装は、中心距離で全体MSTを作り、要求サイズへ切るtanaka-a型がよい。切れない部分は、該当部分木を壊してプリム法で要求サイズ分を取り直す。これに、グループ内 `L` 以下集合の占い改善を足すと、問題の基本構造を壊さずにクエリを使える。

次の段階では、wanui型の距離大小ルールを実装する。クエリ応答から `d(tree_edge) <= d(cross_edge)` を集め、中心座標を動かして違反量を下げる。クエリ集合は最初は「推定座標で近い `L` 点」でよく、後から `distance_rank` と `has_rule` 評価を入れる。

上位化するなら、eijirou型の複数サンプルに進む。1点推定ではなく複数のあり得る座標を持ち、サンプル間でMSTが割れる集合を聞く。構築側も、2グループ再構築だけでなく、容量付き森としてマージ・スプリット・辺交換を焼きなましで回す。

## 重要な実装要素

- 状態表現
  - 中心点だけの `pos[N]`。
  - 都市ごとの候補領域または離散候補。
  - 複数サンプル `samples[S][N]`。
  - 距離大小制約 `short_pair <= long_pair`。
  - グループ集合、木辺、成分サイズ、要求サイズの残数。
- 評価関数
  - 制約違反量 `max(0, d(short)-d(long))`。
  - クエリ内ペアの距離順位平均。
  - 未獲得ルールの多さ。
  - グループ内MSTコスト、または距離順位コスト。
  - サイズ制約違反と辺長和の混合コスト。
- 近傍
  - 都市座標を長方形内で動かす。
  - クエリ集合の1点交換。
  - 2グループの頂点交換。
  - 2グループを壊してプリム法で再構築。
  - 木内に非木辺を入れてサイクル上の長辺を抜く。
- 差分更新
  - 都市に関係する距離大小制約だけ再計算する。
  - グループ再構築時は、対象2グループのコストだけ更新する。
  - 木辺交換では、追加辺と削除辺の差だけ見る。
- 候補管理
  - 既出クエリを避ける。
  - 起点にした回数を制限する。
  - クエリ候補を近傍30個などへ絞る。
  - 距離DAGでは入次数0の都市対だけpriority queueへ入れる。
- 出力判定
  - 各都市がちょうど1グループに属すること。
  - 各グループサイズが `G_k` と一致すること。
  - 各グループ内の辺数が `G_k-1` で連結であること。
  - 占い後の最終出力前に `!` を出すこと。
- パラメータ
  - `L` ごとのクエリ戦略。
  - サンプル数。
  - 座標更新ステップ幅。
  - 焼きなまし温度。
  - クエリ候補数。
  - 推定・構築への時間配分。

## 落とし穴

- MST応答から得た大小関係の向きを逆にすると、推定も辺置換も壊れる。
- `d(a,b) <= d(c,d)` は同値や丸め距離を含むため、厳密な `<` として扱うと矛盾が増える。
- 全ての非木辺制約を素直に追加すると重くなる。重複除去や差分更新が必要である。
- 1点推定に合わせすぎると、真座標では長い辺を選びやすい。
- 範囲の広い都市を普通の都市と同じようにつなぐと、スコアの悪化要因になりやすい。
- 距離順位だけをコストにすると、実距離の差の大きさを失う。遠い辺を避けるには別の近似が必要になることがある。
- 全体MSTから切るだけでは、要求サイズに分けられない部分木が出る。
- クエリを近い点だけに寄せすぎると、同じ局所を繰り返し聞いて情報が伸びない。
- `L` が小さい場合、三角形1個から得られる制約が少ないため、`L` 大ケースと同じ戦略では弱い。
- インタラクティブ出力ではflush忘れでTLEになる。

## 未解決・要検証事項

- tanaka-a氏とuta_ccc氏については、今回のキャッシュで提出実装を確認できた。公式 mya3 はキャッシュが簡易ベースラインであり、公式解説本文の高度な実装細部は引き続き未確認である。
- 公式解説の距離DAGにサイクルが出た場合の扱いは確認できていない。
- 各解法の温度、係数、占い配分はチューニング依存であり、再実装時には再調整が必要である。
- `floor` 付きユークリッド距離と等距離タイブレークを、推定・制約側でどこまで厳密に扱うべきかは要検証である。
- グループ改善で使う近似距離と、最終スコアの真距離のズレをどう評価するかは実装ごとに異なる。
