## 問題の本質

AHC058 は、10 本の独立した生産系列のうち、どの ID にどの時点から資源を集中するかを決める問題である。Level 0 は直接りんごを生み、上位 Level は下位機械数を増やすため、同一 ID 内の強化は掛け算的に効く。一方で、`A` が大きい ID は強いが、コストもばらつくため、序盤から高 `A` に向かうだけでは資金が間に合わない。短期の資金生成、上位 Level への投資、最終的な集中先の選択を同時に扱う必要がある。

## 実装キャッシュ反映

公式itigo相当 `#71635590` と scat_neko `#71760160` の提出コードを読んだ。itigo実装は幅400の3フェーズビームを強い貪欲候補にかけ、その購入列を変更・削除・挿入・swapの焼きなましで後処理する。scat_neko実装は固定グリッドではなく約1950msのランダム再始動貪欲で、集中ID倍率は本文の1000ではなく10000だった。

## 共通している考え方

- 「以降何もしなかった場合の最終りんご数」を評価できると、貪欲・ビーム・後処理の共通部品になる。
- 最終的には同一 ID へ集中投資するケースが多く、固定 ID の全探索や評価倍率が効く。
- 序盤と終盤では良い評価が違う。序盤は短期 horizon やターゲット到達ターン、終盤は最終りんご数が効く。
- 焼きなましや山登りでは、行動列そのものより「強化対象列」を持つ方が近傍を作りやすい。
- ビームサーチでは、候補生成やハッシュで状態数を削らないと 2 秒に収まらない。

## 解法の分類

- 貪欲型: scat_neko、公式の簡単な貪欲・強い貪欲、hitonanode の低収入フェーズ。
- 固定 ID 探索型: scat_neko、terry_u16 方針、G4NP0N 方針、hitonanode の `fixed_j`。
- ビームサーチ型: 公式ビーム、momohara、terry_u16、enari_K。
- chokudai サーチ型: G4NP0N。
- 焼きなまし型: 公式、MathGorilla、aaaaaaaaaa2230、yochan、takumi152。
- 後処理改善型: hitonanode の山登り、Kiri8128 の貪欲後焼きなまし。

## 推奨して理解すべき順序

1. まず scat_neko の貪欲を読む。評価値と集中 ID 補正だけでかなり戦えることが分かる。
2. 次に公式解説を読み、なぜ集中投資 ID とチェックポイントが重要なのかを整理する。
3. enari_K のコードを読み、状態、候補生成、ビーム幅、出力復元の実装形を確認する。
4. ALGO ARTIS レポートで、ビーム・焼きなまし・ローリングホライゾンなどの別解を比較する。
5. hitonanode gist で、フェーズ分けと後処理を足した実装計画を読む。

## 実装するならどのルートか

理解のための最小実装は、scat_neko 型の評価値貪欲がよい。必要なのは正確なシミュレータ、無強化時の将来評価、集中 ID 全探索だけである。

上位化を狙うなら、次に公式のチェックポイント貪欲を足す。さらに伸ばすなら、enari_K 型のビームサーチで複数候補を残すか、hitonanode 型の山登りで貪欲列を改善する。焼きなましは強いが、評価高速化と近傍設計ができてから入れる方がよい。

## 重要な実装要素

- 状態表現: `K`, `B[4][10]`, `P[4][10]`, 現在ターン、行動履歴。
- 評価関数: 候補を 1 回適用した後の無強化将来りんご数、または現在資産 + 近似将来価値。
- 近傍: 1 点変更、insert、erase、swap、ID suffix 固定、Level 引き上げ + 末尾追加。
- 差分更新: 1 ターン生産は Level 0,1,2,3 の順。候補評価では clone が簡単だが、焼きなましでは高速化が必要。
- 候補管理: 固定 ID、集中 ID 倍率、上位候補抽出、ハッシュ重複排除。
- 出力判定: 500 行ちょうど出す。支払えない強化は出さず、必要なら `-1` で待つ。
- パラメータ: 集中 ID、序盤 horizon、序盤終了ターン、ビーム幅、候補数、コストペナルティ、固定 ID 閾値、ブロック長。

## 落とし穴

- 生産順を間違えるとスコアも支払い可否も変わる。
- `K` と `B` は非常に大きくなるため、整数型のオーバーフローに注意する。
- `double` 評価は高速だが、巨大値で丸めや `inf` が出る可能性がある。
- 最終ターンだけを見た貪欲は、序盤の資金生成を軽視して弱くなることがある。
- 安い ID に閉じる局所解と、高 `A` ID に向かいすぎて立ち上がらない失敗の両方がある。
- ビームサーチで重複状態を消さないと、同じような状態が幅を消費する。
- 購入列を焼く場合、支払えない要素をどう扱うかを曖昧にすると評価と出力がずれる。
- パラメータ全探索を広げすぎると 2 秒に収まらない。

## 未解決・要検証事項

- 公式解説のビームサーチ + 焼きなましの接続は、itigo提出キャッシュで確認済み。
- 無強化時の将来りんご数式は、itigo提出キャッシュで4レベル組合せ式として確認済み。
- scat_neko の待機改善条件は提出キャッシュで確認済み。グリッドサーチ範囲は本文画像由来で、提出コードはランダム再始動型だった。
