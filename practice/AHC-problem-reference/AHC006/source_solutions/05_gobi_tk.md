## 解法の全体像

オフィス中心の一辺 450 の正方形に始点・終点が入る注文だけを候補にし、まず pickup 側を貪欲に 50 件選ぶ。その後、残った配達先を TSP と見て 2-opt 山登りで巡回順を改善する。pickup 中に、現在地から次の pickup へ向かう長方形内に、すでに消化可能な配達先があれば寄り道として踏む処理も入っている。

注文選択では、現在位置から注文始点までの距離だけでなく、注文の始点から終点までの距離も加味する。評価式は `現在地から始点までの距離 + 始点から終点までの距離 / n` で、`n=2..6` を試し、最もスコアが良い結果を採用している。

## 主要アイデア

- 遠い注文を避けるため、オフィス中心の一辺 450 の正方形に始点・終点が収まる注文に絞る。
- pickup は貪欲で、現在位置に近く、かつ始点-終点距離も短い注文を優先する。
- `sg_dist_dev` を 2..6 で変え、複数パターンを試して良い解を出す。
- pickup 移動の途中に、マンハッタン距離のロスなしで踏める配達先があれば処理する。
- 50 件選んだ後の未訪問配達先は、TSP として 2-opt 山登りで順序改善する。
- 配達先 TSP は始点を現在位置、終点をオフィスにした経路として扱う。

## 最終コードの構造

### 状態表現

- `Coord` は座標とマンハッタン距離を持つ。
- `Request` は注文 ID、始点 `s`、終点 `g` を持つ。
- `State` は以下を持つ。
  - `pos`: 現在位置
  - `choice`: 選択済み注文 ID
  - `choiced`: 注文選択済みフラグ
  - `route`: 出力する訪問座標列
  - `todo`: これから踏む必要のある座標集合
  - `moved_dist`: ここまでの移動距離
- `Yamanobori` は 2-opt 用に、ノード順 `path`、距離 `score`、距離表 `table`、開始時刻を持つ。

### 観測・制約・入力の扱い

- 入力 1000 件を `Request` として保持する。
- 候補選択時に、始点と終点がともにオフィス中心の正方形内にある注文だけを見る。
- `choose(req)` で注文 ID を選択し、始点と終点を `todo` に追加する。
- `move_to(to)` で座標へ移動し、`todo` からその座標を削除する。
- `todo` は `BTreeSet<Coord>` なので、同一座標は 1 点にまとまる。問題上、同じ座標を一度訪問すれば複数注文の条件を同時に満たせるため、出力座標としては自然である。

### 評価関数

- 注文選択時の貪欲評価:

```text
dist(current, req.s) + dist(req.s, req.g) / sg_dist_dev
```

- 最終候補選択では、構築済み `moved_dist` から公式スコア相当を計算し、`sg_dist_dev=2..6` の中で最大のものを選ぶ。
- 2-opt 中の評価は、残り配達先ノード列の総マンハッタン距離である。

### 探索・構築・更新

- `solve(input, sg_dist_dev)` は次の流れで動く。
  - 選択数が 50 未満の間、評価式が最小の未選択注文を探す。
  - 現在地から次の pickup までの軸平行長方形を作る。
  - その長方形内に `todo` の配達先があれば先に移動する。
  - 注文を選択し、その始点へ移動する。
  - 50 件選んだら、残り `todo` とオフィスと現在位置からノード集合を作る。
  - 距離表を作り、2-opt 山登りで経路を改善する。
  - 改善後の順に残り点を踏み、最後にオフィスへ戻る。
- 2-opt はランダムに区間 `[l,r]` を選び、反転で距離が短くなる場合だけ採用する山登りである。

### 操作・クエリ・出力選択

- `State::print` が、選択済み注文 ID とルート座標列を出力する。
- `main` では `sg_dist_dev=2` の解を作り、続けて `3..=6` を試して、公式スコア換算が高い状態を採用する。

### 時間配分・パラメータ

- `RECT_LIMIT=450`。
- `sg_dist_dev` は 2, 3, 4, 5, 6 を試す。
- 2-opt の山登りは各 `solve` 呼び出し内で約 380ms ぶん走る設計に見える。5 パターン合計でおおむね 1.9 秒を使う。
- 乱数は `Pcg64Mcg::new(890482)` の固定 seed。

## 実装上重要な断片

```text
choose_pickup:
    candidates = requests whose pickup and delivery are inside center square
    select argmin dist(pos, pickup) + dist(pickup, delivery) / n

on the way to pickup:
    rect = bounding_box(pos, next_pickup)
    if todo point is inside rect:
        move_to(todo point)
    then choose order and move_to(pickup)

after all pickups:
    nodes = [current] + remaining todo + [office]
    improve nodes order by 2-opt hill climbing
```

## この解法の本質

この解法は、問題を「pickup 側の構築」と「delivery 側の TSP」に分け、4 時間で実装しやすい形に落としている。pickup 時点では注文選択の自由度が大きいため、中心に近く、始点-終点も短い注文を優先するだけでも一定の品質が出る。配達先は全 pickup 後にまとめて TSP として改善することで、順序最適化の効果を取り込みやすくしている。

途中配達の長方形判定は、マンハッタン距離の性質を利用した局所的な得である。現在地と目的地を結ぶ軸平行長方形内の点なら、経由しても距離が増えない場合があるため、pickup 中でも配達先を自然に処理できる。

## 真似するならまず実装する部分

まずは中心正方形で候補を絞り、`dist(current,pickup) + dist(pickup,delivery)/n` の貪欲で 50 件選ぶ部分を作る。その後、残った配達先を最近傍または 2-opt で並べる。長方形内の途中配達は効果が限定的と記事で述べられているため、後回しでよい。

## 注意点・未理解点

- pickup と delivery をかなり分離するため、上位解法のような入り混じったルートにはなりにくい。
- 中心正方形のサイズ 450 と `sg_dist_dev` はパラメータ依存である。
- `todo` が座標集合なので、同一座標の複数注文を個別には管理しない。出力制約上は同一座標訪問でまとめて満たせるが、注文 ID と訪問条件の対応を考えると実装時に誤解しやすい。
- 2-opt は pickup-before-delivery 制約を気にしなくてよい段階、つまり残りが配達先だけになってから使っている。この分離が実装を簡単にしている。
