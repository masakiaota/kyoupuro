## 解法の全体像

トラックの移動経路を先に1本のwalkとして固定し、そのwalk上でいつ積み、いつ降ろすかを最小費用流で最適化する。初期解では、行方向のジグザグ走査と列方向のジグザグ走査をつなげ、各マスを概ね2回通るwalkを使う。その後、同じ最小費用流を評価関数として、walkの一部を削って移動距離を短くする山登りを行う。

この解法では「土の供給元と需要先の対応」を直接決めない。walkの各時刻でトラックに載っている土量を、フローの流量として決める。経路が固定されれば積み下ろし量の最適化は厳密に解ける、という分離が核である。

## 主要アイデア

- 移動経路の各訪問時刻を別頂点として持ち、同じマスを複数回通る場合も区別する。
- グリッド上のマス頂点とwalk上の時刻頂点を分け、マスからwalkへの流量を積み込み、walkからマスへの流量を積み下ろしとして解釈する。
- walk上の隣接時刻間の流量を、その区間でトラックが運搬する土量とみなす。
- フローのコスト1は、土1単位を積む、降ろす、1辺運ぶことに対応する。移動の固定費 `100 * (walk長 - 1)` は別途足す。
- 初期walkは全体を2方向に舐めるジグザグで作る。
- 山登りでは、`walk[i]` と `walk[i+3]` が隣接していれば中間2点を削除し、最小費用流で総コストが悪化しなければ採用する。
- さらなる改善では、高速な最小費用流、初期walkの多点スタート、追加のwalk短縮遷移を使う。

## 最終コードの構造

読めた最終コードは9.4Gの山登り版である。記事中の9.5G級最終版は未読のため、この節では [Submission #54668251](https://atcoder.jp/contests/ahc034/submissions/54668251) を対象にする。

### 状態表現

- `P { r, c }`: グリッド座標。4近傍判定を持つ。
- `Board H`: 初期高さ。
- `BASE`: `sum(abs(H[i][j]))`。流すべき土量は `BASE / 2`。
- `vector<P> walk`: トラックの訪問時刻列。先頭は必ず `(0,0)`。
- `Action { p, d }`: その時刻の座標と積み下ろし量。`d > 0` が積む、`d < 0` が降ろす。
- `memo[walk]`: 同じwalkに対する最小費用流計算結果のメモ。

### 観測・制約・入力の扱い

- `N = 20` 固定を `assert` する。
- 高さの総和0は問題保証に任せる。
- walkは各隣接点が4近傍であることを `assert` する。
- 最小費用流の流量が `BASE / 2` に達しなければ、そのwalkでは全整地不能として `INF` を返す。

### 評価関数

固定walkに対する評価は以下である。

```text
flow_cost =
    積み下ろし量の合計
  + walk上で土を運ぶ距離付き量の合計

total_cost = flow_cost + 100 * (walk.size() - 1)
score_eval = total_cost を小さくする
```

最小費用流のグラフは次の形で作る。

- 正のマス: `S -> cell`、容量 `h[cell]`、コスト0。
- 負のマス: `cell -> T`、容量 `-h[cell]`、コスト0。
- 各訪問時刻 `k`: `cell(walk[k]) -> visit[k]`、容量無限、コスト1。積み込みに対応する。
- 各訪問時刻 `k`: `visit[k] -> cell(walk[k])`、容量無限、コスト1。積み下ろしに対応する。
- 各walk辺 `k -> k+1`: `visit[k] -> visit[k+1]`、容量無限、コスト1。土1単位を1歩運ぶことに対応する。

### 探索・構築・更新

初期walkは2本のジグザグを連結する。

- 1本目: 行方向に `R...R, D, L...L, D, ...` のように全行を走査する。
- 2本目: 列方向に下から上、上から下を交互に走査する。1本目末尾との重複点は避ける。

山登りは次の近傍のみを使う。

```text
while time remains:
    i = random index in [0, walk.size() - 4]
    if manhattan(walk[i], walk[i+3]) != 1:
        continue
    candidate = walk with walk[i+1], walk[i+2] removed
    if best_actions(candidate).cost <= current_cost:
        walk = candidate
        current_cost = candidate_cost
```

この近傍は、曲がり角付近の小さな迂回を削るものだ。採択判定は焼きなましではなく山登りで、同点も採用する。

### 操作・クエリ・出力選択

最小費用流後、各訪問時刻 `k` について

```text
d = flow(cell -> visit[k]) - flow(visit[k] -> cell)
```

を求め、`d > 0` なら `+d`、`d < 0` なら `d` を出す。訪問時刻間はwalkに沿って `RDLU` を1文字ずつ出す。`d = 0` の時刻では積み下ろし操作を出さない。

### 時間配分・パラメータ

- 読めた山登り版は `optimize_walk(walk, 1900)` で約1.9秒使う。
- 最小費用流はAC Libraryの `mcf_graph<int,int>`。
- 容量上限は `INF = 1e9`。
- 記事ではAC Libraryだとseed 0で600から700回程度、高速MCFでも1500回程度の評価が限界と述べている。
- 9.53G版では、ジグザグ向き2通りと2回ずつの初期パターンに各375ms、最良にさらに400msを使う多点スタートが使われたと説明されている。

## 実装上重要な断片

固定walkから操作列を作る流れは次のように要約できる。

```text
solve_for_walk(walk):
    make graph with visit vertices and cell vertices
    add supply/demand edges from initial heights
    add load/unload edges between cell and each visit
    add carry edges along walk
    run min-cost max-flow
    if flow != total_positive_height:
        return INF
    for each visit:
        d = load_flow - unload_flow
        append Action(walk[k], d)
    return flow_cost + 100 * (len(walk)-1), actions
```

walk短縮は、削除後も4近傍walkが保たれる場合だけ試す。

```text
shortcut:
    a = walk[i]
    b = walk[i+3]
    if adjacent(a, b):
        erase walk[i+1], walk[i+2]
```

## この解法の本質

この問題の難しさは、訪問順、積み下ろし量、積載量が相互に絡む点にある。yosupo解は、訪問順を固定すると残りが最小費用流になることを見抜き、連続量の最適化を厳密解に押し込めている。これにより、局所探索はwalk形状だけを扱えばよくなる。

特に、同じマスを複数回訪れる場合に「マス頂点」と「訪問時刻頂点」を分ける設計が重要である。これにより、ある訪問では積み、別の訪問では降ろすといった動きも自然に表現できる。

## 真似するならまず実装する部分

最初に作るべきなのは、固定ジグザグwalkに対する最小費用流である。これだけで7.9G級になり、かつ後処理として他の訪問順にも使える。

次に、中間2点削除の山登りを追加する。近傍が単純で、walkの合法性判定も4近傍だけで済むため、実装負荷に対する効果が大きい。

上位化するなら、MCFの高速化、多点スタート、より多様なwalk短縮近傍を検討する。

## 注意点・未理解点

- 9.5G級の最終コードは未読のため、高速MCFの具体的な実装、追加遷移、多点スタートの細部は記事本文からの要約に留まる。
- AC Libraryの最小費用流を評価関数にすると、焼きなましには評価回数が不足しやすい。
- `vector<P>` をキーにしたメモは単純だが、walkが大きいため多点スタートや遷移数を増やす場合はメモのコストも考える必要がある。
- 出力時に0の積み下ろしを出さないこと、walkが必ず隣接移動になっていることを確認する必要がある。
- 最小費用流のコストは積み下ろしと積載移動量だけなので、固定移動費 `100` の足し忘れが致命的になる。
