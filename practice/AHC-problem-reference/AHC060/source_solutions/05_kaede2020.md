## 解法の全体像

この記事は、コンテスト中の失敗と復習での改善を追う内容である。最初はUターン禁止だけのランダムウォークから始め、目標長の文字列を作って近い未納品店へ運ぶ貪欲、パラメータ調整型の焼きなましを試した。その後、公式スライドをもとに、BFSで新規納品になる経路を探す方針、文字列ハッシュ化、店から店へのパス列挙、赤化タイミングの焼きなましへ進んでいる。

最終的な復習到達点は、店から長さ12以下のパスを列挙し、自己ループも候補に入れ、赤化タイミングを焼きなます構成である。上位完全再現ではなく、どの改善が効き、どの考えが弱かったかを理解するのに向いた参照元である。

## 主要アイデア

- 長い文字列も短い文字列も1納品1点なので、短い文字列を多く作る必要がある。
- 「文字列を完成させてから近い店へ行く」と、移動中にさらに木を踏んで文字列が伸び、狙いが崩れる。
- 店ごとに新規納品を作りやすい・作りにくい差があり、納品数を均等にする発想は弱い。
- BFS状態には、現在頂点、直前頂点、現在の味、各店の在庫、各木の色が関わる。
- 距離8程度まで探索して、新規納品経路が見つかったら採用する。
- `string` で文字列を持つと重いので、ハッシュや整数表現へ変える。
- 店から店までの短いパスを列挙すると、1歩ごとの探索より目的に近い単位で考えられる。
- 自己ループ、つまり同じ店に戻るパスも在庫を増やす上で重要である。

### 探索・構築・更新

- コンテスト中は、4〜10程度の長さの文字列を作ってから近い未納品店に向かっていた。
- 復習BFSでは距離8まで全探索し、見つかれば経路を復元して採用する。
- 見つからなければ、白い木にいるとき1〜2%程度で赤化し、それもしなければランダムウォークする。
- 赤化確率を10〜30%へ上げる試行はうまくいかなかった。
- 未納品を見つけたらすぐ移動するのではなく、候補を全部評価する試行はメモリ爆発した。
- 店から長さ12以下のパスを全列挙し、各店の保持上限を4000個にすることで14万点を超えた。
- DFS列挙からBFS列挙に変え、自己ループを加え、赤化タイミングを焼きなますことで15万点を超えた。

### 操作・クエリ・出力選択

- BFS/パス列挙で選んだ経路を行動1として順に出力する。
- Wの木にいるとき、確率または赤化ターン条件により `-1` を出力する。
- 店に入った時点の文字列が、その店に未納品なら得点に寄与する。
- 「完成した文字列を運ぶ」のではなく、「店に入った時点で新規になる経路」を選ぶ必要がある。

### 時間配分・パラメータ

- パス列挙上限は `ENUM_MAXLEN=11`、各店 `ENUM_LIMIT_PER_SHOP=3000`。
- 見つからない場合のlookahead BFSは `LOOKAHEAD_LIM=8`。
- コーンは長さ込みの二重hash `ConeKey{h1,h2,len}`。
- 赤化タイミングの焼きなまし対象は全頂点ではなく、赤化を許すグローバル閾値 `TH`。
- 焼きなまし制限は約1900ms、乱数seedは固定42。

## 実装上重要な断片

キャッシュ実装は、各店から店へ向かう短いパスをBFS列挙し、到着店で新規在庫になる最初のパスを使う構成である。パスは中間に店を含まない、直前頂点へ戻らない、終端が店ならそこで打ち切る。自己ループも長さ2以上なら候補に含め、短い順に最大3000本だけ保持する。

赤化は確率ではなく閾値 `TH` で制御する。通常の店間パスで新規在庫が作れず、時刻が `TH` 以降なら、白い木を1つ赤化して新規在庫を作れる計画を探索する。店からその木へ行って `-1` で赤化し、店へ戻って納品する最短計画を選ぶ。

焼きなましは各木の時刻ベクトルではなく、グローバルな `TH` だけを近傍 `±1000` で動かす。`solve_with_threshold` は毎回seed固定で決定的に実行し、スコア差を温度 `5 -> 0.1` で受理する。

```text
復習BFS:
    path = search_new_stock_path(depth_limit=8)
    if path exists:
        execute(path)
    else if current is white tree and random() < p:
        output -1
    else:
        random_walk_without_backtracking()
```

```text
パス列挙:
    for each shop s:
        enumerate paths from s with length <= 12
        keep at most 4000 paths
    during simulation:
        choose a path whose destination stock becomes new
```

## この解法の本質

この記事の価値は、強い最終解法そのものよりも、弱い方針がなぜ弱いかを具体的に示している点にある。近い未納品店へ運ぶだけでは、移動中に文字列が伸びて制御不能になる。文字列を作る場所、通るパス、納品先を一体で考え、店到着時の在庫判定を基準に経路を選ぶ必要がある。

## 真似するならまず実装する部分

学習用なら、距離8 BFSで新規納品経路を探す部分から始めるのがよい。次に文字列をハッシュ化し、店から店への長さ12以下パス列挙へ進む。赤化タイミングの焼きなましは、そのシミュレーションが十分速くなってから追加するべきである。

## 注意点・未理解点

- キャッシュ実装で、候補評価、赤化計画、焼きなまし対象、パス列挙上限は確認できた。
- `string` ではなく長さ付き二重hashを使い、店在庫は `unordered_set<ConeKey>` で持つ。
- 記事本文のパス保持上限4000に対し、提出コードは3000である。
- 各木の赤化タイミングベクトルを焼くのではなく、提出コードはグローバル閾値 `TH` のみを焼いている。
- 上位解法とはスコア差が残っており、差分シミュレーションや高速な在庫判定までは踏み込んでいない。
