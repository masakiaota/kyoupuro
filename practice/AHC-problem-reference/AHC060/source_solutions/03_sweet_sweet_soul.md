## 解法の全体像

各木に「何ターン目以降に訪問したら赤にするか」というパラメータを持たせ、その値を焼きなましで最適化する。ある赤化スケジュールに対する評価は、BFSベースのシミュレーションで行う。シミュレーションでは在庫が重複する経路を避けつつ、未納品文字列を作れる短い経路を貪欲に探す。

特徴的なのは、BFSで通常の visited 管理をしない点である。この問題ではサイクルや遠回りによって別の文字列を作れるため、頂点を一度見たら捨てる探索は弱くなる。グラフの次数が低めで、Uターン禁止により分岐も抑えられるので、visited なしでも実用的に動いたと説明されている。

## 主要アイデア

- 木 `i` ごとに赤化ターン `R_i` を持つ。
- `R_i` を焼きなましで変更し、そのたびにシミュレーションスコアを評価する。
- 経路探索はBFSベースだが、サイクル利用を残すため通常の visited を使わない。
- 在庫が重複する経路は棄却し、新規納品になる短い経路を選ぶ。
- 一定以上探索して見つからない場合は、近くの店へ移動して探索をやり直す。
- 1ノード分のパラメータ変更だけを近傍にし、前回シミュレーションとの差分が出たターン以降だけ再計算する。
- 初期赤化ターンを `[0, 10000]` ではなく `[500, 9500]` に寄せることで、序盤・終盤に単色時間を残す。
- サイクルの多い局所構造を周回しながら在庫を増やす動きが有効だったと観察している。

## 最終コードの構造

以下は記事本文とキャッシュ実装 `#72962370` から確認した構造である。

### 状態表現

- 赤化スケジュール `R_i`: 木 `i` を赤にできる最初のターン
- シミュレーション中の現在頂点 `v`
- 直前頂点 `prev`
- 現在ターン
- 現在のコーンのビット列またはハッシュ
- 各木の現在色
- 各店の在庫集合
- 差分シミュレーション用に、前回の行動列・色変化・在庫状態の履歴を保持していた可能性が高い

### 観測・制約・入力の扱い

- 生成グラフはドロネー分割由来で次数が控えめである点を利用している。
- Uターン禁止により、visited なし BFS でも分岐が抑えられる。
- 店が10個あり、全体の1割を占めるため、探索のゴールに比較的早く到達しやすい。
- 1文字でも違えば新規在庫になるため、W/Rが適度に混ざった盤面では未納品経路が見つかりやすい。

### 評価関数

- 焼きなましの評価値は、赤化スケジュールを固定してシミュレーションしたときの `sum |stock[i]|`。
- 記事では、単純な1%赤化シミュレーションで156k、確率グリッドサーチで162k、山登り版で172k、最終的に焼きなましで175kに到達したと説明されている。

### 探索・構築・更新

- BFSで未納品文字列を作れる経路を探す。
- 通常の visited を持たず、遠回りやサイクルを候補に残す。
- ただし探索が重くなりすぎないよう、一定以上で打ち切って近くの店へ移る。
- 焼きなまし近傍は、1つの木の `R_i` を変更する形。
- 差分シミュレーションでは、変更した `R_i` が実際の行動に影響し始めるターン以降だけを再計算する。
- 最終段階では高速化により、イテレーション数を400程度から少なくとも1500程度へ増やした。

### 操作・クエリ・出力選択

- シミュレーションで選んだ経路を行動1列として出力する。
- 木に到達した時点で現在ターンが `R_i` 以降なら、その訪問タイミングで行動2を挿入して赤化する。
- 店に入ったら現在の文字列を在庫に入れ、コーンを空にする。
- 最終的には、焼きなまし中で最良スコアを出した赤化スケジュールと、そのシミュレーション行動列を出力する。

### 時間配分・パラメータ

- 初期赤化時刻は木ごとに `[500,T-500]`、店は `T+1`。
- BFS打ち切りは `MAX_DEPTH=20`, `MAX_STATES=50000`。
- 近傍は訪問回数100以上の木を選び、赤化時刻を `0..T` の一様乱数へ置き換える。
- 焼きなまし温度は `10 -> 0.05`、制限約1.95秒。

## 実装上重要な断片

キャッシュ実装のシミュレーションは `simulate(convert_at, ...)` にまとまっている。コーン文字列はbase 131の `uint64_t` rolling hashで表し、店ごとに `unordered_set<uint64_t>` の在庫を持つ。BFS状態は現在頂点、直前頂点、親index、深さ、ハッシュを持ち、通常の頂点visitedは使わず、直前頂点への即Uターンだけ禁止する。

BFSは新規在庫になる店を見つけるとそのパスを採用し、見つからない場合は最初に見つけた店へ行くfallbackを持つ。木に入ったときはW/Rをハッシュへ追加し、白かつ `steps >= convert_at[node]` ならその場で赤化アクション `-1` を挿入する。

差分焼きなましでは、赤化時刻を変えた木について、旧時刻と新時刻の小さい方以降でその木を含む最初の既存パスを探し、そのパス開始から suffix だけを再シミュレーションする。受理後は頻出訪問木の集合も更新する。

```text
evaluate(R):
    reset simulation
    while turn < T:
        path = bfs_without_vertex_visited_to_new_stock()
        if path not found:
            path = move_to_near_shop_and_restart()
        execute path, inserting -1 when turn >= R[tree]
    return score
```

## この解法の本質

この解法は、経路選択よりも赤化タイミングの方が非自明だと割り切っている。経路は「未納品になる短いパスを貪欲に選ぶ」シミュレーションに任せ、探索対象を `R_i` のベクトルへ押し込める。さらに visited なし BFS により、局所的なサイクルを使って短い文字列の種類を稼ぐ動きを残している点が強い。

## 真似するならまず実装する部分

まずは赤化スケジュール `R_i` を固定したシミュレータを作るべきである。最初から差分シミュレーションを作るのではなく、visited なしまたは状態を厚くした BFS で新規納品経路を探し、`R_i` をランダム・山登りで少しずつ変える構成から始めるのがよい。

## 注意点・未理解点

- キャッシュ実装で、BFSの打ち切り条件、在庫表現、焼きなまし温度、差分シミュレーションの概要は確認できた。
- visited なし BFS はグラフ構造に依存しており、打ち切り条件が甘いと爆発する。
- 差分シミュレーションは履歴管理が壊れやすい。赤化、在庫、コーン、現在位置をどこから巻き戻すかを慎重に設計する必要がある。
- 初期 `R_i` の範囲 `[500, 9500]` は有効だったとされるが、理論的な根拠は記事中でも弱い。
