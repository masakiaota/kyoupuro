## 問題の本質

AHC043は、駅を置く場所、駅を置く順番、駅同士の接続関係、実際の線路経路、各ターンの建設順を同時に最適化する問題である。収入は毎ターン入るため、序盤の駅選択は終盤まで複利的に効く。一方で、駅は5000、線路は100と費用が大きく異なり、資金不足時の待機や線路先置きがスコアに強く影響する。

解法視点で重要なのは、線路をどこまで正確に扱うかである。線路マスを最初から厳密に持つと探索が重い。上位解法は、探索中は鉄道網を木、駅列、接続方向候補などの抽象状態で持ち、最後または評価時だけ実線路へ近づける。その代わり、次数、方向、交差、復元失敗を避ける制約を入れて、抽象状態が出力不能にならないようにしている。

## 共通している考え方

- 鉄道網は基本的に1つの連結成分として育てる
- 駅間接続は最短マンハッタン距離を基本にする
- 探索中は実線路を完全には持たず、駅列・木・接続候補で近似する
- 家か職場の片側だけカバーされた住民には将来価値がある
- 序盤の駅選択は後から直しにくく、ビーム幅や初期候補を厚くする価値が高い
- 最終スコアは資金シミュレーションで見る必要がある
- 具体経路を遅延するほど、最後の復元失敗を検知・回避する仕組みが必要になる
- 線路先置きは、駅費用と線路費用の非対称性を利用する重要な改善である

## 推奨して理解すべき順序

1. montplusa を読む。駅を頂点、線路を辺とする木として見る基本方針が分かる
2. Ang107 を読む。候補圧縮と差分更新で、初期解を作る具体的な実装が分かる
3. rhoo を読む。駅列焼きなまし、公開コード、線路先置き、禁止構造が分かる
4. shr を読む。線路を未確定にしたまま木を深く探索する上位方針が分かる
5. adapchi を読む。ビームサーチを時間内に回すための幅調整として理解する

## 実装するならどのルートか

理解のための最小実装は、Ang107寄りの「候補圧縮 + 細いビーム」がよい。各マスの距離2カバー集合を作り、候補を減らし、駅を1つずつ追加して収入を差分更新する。線路長は最初は最近接駅までのマンハッタン距離 `-1` で近似すればよい。

次にスコアを伸ばすなら、rhoo寄りに駅列を焼きなます。状態を駅列にし、評価時に貪欲接続して資金シミュレーションする。近傍は順序移動、位置移動、挿入、削除から始める。線路先置き閾値を入れると、資金待ちの無駄を減らせる。

さらに上位化するなら、shr・montplusaのように木の接続関係も状態に含める。既存辺への駅挿入、方向割当、交差判定、部分木最小番号による線路数差分、実行可能性検査を足していく。ただし、この段階から実装難度が急に上がる。

## 重要な実装要素

- 状態表現: 駅列、駅木、接続方向候補、カバー状態、資金・収入・経過ターン
- 評価関数: 最終資金シミュレーション、片側カバーの将来価値、必要線路数、駅・線路費用、線路先置き
- 近傍: 駅追加、削除、位置移動、順序移動、swap、親付け替え、既存辺への挿入、先置き閾値変更
- 差分更新: 距離2カバーの `visited` カウント、家・職場をカバーする駅集合、部分木最小設置番号、最近接接続先キャッシュ
- 候補管理: カバー集合による駅候補圧縮、片側カバー・両側未カバー住民集合、zobrist hash による重複除去
- 出力判定: 資金非負、800行、駅・線路の上書き制約、線路種類、経路連結、接続方向、交差・分岐
- パラメータ: ビーム幅、序盤ビーム倍率、焼きなまし温度、近傍確率、片側カバー係数、線路先置き閾値、時間配分

## 落とし穴

- 線路を抽象化しすぎると、最後に実線路を構築できない
- 駅次数4以下だけでは十分でなく、各辺の上下左右方向を割り当てられる必要がある
- 線分交差では、端点共有と内点接触の扱いを間違えやすい
- 候補圧縮はカバー集合だけを見るため、線路長が短い良候補を消す場合がある
- 最近接駅へ接続する評価は、既存線路上への駅挿入や経路再利用を過小評価する
- 山登り評価で毎回BFS復元まで行うと試行回数が伸びない
- 線路先置きは強いが、先に置いた線路が後で不要になると評価差分が難しい
- 資金判定は集金前に行われるため、駅・線路を置く直前の資金が負にならないかを必ず見る必要がある
- 最終的に線路を駅へ置き換えることはできるが、駅を線路に戻したり線路種を変えたりはできない
