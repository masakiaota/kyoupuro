## 解法の全体像

駅を頂点、駅間の線路を辺とした木を作る問題として扱う。ビームサーチでは線路マスを持たず、駅の座標と駅同士の接続だけを決める。木は次数4以下、各辺に上下左右の接続方向を割り当てられそう、辺を線分として見たとき交差しない、といった制約で実現可能性を保つ。

ビームサーチで得た木を初期解にし、駅位置の微調整、駅の既存区間への挿入、接続元変更などの山登りで改善する。最後に接続方向を確定し、最短路BFSと衝突時の引き直しでグリッド上の線路に復元する。出力は行動キューを作り、資金があれば先頭行動を実行し、足りなければ待機する形でシミュレーションする。

## 主要アイデア

- 鉄道網を1つの木として扱う
- ビームサーチ中は線路マスを持たず、頂点座標と辺だけを持つ
- 木の次数を4以下にし、駅の4方向接続能力を超えないようにする
- 各辺は最短路方向へ接続方向を重複なく割り当てられるものに限る
- 辺同士の交差を禁止し、最後の線路構築失敗を減らす
- ビーム深さは所要ターン、評価は「以降何もしなかった場合のスコア」に片側カバー価値を加える
- ビーム幅は2から10程度で、実態として保険付き貪欲に近い
- 山登りで、線路先置き開始の調整、駅位置移動、駅の区間挿入、接続元変更を行う
- 出力段階で、待機せず未来の線路を敷く開始ターン `t1` と、以降ずっと待機する `t2` を全探索する

## 最終コードの構造

Browserで読めた提出 #63119415 と記事本文から読み取れる実装構造である。

### 状態表現

- 提出 #63119415 では、`BeamSearchState` が探索中の木、`Action` が最終出力、`GameState` が資金シミュレーションを持つ。
- ビーム・山登り中の状態:
  - 駅頂点の座標
  - 駅間を結ぶ辺
  - 駅の構築順を表す配列
  - 現在資金、現在収入、経過ターン
  - 家・職場のカバー状況
- 線路は探索状態には含めず、最後の復元で初めてグリッド上の線路として持つ
- デバッグ用に `Vertex {座標}`、`Edge {座標}->{座標}` のような構築ログを出していた

### 観測・制約・入力の扱い

- 各人の家・職場が駅から距離2以内かどうかで収入対象を判定する
- 1つの連結成分を育てる方針で、分断した複数路線は基本的に考えない
- 木の制約:
  - 各頂点の次数は4以下
  - 各辺に駅から出る方向を重複なく割り当てられる
  - 辺を線分として見たとき交差しない
  - 事故頻度を下げるため、コーナー回避用の追加条件も入れている

### 評価関数

- ビームの深さはターン数に近い所要時間である
- 評価値は、現在の木を構築した後に何もしなかった場合の最終資金を基本にする
- 家または勤務地の片側だけカバーしている住民は、将来もう片方を押さえたときの価値として10から30%程度の収入を加味する
- 同じ深さで比較できればよいため、現在資金、現在収入、片側カバー数のバランスを見た評価になっている
- 山登りでは、実際にシミュレーションして改善した場合だけ採用する

### 探索・構築・更新

- ビームサーチ:
  - 暫定の鉄道木から新しい駅を1つ追加する
  - 新駅は既存駅から線路を伸ばすか、既存辺の途中駅として新設する
  - 幅は2から10程度と狭い
  - 2500マス候補を毎回見るため、高速化しきれず細いビームになった
- 山登り:
  - incomeが2000を超えたあたりから、駅に置き換える予定マスへ先に線路を置く事象を避ける
  - 1駅を周囲2マスのどこかへ移動する
  - 1駅を他の駅区間に挿入する
  - 別の駅から線路を引くよう接続を変える
  - 記事では、順序swapを入れて高速化すれば焼きなまし化できそうだと述べている

### 操作・クエリ・出力選択

- ビーム・山登り後に線路を復元する
- 復元順序:
  - 水平・垂直などルート選択肢がない辺を先に確定する
  - 頂点ごとの正式な接続方向を割り当てる
  - 最短経路方向に順番に線路を引く
  - ぶつかる場合は、先に引いていた辺を消して引き直す
- 復元結果を行動キューにする
- 800ターンを愚直にシミュレーションし、資金が足りていればキュー先頭を適用し、足りなければ待機する
- 改善として、ターン `t1` 以降は待機せず次以降の線路敷設を進める、ターン `t2` 以降はずっと待機する、という2つの閾値を全探索する

### 時間配分・パラメータ

- ビーム幅は2から10程度
- 山登りの試行回数は1万から10万程度と書かれている
- 片側カバーの見込み収入は10から30%程度
- incomeが2000程度を超えた後の線路先置き抑制・調整が出てくる
- `t1` と `t2` は最終シミュレーションで全探索する

## 実装上重要な断片

ビーム状態の遷移:

```text
expand(tree):
    for candidate station p:
        if p can be inserted into an existing edge:
            add vertex p on that edge
        else:
            connect p from a feasible existing station
        if degree <= 4 and directions assignable and no crossing:
            evaluate idle_score + one_side_bonus
```

最終復元:

```text
restore(tree):
    fix straight edges first
    assign directions around each station
    for each edge:
        bfs shortest route
        if collision:
            remove conflicting edge
            build current edge
            rebuild removed edge
```

行動シミュレーション:

```text
for turn in 0..799:
    if can_apply(action_queue.front()):
        apply action
    else if turn >= t1 and future_rail_exists:
        build future rail
    else:
        wait
```

## この解法の本質

この解法は、鉄道網を「木」として扱い、線路の細かい形を後回しにすることで探索を成立させている。線路マスまで持つと、駅を既存区間に差し込む操作や接続元変更が重くなる。一方、木ならビームや山登りで扱いやすい。

ただし、木だけでは出力できない可能性がある。そこで、次数、方向割当、交差禁止という実現可能性に近い制約を探索中から入れる。最後の復元は難しいが、未確定にしておく自由度が大きく、記事ではこの自由度を捨てると大敗しそうだったと述べられている。

## 真似するならまず実装する部分

まずは駅候補を1つずつ追加する木ビームを作るのがよい。線路復元は最初から完全にせず、辺を最短距離で結ぶと仮定して、次数4以下と線分交差なしだけで評価する。

次に、最終復元用のBFSと、資金シミュレーションを作る。余裕があれば、駅の位置移動と既存辺への駅挿入の山登り、最終シミュレーションの `t1`・`t2` 全探索を入れる。

## 注意点・未理解点

- 提出 #63119415 では、`improve`、`improve2`、`improve3`、`CrossCheck`、`GeneralCrossCheck`、`addField`、`ApplyAction` があり、木の改善、交差判定、行動復元を実装している。ただし、コーナー回避用の追加条件や線路復元の細部は完全には追えていない。
- 幅2から10のビームは候補を見落としやすく、山登りでどれだけ補えるかに依存する
- 深さをターン数にする設計は、線路先置きがあるため厳密には足並みがそろわないと記事内でも述べられている
- 最短経路BFSと衝突時の引き直しは、ケース依存のバグが出やすい
- AI生成コードを後から修正した部分は、仕様混在や座標系の不一致に注意が必要だと記事で述べられている
- 山登りで評価ごとに線路復元まで行うと重く、試行回数が伸びにくい
