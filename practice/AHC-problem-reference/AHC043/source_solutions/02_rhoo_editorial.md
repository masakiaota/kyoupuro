## 解法の全体像

駅の位置と設置順を焼きなましで探索し、駅同士の接続関係は評価のたびに貪欲で決める。焼きなまし中は具体的な線路マスを考えず、駅間を最短距離で結べると仮定して必要線路数を見積もり、資金と収入をシミュレーションして評価する。

初期候補として、6駅程度の短い駅列をビームサーチで列挙する。焼きなましでは、駅の順序移動、位置移動、削除、挿入、初期候補列の先頭挿入、線路先置き閾値の変更などを近傍にする。最後に接続方向を割り当て、BFSで実線路を作り、失敗時は原因となる後ろの駅を削除して再構築する。

## 主要アイデア

- 焼きなましの状態は「駅の位置列」と「線路先置きを始める収入閾値」に絞る
- 接続関係は、評価時に毎回貪欲で決める
- 既存辺へマンハッタン距離の総和を変えずに駅を挿入できるなら、線路数0で接続する
- 挿入できない場合は、接続可能な既設駅のうち近い駅へ接続する
- 出力失敗を避けるため、最短経路構築を難しくする部分構造を Level1/Level2 として禁止する
- まず400ターン時点の収入最大化で粗く焼き、その後に生スコアで焼く
- 片側だけカバー・両側未カバーの人を `O(1)` でランダム取得できる集合で管理する
- 線路先置き閾値を近傍として焼きなます
- 最終出力時は、待機の代わりに将来の線路を先に置けるかを閾値で判定する

## 最終コードの構造

提出コードを読んだうえでの要約である。

### 状態表現

- `State` は主に次を持つ
  - `ord`: 駅の座標列
  - `a`: 駅が存在するかのグリッド
  - `score`: 現在評価値
  - `close`: 各駅が近く接続しそうな既存駅。`NULL` は未確定
  - `cover`: 人の家・職場がどちらまでカバーされたかの小さい状態
  - `set`: 家または職場の片方だけカバーされている人を管理する集合
  - `not`: 両方ともカバーされていない人を管理する集合
  - `th`: 線路先置き開始の収入閾値
  - `new`, `new_close`, `seen`, `cnt`, `es`, `lines`, `heap` などの作業領域
- `IndexSet` は整数集合を配列で持ち、挿入、削除、ランダム取得を `O(1)` で行うための構造である
- 入力の住民は家職場距離の降順に並べ、収入が大きい人を選びやすくしている
- 候補駅は、家・職場の周囲マンハッタン距離2以内にあるマスを中心に作る

### 観測・制約・入力の扱い

- 各マスから見て、そのマスを駅にしたときカバーされる家・職場の番号を前計算する
- 各人について、家側と職場側をカバーできる駅候補リストを持つ
- 接続先の選択では、次数5以上、方向が片側へ偏る構造、軸平行線路に隣接して方向が詰む構造、線分交差などを避ける
- Level1の判定は高速に使い、Level2は最後の山登りで使う
- 経路構築に失敗した場合は、原因駅のうち最も後ろに設置される駅を削除して再構築する

### 評価関数

- 評価は、駅列を前から処理し、必要線路数、駅費用、線路費用、収入増分、待機ターンをシミュレーションした最終資金である
- 第1段階では `EVAL_TURN` を400ターン相当にし、評価型を収入最大化にする
- 第2段階以降は `T=800` の生スコアを評価する
- 最後の山登りでは、Level2相当の構築困難構造も考慮した評価を使う
- 初期6駅ビームの評価は、総収入が一定値を超えるまでに必要なターン数を小さくする式である
- 線路先置きでは、収入が `th` 以上で将来線路が残っていれば、待機中に線路を置いたものとして資金を更新する

### 探索・構築・更新

- `solve` は大きく4段階で進む
  - 400ターン時点の収入最大化を短時間焼く
  - 生スコアで焼く
  - Level1制約下で山登りする
  - Level1/Level2制約下で山登りする
- `anneal` は温度を指数的に下げ、`trans` が返す差分を Metropolis 条件で受理する
- `trans` の主な近傍:
  - 状態が空なら初期ビーム候補から駅列を入れる
  - 線路先置き閾値を `±30` 程度動かす
  - 初期候補列の先頭部分列を現在解の先頭に挿入する
  - 両側未カバーの人を選び、家側・職場側をカバーする2駅を挿入する
  - 片側カバーの人を選び、もう片方をカバーできる駅を挿入する
  - 駅を削除する
  - 駅の順序を `±10` 程度ずらす
  - 駅位置を近傍マスへ置き換える
- 接続貪欲では、既存辺への挿入を優先し、不可能なら候補駅の中から交差や方向制約を満たす近い駅を選ぶ
- 近い接続先候補は `close` にキャッシュし、失敗したときだけ線形探索する

### 操作・クエリ・出力選択

- `restore` が駅列と接続情報から具体的な線路を作る
- 接続されている駅が多い駅から上下左右の接続方向を決める
- `min(|dr|, |dc|)` が小さい辺からBFSで具体経路を決める
- 経路が決まったら、`th` を使って800ターンの行動列をシミュレーションする
- 資金が駅費用に足りないとき、収入が閾値以上なら待機の代わりに未来の線路を置く
- 最終的に800行になるまで待機を追加する

### 時間配分・パラメータ

- 初期ビームは約0.2秒、幅200、駅数6
- 焼きなましは約2.75秒
- 400ターン時点の収入最大化が約0.15秒
- 生スコア焼きが約2.5秒
- Level1山登りとLevel2山登りがそれぞれ約0.05秒
- 近傍確率は記事中に明記されており、順序移動と位置移動がそれぞれ0.33、削除と片側カバー挿入がそれぞれ0.15、swapが0.04、閾値変更と初期候補部分列挿入がそれぞれ0.02、2駅挿入が0.005
- 実行時間が2倍で+0.7%、10倍で+2.0%程度伸びるとされている

## 実装上重要な断片

評価時の接続決定:

```text
for station p in ord[1:]:
    if p can be inserted into existing edge without increasing manhattan sum:
        split that edge and rails = 0
    else:
        q = nearest previous station satisfying degree/direction/crossing constraints
        connect p to q
        rails = dist(p, q) - 1
    simulate money, wait, rail cost, station cost, new income
```

焼きなましの受理:

```text
while time remains:
    heat = T0 * pow(T1 / T0, progress^1.2)
    add = heat * log(rand)
    if trans(state, add):
        keep changed state
```

線路先置きシミュレーション:

```text
while money < station_cost:
    if income >= threshold and future_rail_exists:
        build future rail
        money += income - 100
    else:
        wait
        money += income
```

`IndexSet` の役割:

```text
remove(x): swap x with last active element, len--
insert(x): if inactive, put x at active tail, len++
random_choice(): return active_array[rand(len)]
```

## この解法の本質

この解法の本質は、最適化対象を「駅の順序付きリスト」にまで圧縮し、接続と線路は評価時・出力時に貪欲で補う点である。駅列だけなら、順序変更、位置変更、挿入、削除といった近傍を素直に回せる。具体経路を状態に含めないことで、焼きなましの遷移が軽くなる。

ただし、具体経路を無視しすぎると最後に出力できない。そこで、評価時の接続貪欲に禁止構造を入れ、最後の山登りではより厳しい Level2 判定を使う。線路先置きは、この問題の「駅は高く、線路は安いが1ターンを消費する」という非対称性を突いた重要な改善である。

## 真似するならまず実装する部分

まずは駅列を状態にし、評価のたびに「既存駅のうち最も近い駅へ接続する」と仮定して資金シミュレーションする焼きなましを作るとよい。近傍は、駅挿入、削除、位置移動、順序移動だけで始められる。

次に、既存辺への駅挿入、片側カバー人の集合管理、初期6駅ビーム、線路先置き閾値を入れる。出力を安定させる段階で、交差判定、方向割当、失敗時の駅削除再構築を足すのが現実的である。

## 注意点・未理解点

- 提出コードは読めたが、ビットで表された方向・部分構造判定の全パターンは完全には追えていない
- 評価中は線路経路を実際には持たないため、禁止構造が甘いと最後に経路構築で失敗する
- 線路先置きは強いが、過去の最適行動が変わるため厳密差分評価とは相性が悪い
- `close` のキャッシュは高速だが、接続不可になった場合の再探索条件を間違えると不正な評価になる
- 近傍確率と時間配分がかなり細かく調整されており、単純実装では同じ性能にならない
- 記事の改善率 `{+x%}` は提出から要素を外した比較であり、単体加算できる値ではない
