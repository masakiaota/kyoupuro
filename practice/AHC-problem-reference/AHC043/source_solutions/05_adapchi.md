## 解法の全体像

解法自体は解説放送とほぼ同じ、経過ターン数をキーにしたビームサーチである。この記事の主眼は、ビームサーチをchokudaiサーチへ置き換えなくても、ビーム幅を実行中に動的変更すれば時間を使い切れる、という実装方法にある。

各ターンで近傍計算1回にかかる時間を測り、残り時間を残りターンへ均等配分する。そのターンに使える時間を近傍計算時間で割ることで、そのターンのビーム幅を決める。追記では、推定時間を使わず、各ターンに割り当てた時間を使い切るまで近傍生成ループを回す方が楽だと述べている。

## 主要アイデア

- ビームサーチの深さを経過ターン数に対応させる
- 近傍計算関数の実行時間が引数にあまり依存しない前提で、1近傍あたりの時間を推定する
- 残り時間を残りターンへ等分し、各ターンのビーム幅を決める
- 式は `w_k = floor(t_LEFT,k / (T_LEFT,k * t_NEIGHBOR_hat))`
- 最初の数ターンは実測値が少ないため、ビーム幅を適当に設定する
- 追記版では、各ターンに割り当てられた時間を使い切るまでループすれば、近傍時間推定そのものを省ける

## 実装上重要な断片

実測平均で幅を決める版:

```text
for k in 1..T:
    left_time = time_limit - now()
    left_turn = T - (k - 1)
    unit = average_neighbor_time
    width = floor(left_time / (left_turn * unit))
    width = max(width, minimum_width)
    run_beam_layer(k, width)
    update average_neighbor_time
```

追記の時間枠版:

```text
for k in 1..T:
    left_time = time_limit - now()
    left_turn = T - (k - 1)
    deadline = now() + left_time / left_turn
    while now() < deadline:
        generate_and_evaluate_one_neighbor()
    select_next_layer()
```

## この解法の本質

この記事の本質は、探索内容そのものではなく、固定幅ビームの時間見積もり問題を実測制御に置き換えることにある。AHCではケースごとに候補数や評価コストが変わるため、固定幅では時間を余らせたりTLEしたりしやすい。残り時間を残りターンへ配るだけでも、実行時間の安定性が上がる。

chokudaiサーチは時間制御しやすいが、既にターン層のビームを書いている場合は構造を変えるコストがある。動的ビーム幅は、既存のビームサーチを保ったまま時間を使い切る実装上の工夫である。

## 真似するならまず実装する部分

まずは追記版の「各ターンに割り当てた時間を使い切るまでループ」を実装するのがよい。近傍計算時間の推定や平均更新が不要で、バグが少ない。

固定回数のビームが既にあるなら、各層で `deadline` を作り、近傍生成・候補評価を `while now() < deadline` に置き換える。候補が少ない層では早く終わる可能性があるため、最低幅や最大幅、空候補時の扱いは別途決める。

## 注意点・未理解点

- 記事は幅調整が主題で、AHC043固有の状態、評価、候補生成は説明されていない
- 近傍計算時間が引数や状態に大きく依存する実装では、実測平均による幅推定が外れる
- 各ターンの割当時間を使い切る方式でも、候補生成の最後の1回が重い場合は締切を超える
- 序盤は1近傍あたり時間の推定が不安定で、幅を別に決める必要がある
- ターンごとの候補数が少ない場合、時間枠を使い切る前に探索する候補が尽きることがある
