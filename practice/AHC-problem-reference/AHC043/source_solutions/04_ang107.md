## 解法の全体像

駅の設置座標列を解として扱う。まず、駅候補を「カバーできる家・職場集合」で圧縮し、候補数を大きく減らす。その候補上で差分更新ビームサーチを行い、駅列の初期解を作る。ビームの評価はおおむね「1ターン当たりの収益 / 経過ターン」であり、候補を追加するたびにカバー状況、収益、経過ターン、生スコア用の利得を差分更新する。

ビームで終了済みノードを複数復元し、山登り用のより重い評価関数で再評価して初期解を選ぶ。残り時間では、駅の設置タイミング変更と駅位置の近傍移動を山登りで試す。評価時には毎回線路ルートと出力用解を構築するため試行回数は多くない。線路ルートは、将来設置予定の駅をなるべく通るように重み付き最短路を選ぶ。

## 主要アイデア

- `data[i][j]` に、その座標に家または職場がある人の相方座標リストを持つ
- 駅候補を、マンハッタン距離2以内に含まれる家・職場集合が他候補の部分集合にならない座標へ圧縮する
- 圧縮により seed 0 では候補数が約150まで減ったと書かれている
- 差分更新ビームサーチライブラリを使い、状態コピーを避ける
- ビーム状態では、各座標が駅の距離2以内に何個入っているかを `visited` で管理する
- `visited` の `0->1`、`1->0` を使って収入を差分更新する
- 初期2駅は同時に置けるよう、Action に候補インデックスを2つ持たせる
- ビーム幅は `20000000 / M / 圧縮候補数` を基準にし、最初の10駅までは10倍にする
- 山登りでは、1駅の設置タイミング変更と、1駅のマンハッタン距離2以内への移動を試す
- 線路復元では、将来の駅に重みを付け、最短路のうち重み合計が大きい経路を選ぶ

## 最終コードの構造

Browserで読めた提出 #63119477、記事本文、リンク先ライブラリから読み取れる構造である。

### 状態表現

- `beam_search` 名前空間に `Action`、`Evaluator`、`Candidate`、`Selector`、`State`、`Tree` がある。`State::move_forward` / `move_backward` で差分更新する。
- 入力前処理:
  - `data[i][j]`: 座標 `(i,j)` に家または職場を持つ人について、反対側の座標を列挙する
  - 各駅候補が距離2以内に含む家・職場集合
  - 圧縮後の駅候補配列
- ビームの `State`:
  - `visited[i][j]`: 座標 `(i,j)` の周囲距離2以内にある設置済み駅の数
  - `gains[i]`: `i` 番目に置いた駅による最終ターンまでの実質収益。駅・線路費用を引いた値
  - zobrist hash 用の値
- `Action`:
  - `index_1`: 追加する駅候補インデックス
  - `index_2`: 初手で2駅同時に置くための2つ目の候補インデックス
- `Evaluator`:
  - `income`: 1ターン当たりの収益
  - `turn`: 現在ターン
  - `money`: 現在資金
  - `gain`: 追加駅による最終ターンまでの実質収益

### 観測・制約・入力の扱い

- 駅候補圧縮では、距離2以内に含まれる家・職場集合が他候補の部分集合なら捨てる
- 圧縮は平均1%程度の改善だったとされるが、初期資金が少なく線路長が効くケースでは良い座標を消す可能性がある
- 線路長の暫定計算では、既存駅との最小マンハッタン距離 `-1` を使う
- 既存線路上に駅を置いて線路設置を省けるケースはビームの暫定ターン計算では無視する
- 終了ノードは、暫定経過ターンが800を超えるか、全ての家・職場を網羅した場合とする

### 評価関数

- ビーム通常ノードの評価は `income / turn` に相当する「1ターン当たり収益 / 経過ターン」と説明されている
- 終了済みノードの評価は生スコアにする
- `gains` を持つことで、駅設置を最適なタイミングで止めたときの生スコアを計算できる
- 山登りの評価は、毎回線路ルート構築と出力用解生成まで行ったうえでのスコアである

### 探索・構築・更新

- 初期解生成:
  - 差分更新ビームサーチで駅座標列を生成する
  - 遷移は、圧縮候補から新しい駅を追加すること
  - 重複除去は、訪問済み座標集合の zobrist hash で行う
  - 終了ノードは評価値で重複除去したうえで全て復元する
  - 復元した全解を山登り評価関数で再評価し、最良を初期解にする
- 差分更新ビームライブラリ:
  - 探索木を明示的に作り、Euler Tour順に1つの状態を進め戻しする
  - `move_forward` と `move_backward` で状態差分だけを更新する
  - `Selector` がハッシュ重複候補を除去し、上位候補を選ぶ
  - `ObjectPool`、独自 `HashMap`、セグ木などで高速化する
- 山登り:
  - 駅の設置タイミングを変更する
  - 駅位置を距離2以内のランダム位置へ移動する
  - 近傍確率は等確率

### 操作・クエリ・出力選択

- 山登り評価では毎回線路ルートを構築し、出力用行動列も生成する
- 線路経路はBFSで最短路を探す
- 将来設置予定の駅座標に重みを付け、早く設置予定の駅ほど大きい重みにする
- 最短路の中で、通過マスの重み合計が最大のものを採用する
- これにより、後で駅を置く予定のマスをなるべく線路上にし、駅への置換で線路コストを節約する

### 時間配分・パラメータ

- 初期解生成ビームに約1秒
- 残り約2秒を山登りに使う
- 山登りは評価が重く、約1万回程度
- 実行時間を10倍にすると約2%改善すると述べられている
- ビーム幅は `20000000 / M / 圧縮候補数`
- 最初の10駅まではビーム幅を10倍
- 圧縮候補は seed 0 で約150まで減少

## 実装上重要な断片

候補圧縮:

```text
for each cell p:
    cover[p] = set of homes/offices within distance <= 2
keep p if cover[p] is not a subset of another candidate cover
```

`visited` による差分収入更新:

```text
add_station(p):
    for q in cells within distance <= 2 of p:
        visited[q] += 1
        if visited[q] changed 0 -> 1:
            update covered homes/offices and income

undo_station(p):
    for q in cells within distance <= 2 of p:
        visited[q] -= 1
        if visited[q] changed 1 -> 0:
            rollback covered homes/offices and income
```

将来駅を通りやすいBFS:

```text
route(u, v):
    run BFS restricted to shortest distance
    among shortest paths, maximize sum(weight[cell])
    weight[cell] is larger if cell will become a station earlier
```

BFS高速化リンクの要点:

```text
seen_id += 1
mark[p] = seen_id
visited in current BFS iff mark[p] == seen_id
```

## この解法の本質

この解法の本質は、駅候補の圧縮と差分更新で、ビームサーチの分岐数と状態更新コストを同時に落とす点である。AHC043では駅を置けるマスは2500個あるが、カバーできる家・職場集合が同じか劣る候補を削ると、序盤探索の幅を大きくできる。

また、ビーム中の線路長見積もりは粗くし、最後の山登り評価で線路復元まで見るという二段構えになっている。将来駅を通るように線路を引くBFSは、線路を駅に置き換えられるルールを利用した実装寄りの工夫である。

## 真似するならまず実装する部分

まずは各マスの距離2カバー集合を作り、候補圧縮を実装するのがよい。次に、`visited` のカウント差分で収入を更新する単純ビームを作る。

差分更新ビームライブラリまで再現するのが重ければ、最初は状態コピー型ビームでよい。スコアを伸ばす段階で、zobrist hash による重複除去、最初の10駅だけ幅を増やす設定、将来駅重み付きBFSを入れる。

## 注意点・未理解点

- 候補圧縮は平均では効くが、線路長が短い候補を消すリスクがある
- ビームの暫定ターン計算では既存線路上への駅設置を無視しており、評価誤差がある
- 山登り評価で毎回ルート構築すると試行回数が少なくなる
- 差分更新ビームライブラリを使うには、`move_forward` と `move_backward` の整合性が必要で、実装ミスが重い
- 提出 #63119477 では、`Action(idx1, idx2, g)`、`Evaluator(score_a_day, now_turn, now_K)`、`Selector` のhash重複除去、`Tree::dfs` / `update` / `calculate_path` を確認した。`gains` の意図は記事どおりだが、山登り評価とルート復元の全式は完全には追っていない。
- 将来駅重み付きBFSは、最短路制約と衝突回避をどう両立したかの細部が記事だけでは分からない
