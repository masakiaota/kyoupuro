## 解法の全体像

小さい番号のボールから順に「置けた」とみなせる状態を伸ばしていくビームサーチである。基本の遷移は、現在まだ条件を満たせていない最小番号 `cur` のボールを、その上にある `cur` より大きいボールと交換して1段上げる操作である。

状態評価では、大きい数字が下の段にあるほど良く、さらに確定済みの小さい番号が多いほど強く良い、という形にしている。通常のビームサーチだと幅を大きくしたとき状態コピーが支配的になるため、探索木の Euler tour を持ち、1つの状態を apply/undo しながら候補を生成する。

## 主要アイデア

- 状態は盤面 `perm` と数字から位置への逆引き `iperm`、現在確定できた最小未処理番号 `cur` で持つ。
- 遷移は `cur` の位置から上方向の親2候補を見る。親の数字が `cur` より大きい場合だけ、その親と交換する。
- 評価値は `sum sqrt(value) * row(position) + 1000 * placed_count` に相当する。コード上は `placed_count` の増加を `value += 1000` で加える。
- ビームの優先度は評価値が大きい状態ほど良くなるように、ヒストグラムでは `1_000_000 - value / 8` に変換して小さい値を残す。
- Euler tour beam search により、候補状態配列を丸ごとコピーせず、探索木の辺列を辿って状態を再現する。
- 解が見つかったら履歴から操作列を復元し、最後に1手ずつ削除を試す後処理で冗長操作を取り除く。

## 最終コードの構造

### 状態表現

- `perm[465]`: 1次元化した位置にあるボール番号。
- `iperm[465]`: ボール番号から現在位置への逆引き。
- `Gup[pos][0..1]`, `nup[pos]`: 各位置の上方向の隣接候補。
- `Gdown` も初期化されているが、探索の主遷移は上方向である。
- `decode[pos]`: 出力用に1次元位置を `(x, y)` に戻す。
- `beam_state` は `cur`, `value`, undo 用の `hist`, `histvalue` を持つ。
- Euler tour 側は `is_down`, `is_leaf`, `data` を持つ辺列で、`data` は移動候補または葉の評価値を表す。

### 観測・制約・入力の扱い

- 入力を三角形の行順のまま 0..464 の1次元配列に格納する。
- 上下関係だけを `Gup` と `Gdown` に前計算する。
- 最終判定 `solved()` は各位置と親を見て、下のボールが親より小さいなら違反とする。
- 操作列は位置ペアで持ち、出力時に `decode` で座標へ変換する。
- 10000手制限は履歴配列サイズにも反映されている。探索中に解が見つかることを前提にしている。

### 評価関数

- 初期値は全ボールについて `sqrt(ball) * row(position)` の総和。
- 交換時は2位置の寄与だけを引いて足す差分更新を行う。
- `cur` が条件を満たして確定できるたびに `value += 1000` とし、確定済みボール数を大きく評価する。
- ビーム選別用には `v = 1_000_000 - value / 8` をヒストグラム添字にしており、評価値が大きいほど小さい `v` になる。

### 探索・構築・更新

- 初期状態を根とする探索木の葉が現ビーム候補である。
- 葉に到達したら、閾値 `cutoff` と同点保持確率 `cutoff_keep_probability` で残すかを判定する。
- 残す葉から、`cur` の上にあり `cur` より大きい親候補だけを次候補として展開する。
- `do_move` で交換し、`cur` が進められる限り連続して進める。
- `undo_move` は保存しておいた `cur` と `value` を戻し、盤面は逆交換で戻す。
- 各反復後、ヒストグラムから次のビーム幅に対応する `cutoff` と同点保持確率を求める。
- 実装では幅 2000 の探索を3回独立に走らせ、乱択同点処理の揺れを使って良い解を拾う。

### 操作・クエリ・出力選択

- 解が見つかった葉の `stack_moves` を辿り、各 `data` を `{位置, その上の親位置}` に戻して操作列にする。
- `save_solution` では操作列から1手削除しても解けるかを全探索的に試し、短くなる限り繰り返す。
- 複数回のビームサーチで最も短い操作列を `best_solution` として保持し、最後に出力する。

### 時間配分・パラメータ

- 制限時間 2 秒に対し、探索は `TM.elapsed() > 1.975` で打ち切る。
- 1.8 秒を超えたら局所的な幅を `width / 10` に落として完走しやすくする。
- 記事では幅 6000 も可能だが、実装では幅 2000 を3回走らせるほうが少し良かったとしている。
- `placed_count` の重みは 1000、評価のヒストグラム変換は `/8`。

```text
traverse_euler_tour:
    down edge: apply move and push history
    kept leaf: commit uncommitted path, generate children
    up edge: undo latest move, and write an up edge if its path was committed
```

## この解法の本質

「小さい番号から上へ持ち上げる」という単純貪欲の分岐を、そのまま幅広いビームサーチに拡張している点が本質である。さらに、ビーム幅を伸ばすうえで状態コピーがボトルネックになることを見越し、探索木の共有部分を Euler tour で表すことで、盤面を1個だけ更新・巻き戻ししている。評価関数そのものは素直だが、大きい番号を下に残す効果と、確定済みの進捗を強く優先する効果が両立している。

## 真似するならまず実装する部分

まずは1次元化した盤面、逆引き、上方向隣接、`cur` の進捗判定を作る。その上で、状態コピー型の小さい幅のビームサーチを実装すると理解しやすい。Euler tour 化は高速化の核だが、最初から実装するとバグの切り分けが難しいため、通常ビームで評価関数と遷移を確認してから移すのがよい。

## 注意点・未理解点

- Euler tour 実装は強力だが、`do_move` と `undo_move` の完全な対称性が崩れると探索全体が壊れる。
- `cur` を一気に進める処理は、この問題の「小さい番号から確定させる」性質に依存する。
- 後処理の1手削除は毎回盤面を再構築するので単純だが、操作列が長いと重い。ここではサイズが十分小さいため通っている。
- GitLab の compressed variant までは精読していない。AHC021提出で使われているのは非圧縮の Euler tour に近い実装であり、理解には十分と判断した。
