## 解法の全体像

小さい番号から順に上へ持っていく方針を軸に、盤面評価関数を使ったビームサーチへ発展させている。最終解法では、動かさなければならない最小番号のボールについて4方向の移動を候補にし、ビーム幅55で状態を残す。状態の優先順位は、次に動かす必要がある最小番号が大きいこと、次に盤面評価関数が高いことで決める。

記事はコードではなく、コンテスト中と後の段階的な改善の説明である。13,139,945点の評価関数貪欲、13,257,135点の乱択追加、13,426,585点の単純貪欲、13,561,410点のビームサーチが紹介されている。

## 主要アイデア

- 大きい番号から下へ持っていくより、小さい番号から上へ持っていくほうが行き先が明確である。
- 0番は必ず頂点に近い位置へ置く必要があり、小さい番号ほど制約が強い。
- 経路選択では、上方向を優先し、大きい番号を下側へ落とすことを重視する。
- 盤面評価は「下に大きい番号」「内外の位置関係」を重みで表す。
- 最終的には、評価関数付きビームサーチで複数の移動候補を並行して追う。
- ビーム選別は、進捗を第一優先、評価関数を第二優先とする。

## 最終コードの構造

Browserで読めた提出 `43231619` と記事本文を分けて読む。本文の最終ビーム説明に対し、読めた提出は評価関数付きの短いRust実装である。

### 状態表現

- 盤面配列と、ボール番号から座標への逆引きが必要になる。
- ビーム状態には、現在盤面、操作列、次に動かす必要がある最小番号、盤面評価値を持つと考えられる。
- 4方向移動を候補にするため、上下だけでなく横移動も扱う必要がある。

### 観測・制約・入力の扱い

- 入力は通常の三角形盤面として持つ。
- 「動かさなければならない一番小さい数」を各状態で判定する。
- 解が完成した状態、つまり全違反が消えた状態が出たら、そのうち最初に終わったものを出力する。

### 評価関数

- 記事では、下の段ほど大きい重みを与え、ボール番号との積の総和が大きいほど良い、という評価を挙げている。
- さらに外側・内側の位置に関する重みも導入し、上方向移動に関する重みをより大きくするとしている。
- 最終ビームでは、状態選別の第1キーが「次に動かさなければならない一番小さい数」、第2キーが評価関数である。

### 探索・構築・更新

- 1ステップで、現在動かすべき最小番号のボールを左、左上、右上、右の4方向へ動かす。
- 生成後の状態数がビーム幅以下ならすべて残す。
- 状態数がビーム幅を超えたら、優先順位で上位55状態を残す。
- 終了状態が初めて出た時点で、その操作列を出力する。

### 操作・クエリ・出力選択

- 操作は隣接 swap で、対象ボールを4方向に1手動かすものとして生成する。
- 最終出力は最初に完成したビーム状態の操作列。
- 記事からは、同じ手数の複数解をさらに後処理するかは読み取れない。

### 時間配分・パラメータ

- ビーム幅は55。
- 乱択版では、たまに経路選択を乱択にして制限時間いっぱい回し、最小手数を出力したとある。
- 最終ビームの具体的な時間管理、重み係数、同点処理は記事からは不明である。

## 実装上重要な断片

```text
beam = {initial_state}
while beam has no solved state:
    next = []
    for state in beam:
        target = smallest_ball_that_must_move(state)
        for dir in [left, up_left, up_right, right]:
            if dir is valid:
                next.push(apply_move(state, target, dir))
    beam = top 55 by (target_progress, board_evaluation)
output first solved state
```

## この解法の本質

この解法の本質は、単純な上方向貪欲だけでは拾えない横移動や一時的な悪化を、狭いビームで許容している点である。評価関数は完全な最終手数を直接予測するものではないが、「小さい番号の確定が進んでいるか」と「大きい番号が望ましい場所へ寄っているか」を併用することで、探索が無関係な方向へ広がるのを抑えている。

## 真似するならまず実装する部分

まずは「小さい番号から上へ」「親2候補では大きい番号と交換」の貪欲を作り、その後で盤面評価関数を差分計算できるようにする。次に、幅10程度の小さなビームで4方向候補を試すと、記事の最終方針に近づける。重み係数は記事だけでは再現しにくいため、最初は段重みだけで十分である。

## 注意点・未理解点

- 提出コードで `mapped_value` の差分更新構造は確認できたが、記事中で述べるビーム幅55版そのものとの対応は不明である。
- 記事中の外側重みに関する記述は、実装上どの向きの重みを最大化しているかをコードで確認できない。ここは本文の要約に留める。

- 「最初に終わったものを出力」とあるため、同手数内でより短い後処理をしているかは不明である。
