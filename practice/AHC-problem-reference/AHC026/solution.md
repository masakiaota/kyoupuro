## 問題の本質

この問題は、番号順の出庫制約のもとで、箱を何回・何個まとめて動かすかを最小化する並べ替え問題である。移動コストは「箱数 + 1」なので、単に箱数を減らすだけでなく、細かい移動を減らして手数料を節約する必要がある。

解法視点では、次のどちらかを選ぶ問題になる。

- 直接出庫型: 次に必要な箱を掘り出しつつ、近い将来使う箱を良い場所へ置く。
- 列ソート型: いったん各列を出庫しやすい単調状態へ整え、完成後の出庫コストを0にする。

高得点では、どちらの型でも「将来まとめて安く動かせる隣接関係を作る」「小さい箱を塞がない」「取れる箱は余計に動かさない」が重要になる。

## 共通している考え方

- 山の最小値が大きい山は、当面使わない退避先として価値が高い。
- 近い将来取り出す小さい箱を深く埋め直すと損をする。
- 操作1には手数料があるため、1個ずつ動かすより、意味のある塊で動かす方がよい。
- ソート済み、またはそれに近い単調な隣接関係は、将来の移動回数を減らす。
- 出庫可能な箱は、ソートや退避の都合で再移動せず、その場で取るべきである。
- 貪欲単体でも強いが、候補順や閾値を複数試して最良を採用すると伸びる。

## 解法の分類

- 直接貪欲型: AtCoder Editorial、Hatena。
- 列ソート貪欲型: Zenn、note。
- 列ソート + 探索型: Docswell。
- 候補生成改善型: Docswellの割当問題k-best列挙、Hatenaの分割シミュレーション。
- 複数試行・乱択型: AtCoder Editorialの閾値・乱択、noteのソート順ランダム試行。

## 推奨して理解すべき順序

1. AtCoder Editorialの `solve0` を読む。山最小値最大へ逃がす基本貪欲が最短で理解できる。
2. AtCoder Editorialの `solve1..3` を読む。近い番号の箱を別扱いする効果が分かる。
3. Zenn throughの本文と提出コードを読む。各列ソート方針の実装単位が分かる。
4. note phsplsを読む。列ソート方針をどう改善していくかが段階的に分かる。
5. Hatena inaniwaを読む。直接出庫型で高得点化する局所評価の見方が分かる。
6. Docswell hitonanodeを読む。上位化に必要な候補生成と探索の設計が分かる。

## 実装するならどのルートか

理解のための最小実装なら、AtCoder Editorialの `solve0 -> solve1` ルートがよい。連結リスト風に上下関係を持つだけで操作列を作れ、公開コードも短い。

列ソート方針を学ぶなら、Zenn throughの単調列退避をベースにするのがよい。全列がソート済みになれば勝ち、というゴールが明確で、後からnote phsplsの改善を足しやすい。

上位化を目指すなら、次の順が現実的である。

1. 列ソート貪欲を安定実装する。
2. 出庫可能な箱を移動対象から外す。
3. 戻さなくてよい箱を戻さない。
4. 他列トップの巻き込み、退避先優先度、ソート順の複数試行を入れる。
5. 盤面隣接評価を作る。
6. 1列掃き出しを割当問題化し、最良解からk-best列挙へ進む。

## 重要な実装要素

- 状態表現: 山配列だけでなく、箱番号から現在位置を引ける表を持つ。直接貪欲なら `up/down/base` の連結リスト表現が軽い。
- 評価関数: 直接型は移動コストそのもの、列ソート型は単調隣接・ソート済み区間・小さい箱の露出を評価する。
- 近傍: 閾値 `t` の変更、ソート列順の変更、掃き出し分割位置、割当問題のk-best候補。
- 差分更新: 移動操作で、箱の上下関係、山トップ、山最小値、箱位置を同時に更新する。
- 候補管理: 直接貪欲では複数試行の最良操作列、探索型では盤面評価付きの優先キューやchokudaiサーチを使う。
- 出力判定: 操作2は「残っている最小番号」かつ「山の頂上」だけが合法である。ソート中の即時出庫はここを厳密に見る。
- パラメータ: 近傍幅8、閾値9から30、分割回数ペナルティ、k-best列挙数、列挙打ち切り閾値などが候補になる。

## 落とし穴

- 山の向きの取り違え。入力は下から順だが、処理では末尾を頂上にする実装が多い。
- 操作1で指定する箱は、移動する塊の一番下の箱である。箱の上を動かす関数と箱自身を動かす関数を混同しやすい。
- 出庫可能に見える箱でも、まだそれより小さい箱が残っていれば操作2は不正である。
- ソート済み列の上に箱を置いてよい条件を誤ると、以後放置できる前提が崩れる。
- 分割移動は見た目の順序を改善しても、手数料で損することがある。
- 山最小値をキャッシュする場合、移動後の更新漏れで退避先選択が壊れる。
- 即時出庫を入れると、予定していた掃き出し列や割当候補が変わるため、再評価が必要になる。
- 5000操作制限は通常の上位方針では余裕があるが、細かすぎる分割やデバッグ出力混入では危険になる。

## 未解決・要検証事項

- Docswell解法のAHC026本体コードは公開されておらず、評価関数の厳密な数値や実行可能性判定の詳細は未確認である。
- Hatena解法は記事の順位・得点と一致する NKT 提出 #47305648 を読めたが、著者名とAtCoderユーザの対応は順位表との一致による推定である。
- note解法は記事スコアと一致する phspls 提出 #49052188 を読めた。記事内から直接辿れる提出リンクはない。
- 列ソート方針で「どの列を先にソートするか」はスコアに大きく効くが、安定して強い評価式は参照元ごとに異なる。
- 割当問題k-best列挙は強力だが、割当解を合法操作列へ変換する部分の実装設計は別途検証が必要である。
