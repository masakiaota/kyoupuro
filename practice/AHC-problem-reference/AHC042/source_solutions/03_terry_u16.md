## 解法の全体像

「1手ずつ動かす」のではなく、「ある行・列に鬼を集めて一気に外へ運び出す」一連の操作を1つのビーム遷移として扱う。各候補遷移はDPで作る。たとえば、ある列から上へ出すなら、上から順に行を見て、その行の鬼を左右移動で対象列へ持ってきてから上へ流すか、持ってこないかをDPで選ぶ。

ビームサーチの評価は鬼の残数を主に使う。遷移候補は大量に出るため、手数あたりに排出できる鬼の数、すなわちコスパのよい候補だけを残す。盤面コピー型のビームサーチで、Zobrist Hashにより重複盤面を除く。

## 主要アイデア

- 1操作ではなく、「鬼を集めてまとめて出す操作列」をビームの1遷移にする。
- ある列から上下へ、またはある行から左右へ出す遷移を考える。
- 対象レーンの途中にいる鬼だけでなく、直交方向に動かして持ってこられる鬼もまとめて落とす。
- 各遷移の最小手数はDPで求める。
- 福を落とす操作、福を外へ押す可能性がある集め方は不可とする。
- 遷移候補は `手数 / 落とす鬼数` の小さい5個程度に絞る。
- ビーム幅は約200。評価が同じ状態が増えるため、シャッフルで多様性を確保する。
- 重複盤面はZobrist Hashで管理する。

## 最終コードの構造

Browserで読めた提出 #62339553 と記事本文から書く。

### 状態表現

- 盤面全体を文字配列または固定長配列として持つ。
- 各状態は以下を含むと考えられる。
  - 現在盤面
  - ここまでの操作列
  - 現在手数
  - 残り鬼数
  - 盤面ハッシュ
- 差分更新ビームではなく盤面コピー型のビームと記事にあるため、遷移ごとに盤面をコピーして操作列を適用している可能性が高い。

### 観測・制約・入力の扱い

- 入力盤面をそのまま状態にする。
- 遷移生成時に、外周に出る福がないことを確認する。
- 「行を左右に動かして鬼を列へ集める」などの補助操作でも、福が外へ出るならその選択肢は `INF` とする。
- 不可能な集め方はDPの候補から除外する。

### 評価関数

記事では、ビームの評価関数は鬼の数だけで決めていると説明されている。そのため、基本評価は次の形だと読める。

```text
beam_eval(state) = remaining_oni_count
```

ただし、残り鬼数だけだと同評価状態が多くなるため、候補の順序をシャッフルして多様性を補っている。

遷移候補を絞る評価は別で、次を使う。

```text
transition_cost_per_oni = required_turns / removed_oni_count
```

この値が小さい候補を5個だけ残す。

### 探索・構築・更新

各列から上へ出す例では、次のDPを使う。

```text
dp[i][j] = 上から i-1 行目までを使って、
           鬼を j 匹運び出すときの最小手数
```

行 `i` の鬼を対象列へ持ってくる最小手数を `t_i` とすると、遷移は次の形である。

```text
dp[i][j] = min(
    dp[i-1][j] + 1,
    dp[i-1][j-1] + t_i + 1
)
```

前者はその行から鬼を持ってこず、列を1つ進めるだけの選択である。後者はその行の鬼を左右どちらかへ動かして対象列へ入れ、列操作で一緒に出す選択である。

これを、各列の上・下、各行の左・右について計算する。DPで得られた候補操作列を盤面に適用し、ビームの次状態にする。

### 操作・クエリ・出力選択

- 各ビーム遷移は複数操作からなる。
- 操作列は、鬼を対象レーンに寄せる直交操作と、対象レーンを外へ押す操作の並びになる。
- ビームで全鬼が消えた状態の操作列を出力する。
- 1遷移が複数手なので、手数上限 `4N^2` を超えないように状態ごとに現在手数を持つ必要がある。

### 時間配分・パラメータ

- ビーム幅は200程度。
- 各状態で有効にする遷移候補は、コスパのよい5個程度。
- DPが重く、自作差分更新ビームが1手遷移用だったため、盤面コピー型のビームにしたと記事にある。
- ハッシュは盤面のZobrist Hash。後から、福を無視して鬼だけでハッシュ化すると少し伸びるという話を聞いて試した、と脚注にある。

## 実装上重要な断片

```text
generate_transition(board, target_col, direction=up):
    for each row i from top to bottom:
        t_i = min horizontal moves to bring an oni in row i to target_col
        if impossible or drops fuku:
            t_i = INF

    dp[0][0] = 0
    for i in 1..N:
        for j in 0..max_oni:
            dp[i][j] = dp[i-1][j] + 1
            dp[i][j] = min(dp[i][j], dp[i-1][j-1] + t_i + 1)

    reconstruct good j candidates
    return operation sequences with low turns / removed_oni
```

ビーム本体は次の形である。

```text
beam = [initial_state]
while time remains:
    next = []
    for state in shuffled(beam):
        candidates = []
        for lane and direction:
            candidates += generate_transition(state.board, lane, direction)
        keep best 5 transition candidates by turns / killed
        push copied next states
    beam = best width states by remaining_oni_count, removing duplicate hashes
```

## この解法の本質

この解法の本質は、操作の単位を大きくしている点である。1手ずつのビームでは、評価関数が「今の1手で何がよくなったか」を推定しなければならない。terry_u16の方針では、複数手をまとめた遷移が実際に鬼を何匹落とすかまで見えるため、残り鬼数という単純な評価でも探索しやすい。

また、鬼を外へ出すだけでなく、直交方向から同じ行・列へ集めることをDPで扱う点が強い。手作業のルールベースでは見落としやすい「どの行の鬼を一緒に連れていくか」を、局所的な最小化問題として解いている。

## 真似するならまず実装する部分

まずは1方向だけ、たとえば「ある列から上へ出す」遷移生成を実装するのがよい。各行について、左右に何手で鬼を対象列へ持ってこられるか、福を落とさず可能かを計算し、DPで何匹まとめるかを決める。

それが動いたら、上下左右へ一般化し、コスパ上位候補だけを返す関数にする。ビーム幅やハッシュ管理はその後でよい。

## 注意点・未理解点

- 提出 #62339553 では、`solve_beam` が `MAX_TURN=200`, `BEAM_WIDTH=250`, `CANDIDATE_CNT=7` を使う。`State` は盤面、鬼数、手数、履歴indexを持ち、`OpSet` が同一方向の連続操作をまとめて `apply` する。行/列ごとにDPで候補操作列を作り、履歴から出力を復元する。
- `t_i` の計算で、鬼が複数いる行・列をどう選ぶか、福が途中にある場合をどう扱うかは記事本文だけでは完全には分からない。
- ビーム評価が残り鬼数だけだと同点が多く、多様性管理を誤るとすぐに似た状態で埋まる。
- 遷移を大きくすると探索空間は狭くなる。記事脚注にも、操作の形を決め打つデメリットがあると書かれている。
- 盤面コピー型なので、候補生成DPとコピー回数の両方が重くなりやすい。
