## 解法の全体像

1手ずつ操作を追加するビームサーチで、福を落とさない実行可能な操作列をまず作る。ビームの評価は、各鬼について「盤面外までの近さ」と「その方向に福があるか」を見て、鬼ごとの最小コストを総和したものを使う。状態は盤面全体をコピーせず、行・列ごとのbitsetと差分更新で前進・後退させる。

その後、ビームで得た操作列そのものを状態として山登りする。近傍は操作のswap、移動、変更、削除+挿入、削除である。変更後の操作列を最初からシミュレーションし、福を落とさず全鬼を落とせるなら採用する。近傍は操作列長を増やさないため、有効性を保って削除が通ればそのまま手数が短くなる。

## 主要アイデア

- ビームサーチの状態は、鬼・福の位置を行bitsetと列bitsetの両方で持つ。
- 遷移は4方向 x 20本のうち、操作先の外周に福がないものだけ許す。
- 評価値は、各鬼について `min(外までの距離 * 2 + その方向に福があれば1)` を足す。
- 差分更新では、動かした行・列にいる鬼だけ評価値を更新する。福の移動による他レーンの評価変化は近似として無視する。
- ハッシュは操作の累積で持ち、同一ハッシュでは評価がよい候補だけを残す。
- ビームで全鬼が消えた候補が出たら、それを初期解として返す。
- 後処理は操作列の可否だけを判定する山登りで、長さ短縮や操作入れ替えを試す。

## 最終コードの構造

### 状態表現

- `Environment`: `board_size`、初期盤面、最大ターン数、初期鬼数。
- `beam_search::State`: 現在の盤面を以下で保持する。
  - `board_oni_row[20]`, `board_oni_col[20]`
  - `board_fuku_row[20]`, `board_fuku_col[20]`
  - `turn_num`
  - `removed_oni_turn`: 巻き戻し時に、外へ出した鬼を戻すためのスタック
- `Evaluator`: 評価値 `score` だけを持つ。小さいほどよい。
- `Action`: 方向 `dir` と行・列番号 `lane`。
- `Node` / `Candidate` / `Selector`: 差分更新ビームサーチライブラリ由来の探索木と候補管理。
- 山登り側は、`vector<pair<char,int>> actions` を直接状態にする。

### 観測・制約・入力の扱い

- 入力盤面は文字盤面として読み、鬼と福をbitsetに展開する。
- 各操作候補を作るとき、外へ出る位置に福がある場合は候補から除外する。
- ビーム中は福を外に出さない操作だけで進むため、途中の違反は起こさない。
- 山登りの評価では、初期盤面から操作列を愚直に再生し、福が外へ出た瞬間に不採用とする。
- 操作列再生後に鬼が1つでも残れば不採用とする。

### 評価関数

ビームの評価は、各鬼 `(x,y)` について次の4方向コストを計算し、その最小を足す。

```text
up    = (x + 1) * 2 + (同じ列の上側に福があれば 1)
left  = (y + 1) * 2 + (同じ行の左側に福があれば 1)
down  = (N - x) * 2 + (同じ列の下側に福があれば 1)
right = (N - y) * 2 + (同じ行の右側に福があれば 1)
oni_score = min(up, left, down, right)
eval = sum(oni_score)
```

コードでは、操作前に動かす行・列上の鬼の `oni_score` を引き、盤面を更新し、更新後の同じ行・列上の鬼の `oni_score` を足す。記事にもある通り、福の移動によって別の鬼の「途中に福があるか」が変わる影響は差分更新していない。

山登り側の評価はスカラー値ではなく、「この操作列が有効か」だけである。近傍は手数を増やさないため、有効なら採用してよいという割り切りになっている。

### 探索・構築・更新

- ビームサーチ:
  - 深さは最大 `4N^2`。
  - ビーム幅は2048。
  - 各状態から最大80操作を展開する。
  - `Selector` はハッシュ重複を取り除き、評価のよい候補だけを残す。
  - 探索木はDFS順に状態を差分前進・後退させる。
- 差分更新:
  - `update_board_forward(dir,lane)` で該当行・列を1マス動かす。
  - 外へ出た鬼は `removed_oni_turn` に時刻を積む。
  - `update_board_backward(dir,lane)` で逆方向に戻し、必要なら鬼を外周に復元する。
- 山登り:
  - 時間が1.980秒になるまで乱択近傍を試す。
  - 近傍は5種類で、比率はおおむね `0.25, 0.25, 0.25, 0.15, 0.10`。
  - 近傍適用後、操作列を再生して無効ならロールバックする。

### 操作・クエリ・出力選択

- ビームが返す `Action(dir,lane)` を `U,L,D,R` に変換して操作列にする。
- 山登り後の `actions` をそのまま出力する。
- 出力時に追加の検証はしないが、山登りの各採択時に有効性を確認している。

### 時間配分・パラメータ

- 全体の時間上限は約1.98秒。
- ビーム幅は2048。
- ノード容量は `256 * beam_width`、ハッシュマップ容量は `512 * beam_width`。
- 山登りはビーム完了後の残り時間を使う。
- 評価値の福ペナルティは1。距離は2倍している。

## 実装上重要な断片

ビーム遷移は次の形で考えられる。

```text
expand(state, evaluator):
    for dir in U,L,D,R:
        for lane in 0..N-1:
            if outer_cell_has_fuku(dir, lane):
                continue

            delta = 0
            for oni in moved_lane:
                delta -= oni_score(oni)

            apply_shift(dir, lane)

            for oni in moved_lane:
                delta += oni_score(oni)

            push_candidate(evaluator + delta, hash + action_hash)
            rollback_shift(dir, lane)
```

山登りは次の形である。

```text
while time remains:
    mutate(actions)
    if replay(actions) drops no fuku and removes all oni:
        keep
    else:
        rollback mutation
```

## この解法の本質

この解法の本質は、盤面状態をきちんと持つ探索と、操作列だけを直接いじる後処理を役割分担している点である。ビームでは「どう鬼を外へ近づけるか」を粗い評価で探索し、後処理では評価関数を設計せず、「有効性を壊さず手数を削れるか」に集中している。

評価関数も問題に合っている。鬼を完全に落とす手数を正確に見積もるのは難しいが、外周までの距離と進行方向の福の有無は、1手後の改善をよく表す。差分更新を厳密にしすぎず、福移動による全体評価変化を無視した点も、ビーム幅を確保するための実用的な近似である。

## 真似するならまず実装する部分

まずは、bitsetでなくてもよいので盤面を持ち、福を落とさない80操作候補を全列挙するビームサーチを作るのがよい。評価は記事通りの `sum min(distance*2 + fuku_penalty)` で十分である。

次に、操作列を再生して「福を落とさず全鬼を落としたか」を判定する関数を作る。この関数があれば、ビーム後の削除近傍だけでも試せる。swapや変更近傍は後から足せばよい。

## 注意点・未理解点

- 差分評価は近似である。福が移動したことで、動かしたレーン以外の鬼の評価も本来は変わり得る。
- `removed_oni_turn` による巻き戻しは、鬼が外へ出た時刻とDFS順の前後移動が一致している前提で動く。探索木の移動順を崩すと壊れやすい。
- ビームのハッシュは操作列由来であり、厳密な盤面ハッシュではない。衝突や同一盤面判定の意味はコード固有である。
- 山登りの `evaluate` は毎回操作列全体を再生するため、操作列が長い場合は試行回数が落ちる。
- 山登りは手数を増やす近傍を持たないので、いったん遠回りして後で大きく削るタイプの改善は拾えない。
