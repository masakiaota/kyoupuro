## 解法の全体像

縦または横の一続きの道路を「通り」と呼び、全道路を視界に入れる条件を「全ての通りに最低1回到達する」と読み替える。各通りには交差点から到達できるため、解は「通りを巡回する順番」と「各通りでどの交差点を踏むか」で表現できる。

実装では、まず交差点と通りを列挙し、全交差点間の最短距離をダイクストラで前計算する。状態は全通りの順列と、各通りに対応する交差点IDを持つ。近傍は2-optで通り順を区間反転し、反転区間内の各通りについて、直前の交差点から最も近い交差点を選び直す。評価は、開始点から各選択交差点を順に辿って開始点へ戻る距離の負値である。焼きなましでこの評価を改善し、最後に選んだ交差点列をグリッド上の最短経路で復元して出力する。

## 主要アイデア

- 「全道路を見渡す」を「全通りを訪れる」に変換する。
- 経路候補はマス列ではなく、通り列と交差点列で表現する。
- 交差点間の移動距離は、Floyd-Warshallではなく各交差点始点のダイクストラで求める。
- 通り順は2-opt焼きなましで改善する。
- 各通りで踏む交差点は、直前交差点から一番近いものを選ぶ貪欲で決める。
- 差分評価はせず、状態全体を評価し直す。それでも3秒で約150万試行できたと記事にある。
- 最終出力では、交差点列の各区間を実際の最短路として復元する。

## 最終コードの構造

提出 #24899313 のC#コードを確認した。以下は構造の要約である。

### 状態表現

- `MAP[y,x]`: 道路なら進入コスト、障害物なら0。
- `Intersections`: 交差点リスト。先頭に開始点 `(SY,SX)` を追加する。
- `YXToInterSectionIndex[y,x]`: 交差点ID。開始点は重複回避のためここには入れない。
- `Streets`: 縦横の通りリスト。
  - `IsVertical`: 縦通りか横通りか。
  - `SY,SX`: 通りの始点。
  - `InterSections`: その通りに含まれる交差点ID列。
  - `Length`: 通りの長さ。
- `IntersectionsDist[src,dst]`: 交差点間の最短距離。
- `State.Target[i] = (streetIndex, interIndex)`: i番目に訪れる通りと、その通りで踏む交差点。
- `bestPoints`: 最良状態から得た交差点座標列。

### 観測・制約・入力の扱い

- `N si sj` と地図を読み、`H=W=N` として扱う。
- 道路マスの移動コストは、移動先マスの数字を使う。
- 交差点は、道路マスであり、縦方向の隣接道路と横方向の隣接道路を両方持つマスとして列挙している。
- 開始点は交差点リストの先頭に追加する。開始点が通常の交差点としても列挙され得るため、`YXToInterSectionIndex` には開始点用IDを入れない設計になっている。
- 通りは縦横それぞれ、障害物で区切られた長さ3以上相当の連続道路列として登録している。

### 評価関数

- `State.Evaluate()` は、開始点ID `0` から `Target` の交差点を順に辿り、最後に開始点へ戻る距離を合計する。
- 焼きなましの採択では「高いほど良い」として扱うため、合計距離に `-1` を掛けた値を返す。
- 問題本来の得点は全被覆前提なら距離の単調減少なので、この評価で十分である。
- 記事・コード上では、被覆漏れペナルティは不要である。`Target` が全 `Streets` を必ず一度ずつ含むためである。

### 探索・構築・更新

- 初期状態では、通りリストの順番そのままに全通りを並べ、各通りの最初の交差点を選ぶ。
- 近傍は2-opt。`Target[e1:e2]` を反転する。
- 反転後、対象区間の各通りについて、直前の選択交差点から最短の交差点を選び直す。
- 評価は `State.Evaluate()` で全体再計算する。
- 採択は焼きなまし。改善は必ず採択し、悪化は `exp(loss / temperature)` で採択する。
- 不採択なら、保存していた `Target` 配列へロールバックする。
- 最良状態の `Target` と、対応する交差点座標列を保存する。

### 操作・クエリ・出力選択

- `bestPoints` は、開始点、選択交差点列、開始点を並べた座標列である。
- `RetrievePath(bestPoints)` は、隣り合う座標ペアごとにグリッド上でダイクストラを行い、最短路を復元する。
- 復元した方向列を `D/R/U/L` の文字に変換して出力する。
- 復元時は、現在マスの距離から「直前マス + 現在マスへの進入コスト」が一致する隣接マスを辿って戻している。

### 時間配分・パラメータ

- ローカル引数で `t0`, `t1`, `tl` を指定できる。
- 提出時のデフォルトは `t0 = 75`, `t1 = 2.5`, `TL = 2800ms`。
- 温度はコード上では幾何補間 `t0^(1-a) * t1^a` で変化させている。記事本文の「線形」記述とは完全には一致しない可能性がある。
- 256ターンごとに時間を見て温度更新する。
- 乱数シードは71固定。

## 実装上重要な断片

```text
preprocess:
    intersections = [start]
    for each road cell:
        if has_vertical_neighbor and has_horizontal_neighbor:
            add as intersection
    streets = enumerate_vertical_segments() + enumerate_horizontal_segments()
    for each intersection src:
        dist[src] = dijkstra_on_grid(src)
```

```text
apply_2opt(state, e1, e2):
    stash = copy(state.target)
    reverse state.target[e1:e2]
    for i in e1..e2-1:
        prev = start if i == 0 else state.target[i-1].interIndex
        street = streets[state.target[i].streetIndex]
        state.target[i].interIndex = nearest_intersection(prev, street.intersections)
    return stash
```

```text
evaluate(state):
    cur = start
    total = 0
    for target in state.target:
        total += dist[cur][target.interIndex]
        cur = target.interIndex
    total += dist[cur][start]
    return -total
```

## この解法の本質

この解法の本質は、被覆制約を状態が常に満たすように設計した点にある。全通りを順列として必ず1回ずつ持つため、探索中に「全道路が見えるか」を重い集合演算で調べなくてよい。評価は巡回距離だけになる。

また、通り順と交差点選択を完全に分けず、2-optで順序を変えた直後に交差点を貪欲に選び直している点が実装上効いている。交差点選択を固定した2-optより、順序変更の影響をすぐ吸収できる。一方で、交差点選択は局所貪欲なので、通り順全体を見た最適選択ではない。

## 真似するならまず実装する部分

最初に、交差点列挙、通り列挙、交差点間ダイクストラを作る。次に、全通りを固定順に並べて、各通りで直前から最も近い交差点を選び、開始点へ戻る合法解を出す。

その後、2-opt山登りを入れる。焼きなまし、温度調整、Optuna、最終経路復元の高速化は、固定順巡回が正しく出力できてから追加するのがよい。

## 注意点・未理解点

- 通りの端点だけで交差点を含まない連続道路列が存在する場合、`street.InterSections[0]` が空になる危険がある。生成性質上ほぼ避けられるのか、コード上の暗黙前提なのかは完全には確認できない。
- 開始点を交差点リストに重複追加しているため、開始点が通常交差点でもIDの扱いに注意が必要である。
- 記事本文の冷却説明と提出コードの温度更新式にはずれがある。後日調整の過程で変わった可能性がある。
- `RetrievePath` は区間ごとにダイクストラを再実行するため、最終経路復元に一定時間を使う。`TL=2800ms` にしているのはこの余裕を残すためと読める。
- 提出コードは読めたが、Optunaでどのパラメータをどう探索したかのログは読めない。
