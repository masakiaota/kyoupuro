## 解法の全体像

問題を「全道路マスを辿る巡回路」ではなく「必要な交差点集合を選び、その集合をTSP的に巡回する問題」として小さくする。全マスを使った経路で考えると状態空間が大きいが、視界の性質により交差点をいくつか選べば道路を被覆できる。そこで解は、使う交差点の集合として持つ。

選んだ交差点集合に対しては、本格的なTSP最適化よりも最近傍法で巡回コストを評価する。交差点集合の追加・削除・入れ替えのような局所変更で、全道路を被覆するvalid状態を保ちながら山登りする。実行ごとのブレが大きいため、多スタートで複数の局所解を試し、最後に2-optで巡回順を少し改善する。

## 主要アイデア

- 解空間を道路マス列ではなく、交差点の部分集合にする。
- 選ばれた交差点集合で全道路が視界に入ることをvalid条件にする。
- 交差点集合を少し変更し、validを保てる場合にスコアを再計算して山登りする。
- 集合が決まった後の巡回は最近傍法で近似し、TSP部分に時間を使いすぎない。
- 最後だけ2-optをかけて巡回順を改善する。
- 多スタートで、離れた局所解を複数探索する。
- 記事末尾では、交差点ベースより辺ベースの状態の方が実装しやすく、スコア的にも良かったかもしれないと振り返っている。

## 最終コードの構造

提出 #24827996 の実装に基づく構造である。本文と関連Tweetで述べる「交差点集合を選び、最近傍で巡回し、多スタートと2-optで改善する」方針が確認できる。

### 状態表現

- `Cross`: 交差点候補。座標、ID、通行コストを持つ。
- `@crs`: 開始点を含む交差点リスト。
- `view_count`: 選択交差点集合が各道路マスまたは視界対象を何回カバーしているかを表す配列。
- `use_idx`: 現在使う交差点ID集合。
- `@cr_dist`: 交差点間の最短距離。
- `path`: 最近傍法で作った交差点巡回順。0番を開始点として先頭・末尾に置く。

### 観測・制約・入力の扱い

- 道路マスと障害物を読み、縦横の連続道路列または道路マス集合を被覆対象にする。
- 各交差点を選んだとき、同じ行・列で障害物までの道路が視界に入る。
- 集合の追加・削除時に被覆数を更新し、未被覆道路が残らないことをvalid条件にする。
- 開始点は巡回の起点・終点として扱う。開始点が交差点でない場合も、距離計算の基点には含める必要がある。

### 評価関数

- 主要な評価は、選んだ交差点集合を最近傍法で巡回したときの総移動コストである。
- 問題の得点は全被覆なら `t` の単調減少なので、評価は `-t` として最大化すればよい。
- 集合がvalidでない場合は採択しない、または強いペナルティを与える。

### 探索・構築・更新

- 初期解は `select_crs` で全道路を被覆する交差点集合を作る。
- `update_crs(use_idx, view_count)` で交差点集合を変更する。削除で被覆が崩れる場合は、必要な交差点を追加してvalidを保つ。
- 集合変更後は `solve_single(use_idx)` で最近傍巡回を作り直して評価する。
- `solve` は `MULTISTART = 10` で時間を10分割し、各スタートの最良を取る。
- 最終段階の `improve(path, score, tl)` は2-optで巡回順を改善する。

### 操作・クエリ・出力選択

- 最良の交差点集合を決める。
- 最近傍法と2-optで交差点順を決める。
- 隣接する交差点間はグリッド上の最短経路でつなぎ、開始点へ戻る移動列を出力する。

### 時間配分・パラメータ

- 提出 #24827996 では `TL = 2960`, `MULTISTART = 10`。
- 2-optの受理用に `INITIAL_COOLER = 0.01`, `FINAL_COOLER = 1.00` を持つ。
- TSPは最近傍法を主に使い、最後だけ2-optに限定している。

## 実装上重要な断片

```text
make_initial_solution():
    selected = empty_set()
    while uncovered_exists:
        add_intersection_that_covers_uncovered_roads()
    return selected

score(selected):
    order = nearest_neighbor_tour(start, selected)
    return -tour_length(order)

hill_climb_one_start():
    selected = make_initial_solution()
    while time_for_this_start:
        candidate = modify_selected_intersections(selected)
        if is_valid(candidate) and score(candidate) >= score(selected):
            selected = candidate
    order = two_opt(nearest_neighbor_tour(start, selected))
    return selected, order
```

## この解法の本質

この解法の本質は、被覆対象と巡回対象を分けたうえで、巡回対象を「交差点集合」という小さな組合せ問題に落とした点にある。交差点集合を状態にすると、被覆のvalid判定と巡回コストの評価が明確に分かれる。TSP部分を厳密に解かず、最近傍法に任せることで、探索時間を「どの交差点を使うべきか」に集中できる。

一方で、本人の振り返りにもある通り、この問題で本当に辿るべき対象は交差点ではなく道路列・辺である。交差点集合ベースは分かりやすいが、通路ごとの到達点選択や順序を同時に扱う辺ベース解法の方が、状態表現として自然な可能性がある。

## 真似するならまず実装する部分

まずは交差点を列挙し、各交差点がどの道路列を視界に入れるかを前計算する。次に、貪欲で全道路を被覆する交差点集合を作り、その集合を最近傍法で巡回するところまで作る。

局所探索は、最初は「選択済み交差点を1つ削除してもvalidなら削除」「未選択交差点を1つ追加して巡回距離が縮むなら採用」のような単純な近傍から始めるのがよい。多スタートと2-optはその後でよい。

## 注意点・未理解点

- 最終提出 #24827996 をBrowserで読めたため、`select_crs`、`update_crs`、`update_view_count`、最近傍 `solve_single`、2-opt `improve`、多スタート数は確認済みである。
- 交差点集合だけでは、通路上のどこを実際に通るかを直接表現できない。最短経路復元で意図しない通路を通る場合の扱いは不明である。
- 最近傍法の巡回順は高速だが、交差点集合の評価として粗い。集合の良し悪しと最終2-opt後の良し悪しがずれる可能性がある。
- 多スタートの回数や初期解生成のランダム性は、再現時のスコアに大きく影響しそうである。
- 関連Tweetは oEmbed 経由で読めたが、添付画像や返信ツリーまでは精読していない。
