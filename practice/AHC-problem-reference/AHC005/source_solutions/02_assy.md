## 解法の全体像

道路マスを直接すべて巡回するのではなく、縦または横に連続する「通路」をすべて一度ずつ触れば全道路マスが視界に入る、という形に問題を縮約する。まず全通路を列挙し、各通路に含まれる交差点を記録する。さらに各交差点と開始点からダイクストラを行い、交差点間の移動距離を前計算する。

探索では「通路を訪れる順番」を解として持ち、この順番を2-opt近傍だけで焼きなます。評価は、現在いる交差点から次の通路に含まれる交差点のうち最も近いものへ貪欲に移動したときの総距離で近似する。最終的には、焼きなましで得た通路順を固定し、実際の最短経路を計算して出力する。

## 主要アイデア

- 視界条件を「縦横の連続通路を少なくとも一度訪れる」問題に変換する。
- 各通路に対して、到達候補となる交差点集合を持つ。
- 交差点と開始点を始点にしたダイクストラで、交差点間距離を前計算する。
- 解は全通路の順列として持つ。
- 順列の評価では、次の通路に含まれる交差点のうち現在地点から最も近い交差点を選ぶ。
- 近傍は2-optのみで、通路順の区間反転を焼きなましで採択する。
- 最終出力では、通路順を固定したうえで実際の最短経路をつなぐ。

## 最終コードの構造

提出 #24827956 の実装に基づく構造である。記事本文の「通路順列 + 2-opt焼きなまし + 最終経路復元」と一致する。

### 状態表現

- グリッド `N x N` と各道路マスの進入コスト。
- `ways`: 縦横の連続道路列。各要素は始点・終点を持つ `way`。
- `juncs[way_id]`: その通路上で到達候補になる交差点座標集合。
- `road`: 道路マス一覧。
- `dist[sy][sx][gy][gx]`: 各道路マス始点からのダイクストラ距離。
- 焼きなまし状態として、通路IDの順列 `p`。
- `calc_dist(p, nw)`: 通路順を固定し、各通路で現在位置から最も近い交差点を貪欲に選んだ距離を返す。
- `calc_command(p, nw)`: 通路順を固定し、動的計画的に候補交差点を選びながら実際の移動文字列を復元する。

### 観測・制約・入力の扱い

- 道路マスは `5..9` の進入コスト、障害物は通行不可として読む。
- 交差点は、縦方向の道路隣接と横方向の道路隣接を両方持つ道路マスとして抽出するのが自然である。
- 各通路は障害物で切れる縦横の連続道路列として列挙する。
- すべての通路を訪問対象にすることで、視界被覆の判定を個別マス単位で持たない。

### 評価関数

- 焼きなまし中の評価値は、通路順に沿って貪欲に交差点を選んだときの巡回距離である。
- 最大化スコアではなく、総移動時間 `t` の最小化として扱う。
- 問題本来の得点は `10000 + 1e7 * N / t` なので、全道路を視界に入れる前提では `t` を小さくすればよい。

### 探索・構築・更新

- 初期状態は `p[i] = i` の通路ID順列。
- 近傍は2-opt。ランダムな `l,r` を選び、`reverse(p.begin()+l, p.begin()+r+1)` を行う。
- 評価は差分更新せず、毎回 `calc_dist` で開始点から順に貪欲計算し直す。
- 記事によると通路数は100前後で、差分計算なしでも十分回った。
- 遷移回数は約200万回。
- 焼きなましスケジュールは線形冷却が良かったとされる。

### 操作・クエリ・出力選択

- 最終的な通路順を決める。
- `calc_command` で通路ごとの到達交差点を選び、`dist` を逆向きに辿る形で実際の `U/D/L/R` を復元する。
- 出力は `U/D/L/R` の移動列で、開始点に戻る必要がある。

### 時間配分・パラメータ

- 本番中は、山登りから焼きなましへ移行し、最後に経路を最短経路化した。
- 提出 #24827956 では `T_init = 40`, `T_end = 0.0001`。
- 100反復ごとに経過時間を見て、2950msまで線形冷却する。
- 近傍は2-optのみで、実測では記事通り約200万回規模が回る設計である。

## 実装上重要な断片

```text
preprocess:
    streets = enumerate_all_horizontal_and_vertical_segments()
    intersections = enumerate_intersections_and_start()
    for p in intersections:
        dist[p] = dijkstra_on_grid(p)

evaluate(order):
    cur = start_intersection
    total = 0
    for street in order:
        nxt = argmin(inter in street.intersections, dist[cur][inter])
        total += dist[cur][nxt]
        cur = nxt
    total += dist[cur][start]
    return total

anneal:
    order = initial_permutation()
    while time_remains:
        new_order = reverse_subarray(order, l, r)
        accept_by_annealing(-evaluate(order), -evaluate(new_order))
```

## この解法の本質

この解法の本質は、視界被覆の管理をマス単位から通路単位に落とし、問題をほぼTSPに変換した点にある。全マスの被覆集合を毎回更新しようとすると重いが、通路を一度訪れればその通路上の道路は見える。よって、被覆制約は「全通路を訪れる」という強いが分かりやすい制約に置き換えられる。

また、交差点選択を厳密に同時最適化せず、各通路で現在地点に最も近い交差点を選ぶ貪欲に寄せたことも重要である。短期コンテストでは、通路順という小さな状態だけを焼きなまし対象にして、評価を単純にする判断が強い。

## 真似するならまず実装する部分

まず実装するべきなのは、通路列挙と交差点間ダイクストラである。これができれば、全通路を固定順で巡回するだけでも合法解を作れる。

次に、通路順の2-opt山登りを作る。焼きなましの温度調整や最終経路の最短経路化は、固定順巡回が動いてから追加すればよい。

## 注意点・未理解点

- 最終提出 #24827956 をBrowserで読めたため、交差点定義、通路列挙、`calc_dist`、`calc_command`、温度値は確認済みである。
- 「全通路を1度ずつ触れば全マスが見える」は実装上、縦横どちらの通路IDを列挙するかで重複や漏れが起きやすい。
- 貪欲に交差点を選ぶ評価は、最終経路の厳密最適とは異なる。記事では最終経路決めで0.2%程度の改善とされるが、ケース依存である。
- 2-optだけだと、通路順の大きな構造変更が苦手な可能性がある。
- 線形冷却が良かったことは分かるが、温度値は不明である。
