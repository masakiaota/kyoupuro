# AHC 解法精読メモ作成指示書

## 目的

各 `contest_dir` について、`problem_description.txt` と `solution_urls.md` に記載された解説記事・公式解説・公開コードを読み、参照元ごとに解法メモを作成する。

目的は、AIや人間が後から解法の意図、本質、実装上の重要点、各解法の違いを理解できるように整理することである。

## 入力

対象ディレクトリ:

```text
practice/AHC-problem-reference/<CONTEST>/
```

必ず読むファイル:

```text
problem_description.txt
solution_urls.md
```

`solution_urls.md` に記載された各 URL を参照元として扱う。

## 出力構成

各 `contest_dir` に次の構成でファイルを作成する。

```text
practice/AHC-problem-reference/<CONTEST>/
├── problem_description.txt
├── solution_urls.md
├── source_solutions/
│   ├── 01_<source_name>.md
│   ├── 02_<source_name>.md
│   └── ...
└── solution.md
```

`source_solutions/*.md` は参照元ごとの精読メモである。`solution.md` は、個別メモを読んだうえで作る統合メモである。

## 作業手順

### 1. 問題を理解する

まず `problem_description.txt` を読み、次を把握する。

- 入力
- 出力
- 操作・制約
- スコア計算
- 何を最適化する問題か
- 失敗条件
- 実装時に守るべき制約

この段階では詳しい解法を書かなくてよい。

### 2. `solution_urls.md` を読む

`solution_urls.md` の各行について、次を確認する。

- タイトル
- URL
- 著者・サイト
- 種別: 公式解説、上位解説、参加記、コード、資料など
- 備考

各 URL に対応して `source_solutions/NN_<source_name>.md` を作成する。ファイル名は、順序が保てるように2桁番号を付ける。

例:

```text
01_official_wata.md
02_terry_u16.md
03_eijirou.md
```

### 3. 各参照元を精読する

各 URL について、以下の順に読む。

1. 記事・解説本文を読む
2. 記事内にコード、提出リンク、GitHub、gist、疑似コードがあれば読む
3. 最終解法のコードが読める場合は、構造と重要部分を確認する
4. 読めないものがあれば、読めない理由を明記する

コードがある場合、コードそのものを長く貼り付けてはいけない。代わりに、状態表現、評価関数、探索、更新、出力判定などを要約する。

## `source_solutions` のフォーマット

各 `source_solutions/NN_<source_name>.md` は、必ず次の構成にする。

````markdown
# <CONTEST> - <source_name> 解法メモ

## 参照元

- 記事:
- 著者:
- サイト:
- 種別:
- 成績・順位:
- コード有無:
- コードを読めたか:
- 読めなかったもの:

## 解法の全体像

この参照元の最終解法、または主張している解法が、全体として何をしているかを書く。

問題設定をなぞるのではなく、この人の解法の流れを書く。

## 主要アイデア

箇条書きで、解法の核となるアイデアを書く。

例:

- 状態を何として持つか
- 何を評価するか
- どのように候補を作るか
- どのように局所探索・焼きなまし・貪欲を行うか
- どのようにクエリ・操作・構築を選ぶか
- どのように最終出力を決めるか

## 最終コードの構造

コードを読めた場合は必ず書く。コードがない場合は「コードなし」と書き、記事本文から推測できる実装構造を書く。

### 状態表現

- 主要な構造体・配列
- 状態が表すもの
- 状態に含める値
- 差分更新に必要な値

### 観測・制約・入力の扱い

- 入力をどう前処理するか
- 観測や制約をどう保持するか
- 違反や矛盾をどう扱うか

### 評価関数

- 何を最大化・最小化するか
- スコア、コスト、ペナルティ、尤度などの式
- 近似している場合は何を近似しているか

### 探索・構築・更新

- 貪欲、局所探索、焼きなまし、ビームサーチ、DP、乱択など
- 近傍・遷移
- 採択条件
- 差分更新
- 候補集合の管理

### 操作・クエリ・出力選択

- 次の操作をどう選ぶか
- 何を基準に出力するか
- 最終回答や提出タイミング

### 時間配分・パラメータ

- 時間制限への対応
- 候補数
- 温度
- 閾値
- 試行回数
- その他チューニング値

## 実装上重要な断片

実装に効く処理を、短い疑似コードや箇条書きで書く。

長いコード引用は禁止。関数単位・処理単位で要約する。

例:

```text
update_state(move):
    old_score = score
    apply delta
    new_score = score
    if accept:
        commit
    else:
        rollback
```

## この解法の本質

この解法が何をうまく利用しているのかを文章で書く。

単なる手順ではなく、なぜ効くのか、他の問題にも移せる考え方は何かを書く。

## 真似するならまず実装する部分

この解法を簡略化して実装するなら、最初に作るべき部分を書く。

上位解法の全要素を列挙するのではなく、最小限どこから始めるべきかを明確にする。

## 注意点・未理解点

- 記事から読み取れなかった点
- コードを読んでも意図が分からなかった点
- パラメータ調整依存の部分
- 実装するときに壊れやすい点
- 推測で書いている部分
````

## `solution.md` のフォーマット

個別メモをすべて作成した後、統合版 `solution.md` を作る。

`solution.md` は次の構成にする。

````markdown
# <CONTEST> 統合解法メモ

## このメモの位置づけ

このメモが、参照元ごとの精読メモを統合したものであることを書く。

## 個別メモ一覧

- [01_xxx.md](source_solutions/01_xxx.md): 何が分かるメモか
- [02_xxx.md](source_solutions/02_xxx.md): 何が分かるメモか

## 問題の本質

この問題は何を最適化・推定・構築する問題かを書く。

問題文の再説明ではなく、解法視点での本質を書く。

## 参照解法の比較

| 参照元 | 主方針 | 実装難度 | 強み | 弱み | 真似すべき要素 |
|---|---|---:|---|---|---|

## 共通している考え方

複数の解法に共通する本質を書く。

## 解法の分類

参照元の解法を分類する。

例:

- 貪欲型
- 焼きなまし型
- ビームサーチ型
- 確率推定型
- 制約伝播型
- 構築型
- 後処理改善型

## 推奨して理解すべき順序

人間が読むときの順序を書く。

例:

1. まず公式解説で問題の見方を理解する
2. 次に実装が具体的な参加記を読む
3. 最後に上位解法の高度な工夫を見る

## 実装するならどのルートか

人間が試しに実装するなら、どの参照元をベースにするのがよいかを書く。

ただし、完全再現を目的にしない。「理解のための最小実装」と「上位化の方向」を分ける。

## 重要な実装要素

参照元を横断して、実装上重要な要素を書く。

- 状態表現
- 評価関数
- 近傍
- 差分更新
- 候補管理
- 出力判定
- パラメータ

## 落とし穴

- WA になりやすい点
- TLE になりやすい点
- スコアが悪化しやすい点
- 抽象的には正しいが実装すると弱い方針

## 未解決・要検証事項

記事やコードを読んでも確信できない点を書く。

## 参照元

URL一覧を書く。
````

## 文章の方針

- 日本語で書く
- 文体は常体
- 解説ブログの文章を長く引用しない
- コードを長く転載しない
- 推測と事実を分ける
- 「分からない」ことは分からないと書く
- 実装上重要な断片は疑似コードで書く
- 参照元ごとの違いが消えないようにする
- 統合時に、複数解法を無理に1つの解法へ平均化しない

## 禁止事項

- 参照元を読まずに一般論で埋める
- 複数サイトの知見を混ぜて、誰由来か分からない形にする
- コードが読めていないのに「最終コードでは」と断定する
- 長いコードや記事本文を転載する
- 「ベイズが重要」「焼きなましが重要」のような抽象語だけで終える
- 実装上の状態、評価、更新を書かずに本質だけを書く
- 読めなかったリンクやコードを黙って無視する

## 完了条件

各 `contest_dir` について、次を満たせば完了とする。

- `source_solutions/` に URL 数ぶんの個別メモがある
- 各個別メモに、参照元、コード有無、解法全体像、主要アイデア、コード構造、本質、注意点が書かれている
- `solution.md` に、個別メモの比較と統合が書かれている
- 読めなかったURL・コードが明記されている
- 参照元リンクが残っている
