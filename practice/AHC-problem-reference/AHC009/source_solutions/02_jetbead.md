## 解法の全体像

この記事は単一の最終解法ではなく、AHC009で有効だった方針を横断的に整理している。大枠は「初期解を作り、山登り・焼きなまし・ビームサーチで改善する」問題として捉える。

命令列の前半を変えると後半の確率分布まで変わるため、本来はビームサーチが自然に見える。一方、実際には忘却と壁衝突で分布が広がり、単純な山登りや焼きなましも強かった。初期解はBFS、01BFS、ダイクストラ、貪欲、右下偏重ランダム、壁まで進むハイパーロボット風方針、ビームサーチなどが挙げられている。

## 主要アイデア

- 問題の主戦場は、命令列を直接最適化する局所探索と、確率分布を持つビームサーチの比較である。
- 良い解は「大きな確率塊を右下方面へ運び、散った確率を後半で拾う」形になりやすい。
- スコアは到達しなければ0なので、早さだけでなく到達確率を上げることが重要である。
- 評価関数には実スコアのほか、各マスの `存在確率 * ゴールまでの距離` の総和を使う近似がある。
- スコア計算は愚直な `O(LHW)` でも数千から1万回程度回せるが、1次元配列化や前後DPで大きく高速化できる。
- 近傍は1文字変更、削除、挿入、ダブらせ、swap、区間反転、削除して別位置へ挿入など。
- 壁にぶつけて確率を集める方針は強いが、コの字型や一手戻りが必要なケースで詰まりやすい。
- `p` によって有効戦略が変わる。小さい `p` では分布がぼやけにくくビームや貪欲が相対的に効き、大きい `p` では焼きなましやダブらせが効きやすい。

## 最終コードの構造

コードなし。以下は記事本文とリンク先発言から復元できる実装構造である。

### 状態表現

- 命令列 `cmd`
- 壁判定 `can_move[y][x][d]`
- 確率DP用の `prob[y][x]`
- ビームサーチをする場合は、各ノードに命令列とその時点の確率分布を保持する。
- 前後DP高速化を使う場合は、前からの存在確率 `prefix[t][cell]` と、後ろからの価値 `suffix[t][cell]` を持つ。

### 観測・制約・入力の扱い

- `h`, `v` の2種類の壁配列を直接参照すると事故りやすいため、`can_move[y][x][d]` に変換するのが有効とされている。
- 長さ `200` と文字種 `UDLR` の制約だけ守ればよい。
- ゴールに到達した確率はそれ以降の遷移から除外する。

### 評価関数

主評価は期待スコアDPである。

```text
score = sum_t Pr[first_arrive_at_goal_after_t] * (401 - t)
```

近似評価として、リンク先発言では次の形が挙げられている。

```text
approx = real_score - sum_cell prob[cell] * dist_to_goal[cell]
```

また、ビーム系では `dist^alpha * prob` のような距離ペナルティをターンごとの状態評価に使う例がある。

### 探索・構築・更新

初期解候補:

- BFS/ダイクストラでスタートからゴールへの経路を作る。
- 曲がりに追加コストを置く01BFS。
- 壁にぶつかるまで同方向に進む「ハイパーロボット」風の経路。
- 右・下を多めにしたランダム200文字。
- 確率最大マスからゴールへ進む貪欲。
- ビームサーチで確率分布ごと状態を伸ばす。
- 多点スタートで初期解依存を弱める。

局所探索近傍:

- 1文字変更
- 1文字削除
- 1文字挿入
- 隣の命令を挿入してダブらせる
- 2点swap
- 区間反転
- 1文字削除して別位置へ挿入
- 1点追加と1点削除を1ムーブにまとめる

高速化:

- 2次元配列ではなく1次元配列でDPする。
- 変更ターンより前のDPは再計算しない。
- 前からのDPと後ろからのDPを持ち、1文字変更時の差分スコアを `O(HW)` で見積もる。
- 変更位置をターン順に処理すると、前側DPを逐次更新しやすい。

### 操作・クエリ・出力選択

- 最終的には最も評価値の高い命令列を出力する。
- ビームサーチでは、各ターンの候補状態から評価値上位を残し、最後に実スコア最大の列を採用する。
- 焼きなましでは常に現在解と最良解を持ち、時間切れ時に最良解を出す。

### 時間配分・パラメータ

- 記事は個別パラメータを固定していない。
- 参加者発言では、愚直スコア計算でも数千から1万回程度の評価が可能とされている。
- 前後DPによる差分計算では、後日解で大幅な高速化と76%超のスコアが報告されている。

## 実装上重要な断片

score(cmd):
    prob[start] = 1
    for c in cmd:
        next = move_or_stay(prob, c)

        next[goal] = 0
        prob = next

## この解法の本質

この記事から見える本質は、AHC009が「経路探索」ではなく「確率分布の制御」問題だという点である。最短経路を見つけるだけでは、忘却で遅れた確率質量が落ちる。壁にぶつける、命令をダブらせる、後半に散った確率を拾う、といった操作で、確率分布をゴールへ吸い込ませる必要がある。

また、実スコアが期待値として正確に計算できるため、評価関数を変に作り込むより、まず正確なスコアを高速に回すことが有効だった。ビームサーチ・貪欲・焼きなましの差は、結局「どの初期分布・命令列候補を作るか」の違いとして整理できる。

## 真似するならまず実装する部分

最初はTERRY/Bondo型の、BFS初期解と愚直DP評価の山登り・焼きなましを作るのがよい。Jetbeadメモから真似するなら、次に追加するのは以下である。

- `can_move[y][x][d]` の前処理
- 1次元配列によるスコアDP高速化
- ダブらせ、挿入、削除、削除+挿入近傍
- `p` が小さい場合のビーム・貪欲、大きい場合のダブらせ重視という分岐

前後DP差分は強力だが、実装の複雑さが上がるため、愚直DPで近傍の効き方を確認してからでよい。
