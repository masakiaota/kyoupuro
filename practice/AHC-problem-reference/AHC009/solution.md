## 問題の本質

この問題は、1本の経路を作る問題ではなく、忘却と壁衝突で広がる確率分布をゴールへ吸い込ませる命令列を作る問題である。

各ターンでは、確率 `p` で命令が無視され、壁方向でもその場に残る。そのため、同じ命令列でも高橋くんの位置は1点ではなく `20x20` の分布になる。スコアは「各ターンに初めてゴールへ到達した確率」に `401-t` を掛けた期待値なので、単に最短で着くよりも、到達確率を高くすることが重要である。

有効な操作は大きく3種類ある。

- 本筋の経路を作る: BFS、ダイクストラ、壁滑り、ビームサーチ。
- 忘却に備える: 命令をダブらせる、壁にぶつけて確率を同期させる。
- 取りこぼしを拾う: 命令列を焼きなまし・山登りで微調整する。

## 参照解法の比較

| 参照元 | 主方針 | 実装難度 | 強み | 弱み | 真似すべき要素 |
|---|---|---:|---|---|---|
| terry_u16 | 乱択ダイクストラ初期解 + ダブらせ + 焼きなまし | 中 | 1位解法で再現性が高い。実スコアだけで強い | 初期解ガチャと定数倍高速化に依存 | `ceil(L/(1-p))` までのダブらせ、コピー近傍 |
| jetbead | 解法横断整理 | 中〜高 | ビーム、前後DP、`p` 分岐まで見える | 単一コードではない | 1次元DP、前後DP差分、近傍一覧 |
| tsukammo | 壁寄せ貪欲 + 4手先読み | 中 | 確率分布を集団として見る発想が明確。提出コードで評価式も追える | 貪欲単独はケース差に弱い | `prob * distMap` の先読み評価 |
| Bondo416 | BFS初期解 + 4近傍山登り/焼きなまし風探索 | 低 | 実装が短く、提出コードも読みやすい | 初期解が1本で、ダブらせが弱い | 最小局所探索実装、区間反転・swap |
| bowwowforeach | 壁滑り初期解 + 追加/削除/ダブらせ焼きなまし | 中 | 壁を使った確率同期の考え方が強い | 到達不能地形に弱い | 壁まで進む停止位置前計算、ダブらせ近傍 |

## 共通している考え方

多くの解法は、最終的に命令列を直接最適化している。違いは初期解の作り方と評価計算の速さである。

- 確率DPで実スコアを計算する。
- ゴール到達確率は加点後にDPから取り除く。
- 最短路だけでは忘却に弱いので、命令の重複や壁衝突を使う。
- 初期解の質が焼きなまし結果を大きく左右する。
- 近傍は単純でも効く。追加、削除、変更、swap、反転、ダブらせが中心。
- `p` が大きいほど分布がぼやけ、焼きなましやダブらせが効きやすい。
- `p` が小さいほど分布が鋭く、貪欲やビームの評価設計が相対的に重要になる。

## 解法の分類

- 焼きなまし・山登り型: terry_u16、Bondo416、bowwowforeach、Jetbead内の多数参加者
- ビームサーチ型: Jetbead内のPsyho、Shun_PI、highjump、soraie などの発言
- 壁寄せ・壁滑り型: tsukammo、bowwowforeach、tomerun発言
- 貪欲評価型: tsukammo、ValGrowth、Shun_PI、shun_skycrew発言
- 後処理改善型: 初期解を作ってから文字列近傍で山登り・焼きなましする方針全般
- 高速化型: wata/colun発言の前後DP差分、1次元配列化

## 推奨して理解すべき順序

1. Bondo416を読む。BFS初期解、スコアDP、文字列近傍という最小構成が分かる。
2. TERRYを読む。ダブらせ初期解、多点乱択、コピー近傍で1位水準に近づく流れが分かる。
3. bowwowforeachとtsukammoを読む。壁を使って確率を集める意味が分かる。
4. Jetbeadを読む。ビームサーチ、前後DP、高速化、`p` による方針差を横断的に補う。

## 実装するならどのルートか

理解のための最小実装は、Bondo416型をベースにするのがよい。

```text
1. 入力を can_move[y][x][d] に変換する
2. BFSで最短路を作る
3. 確率DPで score(cmd) を実装する
4. 追加・削除・変更・swap・反転の山登りを入れる
```

次にTERRY型へ寄せる。

```text
5. ダイクストラの辺重みを乱数化し、多点初期解を作る
6. 初期解を ceil(L/(1-p)) 付近までランダムにダブらせる
7. コピー近傍を入れる
8. 温度付き焼きなましにする
```

上位化するならJetbeadの高速化・探索を足す。

```text
9. score DPを1次元配列にする
10. 変更ターン以降だけ再計算する
11. 前後DPで1点変更差分を O(HW) にする
12. pが小さいケース向けにビームサーチ初期解を追加する
```

壁滑り型は、安定実装よりも発想理解として先に読む価値がある。採用するなら、BFS/乱択ダイクストラ初期解の候補の1つとして混ぜるのが安全である。

## 重要な実装要素

### 状態表現

最低限は次で足りる。

```text
cmd: Vec<char> or String
can_move[20][20][4]: bool
next_cell[20][20][4]: (i, j)
prob[20][20]: f64
best_cmd, best_score
```

壁配列 `h`, `v` を毎回直接見ると添字ミスを起こしやすい。最初に `can_move` へ正規化する。

### 評価関数

実スコアDPを使う。

```text
score(cmd):
    prob[start] = 1
    score = 0
    for t, c in enumerate(cmd, start=1):
        next = 0
        for cell:
            if can_move[cell][c]:
                next[to] += prob[cell] * (1-p)
                next[cell] += prob[cell] * p
            else:
                next[cell] += prob[cell]
        score += next[goal] * (401 - t)
        next[goal] = 0
        prob = next
    return round(250000 * score)
```

この評価を正しく書けるかが最重要である。ゴールを吸収扱いにして以降も動かすと二重加点になるため、加点後に `next[goal]=0` とする。

### 近傍

まず入れるべき近傍は次である。

- ランダム位置にランダム方向を挿入
- ランダム位置を削除
- ランダム位置を別方向に変更
- ランダム2点をswap
- ランダム区間を反転
- ランダム位置の命令を直後にコピー
- ランダム位置の命令を削除して別位置に挿入

AHC009ではコピー・ダブらせ近傍の価値が高い。忘却で1手遅れた確率質量を、本筋に戻しやすくなるためである。

### 差分更新

最小実装では毎回 `O(L*20*20)` の全再計算でよい。2秒で数千回は回る。

高速化の順序は次が自然である。

```text
1. probを1次元配列[400]にする
2. 壁判定と遷移先を前計算する
3. 変更位置より前のDPを再利用する
4. 前後DPを使って1点変更の差分をO(400)で評価する
```

前後DPは強力だが、挿入・削除・反転まで含めると管理が難しくなる。まずは1点変更や順方向更新に限定して使うのがよい。

### 候補管理

初期解候補は1本に絞らない。

- BFS最短路
- 乱択ダイクストラ経路
- ダブらせ済み経路
- 壁滑り経路
- 右下偏重ランダム列
- 貪欲・ビームで作った列

各候補を実スコアで評価し、上位を焼きなましの開始点にする。TERRY解の強さは、多点初期解と実スコア選抜にかなり依存している。

### 出力判定

- 長さは必ず `200` 以下。
- 文字は `U`, `D`, `L`, `R` のみ。
- 短すぎる列は到達率が低くなりやすいため、削除近傍に下限を設けると安定する。
- 最終出力は現在解ではなく、探索中の最良解にする。

### パラメータ

参考値:

- 初期解生成: 0.05〜0.1秒
- 焼きなまし: 残り時間ほぼ全て
- ダブらせ目標長: `ceil(shortest_len / (1-p))`
- TERRY温度: `1e5 -> 1e2`
- 近傍比率: 最初は均等でよい。Bondo型なら追加・反転・swap・削除を `30/30/30/10` 程度。

## 落とし穴

- ゴール到達確率をDPから消し忘れると、同じ確率を何度も加点してしまう。
- スコア式は `401-t` であり、`201-t` ではない。到達できればかなり大きく、到達確率の重要度が高い。
- `h` と `v` の添字は混乱しやすい。`L` や `U` で `-1` 添字を踏まないよう、先に `can_move` を作る。
- 最短路だけを出すと、忘却で1手でも遅れた確率が本筋から外れやすい。
- 壁滑りだけに依存すると、コの字型や一手戻りが必要な地形で破綻する。
- 焼きなましの前半で命令列を壊しすぎると、ゴールに全く届かない平坦なスコア領域に落ちる。
- `p` が小さいケースでは分布が鋭く、1文字変更のスコア面が荒くなりやすい。
- 愚直DPは実装しやすいが、近傍を増やすと評価回数が足りなくなる。1次元化だけでも効く。

## 未解決・要検証事項

- 前後DP差分を、挿入・削除・反転を含む近傍へどう広げるのが最も楽か。
- `p` に応じた最適な近傍比率と温度。
- 壁滑り初期解を、到達不能ケース込みで安定して候補化する方法。
- ビームサーチ初期解と焼きなまし初期解の切替条件。
- Bondo記事では焼きなましと説明されているが、提出コードでは時刻計算の都合で悪化採択が実質無効に見える。これが意図通りだったか、どの程度スコアに影響したか。
