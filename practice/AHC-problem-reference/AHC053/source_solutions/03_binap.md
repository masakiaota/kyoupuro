## 解法の全体像

試行過程として、各山1枚、2枚、4枚、6枚固定へと発展している。最終的には、各山に6枚ずつ割り当てる方針を採用し、Aは `[(L/6)*0.99, (U/6)*1.01]` 程度の範囲から作る。Bの各山に対して、残りカードから6枚組の和がBに近い組を貪欲に選ぶ。

直接6枚組を全探索するのは重いため、3枚組を時間内で列挙し、半分全列挙的に近い和を探す。実装ではペア配列の使い回しや3つ組のuint32表現など、定数倍高速化が重要だったと説明されている。

## 主要アイデア

- 事前に2枚組や4枚組のセットを固定してから山に割り当てると、候補数が少なくマッチング能力が弱い。
- 各山を処理するたびに、残りカードからそのBに近い組を探す方が強い。
- 2枚固定では、ソート済みA上の尺取りで最良ペアを `O(N)` で探せる。
- 4枚固定では、全ペア和を列挙し、2+2の半分全列挙で近い4枚を探せる。
- 4枚固定では端のBが悪くなったため、Aの生成範囲を少し広げることが効いた。
- 6枚固定では、3枚組を列挙し、時間内に十分な候補数を作ることで大幅に改善した。
- 定数倍高速化がスコアに直結した。

## 最終コードの構造

以下は記事本文から推測していた構造である。キャッシュ実装で確認した差分は後述する。

### 状態表現

- `A[500]`: `L/6` から `U/6` 付近を少し広げた範囲のカード値。
- `used[500]`: 既に山へ割り当てたカードかどうか。
- `X[500]`: 出力する山番号。未使用は0。
- 3枚組候補: 3枚のカード添字とその和をコンパクトに保持する。記事ではuint32_tへの詰め込みが言及されている。
- ペア和配列: 6枚探索の中間や高速化のために使い回す。

### 観測・制約・入力の扱い

- AはBを見る前に生成する。
- Bを読んだ後、各山について残りカードから6枚を選ぶ。
- 一度使ったカードは候補から除外する。
- 山の処理順について記事では明示が薄いが、各山ごとに貪欲に組を決め、決まったカードを除外する流れだと読める。

### 評価関数

- 各山の局所評価は `|sum(selected cards) - B_j|`。
- 全体評価は最終的に `sum_j |S_j-B_j|`。
- 2枚・4枚・6枚の議論では、組合せ候補数が増えるほど期待誤差が下がるという見積もりを使っている。

### 探索・構築・更新

- 1枚:
  - Aを `[L,U]` からランダム生成し、BとAを昇順に並べたDPで最適割当する。
- 2枚:
  - Aを `[L/2,U/2]` 付近から生成する。
  - 残りカードからBに最も近いペアを尺取りで探す。
- 4枚:
  - Aを `[L/4,U/4]` 付近、最終的には少し拡張した範囲から生成する。
  - ペア和を列挙し、2ペアの和でBに近いものを探す。
- 6枚:
  - Aを `[L/6*0.99,U/6*1.01]` から生成する。
  - 3枚組を大量に列挙し、3+3でBに近い6枚組を探す。
  - ペア列挙を使い回し、3つ組の添字を圧縮して高速化する。

### 操作・クエリ・出力選択

- Aを先に出力する。
- B読取後、各山に選んだ6枚へ山番号を設定する。
- 使われなかったカードは0として捨てる。
- 6枚固定なので、50山で300枚使用し、残り200枚は捨てる想定になる。

### 時間配分・パラメータ

- 4枚固定の範囲拡張は `0.99` から `1.01` 程度。
- 6枚固定では `5e6` 組程度の3枚組列挙が間に合ったとある。
- コンテスト終盤に実装したため、焼きなましではなく組合せ探索の定数倍高速化に時間を使っている。

## 実装上重要な断片

```text
best_pair(A_remaining, target):
    sort A_remaining
    l = 0, r = len(A)-1
    while l < r:
        update best by |A[l] + A[r] - target|
        if A[l] + A[r] < target: l += 1
        else: r -= 1
```

```text
best_six_by_triples(remaining, target):
    triples = enumerate many 3-card sums
    sort triples by sum
    find two disjoint triples with sum close to target
    mark their six cards used
```

## この解法の本質

この解法の本質は、Aの生成よりも「Bを見た後にどれだけ多くの組合せ候補と照合できるか」を重視したことだ。あらかじめセットを作ると候補数は `O(N)` 程度に潰れるが、残りカードからその場でK枚組を探せば、実際に使える組合せ空間は大きい。Kを6まで上げ、半分全列挙で現実的な時間に落とした点が強い。

## 真似するならまず実装する部分

まずK=4固定で、ペア和列挙による2+2探索を作るのがよい。次にK=6へ拡張し、3枚組候補の数を制限しながら3+3探索を入れる。記事の最終順位を狙うには、候補列挙と使用済み判定の定数倍高速化が必要になる。

## 実装確認（提出 69364251）

キャッシュ実装は C++ で、Aは `[floor(L/6*0.995), ceil(U/6*1.01)]` を `[1,U]` にclipした整数一様乱数で生成する。記事の下限0.99系の説明より、実装は下限0.995、上限1.01だった。

3枚組は `TP { long long sum; uint32_t pack; }` で持ち、10bitずつ `a | b<<10 | c<<20` にpackする。`SAMPLES=5000000` 個の重複なしランダム3枚組を作ってソートし、各カードから含まれる3枚組indexへの `incident` を保持する。

各 `B` についてtwo-pointerで2つの3枚組、つまり6枚を探す。差が改善したときだけunpackし、6枚の未使用性と相互重複を確認する。採用後は使ったカードに関連する3枚組を `invalid` にし、未使用カードは山0に割り当てる。山順やB順の並べ替えはなく、対話形式に合わせてA出力後とX出力後にflushする。

## 注意点・未理解点
