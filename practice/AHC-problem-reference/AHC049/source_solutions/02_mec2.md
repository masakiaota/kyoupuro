## 実装キャッシュで確認した内容

- 初期状態は各箱を単独グループにする。`group_ids[i][j]` と `group_cost[id]` で所属と局所コストを持つ。
- `evaluate_cost_highspeed` はグループ内の箱を重さ昇順に並べ、最後に出口番兵を足して距離・耐久を計算する。耐久違反は `1e9`。
- 入力後に `w` へ乱数 `0.01*rand` を足して同重さの tie を崩す。距離は全400点対で前計算する。
- 焼きなましは1.98秒、温度 `1e3 -> 1e-2`。10000試行ごとに時間、1000試行ごとに温度を更新する。
- 近傍はランダムな箱と近傍5x5内の箱のグループを選び、1個または1/3確率で2個を受け渡す。2/3程度は swap、残りは片方向移動である。
- taboo list は直近採択した箱周辺を少し避ける目的だが、コードでは `i1,j1` を2回更新しており `i2,j2` 側の taboo 更新が抜けているように読める。
- 最良解は時間経過80%以降の改善時のみ `best_ans_groups` に保存する。出力は各グループを重さ昇順で再並べ、逆順に拾って出口へ戻る。

## 解法の全体像

一度に運ぶ箱の集合をグループとして、グループ分けを焼きなましで改善する。本番解では、初期状態として各箱を 1 グループに 1 個ずつ入れ、近いグループ間だけで箱を受け渡す。各グループ内では箱を重い順に積むとし、その順序で出口へ運んだときの移動回数を評価値にする。

状態は、各グループが持つ箱座標の配列、各箱がどのグループに属するか、各グループの現在の生スコアで構成される。近傍で触ったグループだけを再評価し、耐久不足になる遷移は禁制にする。

延長戦では、1 個 swap、複数個 swap、高速化で順にスコアを伸ばしている。操作 2 は使っておらず、グループ独立方針では操作 2 を入れるにはグループ間の順序や相関を考える必要があると述べている。

## 主要アイデア

- 箱の回収をグループ単位に分け、グループ間の箱移動を焼きなましで探索する。
- 初期解は各箱単独グループなので、必ず valid で全箱を回収できる。
- 近傍は任意グループ間ではなく、マンハッタン距離が 4 以下の近いグループ間での箱受け渡しに限定する。
- 遠い箱を取りに行くなら、その周辺の箱も同時に拾う方が移動距離を減らしやすいという地理的性質を使う。
- グループ内では重い順に箱を拾う・積むとする。重い箱ほど耐久も高い傾向がある入力生成を利用している。
- 評価値は、そのグループを実際に出口へ運ぶための移動手数の合計で、耐久が足りなければ遷移を禁制にする。
- 時間計測は 1000 ステップごとに行い、毎回時計を読むコストを避ける。
- 延長戦で、箱 1 個の swap、複数箱の swap、ループ回数増加が有効だった。

## 最終コードの構造

以下は記事本文由来の整理を含む。提出 #67043260 の実装差分は上の「実装キャッシュで確認した内容」を優先する。

### 状態表現

- `groups[g]`: グループ `g` に含まれる箱の座標列。
- `belong[i][j]` または `belong[id]`: 箱が属するグループ ID。
- `group_score[g]`: グループ `g` を重い順で運んだときの移動手数。
- `valid[g]`: そのグループが耐久制約を満たすか。
- `candidate_edges`: 近いグループ間だけを選ぶための候補関係。記事ではマンハッタン距離 4 以下が基準。
- `total_score`: 全グループの移動手数合計、または AtCoder 得点へ変換した値。

### 観測・制約・入力の扱い

- `w` と `d` は箱ごとに保持し、グループ再評価時に重い順で並べる。
- 重い箱ほど耐久力が高い傾向があるため、重い箱を下にする単純な順序でもかなり耐久制約を満たしやすい。
- 各グループは出口から出発し、グループ内の箱を拾い、出口へ戻る独立ルートである。
- 箱を置く操作は使わないため、盤面上の空きマスや途中置き状態は状態に含めない。

### 評価関数

評価は「グループを重い順で積んで運んだときの生スコア」と書かれている。全箱回収を前提にすると、これは実質的に移動手数 `T` の最小化である。

```text
cost(state) = sum route_len(group)
if any group violates durability:
    state is forbidden
```

実スコアへは `N^2 + 2*N^3 - T` で変換できる。探索では `cost` が小さいほど良い。

### 探索・構築・更新

- 初期状態: 399 個の箱をそれぞれ独立グループに入れる。
- 本番近傍: 距離が近い 2 グループを選び、片方の箱 1 個をもう片方へ移す。
- 延長戦近傍: 箱 1 個の swap、複数箱の swap を追加する。
- 移動先候補はマンハッタン距離が 4 以下のグループに限定する。
- 近傍適用後、触ったグループだけを重い順に並べ直し、移動距離と耐久を再計算する。
- invalid なら不採択。valid なら焼きなましの採択条件で状態を更新する。
- ループ回数は本番 200 万回程度、延長戦の高速化で 300 万回程度に増やしたと記載されている。

### 操作・クエリ・出力選択

- 出力では、各グループについて箱を重い順に回収し、最後に出口へ戻る。
- グループの実行順は、各グループが出口で閉じるため移動手数には影響しにくい。
- 操作 2 は使わず、pickup の `1` と移動操作だけで構成する。
- 最短経路の具体的な上下左右の順序は記事からは分からない。

### 時間配分・パラメータ

- 距離制限: グループ間の受け渡しはマンハッタン距離 4 以下。
- 時間計測: 1000 ステップごと。
- ループ回数: 本番は約 200 万回、延長戦高速化後は約 300 万回。
- 近傍: 本番は箱移動、延長戦で 1 個 swap、複数個 swap。
- 記事中のスコア推移では、swap 追加と高速化の効果が具体的に示されている。

## 実装上重要な断片

```text
initialize():
    for each box:
        create a group containing only that box
        belong[box] = group_id
        group_score[group_id] = round_trip_distance(box)
```

```text
try_move_one_box():
    g1 = random group
    g2 = random nearby group within distance <= 4
    box = random box in g1
    old = score(g1) + score(g2)
    move box from g1 to g2
    sort boxes in touched groups by decreasing weight
    new = eval(g1) + eval(g2)
    accept if valid and annealing_accept(new - old)
```

```text
eval_group_heavy_order(group):
    order = boxes sorted by decreasing weight
    route = length of exit -> order -> exit
    if durability check fails:
        return forbidden
    return route
```

## この解法の本質

近い箱を同じ便にまとめるだけで、出口から遠い場所への往復回数を減らせる。この解法は、その直感を「近いグループ間でしか箱を渡さない」という強い制約にして、探索の無駄を減らしている。

また、初期解を各箱単独にすることで valid 性を確保し、グループ単位の局所更新だけで改善する。グループ内順序を重い順に固定するのは探索空間をかなり狭めるが、本番 4 時間では実装しやすく、入力生成の `d` が `w` に比例する性質にも合っている。

## 真似するならまず実装する部分

最初に、各箱単独グループから始める焼きなましを実装するとよい。評価は重い順固定で十分である。近傍は、近いグループへの 1 個移動だけに絞る。

次に、1 個 swap を追加する。複数個 swap や距離制限のチューニングは、ロールバックが安定してからでよい。時間計測を間引く実装も、反復数がスコアに直結するため早めに入れる価値がある。

## 注意点・未理解点

- 記事本文だけでは温度や近傍比率は不明だったが、提出 #67043260 で確認できた。
- グループの「距離」を、代表点、重心、箱どうしの最小距離のどれで判定しているかは記事だけでは確定できない。
- 重い順固定は実装しやすいが、Moegi 解説では順序制限解除で伸びたとされており、十分な反復では探索空間を狭めすぎる可能性がある。
- グループ独立方針では、操作 2 を使った途中置きの効果を取り込みにくい。
- 空グループの扱いやグループ ID の詰め直しは、実装時にバグりやすい。
